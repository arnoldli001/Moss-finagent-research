## 一、每轮对话的三步对账（T0 抽取 → T1 对账 → T2 落账）

> **触发条件**：只要用户在对话里说出了一个**可观察的行为要求**（新增功能、
> 改口径、改阈值、改顺序、改界面），就走这三步。
> 纯提问、纯闲聊、别人家仓库的事 → 不进台账（但要在回复里说明"这条不算需求"）。

### T0 抽取：把用户输入拆成**可判定的条目**

**用户给的是话，台账要的是条目。** 拆解模板（照抄）：

| 字段 | 要求 | 反例 |
|---|---|---|
| **需求原话** | 用户原话，可截断，**不得改写语义** | ❌「用户希望优化数据获取」 |
| **可观察行为** | 做到之后**看到什么**/量到什么 | ❌「提升了体验」 |
| **关键词** | 供脚本 grep 的**机器可读**词（优先英文标识/字段名） | ❌ 只用中文口语词 |
| **PRD 章节** | 命中或应落在哪节（`PRD-3.1`） | ❌ 空着 |
| **判定** | 新增 / 冲突 / 细化 / 已覆盖 / 非需求 | ❌ 一律写"新增" |

**一句话需求常常拆出多条**（本项目实测：「事件告警最多保留三天」由
`alert_expire_days` + `retention_alert_days` **两个**字段共同决定 ——
只改一个等于没生效，而两边都会以为自己对了）。
**拆不出第二条时，先问"要改哪几处才能产生这个可观察行为"。**

### T1 对账：三条命令，逐个关键词

```bash
# ① 这个词在三面（PRD / 台账 / 仓库）各是什么状态？
uv run python scripts/prd_sync_check.py --keyword "<关键词>"

# ② 台账完整性：PRD 每个章节都登记了吗？证据路径还在吗？
uv run python scripts/prd_sync_check.py --ledger

# ③ 台账表格骨架（章节 ID 由脚本从 PRD 现读，不许手写）
uv run python scripts/prd_sync_check.py --list-sections
```

**三态结论 + 强制动作**（脚本直接给出来，不许自己另起一套）：

| 结论 | 含义 | 强制动作 |
|---|---|---|
| `OK` | PRD 与台账都提到了 | 仍要人工确认**口径是否一致**（脚本只查存在性） |
| `MISS_LEDGER` | PRD 有、台账无 | 老需求从未登记 / 本轮没落账 → 台账补一条 |
| `MISS_PRD` | **仓库做了、PRD 查不到** | ★ **补写 PRD + 登记 CHG** |
| `TODO` | 三面都查不到 | 没量到 ≠ 量到 0 → 换关键词（可能用词不同）后**人工判断**，不许当通过 |

### T2 落账：**对话结束前必须做**（这是本 skill 的交付物）

| 判定 | 处置 | PRD 是否已更新 | 状态 |
|---|---|---|---|
| **新增**（PRD 没有，用户要了） | 补写 PRD 对应章节（或末尾新增章节） + 登记 `CHG-xxxx` | 是 | 已闭环 |
| **冲突**（PRD 写的和用户/现实不一致） | 改写 PRD：**旧口径标注废止 + 留 CHG 号**，新口径写进去 | 是 | 已闭环 |
| **细化**（PRD 有，但阈值/清单不够判定） | 补进 PRD（把"支持 X"变成"X ≤ N 次/KB"） | 是 | 已闭环 |
| **已覆盖** | 只登记"无差异"（可省，但建议留一行防下一轮重查） | — | 已闭环 |
| **非需求**（提问/闲聊/他人的事） | 不登记，在回复里说明 | — | — |
| **本轮落不进 PRD**（待用户确认 / 影响面未定） | **只登台账，处置=待办、状态=待办** | 否 | 待办 |

> ★ **只登台账不改 PRD 的条目，状态不许写"已闭环"。**
> 这不是文风要求，是脚本的硬校验（两条）：
> ① `类型 ∈ {新增,冲突,细化}` 且 `状态=已闭环` 而 `处置 ∉ {补写PRD,改写PRD}`
>    （**冲突类**多一种合法处置：`标注废止`）→ **报 ERROR**；
> ② 台账写「PRD 已更新=是」，但 `docs/PRD.md` 里**搜不到这个 CHG 号** → **报 ERROR**
>    （"我改了 ≠ 它生效了"：不许在台账里单方面宣布改了 PRD）。
> 用户要的是"没有的补贴进去，有差异的改动"，而"只登台账"正好两件都没做。

### 1.1 脚本不在时怎么降级（诚实登记）

`scripts/` 与 `.trae/` 在本仓库**默认不随发布**（`.gitignore:84 /scripts/*`、`:116 /.trae/`），
所以克隆出来的仓库里 `prd_sync_check.py` 可能不存在。此时：

| 还能做 | 怎么做 |
|---|---|
| 对账第三节（章节覆盖） | `grep -n '^##\{1,2\} ' docs/PRD.md` 现读章节，逐个对照台账 §2 |
| 对账第一节（落 PRD 才算闭环） | 人工检查：每条 `已闭环` 的 CHG 号**必须在 `docs/PRD.md` 里搜得到** |
| 对账第二节（证据可复跑） | 逐条 `Test-Path` 证据路径 |
| **不能做** | 关键词三态扫描（需要脚本）→ 如实说"没量到"，**不许当通过** |

> 测试侧已按 AGENTS.md「交付完整性硬约束」加模块级 `pytest.skip(..., allow_module_level=True)`
> 守卫，做**知名降级**而不是静默红灯（`tests/unit/test_prd_sync_check.py`）。
> 是否把脚本/skill 加进发布白名单是**政策决策**，见台账 `CHG-0044`。

## 二、三类出入 × 三种处置（含唯一被禁止的动作）

### 2.1 三类出入

| 类型 | 症状 | 危险 |
|---|---|---|
| **PRD 有、仓库无** | 写了从未实现 / 已废弃 | 看文档的人会以为有 |
| **仓库有、PRD 无** | 实测 QMT / 竞价 / ETF / 拥挤度全是这一类 | 需求史断档，"为什么有这功能"无据可查 |
| **两边都有、口径冲突** | 数值 / 名称 / 顺序 / 技术选型不一致 | 最贵：两边都以为自己是对的 |

### 2.2 三种处置

**① 补写（新增）** —— 在命中章节追加条目，或**在末尾**新增 `## 十三、…`。

**② 改写（冲突）** —— ★ **禁止直接删掉旧口径**。正确写法（三选一，都要留 CHG 号）：

```markdown
- ~~本地运行 PostgreSQL + Redis~~ → 默认 SQLite 零依赖（PostgreSQL/Redis 可选）
  （废止于 2026-09-28，CHG-0007：与「零依赖启动」冲突，见 AGENTS.md）

> ⚠️ **已废止（CHG-0007，2026-09-28）**：原「Keycloak + OPA」改为进程内 RBAC。
>   原因：当前阶段零外部依赖；恢复路径见 `docs/MULTI_TENANCY_DESIGN.md`。
```

**为什么必须留废止痕迹**：变更史本身就是需求，"为什么改"下一轮还会被问到。
直接删掉 = 下一个人只看到新口径，**于是把旧口径当"从没提过"，重复提一遍**。

**③ 只登台账** —— 仅用于"本轮落不进 PRD"（待确认 / 影响面未定），
必须 `处置=待办`、`状态=待办`，并写明**卡在哪**。

### 2.3 章节编号稳定性（容易踩）

- **只在 PRD 末尾新增章节**。插在中间会让后面所有 H2 重编号 →
  台账里 `PRD-7.2` 这类引用**集体错位**，而脚本只会报"幻影章节"，
  人却会以为是台账写错了。
- 章节 ID 一律用 **`--list-sections` 现读的输出**，不手抄。

### 2.4 折叠归档（需求改了又改时的正确姿势）

> 用户 2026-09-28 问：「如果我需求改了又改，历史 PRD 需求是不是可以自动删除？」
> **裁定：不删除，折叠（tombstone）。** 落地在 `docs/PRD.md` **§13**。

| 做法 | 结果 |
|---|---|
| ❌ 直接删掉旧口径 | 变更史断档；下一个人把旧口径当"从没提过"再提一遍（本项目实测：`docs/DATA_SOURCE_ROUTING.md` 至今写 qmt 在链首，与配置相反） |
| ❌ 只加废止注、不做任何整理 | PRD 越改越长，正文里现行与废止混在一起 → 没人读了 |
| ✅ **正文只留现行口径 + 原处一行指针 + 原文整段折进 §13.3** | 人读短的现行版，历史逐字可追；**CHG 号仍在本文件可见** → 脚本判据②照样通过 |

操作次序（四步，缺一步就会红）：

```
① 正文原处：保留原文 → 加 `⚠️ 已废止（CHG-xxxx，日期）` → 再留一行"原文已折叠到 §13.3.x"
② §13.3 归档区：把被取代的**整段原文**逐字搬进来（不润色、不删减；用 #### 四级标题，不产生新章节 ID）
③ §13.1 tombstone 表：加一行「条目 | 原口径（章节·CHG） | **现行口径**」
④ 台账：登记 CHG，`处置=改写PRD`、`PRD 已更新=是`
```

**两条硬约束仍然适用**：CHG 号必须在 PRD 里可见；新增章节必须同步台账章节表
（加 §13 时 `--ledger` 会立刻报 4 个"未登记"——那就是设计行为，不是 bug）。

**"现行口径"只有一个入口**：§13.1。任何"现在到底是多少"的问题，答案必须能在
§13.1 找到**数值**，而不是"看代码吧"。

## 三、可执行命令（本 skill 的机器部分）

```bash
uv run python scripts/prd_sync_check.py --keyword "QMT"      # 三态对账（有 MISS 时退出码 1）
uv run python scripts/prd_sync_check.py --ledger             # 台账完整性（默认动作）
uv run python scripts/prd_sync_check.py --list-sections      # PRD 章节 → ID 映射
uv run python scripts/prd_sync_check.py --self-test          # 自证：喂坏输入必须报错
```

**退出码**：`0` 通过 / `1` 有未对账项或台账未达标 / `2` 需求基线或台账文件缺失。

### 3.1 台账校验的硬判据

| 判据 | 防的是什么 |
|---|---|
| PRD **现读**的每个章节 ID 都在台账「章节登记表」里 | 新增章节后忘登记（静默漏账） |
| 台账里的章节 ID 都真实存在于 PRD | 章节重编号后的**幻影引用** |
| 条目枚举合法（类型/处置/状态）+ ID 唯一 + 日期格式 | 用自由文本糊过去 |
| **证据里至少一个路径真实存在** | 「我改了」式证据（不可复跑） |
| ★ `新增/冲突/细化` + `已闭环` ⇒ `处置=补写/改写PRD`（冲突类可 `标注废止`） | **只登台账不改 PRD** |
| ★ `已闭环` + `PRD 已更新=是` ⇒ PRD 里**搜得到该 CHG 号** | **假闭环**：在台账里宣布改了 PRD，而 PRD 没动 |

### 3.2 自证（`--self-test`，五类坏输入必须报出来）

```
✅ 自证通过：已知缺失 / 幻影章节 / 失效证据 / 未落 PRD 的闭环 / 假闭环，五类坏输入都能报出来
```

**只会报 OK 的检查等于没有检查。** 这四类就是本项目踩过的假绿通道：
解析器坏掉 → 0 章节自然"全覆盖"；围栏代码块没跳过 → 幻影章节；
关键词判据写反 → 不存在的词也报 OK。

> 实测细节：`docs/PRD.md` §10.1 里嵌了一整段 ```markdown 模板，
> 里面有 `## 项目定位`、`## 环境配置` 这类标题。**不跳围栏代码块，
> 就会把这些当成真章节**去要求台账登记 —— 而且不报错。

## 四、台账规范（`docs/REQUIREMENT_CHANGELOG.md`）

### 4.1 两张表

**① 章节登记表**（PRD 每个 H2/H3 一行，由 `--list-sections` 生成）

| 章节 ID | PRD 标题 | 层级 | 章节登记状态 | 备注 |
|---|---|---|---|---|

`章节登记状态 ∈ {已登记, 无差异, 待确认}`

**② 变更台账**（每轮对话的需求增删改，一行一条）

| 变更 ID | 日期 | 类型 | PRD 章节 | 需求原话 | 处置 | PRD 已更新 | 状态 | 证据 |
|---|---|---|---|---|---|---|---|---|

枚举（**只认这些值，脚本会校验**）：

- `类型 ∈ {新增, 冲突, 细化, 废止, 非需求}`
- `处置 ∈ {补写PRD, 改写PRD, 标注废止, 仅登记台账, 待办}`
- `PRD 已更新 ∈ {是, 否}`
- `状态 ∈ {已闭环, 待办, 待确认}`
- `变更 ID`：`CHG-\d{4,}`，单调递增，**永不复用**
- `证据`：至少一个 `路径:行号`，且路径真实存在

### 4.2 四条纪律

1. **不删历史。** 状态从 待办 → 已闭环 可以改，条目本身不许删（删了就丢变更史）。
2. **证据可复跑。** 写 `docs/PRD.md:275` / `configs/models.yaml:12`，
   不写「已确认」「见代码」。
3. **需求原话不得改写。** 概括过的需求下一轮无法复核（与
   `claim-evidence-consistency` 同源：结论必须能被原文检验）。
4. **待办要写卡点。** 「待办」不是垃圾桶，要写清"等谁确认什么"。

## 五、五类失败模式速查

| # | 失败模式 | 症状 | 对策 |
|---|---|---|---|
| 1 | **只登台账不改 PRD** | 台账很漂亮，PRD 还是 2026-09-14 那版 | T2 硬规则 + 脚本第 5 条判据（会报 ERROR） |
| 2 | **覆盖旧口径** | 直接删掉冲突的原文，变更史消失 | §2.2 废止标记法，留 CHG 号 |
| 3 | **把"我们实现了"当"需求变了"** | 拿代码现状去改 PRD 的原始要求 | 实现超前 ≠ 需求变更：登记为「仓库有 PRD 无」，PRD 里**补写**而不是改写用户原话 |
| 4 | **写不可判定的条目** | PRD 里写"支持多数据源""优化性能" | 条目必须带阈值/清单/字段名/错误码；否则下一轮无法对账 |
| 5 | **只对被点到的那一个词** | 用户说"QMT"就只对账 QMT | 与 `requirement-closure-and-impact` 同源：先问"这是一个点还是一类"，再 `--keyword` 批量扫 |

### 5.1 一条最容易被忽略的：**PRD 里的示例代码块不参与对账**

`docs/PRD.md` §10.1 的 AGENTS.md 模板已经与现网 `AGENTS.md` 严重脱节
（模板里写"每个 Agent 封装为独立 FastAPI 微服务"，现实是单进程分层架构）。
对账时要显式判定：**这是示例，还是需求？** 是需求 → 单独登记 `CHG`；
是历史示例 → 在 PRD 里标注「示例，已被 CHG-xxxx 取代」。

## 六、执行清单

### 6.1 每轮对话开始（收到用户输入后，动手写代码前）

```
□ 把输入拆成条目（需求原话 / 可观察行为 / 关键词 / PRD 章节 / 判定）
□ uv run python scripts/prd_sync_check.py --keyword "<关键词>"   # 逐条
□ 结论 MIS_PRD  → 先补 PRD 再改代码（需求先落地，实现才有据）
□ 结论 冲突      → 先写废止标记，再改实现
□ 结论 TODO      → 换关键词重扫；仍查不到就写明"没量到"，人工判断
```

### 6.2 每轮对话结束（**宣布交付前**）

```
□ uv run python scripts/prd_sync_check.py --ledger     # 必须 0 ERROR
□ 本轮每条需求都有落点？找不到落点的状态是不是"待办"？
□ ★ 每条「已闭环 + PRD 已更新=是」的 CHG 号，在 docs/PRD.md 里**搜得到**吗？
   （搜不到就是假闭环 —— 在台账里宣布改了 PRD 而 PRD 没动）
□ 新旧口径都在？旧口径有没有被静默删掉？
□ 章节编号动过没有？（只在末尾新增）
□ 台账证据路径都还存在？
□ uv run python scripts/prd_sync_check.py --self-test    # 检查器本身还可信
```

## 七、换开发工具后还生效吗（跨工具可移植性）

> 用户 2026-09-28 问：「如果我换了开发工具，是否这个 PRD 动态维护功能还生效？」

**分三层，结论不同 —— 别把它们混成一句"生效/不生效"**：

| 层 | 载体 | 换工具后 | 靠什么保证 |
|---|---|---|---|
| **可执行** | `scripts/prd_sync_check.py` | ✅ 照旧 | 纯标准库（无网络、无 LLM、无第三方依赖）→ 任何工具能跑命令就能用 |
| **基线与台账** | `docs/PRD.md`（含 §13）、`REQUIREMENT_CHANGELOG.md`、审计文档 | ✅ 照旧 | 纯 markdown，谁都能读能改 |
| **纪律触发** | `AGENTS.md`（跨工具事实标准）+ `.trae/skills/*/SKILL.md`（**Trae 专有路径**） | ⚠️ 看工具 | 根 `AGENTS.md` 被多数工具自动读；`.trae/` **不会**被别的工具加载 → 必须有转发层 |
| **兜底门禁** | `.github/workflows/ci.yml` 的「需求—PRD 对账门禁」 | ✅ 照旧 | 不经过任何 AI 工具，`--self-test` + `--ledger` 在 CI 里跑 |

### 7.1 转发层（**只转发，不复制**）

| 工具 | 读什么 | 本仓库的做法 |
|---|---|---|
| Claude Code | `CLAUDE.md`（支持 `@path` 导入） | `CLAUDE.md` 第一行 `@AGENTS.md` + 三条命令 |
| Cursor | `.cursor/rules/*.mdc` | `.cursor/rules/requirement-prd-sync.mdc`（`alwaysApply: true`） |
| GitHub Copilot | `.github/copilot-instructions.md` | 同名文件，指向同一份 SKILL.md |
| DeepSeek Harness / 多数 CLI Agent | 根 `AGENTS.md` | 直接读，无需转发 |
| Trae | `.trae/skills/*/SKILL.md` | 事实源本体 |

**铁律**：转发层里**不许出现规则正文**，只许出现"看哪个文件 + 三条命令"。
理由是本项目实测过的故障模式：同一个 key 写在 3 处，只改 1 处 →
**情报 5 个端点对所有人 403**。复制即漂移。

### 7.2 换工具前/后的自检（两条，都是布尔）

```
□ 克隆这个仓库（只有 git 跟踪的文件），`scripts/prd_sync_check.py` 还在吗？
  → 在：三条命令可跑。不在：AGENTS.md 里那条命令就是死链（判据 3 会报）
□ 新工具读了 AGENTS.md 吗？让它复述"落 PRD 才算闭环"那两条判据，答不出就是没读
```

### 7.3 已知边界（诚实登记）

- **台账/审计文档是否随公开仓库发布**尚未裁定（含内部成本数字）→
  未发布时 CI 的 `--ledger` 只能打 `::warning::` **显式跳过**；
  机器保证此时只在开发机成立。
- `.trae/skills/` 里**只有本 skill** 在 `.gitignore` 白名单内（其余 skill 仍不发布）
  —— 别的工具克隆后看不到那些 skill，这是既定政策，不是遗漏。
