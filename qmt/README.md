# 集合竞价选股 V3 · QMT 实盘部署说明

> 配套文件：
> - `auction_v3_qmt.py` —— **方案 A**：单机自包含（选股+执行都在这一个文件里）
> - `signal_server.py` —— **方案 B**：本地选股信号端（跑在有完整数据的机器上）
> - `qmt_executor.py` —— **方案 B**：QMT 执行端（只下单，不做选股）
> - `SIGNAL_CONTRACT.md` —— 方案 B 的接口契约
> - `test_parity.py` / `test_executor.py` —— 两套一致性校验

---

## 零、先选部署方式

| | 方案 A：单机自包含 | **方案 B：信号端 + 执行端（推荐）** |
|---|---|---|
| 文件 | `auction_v3_qmt.py` | `signal_server.py` + `qmt_executor.py` |
| 数据 | 只有 QMT | QMT + warehouse.db + eltdx |
| 打分维度 | **最多 76.5/100**（题材 12 + 龙头 3 + 封流比 6 + 昨日质量一半缺失） | **完整 100/100** |
| 门槛 55 分 | **失效，必须重新标定** | **直接沿用回测的 55 分，无需标定** |
| 规则①（抢跑清仓） | 无法判定 | 可判定 |
| 适用 | 只有一台 QMT 机器、拿不到仓库数据 | 本地有仓库环境（本仓库就是） |

**方案 B 的本质**：QMT 的 `xtdata` 拿不到「涨停原因/题材」，那就**不勉强**——
让有数据的本地机器负责选股，QMT 只负责它擅长的事：**下单与成交回报**。

```
本地（有 warehouse.db + eltdx）              QMT（券商柜台旁）
  09:25  service.run_selection()  ← 12维完整打分
         ↓ 写 signals/buy_YYYYMMDD.json
         ────────── 原子写文件 / HTTP ──────────→  读信号 → 校验 → 09:30 下单
  09:26  算持仓股「抢跑」标签
         ↓ 写 signals/sellalert_*.json ─────────→  14:56 规则①用它判定
                                                 14:56 规则②-⑦ QMT 自己判
         ←──────── signals/fill_*.json ────────  成交回报
```

**降级自保**：本地心跳超过 180s 没更新 → QMT **停止开仓**（没有选股依据宁可不做），
但**价格类止损 ②-⑦ 照常执行**。本地电脑关机、断网、崩溃，持仓依然有保护。

### 0.1 「只用方案 B」具体是什么

**7 个文件里，你只运行 2 个、常驻 1 个，其余都是库或测试。**

| 文件 | 方案 B 里的角色 | 要不要运行 |
|---|---|---|
| `signal_server.py` | 本地选股信号端 | ✅ **运行**（跑在本地机器） |
| `qmt_executor.py` | QMT 执行端 | ✅ **运行**（跑在 QMT 机器） |
| `paper_trader.py` | **纸面模式**（真实信号+真实行情，不下单） | ✅ **建议先跑一周** |
| `auction_v3_qmt.py` | **仅作为库被 import**（券商封装 Broker、状态 State、卖出规则 plan_sells、行情适配） | ❌ **不要单独运行** |
| `SIGNAL_CONTRACT.md` | 接口契约文档 | 读 |
| `README.md` | 本文件 | 读 |
| `test_executor.py` / `test_paper.py` / `test_parity.py` | 三套校验 | 上线前各跑一次 |

> ⚠️ **绝对不要同时把 `auction_v3_qmt.py --live` 和 `qmt_executor.py --live` 跑起来。**
> 两个进程写**同一个** `auction_v3_state.json`，各自独立下单 →
> **同一只票会被买两次，仓位翻倍。** 实测两者指向同一路径。
> `auction_v3_qmt.py` 在方案 B 里只是被 import 的模块。

**方案 B 的每日 5 个任务**（前 4 个在本地机器，最后 1 个在 QMT 机器）：

| 时间 | 机器 | 命令 | 作用 |
|---|---|---|---|
| **09:00 常驻** | 本地 | `python signal_server.py --phase heartbeat` | 心跳守护（**不加这个参数会永不退出，正是常驻语义**） |
| 09:10 | 本地 | `python signal_server.py --phase preheat` | 预热昨日涨停/连板/题材 |
| 09:25 | 本地 | `python signal_server.py --phase buy` | 完整 12 维打分 → 写买入计划 |
| 09:25 | **QMT** | `python qmt_executor.py --phase buy --live` | 读计划 → 09:30 下单（截止 09:40） |
| 09:26 | 本地 | `python signal_server.py --phase sellalert` | 算持仓股「抢跑」标签 |
| 14:52 | **QMT** | `python qmt_executor.py --phase sell --live` | 规则②-⑦ + 规则① → 收盘集合竞价 |

> 🔴 **心跳任务必不可少。** 执行端读不到新鲜心跳（>180s）就判定本地离线，
> **拒绝一切开仓**。`--phase buy/sellalert/preheat` 每次跑完也会顺手写一次心跳，
> 但那只是一次性快照 —— 14:52 的卖出离 09:26 已过去 5 个多小时，
> 没有常驻心跳的话规则①会被跳过（价格类止损 ②-⑦ 仍然生效，不会裸奔）。

**跨机部署只改一个参数**：本地加 `--http-port 8765`，
QMT 端把 `--signal-dir` 换成 `--signal-url http://<本地IP>:8765`。

### 0.2 先跑纸面模式（强烈建议，至少一周）

**在投入真钱之前**，用 `paper_trader.py` 把「模型以为的成交价」和「真实可成交价」
逐笔对比出来。这是整套系统里唯一能验证**最大那个未验证假设**的手段。

```powershell
# 09:25 出信号后跑；决定 → 等 360s → 用 9:30 真实开盘价结算
python qmt\paper_trader.py --phase buy  --settle-after 360

# 14:52 判卖出；等 540s → 用 15:00 真实收盘价结算
python qmt\paper_trader.py --phase sell --settle-after 540

# 随时看滑点报告
python qmt\paper_trader.py --phase report
```

**它与实盘的唯一差别是 broker**：`qmt_executor.execute_buy / execute_sell`
**一行不改**地被复用，只是拿到一个 `PaperBroker`。所以验证的是**真实的决策路径**，
不是另写一套简化逻辑。

**不用 `--account` / `--mini-path`** —— 纸面模式不连交易柜台，只取行情，
所以它**不可能**误下真单。

报告会给出三个回测里看不见的数字：

| 指标 | 为什么重要 |
|---|---|
| **未成交率** | 限价买单在 9:30 跳空时**根本买不到**；回测假设 100% 成交 |
| **不利滑点 (bp)** | 买贵 / 卖贱了多少（已按方向归一，两边可直接比较） |
| **滑点成本占比** | 相对成交额的百分比，可和手续费率直接比大小 |

> ⚠️ 纸面模式**不模拟排队与部分成交**，因此它的结果是**滑点的下界** ——
> 真实成交只会更差。若纸面就已经显示滑点吃掉大半利润，实盘不必再看。

产出：`paper_state.json`（纸面账户）、`paper_fills.csv`（逐笔滑点流水）。

## ⚠️ 上线前必读：三件事

### 1. 收益预期必须按全周期口径

回测的「近 1 年年化 +280%」是**单一市场环境**下的结果（241 个交易日、219 笔交易）。
**四年全周期年化只有 +13.81%，最大回撤 −51.11%。**

把单一年份的年化当成这个策略的预期收益，会在实盘里被现实迅速纠正。
请以 **年化 13.81% / 回撤 −51%** 作为心理基准，并**先用小资金跑 1-3 个月**。

### 2. QMT 缺三块数据，最多还原 76.5/100 权重

> **这一条只对方案 A 成立。方案 B 因为选股在本地跑，12 维一个都不缺，门槛 55 分直接可用。**

| 维度 | 权重 | QMT 能否计算 | 原因 |
|---|---:|---|---|
|---|---:|---|---|
| 题材热度 | 12 | ❌ | QMT 无「涨停原因/题材」数据 |
| 题材龙头 | 3 | ❌ | 同上 |
| 封流比 | 6 | ❌ | 需要涨停封单量，日线数据没有 |

本脚本按仓库既定口径「**缺席维度按剩余权重归一化**」处理。**直接后果：**
**归一化后分数分布变了，原 55 分门槛不再等价。** 上线前必须重新标定：

```bash
python auction_v3_qmt.py --calibrate --account 你的账号 --mini-path 你的路径
```

它会打印候选池的 p0/p10/p25/p50/p75/p90 分位，据此修改文件顶部的 `SCORE_THRESHOLD`。

**补救办法（方案 A）**：把题材数据放到 `theme_data.csv`，脚本会自动读取并启用这三个
维度（列名见 `§1.10` 注释）。**但更彻底的办法是直接用方案 B** —— 选股在本地跑，
题材、封单、竞价秒级序列本来就有，连门槛都不用重标。

### 3. 撮合假设与回测不同

| 环节 | 回测假设 | 实盘实际 | 影响 |
|---|---|---|---|
| 买入 | 9:25 集合竞价撮合价成交 | 9:25 定格后下单 → **9:30 连续竞价成交** | 有滑点。脚本用「9:25 价 ×(1+1%) 限价单」逼近 |
| 卖出 | 收盘价判定 + 收盘价成交 | 14:56 用当时价判定 → 委托参与 **14:57-15:00 收盘集合竞价** | 成交价≈收盘价，但**判定输入是 14:56 的价** |

回测中 **87% 的卖出**是「收盘判定 + 收盘成交」这一乐观假设，且从未做过成交价压力测试。
这是本策略最大的未验证风险。

## 一、环境准备

### 1.1 开通 QMT 极简模式
联系东莞证券客户经理开通 **QMT（迅投 miniQMT）** 权限，并确认已启用「**极简模式**」。
xtquant 通过本地 `userdata_mini` 目录与客户端通信，**客户端必须保持运行并登录**。

### 1.2 Python 环境
- 64 位 Python **3.6 ~ 3.12**
- 依赖：`xtquant`（随 QMT 客户端提供）、`numpy`、`pandas`
- 找到 `xtquant` 所在目录（通常在 QMT 安装目录下），把它加入 `PYTHONPATH`，
  或直接用 QMT 自带的 Python 解释器运行

### 1.3 定位两个关键参数
| 参数 | 怎么找 |
|---|---|
| `--mini-path` | MiniQMT 安装目录下的 `userdata_mini`，例如 `D:\东莞证券QMT\userdata_mini` |
| `--account` | 你的**资金账号**（不是股东代码） |

建议写成环境变量，避免命令行里出现账号：
```powershell
$env:QMT_ACCOUNT   = "你的资金账号"
$env:QMT_MINI_PATH = "D:\东莞证券QMT\userdata_mini"
```

## 二、首次运行（务必按顺序）

```powershell
# ① 一致性校验 —— 必须全绿才继续
python qmt\test_parity.py

# ② 空跑：只选股打印，不下单（09:05 前启动，让它采集到 9:15-9:25 的竞价序列）
python qmt\auction_v3_qmt.py --buy-only

# ③ 标定门槛（看打分分布，改 SCORE_THRESHOLD）
python qmt\auction_v3_qmt.py --calibrate

# ④ 继续空跑 3-5 个交易日，核对：
#    · 选出来的票是否合理
#    · 候选池数量、否决原因分布
#    · auction_v3_run.log 有无 [WARN]/[ERROR]

# ⑤ 小资金实盘（把 --live 加上）
python qmt\auction_v3_qmt.py --buy-only --live
```

> **`--live` 不加就永远只打印不下单。** 这是刻意的设计。

## 三、日常调度

策略只在两个时点动作，**建议用两个独立的计划任务**（而不是一个常驻进程 ——
常驻进程一崩，下午的卖出席位就没人管了，风险不对称）。

| 时间 | 命令 | 说明 |
|---|---|---|
| **09:05** | `python auction_v3_qmt.py --buy-only --live` | 盘前准备 → 采集竞价序列 → 9:25 选股 → 下单 |
| **14:52** | `python auction_v3_qmt.py --sell-only --live` | 卖出判定 → 委托参与收盘集合竞价 |

Windows 计划任务示例（任务计划程序 → 创建任务 → 操作）：
```
程序:   C:\Python311\python.exe
参数:   D:\qmt\auction_v3_qmt.py --buy-only --live
起始于: D:\qmt
```
> 早晨那次任务**必须在 09:15 之前启动**，否则采集不到完整竞价序列，
> 承接强度与跳空值会缺失（对应维度自动从权重中剔除，脚本会打 WARN）。

不加 `--buy-only/--sell-only` 时脚本会按当前时间自动判断阶段，盘中（09:30-14:50）
运行会直接退出并提示。

## 四、策略规则速查

### 4.1 前置筛选（9 条 + V3 追加 2 条）

| # | 条件（命中即剔除） |
|---|---|
| 1 | 上个交易日非涨停 |
| 2 | 无涨跌幅限制 |
| 3 | ST |
| 4 | 昨日收盘价缺失 |
| 5 | 昨日收盘价 ≥ 37 元 |
| 6 | 20 日均价缺失 |
| 7 | 昨日收盘价 ≤ 20 日均价 |
| 8 | 流通市值缺失 |
| 9 | 流通市值 ∉ (15 亿, 110 亿) |
| V3+ | 剔除 `300/301/688` 开头 |
| V3+ | 剔除 15~40 亿市值段 → **实际可买 40~110 亿** |

### 4.2 一票否决（10 条）

ST / 无涨跌幅限制 / 开盘涨幅 <2%（抢筹豁免）/ 开盘涨幅 >6%（大量抢筹豁免）/
竞价量比 >15%（抢筹豁免）/ 强转弱 / 急剧下坠型 / **抢跑** / 市场炸板率 >60% /
情绪周期闸门关闭（退潮期、冰点不做接力）

### 4.3 十二维打分（权重和 = 100）

| 权重 | 维度 | 打分方式 |
|---:|---|---|
| 19 | 竞价量能 | 6 档分段（2~3 最优，>10 压到 0.2） |
| 14 | 开盘位置 | 2~4% 最优，>9% 降至 0.25 |
| 12 | 承接强度 | 0~100 线性（来自 9:20-9:25 竞价轨迹） |
| 12 | 题材热度 | 0~1 线性 ❌ QMT 缺 |
| 10 | 连板梯队 | 3 板峰值 1.0，首板 0.55 |
| 7 | 情绪周期 | 温度/100 + 阶段修正 |
| 6 | 封流比 | ≥3% 满分 ❌ QMT 缺 |
| 5 | 竞价情绪 | 候选池整体高开程度 |
| 5 | 昨日质量 | 封流比 + 竞价额占比 的均值（半缺） |
| 4 | 盘口适配 | 竞价额/流通市值，1%~5% 最优 |
| 3 | 换手率 | 5~20% 最优，>30% 降到 0.35 |
| 3 | 题材龙头 | 龙头 1.0 / 并列最高 0.8 ❌ QMT 缺 |

加分：抢筹 **+4**、大量抢筹 **+5**（取最高档）

### 4.4 买入与仓位

| 规则 | 取值 |
|---|---|
| 每日买入 | 分数最高的 **3** 只（最高连板 ≥7 时降为 2 只） |
| 单只仓位 | 权益 × **30%**（最高连板 ≥7 时 20%） |
| 抢筹加成 | 带「抢筹」标签 → 本次仓位 **×1.2** |
| 加仓 | 已持有该股 → 本次买入额 = 已有市值 × **30%** |
| 单只上限 | ≤ 权益 × **35%** |

### 4.5 卖出规则（严格优先级，命中即返回）

| 序 | 条件 | 动作 | 实盘判定时点 |
|---|---|---|---|
| ① | 市场最高连板 ≥7 且持仓盈利 且当日竞价**抢跑** | 清仓 | 14:56（标签取自早盘 9:25） |
| ② | **收盘**亏损 ≥ **5%** | 清仓 | 14:56 |
| ③ | 当日**收盘**跌幅 ≥ **7%** | 清仓 | 14:56 |
| ④ | 收盘跌破 **5 日线** | 清仓 | 14:56 |
| ⑤ | 持有满 **10 个交易日** | 清仓 | 14:56 |
| ⑥ | 收益 >10% 且当日跌 >2% | 卖 30% | 14:56（可与⑦叠加） |
| ⑦ | 买入次日收盘**未涨停** | 卖 50% | 14:56 |

T+1 约束：买入当日不可卖（用 `can_use_volume` 保证）。

> ⚠️ **规则⑦请不要关闭。** 回测显示它单独贡献了约 97 个百分点的收益差 ——
> 它的实质不是止盈，而是「**T+1 未封板 = 弱势 → 减半仓**」的过滤器：
> 对最终止损的 118 个买点，把每元交易额亏损从 −7.58% 收窄到 −4.50%；
> 对盈利仓位几乎零影响。

### 4.6 组合层净值回撤熔断（默认**关闭**）

`DD_BREAKER_ROLL = 0`。回测中「回看 40 日、回撤 >10% 即停止开仓」把四年年化从
13.81% 提到 26.83%、最大回撤从 −51.11% 收到 −29.13%。但该参数是在**同一样本**上
选出的，未做 walk-forward 验证。建议先 dry-run 观察，确认后再改这个常量。

## 七、故障排查

| 现象 | 原因与处理 |
|---|---|
| `连接 MiniQMT 失败` | 客户端没启动/没登录/极简模式未开；确认 `--mini-path` 指向 `userdata_mini` |
| 股票池为空 | 板块数据未下载。在 QMT 客户端里下载一次板块分类与日线数据 |
| 候选池为 0 | 正常，弱市里昨日涨停股可能全部被前置筛选剔掉（看日志的筛选 note） |
| 承接强度全为「不做承接判定」 | 9:20 后采集到的点 <8 个 → 启动太晚或 `POLL_INTERVAL` 太大 |
| 全部维度缺席 | 日线没下载。首次运行前先在 QMT 里补充历史数据 |
| 日志出现「非本策略持仓」 | 账户里有手工买入的票。默认不接管；如需接管把 `ADOPT_UNKNOWN_POSITIONS` 改 True |
| 下单被拒 | 看 `on_order_error` 回调的 `error_msg`；常见是资金不足、涨跌停价外、无可用股份 |
