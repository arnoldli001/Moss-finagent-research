### 建议 4：A05 / A06 能否提速，批量合到 1 次 LLM

**可行性：✅✅ 强烈推荐（这是本轮最高 ROI 的一条，且我上一轮判断错了）**

**先纠正我上一轮的说法**：我曾说"A05/A06 改批量合 1 次 LLM"，后来读代码发现**它们各自已经是单次批量调用**（所有条目一次发、一次返回列表）。所以「各自内部」没有合并空间。

**但「A05 与 A06 之间」有**：

| | 现状 | 合并后 |
|---|---|---|
| 调用次数 | **2 次**（A05 核验 + A06 抽取） | **1 次** |
| 输入 | 同一个 `info_items` 列表 | 同 |
| system prompt | 两套（核查员 / 结构化专家） | 合成一套 |
| 输出 | `{"reviews":[...]}` + `{"events":[...]}` | `{"reviews":[...], "events":[...]}` |
| 云端墙钟 | 2 次 × ~10s（**并发时取 max ≈ 10s**） | 1 次 ≈ 12s（输出更长） |
| 成本 | 2 次 | 1 次（省 ~40% input 重复） |

**⚠️ 关键判据**：因为 A05/A06 **当前是并发的**（`store → verify_info ∥ extract_events`），
合并的**墙钟收益有限（≈0，因为取 max）**，但**成本和稳定性收益是实的**：
- input 只发一次（两个 prompt 的 info_items 重复部分省掉）
- **少一次失败面**（两次调用任一次 JSON 坏都要重试）
- 少了 2 路并发对 provider 配额占用

**结论**：**做，但按"降本 + 降故障面"立项，不要按"省时间"立项**（省时间会失望）。
