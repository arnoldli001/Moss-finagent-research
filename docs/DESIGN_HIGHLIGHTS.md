# 设计亮点与难点

> 面试时"我做了什么"不值钱，"我为什么这么选、代价是什么"才值钱。
> 每一条都按 **问题 → 取舍 → 做法 → 代价** 四段写，可直接背。

---

## 亮点 1 · 所有 LLM 调用必须过网关（架构红线）

**问题**：19 个 Agent 各写各的 `openai.chat.completions.create`，会出现
成本不可见、没有降级、失败无留痕、模型名散落各处。

**取舍**：把网关做成**唯一入口**（红线写进模块 docstring），代价是每个 Agent
多一层依赖注入、且网关成为潜在单点。换来的是一处控制成本与可靠性。

**做法**（`src/infrastructure/llm/gateway.py`，221 行）：

```
complete(tier, system, prompt)
  ├─ 取消检查        在调用 provider 前拦截，避免浪费 token
  ├─ 输入硬截断      超长 prompt 尾部截断
  ├─ 语义缓存        命中直接返回并落审计（cached=True）
  ├─ token 预算      单任务累计超限 → 直接拒绝，不再调用
  └─ 降级链          for model in routing[tier]:
                       熔断器 allow_request? 否 → 记录并 continue
                       provider.chat() → 失败 record_failure + continue
                       成功 record_success + 累计 token + 写缓存
```

**难点**：熔断器必须按 **provider** 而不是按 model 计数 —— 云端 API 挂了，
换同 provider 的另一个模型没有意义，必须直接降级到别的 provider。

**可讲的细节**：`max_tokens` 有**双层上限**（模型配置 + 全局硬上限），
防止某个 Agent 在配置里写个 100k 把预算打穿。

## 亮点 2 · 分层模型路由：把"分类任务"从云端拉回本地

**问题**：Planner 只做"从指标目录 + Agent 目录里挑子集"，是纯分类任务，
但每次调用云端模型要 18 秒且按 token 计费。

**取舍**：本地 `qwen2.5:1.5b` 精度略低，但 **3–5 秒且零 token 成本**。
规划错一个 Agent 的代价远小于每轮省下的 15 秒。

**做法**（`configs/models.yaml`）：

| 层级 | 任务 | 主模型 | 备模型 |
|---|---|---|---|
| light | 数据清洗、格式化 | 本地 1.5B | deepseek-flash |
| medium | 信息层去伪/提取 | 本地 8B | deepseek-flash |
| reasoning | 宏观/中观/微观/风控 | deepseek-flash | 本地 8B |
| decision | 最终投研建议 | deepseek-v4-pro | deepseek-flash |

**代价**：本地模型常驻 GPU（`keep_alive=24h`，约 12GB 显存）；
首次冷启动 28 秒 —— 这个数字必须预热掉（见 `docs/DEMO_GUIDE.md`）。

## 亮点 3 · 数据层三级故障转移 + 「绝不回退模拟数据」

**问题**：本地行情源（QMT）经常没启动；远端接口（AkShare）偶发 WAF 封锁。

**做法**：

```
分档 TTL 缓存 → per-key lock → QMT → CSV → AkShare → 报缺口
```

- **分档 TTL**：月频宏观 24h / 估值 12h / 行情 4h / 实时流动性 5min。
  统一 TTL 会导致要么宏观数据被反复拉、要么盘中行情过期。
- **per-key lock**：防缓存击穿 —— 同一 key 的并发请求只放一个到远端。
- **硬约束**：真实源全失败时**绝不回退 simulated**，宁可报数据缺口。

**取舍**：这条红线会让演示偶尔"没数据"，看起来不如那些总能返回数字的系统。
但**假数据进了投研建议比没数据危险得多**。我把它作为明确的工程价值主张，
而不是缺陷藏起来。

## 亮点 4 · 规则总表 + 位掩码引擎（本仓库最近的一次重构）

**问题**：集合竞价选股的判定散在 4 个文件、329 处 `if/elif` 里，
且存在**隐性顺序约束** —— 「规则 6 必须先于规则 5」，因为规则 6 会给票打个标签，
规则 5 靠这个标签豁免。改一次顺序就静默出错。

**做法**：把规则变成**数据**，执行变成**解释器**。

```
compile_rules(config) → RuleSet（进程启动编译一次）
    PREFILTER 9 条 · ASSIGN 1 条 · VETO 10 条（位掩码）· DIMS 12 个分档表
```

**两个关键设计**：

1. **顺序耦合消失**：打标签与否决拆成两遍纯函数。Pass1 同时求值所有打标签规则，
   Pass2 按 Pass1 之后的标签集合算豁免。谁先谁后都一样。
2. **位掩码可落库、可统计**：10 条否决压成一个 `uint16`，比存一串 JSON 原因省得多；
   `hit.sum(axis=0)` 一行就能看出"今天哪条规则杀得最多"。

**难点 —— 也是最该讲的部分**：这是**纯重构，行为必须逐位不变**。
我建了黄金回归：冻结真实行情录像带，**47 只票 × 12 维逐位比对**。

它抓出了两个肉眼绝对看不出来的 bug：

| bug | 症状 | 怎么抓到 |
|---|---|---|
| `Curve.at` 越界兜底两边都取"首段 y_lo" | 「竞价额/昨日成交额 = 1.0」（远超上界 0.06）被判 **0 分而非满分**，`previous_day` 整体差 0.5，18 只票总分漂移 | 逐维 diff |
| `Seg.hit` 把 `lo` 写成开区间 | 换手率**恰好 3.0** 的票两段都不命中，掉到兜底 0 分 | 逐维 diff |

定位手段：把 git HEAD 的旧实现加载进来做逐维对比，最终 **564 处全部一致**。

**性能 —— 结论和直觉相反**：

| 环节 | 耗时 | 占比 |
|---|---:|---:|
| `ecology.build_snapshot()` 生态序列 | **1223 ms** | **99.3%** |
| 规则判定（特征 + 12 维 + 10 条否决 + 出池） | 8.1 ms | 0.66% |

profile 热点全是 `sqlite3.fetchall` 与 pandas —— 根因是**生态序列每轮都读
`daily`/`stk_limit`/`daily_basic` 三张全市场表**（约 208 万次元素操作），
而这个序列**一天只变一次**。

> **面试金句**："所以这次重构的速度收益应该记在'把一天一变的结果挪出热路径'上，
> 规则侧买的是可读性，不是毫秒 —— 规则本身只占 120 秒窗口的 0.007%。"

## 亮点 5 · 自学习数据补充：让系统自己补数据源

**问题**：某个指标取不到时，原流程是"报缺口 → 等开发者写 connector"。

**做法**：`DataGapResolverAgent` 让 LLM 生成采集代码，再走**两道安全闸**：

```
LLM 生成 connector 代码
  ├─ ① validate_connector_code(code)   AST 静态校验（禁 import os/subprocess、禁 eval）
  └─ ② sandbox_test(code, indicator)   子进程沙箱冒烟，15s 超时
        ↓ 双通过
      落库注册，后续复用（自动沉淀，不是用完即丢）
```

**为什么必须两道**：静态校验挡不住"看起来合法但会打死接口"的代码
（比如无限重试）；沙箱挡不住"某个分支才触发"的恶意代码 —— 两者互补。

**代价**：沙箱是子进程级隔离，**不是安全容器**，只适合"半信任"的生成代码
在小规模数据源上使用。这一点必须主动说，不能吹成"安全沙箱"。

## 亮点 6 · 面向机构的多租户与合规（Chinese Wall 落地）

**问题**：这是**机构内部**的量化平台，不是公众 SaaS。隔离的重点完全不同 ——
主要风险不是"客户 A 看到客户 B"，而是**研究员看到别人的在研策略**、
**投资端看到研究端未发布的结论**（《证券法》第 54 条：禁止利用未公开信息交易）。

**取舍**：把权限拆成**三个正交维度**而不是一个"级别"。

| 维度 | 回答 | 落地 |
|---|---|---|
| RBAC | 能做什么动作 | `Role` × `_POLICY` 动作矩阵 |
| ABAC | 能看什么等级 | `DataClass` 四级 × `Principal.clearance` |
| 信息隔离墙 | 能看哪个部门的在研内容 | `WallGroup` + `WallCrossing` |

**为什么必须正交**：合规岗权限高（要看全部审计）但**不该**看策略源码；
PM 权限低但**需要**看持仓。合成一个维度必然出现"越权即升权"——
为了让他看持仓而顺手给了策略权限。

**跨墙的设计**：不是一个配置开关，而是一个**必须显式传参的对象**：

```python
authorize(READ_STRATEGY, resource, wall_crossing=WallCrossing(
    approver="compliance-01", reason="监管核查"))
```

不传就拒绝；`approver/reason` 必填、自动盖时间戳、进审计。
**这样"跨墙"在代码里无法悄悄发生。**

**代价**：每个路由都要正确取 Principal，写错的后果是 401 而不是静默放行 ——
这**正是想要的**（忘了鉴权必须表现为失败）。

## 亮点 7 · 把合规红线变成 CI 门禁

**问题**：`SECURITY_COMPLIANCE.md` 早就写了红线（禁止硬编码密钥、禁止日志输出完整 Prompt），
但仓库里**一条实现都没有**。合规要求写在文档里没人执行。

**做法**：独立 CI job `compliance`，失败**不允许合并**（与普通单测失败的处置不同）。
`tests/unit/test_compliance_gate.py` 每条用例对应一条要求，出处写在注释里。

**门禁上线当天就抓到三个真问题**（全在 `.env.example`）：

1. `POSTGRES_PASSWORD=moss_finagent` —— **一个能用的默认密码**，会诱导部署时直接照抄
2. `ALERT_EMAIL_TO=1027312283@qq.com` —— **真实个人邮箱进了版本库**
3. `DEEPSEEK_API_KEY=sk-your-deepseek-key-here` —— 形似真 key

**这次经历本身最值得讲**：我写完门禁先跑了一遍，以为会全绿，结果红了三条。
如果只是"写了检查但没跑"，这三个问题会一直躺在仓库里。

**顺带修正的一个"假实现"**：`rls.py` 的 `_inject_tenant_filter` 取了租户、
遍历了表，然后 `return stmt` —— docstring 声称注入了 `WHERE tenant_id = ?`，
**实际什么都没做**。这比没有更危险，因为它让人以为已经隔离了。
重写后只做它真正能做到的事，并把边界（"应用层 RLS 防疏漏，数据库原生策略才是边界"）
写进文档。

## 亮点 8 · 消除重复实现：一条规则 5 处实现、3 处是错的

**问题**：`sh/sz` 交易所归属规则散在 5 处，其中 3 处只判断 `6/9` 开头、**漏了沪市 `5` 段**。
后果：588170（科创 50 ETF）被判成深市 → 取数全空，且**报错信息完全指不到原因**。
项目里甚至有一条注释记录过这个坑，但另外三处没改。

**做法**：收敛到 `src/core/symbols.py` —— 选 `core` 是因为它是**唯一的底层包**
（出度为 0），连接器与做 T 都能 import 而不产生跨层耦合。

**顺带修的另一类问题**：`configs/intraday.yaml` 的路径是 **CWD 相对且无 env 覆盖**，
服务不在仓库根启动时只打一条 WARNING 就回退内置默认值 ——
**用户改的权重与阈值静默失效**。已改为绝对路径 + `INTRADAY_CONFIG` 环境变量覆盖，
与另两个模块的约定对齐。

# 难点清单（面试官爱追问的）

### D1 · "19 个 Agent 怎么保证不互相打转？"

ReAct 循环有 `max_steps=3`，且每个 Agent 最多追问 1 次；Planner 按指标目录
与 Agent 目录挑子集，**不是每次都全唤醒**。审计层（A18）做完整性 + 封存校验。

### D2 · "怎么防 LLM 幻觉？"

三件事，且**不声称完全解决**：

1. **时效红线**：拒绝引用过期数据（最高优先级规则）；
2. **审计链**：落 `prompt_hash` / `response_hash` / token / 延迟 / 降级链，
   任何一条结论都能回溯到当时喂进去的原文；
3. **审计 Agent**：A18 做完整性校验 + 封存。

诚实的说法是："我把幻觉从'不可发现'变成'可发现、可追溯'。"

### D3 · "回测有没有未来函数？"

三条纪律：① 回测引擎**不含 LLM**（纯本地规则计算）；
② 因子/信号只用 `t` 时刻及以前的数据，取数按 `trade_date` 钉死；
③ 提供 `--synthetic` 确定性合成数据，用来验证**机制本身**正确。

### D4 · "为什么不用 AutoGen？"

需要**可控的 fan-out/fan-in**：A09 中观 + A10 微观 + A13 行业 并行，
再 fan-in 到 A17。AutoGen 的 group chat 是黑盒，控不了并发度、控不了失败边界、
也控不了"哪个 Agent 在什么时候说话"。

### D5 · "VaR 为什么用历史模拟法？"

参数法（方差-协方差）假设正态分布，会**系统性低估尾部风险** —— 而 A 股的
尾部恰恰是最需要看的。历史模拟法不假设分布，代价是需要 ≥50 天样本、
且无法外推历史未出现过的极端情形（所以我另外做了压力测试补这一块）。

### D6 · "分层回测的空头腿怎么处理？"

**A 股不可做空**，所以 H-L 价差只用于**因子有效性检验**（看单调性），
不当作可交易策略。这一点如果不说清，量化面试官一定会追问。

### D7 · "IC 为什么用 Spearman 而不是 Pearson？"

因子与收益的关系通常是**单调但非线性**的，且因子值有极端值。
Spearman（秩相关）对异常值稳健、只要求单调关系，比 Pearson 更贴合场景。

### D8 · "中性化为什么必须带截距项？"

OLS 回归若不带截距，常数项会被强行吃进 beta，导致因子暴露估计有偏。
多一列常数项，换来符合计量规范的结果。
