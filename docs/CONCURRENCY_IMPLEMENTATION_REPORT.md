## 零、先看这个：20 元/天预算的真正含义

**实测结论：投研分析很便宜，烧钱的是主线模块。**

审计日志（`data/audit/llm_audit.jsonl`，43104 条记录）按 agent 分账：

| Agent / 来源 | 累计成本 | 说明 |
|---|---:|---|
| `mainline_relevance` | **484.11 元** | 主线题材相关性逐股打分 |
| `mainline_member_pure` | **117.25 元** | 成分股提纯 |
| `A17_recommend` | 7.28 元 | 投研决策层 |
| 其余投研 Agent | 各 < 0.5 元 | A10/A11/A12/A13… |
| **投研分析合计（80 次）** | **8.62 元** | **单次中位 0.0527 元** |
| **总计** | **617.53 元** | 其中 **2026-09-20 单日 487.57 元** |

**一句话：投研分析单次 0.05 元，而主线相关性打分一天能吃掉 487 元。**

所以 20 元/天预算下：

| 口径 | 数值 |
|---|---|
| 单次分析成本（中位） | **0.0527 元** |
| 单次分析成本（p90，保守） | **0.2237 元** |
| 20 元全给投研 → 每日可做 | **379 次**（中位口径）/ 89 次（p90 口径） |
| 折算 | **约 0.63 任务/分钟**，即约 **16 次/小时** |

⚠️ **这意味着：成本是比并发更紧的约束，紧约 10 倍。**
并发天花板是 6.6 任务/分钟（3960 次/天），但预算只允许 379 次/天。
**加并发参数不会让你服务更多人，只会更快烧完预算。**

**必须优先处理**：`mainline_relevance` 若不受约束地跑一天，
20 元预算当场归零，之后所有投研请求全部 503。
本次新增的日预算护栏会拦住投研请求，但**不会**拦住主线批量作业
（见 §3.5 的设计说明）—— 那需要在它们自己的入口查 `remaining()`。

## 一、最大并发量：答案

### 1.1 直接回答

| 问题 | 答案 |
|---|---|
| **真正同时提交**（N 人同一秒点分析），即时响应 | **4 个**（默认 `MOSS_RESEARCH_MAX_INFLIGHT=4`） |
| 超出 4 个会怎样 | **排队**，不是失败也不是拖垮。等 `MOSS_RESEARCH_QUEUE_TIMEOUT`（默认 30s）拿不到名额才返回 503 |
| **稳态吞吐上限**（并发维度） | **6.6 任务/分钟**（≈ 400 任务/小时） |
| **稳态吞吐上限**（20 元预算维度） | **约 16 次/小时** ← **实际生效的上限** |
| 折算成"在线用户" | 约 **379 个**「平均每 15 分钟点一次」的活跃用户（按预算口径） |
| 想更高并发怎么办 | 调 `MOSS_RESEARCH_MAX_INFLIGHT`；**但真正的天花板是 20 元/天预算** |

### 1.2 两个天花板必须分开看

```
并发天花板  = 闸门 ÷ 单任务时长 = 4 ÷ 36.2s = 6.6 任务/分钟 = 3960 次/天
成本天花板  = 日预算 ÷ 单次成本 = 20 ÷ 0.0527 = 379 次/天
                                              ↑ 这个先撞到（紧 10 倍）
```

**结论：`MOSS_RESEARCH_MAX_INFLIGHT=4` 保持不变即可**，它已经足够
（4 并发 × 36 秒 ≈ 6.6/分钟，而预算只允许 0.63/分钟）。
再调大闸门只会让更多任务同时烧钱，不会提升可持续服务的用户数。

### 1.3 这个数字是怎么来的（实测，不是估的）

```
单任务墙钟时长 T   : 中位 36.2s   p75 111.3s   p90 179.3s   max 408.2s
单任务 LLM 调用数  : 中位 4 次    p90 8 次      max 11 次
单任务 token       : 中位 34,001  p90 70,918    max 714,842
单次 LLM 延迟      : 中位 18.3s   p90 60.4s     p99 96.4s
单次分析成本       : 中位 0.0527 元  p90 0.2237 元  max 0.7433 元
```

**关键洞察：单任务中位 36.2 秒，而只有 4 次 LLM 调用。**
说明任务时长由 **LLM 的秒级延迟**主导，不是本机 CPU/IO 瓶颈。
所以容量模型就是 Little's Law：`吞吐上限 = 闸门 ÷ T`。

用 Erlang-C 算排队等待后（`scripts/capacity_model.py` 可复现）：

| 闸门 c | 吞吐上限（任务/分钟） | 70% 负载下的排队等待 | 对应 LLM 调用速率（次/分钟） |
|---:|---:|---:|---:|
| 2 | 3.3 | 34.8s | 9.3 |
| **4（默认）** | **6.6** | **12.9s** | **18.5** |
| 6 | 9.9 | 6.8s | 27.8 |
| 8 | 13.2 | 4.1s | 37.1 |
| 12 | 19.9 | 1.9s | 55.6 |
| 16 | 26.5 | 1.0s | 74.2 |

### 1.4 参数一览（都可用环境变量覆盖）

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `MOSS_LLM_DAILY_BUDGET_CNY` | `20` | **LLM 日成本预算（元）。0 = 不限** |
| `MOSS_RESEARCH_TASK_RESERVE_CNY` | `0.25` | 单任务预扣额度（实测 p90 向上取整） |
| `MOSS_RESEARCH_MAX_INFLIGHT` | `4` | 同时在飞的投研任务上限 |
| `MOSS_RESEARCH_QUEUE_TIMEOUT` | `30` | 排队等名额的秒数，超时返回 503 |
| `MOSS_RESULT_CACHE_MAX` | `500` | 结果缓存条目上限 |
| `MOSS_TASK_KEEP` | `200` | 已完成任务保留条数 |
| `MOSS_TASK_TTL` | `3600` | 已完成任务保留秒数 |

## 二、实测改善

`scripts/bench_concurrency.py --compare`（可复现）：

### 2.1 LLM 语义缓存：事件循环阻塞 **降低 847×**

```
缓存文件数           : 3158
并发查找数           : 8

改造后（内存语义索引）
  冷启(未建索引) 总耗时:    791.1 ms   事件循环最大滞后  18.2 ms
  热态(索引已建) 总耗时:      2.5 ms   事件循环最大滞后   2.2 ms

改造前（同步全目录扫描）
  并发查找总耗时       :   2155.7 ms   阻塞事件循环   2155.7 ms

  => 事件循环阻塞改善: 847x
  => 并发总耗时改善  : 847x
```

这条是**对"并发时响应更快"贡献最大的一项**。原来每次缓存未命中都要
在事件循环上同步解析 3158 个文件，8 个并发请求合计**冻结整个进程 2.16 秒** ——
期间所有用户的所有请求（包括健康检查、页面轮询）全部卡住。
现在索引常驻内存，未命中查找降到 2.5ms 且几乎不占事件循环。

冷启那 791ms 是**一次性**建索引代价，且已经用
`_warm_llm_cache_index()` 挪到启动后台任务，不进任何请求路径。

### 2.2 TaskStore：内存泄漏已封顶

```
3000 个完整任务生命周期后：
  tasks=200 (上限 200)   tokens=200   handles=0   live_state=0
```

改造前是**任务 3000 / tokens 3000 全部常驻**（只增不减）。
现在按「TTL 1 小时 + 容量 200」双阈值淘汰，且
`_tasks` / `_tokens` / `_handles` / `_live_state` **四表同步回收**。

**在飞任务永不淘汰** —— 这条有专门的测试用例守着
（`test_task_store_keeps_inflight_tasks_despite_capacity`），
因为淘汰在飞任务会让轮询 404、取消失效。

### 2.3 准入控制：峰值被钳住

```
提交 32 个任务，闸门 4：
  served=32   peak_inflight=4   wall=269ms
```

峰值在飞数**严格等于闸门值**，不再随提交量线性膨胀。

## 三、改了什么（逐文件）

### 3.1 `src/api/routes/research.py` — 三层流量治理

按代价从低到高，在 `submit_analyze` 入口依次设卡：

```
请求 → ① 结果缓存命中？ → 直接返回（0 成本）
        ↓ 未命中
       ② 相同查询正在算？ → 复用它的 task_id（不新起管线）
        ↓ 无
       ③ 抢准入名额（等 30s）→ 抢到才起管线；超时返回 503
```

**第 2 层（同问合流）是这次最巧的一处**：原实现的击穿窗口是
"检查缓存未命中 → 管线跑完才写缓存"之间隔着**整个管线时长（中位 36 秒）**，
这期间任何相同查询都重跑一遍。10 人同时点同一个热门问题 = 10 条完整管线。

修法是**开始执行时就用 qhash 占位登记 leader 的 task_id**，
后到的请求直接拿到同一个 task_id 去轮询。选这个方案而不是
"future 等结果"，是因为本项目前端本来就是「提交拿 task_id → 轮询」模型，
复用 task_id 天然契合既有交互，也避免长连接在代理/网关处被掐断。

新增 `GET /api/v1/research/capacity` 观测接口。

### 3.2 `src/infrastructure/llm/cache.py` — 内存语义索引

新增 `_SemanticIndex`：按 `(agent_id, scope)` **两级分桶**存 3-gram 向量。

为什么分桶是重点：语义复用**必须同时满足** agent_id 与 scope 两个作用域
（防 `light` 层小模型结论被 `decision` 层复用、防 A05/A06 输入重叠导致结论串台）。
原实现是"解析全部文件 → 再丢掉 99%"，分桶让过滤变成"直接取桶"。

新增 `aget()` 异步入口（扫描走 `asyncio.to_thread`）与 `warm_up()` 预热。
索引懒建 + `put()` 增量更新，旧缓存目录**无需迁移**。

`gateway.py` 相应改用 `await self._cache.aget(...)`。

### 3.3 `src/api/tasks.py` — 双阈值淘汰

`evict()` 按 TTL + 容量淘汰**已终结**任务；`create()` 与 `_run` 收尾时触发。
新增 `stats()` 供观测。`TaskRecord` 增加 `finished_at` / `deduplicated` 字段。

### 3.4 `src/api/main.py` — 启动预热

`_warm_llm_cache_index()` 后台任务，延迟 5 秒执行，失败只记日志
（未建时按需懒建，行为不变）。

### 3.5 `src/core/budget.py`（新增）— 日成本护栏

**为什么需要**：原有护栏只有 `llm_token_budget_per_task`（**单任务** 20 万 token），
它防"单个任务失控"，**完全不防"很多任务累加"**。20 元/天约束下，
一次没节制的批量打分就能把整天额度用光，且表现为
"余额不足"这种**看起来像配置错误**的形态。

设计要点：

- **按日累计**（本地日期），投研请求、定时作业、批量脚本共用同一个池子；
- **预扣 + 结算**：任务开始前按 p90 成本预扣 0.25 元，结束后退还。
  为什么必须预扣 —— 突发时所有任务都还没产生 token 消耗，只看已花费
  会集体放行、集体超额（TOCTOU）；
- **价格从 `configs/models.yaml` 读**，不在代码硬编码（改价只改配置）；
- **只拦投研入口**：`mainline_relevance` 这类批量作业只记账、不拦截。
  理由：它们有自己的调度与重试语义，在这里硬拦会把"跑了一半的批处理"
  变成脏状态（写出一半的分数、下一轮又重算）。它们该在自己的入口
  判断 `budget.remaining`。

`gateway.py` 的每次成功调用都会记账（含 `by_source` 分账），
所以 `/health` 的 `llm_budget.by_source` 能直接回答"钱花在哪了"。

### 3.6 新增文件

| 文件 | 用途 |
|---|---|
| `src/core/budget.py` | 日成本预算护栏（记账 + 预扣 + 分账） |
| `scripts/bench_concurrency.py` | before/after 并发基准（含改造前实现复现） |
| `scripts/capacity_model.py` | 容量模型，从审计日志算闸门建议值（Erlang-C） |
| `scripts/cost_model.py` | 成本核算：单次分析成本 + 日预算容量 |
| `tests/integration/test_research_concurrency.py` | 13 个治理行为回归测试 |

### 4.3 过程中抓到的一个 latent bug

给 gateway 加成本记账时，我在 `except` 分支里写了 `logger.debug(...)`，
但 **`gateway.py` 根本没有定义 logger** —— `py_compile` 检查不出来
（语法合法），只有 ruff 的 F821 报了。若真触发（记账失败），
会抛 `NameError` 把一次正常的 LLM 调用变成异常。
已补 `logger = logging.getLogger(__name__)`。

### 4.4 发现并修掉的一个隐蔽 bug

加 `/research/capacity` 时，我把它放在了 `/research/{task_id}` **之后**。
Starlette 按注册顺序取第一个匹配路由，于是 `capacity` 被当成 task_id 吃掉：

```
GET /api/v1/research/capacity  ->  MATCHED BY: /api/v1/research/{task_id}
```

实测确认后调整为在 `{task_id}` 之前注册，并加了
`test_capacity_endpoint_is_reachable_and_not_shadowed` 守住这个顺序。

## 五、还剩什么没做

本次做了评估里的 **P0 四项**（单文件内、不动架构）+ 日预算护栏。以下按需推进：

| 项 | 状态 | 说明 |
|---|---|---|
| **限制 `mainline_relevance` 用量** | ⬜ **最该做** | 它是 484 元的消耗源。20 元预算下必须给它设上限，否则投研请求会被它挤到 503 |
| 结果缓存/TaskStore 外置到 Redis | ⬜ 未做 | **做完才能加 `--workers N`**。现在加多 worker 会出现"worker A 提交、轮询打到 B → 404" |
| 数据层切 PostgreSQL | ⬜ 未做 | 工厂已支持 `DATA_BACKEND=postgres`，但目前 SQLite 写入仍是串行点 |
| 租户级配额 | ⬜ 未做 | 现在是**全局**日预算（所有租户共享 20 元），没有 per-tenant 细分 |
| 事件循环滞后监控 | ⬜ 未做 | 建议加为常驻指标 —— 它是发现"同步阻塞"的唯一直接信号 |
| 预算持久化 | ⬜ 未做 | 当前账本在**进程内**，重启后当日已花额度会归零。多进程/重启频繁时需落库 |

## 六、上线建议

1. **`MOSS_RESEARCH_MAX_INFLIGHT` 保持 4** —— 成本才是约束，
   调大闸门不会服务更多人，只会更快烧完预算。
2. **给 `mainline_relevance` 设用量上限**（第一优先级）。
   它不受本次护栏拦截，而它是 484 元的消耗源。
3. **观察 `/api/v1/research/capacity`**：
   - `budget.used_pct` 长期 > 80% → 预算偏紧，用户会开始吃 503
   - `budget.by_source` → 直接看钱花在哪，若投研不是大头说明别处在烧
   - `inflight` 长期等于 `max_inflight` → 闸门偏小（用户在排队）
   - `task_store.tasks` 长期贴住 `max_tasks` → 淘汰阈值要调小
4. **前端要显示预算/排队状态**：503 的 `detail` 带了具体金额与在飞数，
   直接展示比让用户看到报错好。
5. **业务上引导收窄 `analysis_type`**：`stock` 比 `full` 少一个数量级的
   LLM 调用（实测 plan 的 agents 数：full=10, stock=8, macro=3）。
   在成本约束下这是最有效的省钱手段。
6. **暂时不要加 `--workers`**，直到状态外置完成。

## 七、一句话总结

改造前的问题不是"并发不够"，而是**没有闸门**：N 个用户 = N 条完整管线，
语义缓存每次未命中冻结事件循环 2 秒，任务表只增不减。

现在：三层流量治理（结果缓存 → 同问合流 → 准入闸门）+ 日成本护栏，
实测事件循环阻塞降 **847×**、内存泄漏封顶、峰值在飞数被钳住。

**但 20 元/天 意味着真正的天花板是成本，不是并发 ——
约 16 次/小时，比并发上限紧 10 倍。**
所以要服务更多用户，方向是**降低单次成本**（收窄 analysis_type、
提高缓存命中、限制主线模块），而不是调大并发闸门。
