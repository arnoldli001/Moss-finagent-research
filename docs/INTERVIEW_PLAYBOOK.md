## 0. 两套讲法

### 0.1 三十秒版（电梯陈述）

> "我做的是一个 A 股**超短与做T**的投研系统，核心不是'再写一个选股公式'，而是解决三件事：
> **第一，把交易员的经验变成可复现的打分**——把《》等超短语料里的 300 多个文件，抽成六个**互斥**的战法分类器和十一个打分维度，权重合计 100，每一项都能指回原文出处。
> **第二，把'什么时候该用哪套打法'交给情绪周期**——用涨停家数、炸板率、最高连板算周期阶段，用最近 10 个交易日的'当日最高连板'序列找波峰定生态和压力位。
> **第三，也是最花时间的，是把数据链路的坑堵死**——静默用两天前的旧行情、ST 过滤空转、缓存重启就没了，这些比模型不涨更致命。"
>
> 落地形态：FastAPI + SQLite + React，15 GB 本地行情仓库，LightGBM 三档模型，六个定时作业。

### 0.2 三分钟版（按"问题—判断—动作—结果"讲）

| 段落 | 讲什么 | 落点数字 |
|---|---|---|
| 背景 | 超短打法的知识散在几百份 docx/pdf 里，人脑记不住，且"该不该做"依赖当天的市场结构 | 语料 344 个文件 |
| 判断一 | 六个战法**不能加权求和**——它们由**择时**决定，冰点该用破冰式、而追击式在冰点恰恰是禁忌。加权求和等于把"该做"和"不该做"平均成一个没意义的中间值 | 六式互斥分类器 |
| 判断二 | 打分必须**可解释到原文**。每个维度的权重是"我们自己标的"，所以每条都标注出处；拿不到的维度**从分母剔除而不是补 0**，再加覆盖率惩罚 | 11 维 / 合计 100 |
| 判断三 | 最容易亏钱的不是模型不涨，而是**静默地用错数据**。所以全链路做了"不猜、不臆造、缺口必须显式报出来" | 见第 4 节 |
| 结果一 | 竞价选股：9:25 出池，11 维打分 + 六式裁定 + 生态压力位，全链路 9:27 前完成 | 预热 120–159s → 缓存后 0.02s |
| 结果二 | 量化选股：LightGBM 三档（20–150 / 150–500 / 500 亿+），26 个特征，按每只票自己的流通市值分发模型 | 阈值=当日截面 90 分位 |
| 结果三 | 超短战法回测：**如实报出"四个战法里三个在这个区间是负期望"**，没有粉饰 | 见 2.5 |
| 收尾 | 我在这套系统里最看重的能力是"**知道自己在什么时候是错的**"——数据缺口、样本量不足、假设未经验证，都要写进报告 | — |

## 1. 项目全景

### 1.1 一句话定位

面向 A 股**短线（超短/做T）**的投研与决策辅助系统：**知识工程（语料→规则）+ 机器学习（三档选股模型）+ 工程纪律（数据新鲜度与可解释性）** 三条腿。

### 1.2 模块地图

| 模块 | 一句话 | 主输出 | 关键技术点 |
|---|---|---|---|
| **竞价选股** | 每日 9:25 从昨日涨停池里挑出次日可接力的票 | 候选池 + 11 维打分 + 六式裁定 + 生态/压力位 | 竞价逐秒序列、承接强度、互斥分类器 |
| **量化选股** | 每个开市日 9:25–9:45 与 14:45 用三档模型全市场选股 | 20 只票 + 得分 + 分档 + 命中板块 | LightGBM 分档、26 特征、截面分位阈值 |
| **做T辅助** | 日内分时多因子打分，给低吸/高抛/止损三条线 | 总分 + 档位 + 信号 + 关键价位 | 14 维权重、客观数据拟合价位、无未来函数 |
| **日K（擒牛线）** | 日线级别的量价体系与战法信号 | K线+擒牛线+量柱+B/S 战法 | 通达信公式移植、量柱体系 |
| **超短战法回测** | 把六式拿去跑历史，出胜率/收益/回撤 | 分模式胜率、账户净值、卖出原因分布 | **复用实盘分类器**、T+1 制度、成交可行性 |
| **资金流监控** | 板块近 10 日净流入趋势 + 个股大单净额排行 | 板块趋势图 + 进出前 10 | 大单净额/流通市值、Parquet 缓存 |
| **板块拥挤度** | 板块拥挤度水位与历史分位告警 | 水位 + 分位 + 告警列表 | 长历史序列、217 万行日更 |

| **调度** | 20 个 cron 作业统一注册 | 运行记录 + 状态 | 单一事实源 registry、窗口判定 + 当日去重 |

### 1.3 数据流（从源到前端）

```
akshare / 东财 / 腾讯 / QMT(xtquant) / eltdx(通达信协议) / Tushare
        │
        ├─→ 实时类（竞价逐秒、盘口、资金流快照）── TTL 缓存 ──┐
        │                                                      │
        └─→ 历史类（日线/估值/涨跌停/资金流）                   │
                 ↓ 按交易日分区的 Parquet 缓存                   │
                 ↓ ingest（增量、幂等 UPSERT）                  │
              SQLite 仓库 data/quant/warehouse.db（15.3 GB）    │
                 ↓ load_dataset(dataset, start, end, columns)  │
                 ↓ 统一返回 (DataFrame, 来源字符串)             │
        ┌────────┴────────┬─────────────┬──────────────┐       │
     因子面板          竞价特征       生态序列       拥挤度序列  │
        ↓                 ↓              ↓             ↓       │
   LightGBM 三档      11 维打分      六式分类器     水位/分位    │
        └─────────────────┴──────────────┴─────────────┴───────┘
                              ↓ FastAPI
                    React 前端（自选池 / 图 / 表格 / 告警）
```

### 1.4 分层为什么这么切

- **服务层（Host composition）与 Agent Preset 分离**：跨会话共享的东西（持久化、沙箱、模型路由、子智能体注册表）放宿主；一次会话自己贡献的能力（工具、人设、提示词段落）放 Agent Preset。
- **取数层统一入口**：所有数据访问必须走 `load_dataset()` / 仓库 API，禁止各模块直连数据库——否则"这次到底查的库还是文件"会变成查不出来的问题（回测复现性依赖它）。这也是 AGENTS.md 里"禁止直接连接数据库"的落地方式。
- **打分与展示分离**：打分器是纯函数（`score_*(feature, config)`），输入是 dict、输出是 `(0~1, 人话说明)`，不碰 IO。所以它单测覆盖率极高，也能被回测复用。

## 2. 模块逐个拆解

> 每个模块统一按这个模板讲：**定位 → 选股逻辑 → 打分逻辑（分层）→ 关键参数 → 输出字段 → 亮点 → 已知限制**。

### 2.1 做T辅助（日内分时）

**定位**：日内顺周期做T的可行性判断 + 三条价位线。它不是"看多还是看空"，而是"今天适不适合动手、在哪动手"。

**选股逻辑**
- 标的来自**自选池**（`configs/intraday.yaml` 的 watchlist），不是全市场扫描——做T是持仓管理动作，不是选股动作。
- 盘中由服务端**两条节奏**自动刷新：现价/涨跌幅 5 秒（报价快车道）、总分/信号 60 秒（整表重算）。
- 交易时段 09:15–11:30 / 13:00–15:00 自动重算，非交易时段不空跑。

**打分逻辑（分层）** —— 十四维，权重合计 **100**：

| 层 | 内容 |
|---|---|
| L0 原始数据 | 分时序列、分钟K、日线、筹码分布、板块行情、指数成交额、海外映射、新闻 |
| L1 客观指标 | 箱体位置、VWAP 偏离、布林带位置、MACD、KDJ/RSI、缠论结构（分型/笔/中枢）、筹码集中度、周期阶段、板块排名、海外联动、消息面 LLM 分 |
| L2 因子分 | 每个因子各自 clip 到 **`[-1, +1]`**，附带 detail / inputs / available / gap |
| L3 总分 | `Σ(因子分 × 权重)`，权重合计 100 → 总分 **`[-100, +100]`** |
| L4 档位 | `≥+30` 强买区 / `≥+20` 买入区 / `≤−30` 强卖区 / `≤−20` 卖出区 / 其余中性 |
| L5 信号 | 4 类 × 4 强度（`low_buy/high_sell/stop_loss/none` × `solid/hollow/forced_exit/none`） |
| L6 卖点 | 三条日内卖点规则 + 「有承接」反向 veto |

权重表（`configs/intraday.yaml`，实测合计 100）：

| 维度 | 权重 | 衡量什么 |
|---|---:|---|
| `box` 箱体 | **17** | 价格在箱体中的位置（最高权重） |
| `chan` 缠论 | 12 | 分型/笔/中枢结构 |
| `vwap` | 11 | 相对 VWAP 的偏离 |
| `chip` 筹码 | 8 | 筹码集中度与获利盘 |
| `boll` 布林带 | 8 | 带内位置与带宽 |
| `macd` | 6 | 趋势动能 |
| `kdj_rsi` | 6 | 超买超卖 |
| `sentiment` | 6 | 消息面情绪（LLM） |
| `index_volume` | 6 | 大盘成交额环境 |
| `cycle` | 6 | 情绪周期阶段 |
| `board_rank` | 4 | 所属板块涨幅排名 |
| `overseas` | 4 | 海外映射标的联动 |
| `news` | 3 | 新闻面 |
| `character` | 3 | 股性（历史波动/连板基因） |

阈值：`action: 30`（动手线）、`hint: 20`（提示线）、`0 < hint < action` 是硬校验。

**总分怎么算（和竞价选股**刻意不同**，这是最容易讲混的一处）**

```
total = Σ(因子分_i × w_i)          # 因子分 ∈ [-1,1]，权重和 = 100 → total ∈ [-100,100]
                                   # 因子 unavailable → 贡献 0，**且不计入 available_weight**
```

- **不补 0、也不从分母归一化**——缺失维度的贡献就是 0，并把它的权重从 `available_weight` 里剔掉、原因写进 `gaps`。
  > 对比 2.4 竞价选股：那里是**从分母剔除 + 覆盖率惩罚**。两套口径不一样，为什么？
  > 竞价选股是"**横截面选优**"——分数要在同一天的候选之间比大小，缺失维度归一化才不会系统性压分；
  > 做T是"**绝对档位判断**"——总分要和固定的 ±20/±30 阈值比，从分母归一化会让"只有一个维度有数据"的票拿到虚高的绝对分。**同一个问题在两种使用场景下答案不同。**
- **四舍五入口径**：累加的是**四舍五入后的贡献分**（`round(contribution, 2)`），保证前端表格逐行相加 == 总分，没有 0.01 的裂缝。
- **覆盖率门槛 `MIN_COVERAGE_FOR_SOLID = 0.7`**：有效权重 <70 时把 `solid`（实心信号）**降级为 `hollow`（空心）**，reason 追加"有效权重仅 X/100（<70），已降级为软提示"。注意它**只降级、不置 None**——数据不全时仍然给结论，只是不给强信号。
- **三条一票否决**：① **止损硬约束**（`price ≤ 止损位` → `forced_exit`，且低吸分支根本不被求值）；② 覆盖率 <70 降级实心；③ **情绪周期退潮/冰点闸门**（只禁低吸，**不禁高抛减仓**——减仓在退潮期恰恰是对的）。

**关键价位（低吸 / 高抛 / 止损）——规则口径**

| 线 | 规则 |
|---|---|
| 低吸 | `box_low`；若布林下轨**在现价下方**，取 `max(箱体下沿, 布林下轨)` |
| 高抛 | `box_high × (1 + buffer)`；若布林上轨在现价上方，取 `min(箱体上沿, 布林上轨)` |
| 止损 | `低吸线 − max(1% × 低吸线, 0.5 × ATR)` |
| 档位差护栏 | 过窄围绕**原档位中点**外扩到 `1.5%×现价`；过宽围绕**现价**内缩到 `8%×现价` |
| 低吸线必须在现价下方 | 否则用 `现价 − 0.3×ATR` 给真实位置（无 ATR 时用 1% 或箱体距离的 1/4 兜底） |

**神经网络拟合口径（用户要求"每个个股都要拟合一下"）**
- 输入 7 个客观维度：筹码量能结构 / 箱体压力位 / 缠论结构 / VWAP偏离 / 布林带 / MACD / KDJ·RSI（另 7 维做后置调整）；
- 输出形式是**分位数锚点**：`低吸线 = Σ w_k × 锚点_k(P05…P30)`、`高抛线 = Σ v_k × 锚点_k(P70…P95)`、`止损位 = Σ u_k × 锚点_k(P97…P99.5)`；锚点 = 该股"每根 bar 相对当日均价的偏离幅度"的经验分位数；
- 绝对价格 = `当日均价(VWAP) × (1 ± pct)` ——**所以线天然跟着个股自己的波动尺度走**，不是一个全局百分比；
- 三个有界乘数（各夹 0.5~1.5）：`structure`（指数量能、股性）、`environment`（情绪/周期/海外/板块）、`micro`（消息面）；
- **启用闸门（自称"本模块最重要的安全阀"）**：留一日成功率 ≥ **0.80** 且触及样本 ≥ **20**，不过闸门**回退规则口径**；
- 拟合后仍过三条硬约束：低吸 < 高抛、止损 < 低吸、低吸与现价留 0.2% 间隙。

**信号触发**
- 判定顺序即优先级：**止损 → 低吸 → 高抛 → none**。
- 低吸：触及低吸线（带宽 0.3%）**或** VWAP 偏离 `z ≤ -1.5`，且总分 `≥ +20`；要出 `solid` 需 `≥ +30` 且未被覆盖率降级。
- 高抛：触及高抛线 **或** `z ≥ +1.5`，且总分 `≤ -20`；`solid` 需 `≤ -30`。
- **图上标记用盘中极值判定**（低吸看 bar 的 low、高抛看 bar 的 high），实时信号用现价 —— 这两者口径不同是刻意的，见踩坑 17。
- 逐 bar 回放（`replay_levels` / `replay_totals`）**每个 bar 只用当日截至该 bar 的数据**，不引入未来信息。

**输出字段（分层）**
- L0：`Bar` / `TrendPoint` / `Quote` / `SourceAttempt`
- L1：`build_intraday_features()` / `build_oscillator_features()` / `day_level_constants()`
- L2：`FactorContext`（60+ 个字段：price/vwap/dev_z/box_*/pct_b/bandwidth/macd_*/kdj_*/breadth/board_*/news_*/index_*/chan_*/chip_*/cycle_*/character_*）
- L3：`FactorOutcome` → `FactorScore{key,label,weight,score,contribution,detail,inputs,available,gap}`
- L4：`ScoreCard{total, threshold_action, threshold_hint, zone, verdict, factors, weights_sum, available_weight, gaps}`
- L5：`TradeSignal{kind,strength,triggered,price,ts,total_score,reason,blocked_by_stop_loss,target_level,pushed}` / `SignalMarker`
- L6：`LevelSet{low_buy,high_sell,stop_loss,stop_basis,...}` / `LevelPoint` / `ScorePoint`
- L7：`IntradaySnapshot{quote,trend,bars,levels,scorecard,signal,markers,score_series,level_series,valuation,sentiment,news,index_volume,overseas,level_fit,sell_points,health,...}`

**六套权重模板（`weight_profiles.py`）**：`balanced`（默认）/ `swing` 震荡回归型 / `trend` 趋势跟随型 / `dragon` 高换手连板 / `low_vol` 低波动钝化 / `legacy` 原始十因子口径。**权重硬校验**：合计必须恰好 100（偏差 >1e-6 抛 `ConfigError`），字段集合必须与因子目录一致。

**日线做T是另一套 7 因子**（合计 100）：`trend 20 / chan_daily 18 / volume 16 / position 14 / signal_rule 12 / cycle 10 / character 10`。

**亮点**
- 主打"**顺周期**"：同一套低吸规则在主升期和高位震荡期的胜率差一个数量级，所以周期不是加分项而是**闸门**。
- **拟合带安全阀**：神经网络拟合只在"留一日成功率 ≥80% 且样本 ≥20"时启用，否则自动回退到规则口径——不会因为一个没训好的模型给出荒谬的线。
- **两套缺失口径按场景选择**（见上）：横截面选优用归一化，绝对档位判断用剔除分母。

**已知限制（要主动说）**
- 消息面打分依赖 LLM，有幻觉风险 → 做了时效红线与缓存，见 `INTERVIEW_FAQ_OPTIMIZATION.md`。
- 分时数据源存在多源拼接，`health.stale` 按分钟K的日期判断，而分时可能来自另一个源 → 现在按分时自己的 ts 判断。
- 档位拟合单票 0.3~2 秒，做T面板不做全市场扫描，所以这个成本可接受；**放到全市场就不成立了**。
- 情绪周期闸门目前主要作用在 impact/展示层（`ready = low_ready and not cycle_blocked`），`decide_signal` 里没有完全接住——这是已知的不一致，被问到要承认。

### 2.2 日K（擒牛线 + 量柱 + B/S 战法）

**定位**：日线级别的量价体系，把通达信公式（NML / QRL / CBX20 / CBX60 / SMX）与自研的量柱体系画在同一张图上，并给出 B1–B15 / S1–S6 战法信号。

**选股逻辑**：本模块不做选股，只做**持仓标的的日线诊断**（与做T共用自选池与当前代码）。

**打分逻辑（分层）**：不输出 0–100 总分，输出的是**信号 + 结构标签**：
- 擒牛线五条（NML/QRL/CBX20/CBX60/SMX）→ 多空分界
- 量柱体系 → 高量柱 / 低量柱 / 倍量柱 / 梯量柱
- 高量柱攻防 → 支撑/压力
- B/S 战法 → `daily_signals.py` 里的 B1–B15、S1–S6

**关键设计决定（面试爱问）**
- **K线柱状图与均线是两件事**：早期一次改动误删了 K线柱、把均线一起去掉，用户明确纠正"去掉的是均线，不是 K线"→ 现在是"grid → candles → 安全线 → 擒牛线"的绘制顺序，`showCandle` 默认开，**不画均线**。
- 成交量柱与 K 线共用时间轴，避免两套缩放对不齐。

**已知限制**：公式移植自通达信，存在"同一条线在不同软件上因复权口径不同而微差"的问题；用 `quant_adj_factor` 做前复权，但不能保证与所有第三方软件逐点一致。

### 2.3 量化选股（三档 LightGBM 模型）

**定位**：全市场选股，每个 A 股开市日 **09:25–09:45** 与 **14:45** 各跑一轮。**结果不自动写自选池**——用户点「＋加自选」才写，避免模型选错污染做T主链路。

**选股逻辑（从全市场到名单）**

1. **股票池**：全市场 → 剔 ST、剔北交所、上市 ≥120 天 → 按近 20 日成交额取前 800 只（`max_stocks: 800`）。
2. **候选池可切换**：勾选自定义板块后，候选池换成板块成分（**进池过滤，不是选完再筛**——阈值是按当日截面分位取的，先在全市场算阈值再筛板块会变成"全市场前 10% 里恰好属于该板块的那些"，板块一变小命中数就趋近 0）。
3. **特征面板**：5 年历史，`min_bars=60`，**26 个特征列**。
4. **模型打分**：按每只票自己的**流通市值**分发到对应档位的模型（不是先定模型再打全市场）。
5. **阈值出池**：`threshold_mode = percentile`，取**当日横截面 90 分位**作为阈值；`top_n = 20`。

**三档划分**（`cap_buckets.ranges`，单位元）：

| 档位 | 流通市值区间 |
|---|---|
| 20–150 亿 | `[2e9, 1.5e10)` |
| 150–500 亿 | `[1.5e10, 5e10)` |
| 500 亿+ | `[5e10, ∞)` |

**为什么分档**：不同市值段的定价机制不同（小盘看资金与情绪、大盘看基本面与流动性），混在一起训练会让模型学到"市值本身"而不是"这只票好不好"。分档后每档独立训练、独立评估，选股时按票的市值自动选模型。

**标签定义（面试必考，且这里最容易讲错版本）**

当前口径是 `label_mode = "band"`（用户 2026-09-17 定的新口径），**不是**早期那版"3 日涨幅 >7%"：

| | 条件 | 含义 |
|---|---|---|
| **正样本** | `未来3日最高价 / 当日收盘 > 1.08` **且** `未来3日最低价 / 当日收盘 > 0.96` | 涨得上去**且**回撤不深 |
| **负样本** | `未来3日最高价 / 当日收盘 < 1.05` **且** `未来3日最低价 / 当日收盘 < 0.95` | 涨不动**且**跌破 |
| 其余 | `LABEL_DROP = -1`，**剔除** | 模糊样本不参与训练 |
| 买入价 | **当日收盘价**（尾盘买入） | 与"14:45 尾盘窗口"一致 |

- **为什么正样本要加"且最低价 > 0.96"**：只要求涨幅会选出"先砸 8% 再拉 9%"的票——那种票拿不住。加上回撤约束后，正样本是"**买入后不难受**"的票。
- **为什么负样本也要两个条件**：只要求"跌"会把"横盘没动"也算成负样本，而横盘不是"该躲"，只是"没机会"。
- `horizon_days = 3`；未来最高价用反向 rolling 求（`series[::-1].rolling(3).max()[::-1]`），未来收盘用 `shift(-3)`；尾部 3 天无完整未来窗口的一律剔除。
- 旧口径 `excess`（保留可切换）：正 = 未来 3 日**盘中最高超额收益**（减当日全市场等权）> `positive_intraday_pct=7.0`；负 = 未达标且 3 日后收盘超额 < `negative_close_pct=-2.0`。**`config.yaml` 里那几个 `positive_intraday_pct / negative_close_pct / use_excess` 属于这个旧口径**，讲的时候别把它们挂到 band 上。

**模型**：`LGBMClassifier`（`objective=binary`、`metric=auc`、`boosting_type=gbdt`、`num_leaves=31`、`learning_rate=0.05`、`n_estimators=400`、`min_child_samples=50`、`feature_fraction=0.8`、`bagging_fraction=0.8`、`bagging_freq=1`、`lambda_l2=1.0`、`n_jobs=4`、`seed=20260917`）。
切分：`test_ratio = 0.2`，**按时间切分（禁止随机切分）**，切点按**交易日数量**算。

**实测指标（三档模型的真实 meta.json，不是 mock）**

| 档位 | 训练区间 | 训练行数 | 测试行数 | 正样本率 | AUC | **日内 AUC 均值** | **RankIC** |
|---|---|---:|---:|---:|---:|---:|---:|
| 20–150 亿 | 2021-09-22~2025-09-11 | 28,526 | 3,908 | 0.4166 | 0.6383 | **0.7008** | **+0.1828** |
| 150–500 亿 | 同上 | 17,538 | 9,216 | 0.4056 | 0.6250 | 0.6818 | +0.1172 |
| 500 亿+ | 2021-09-22~2025-09-12 | 10,890 | 10,705 | 0.3369 | 0.5957 | 0.6480 | +0.0999 |

> **面试怎么讲这三个数**：AUC 0.60~0.64 在日频股票预测里是**正常水平**（不是 0.9 那种过拟合数字）；更该看的是 **RankIC +0.10~+0.18**，因为选股本质是**排序问题**而不是分类问题；**日内 AUC 均值**（0.65~0.70）高于整体 AUC，说明模型在**同一天内部**区分度更好——这正是选股需要的。
> 同时要主动说：**RankIC 从 0.18 递减到 0.10**，市值越大越难预测（大盘股定价更有效），这符合直觉，也说明分档是必要的。
> 特征重要性：三档的 top1 都是 `box_breakout`（箱体突破）；`market_broken_rate` 的 gain 在三档里都是 **0.0**（空转特征，该清理）。

**26 个特征（5 大类，顺序即训练列顺序）**

| 类别 | 数量 | 特征 |
|---|---:|---|
| 板块资金流 | 4 | `sector_flow` / `sector_flow_avg` / `sector_pct_rank` / `sector_limitup_count` |
| 个股资金流 | 4 | `stock_main_flow`（主力净额/流通市值）/ `stock_elg_flow`（超大单净额/流通市值）/ `stock_flow_strength`（主力净额/成交额）/ `stock_flow_avg` |
| 技术面 | 7 | `vwap_deviation` / `macd_dif` / `macd_hist` / `boll_pct_b` / `boll_bandwidth` / `box_position` / `box_breakout` |
| 情绪面 | 4 | `market_limit_up` / `market_limit_down` / `market_broken_rate` / `sentiment_ma` |
| **交叉项** | 7 | `cross_sector_stock_flow` / `cross_sector_flow_strength` / `cross_sentiment_vwap` / `cross_sentiment_macd` / `cross_sentiment_box` / `cross_flow_boll` / `cross_box_flow` |

- **7 个交叉项是刻意的**：单看"板块有资金"或"个股有资金"都不够，真正要抓的是"**板块有资金 且 个股是承接方**"——这种非线性交互靠规则很难写，交给树模型学。
- 所有资金流类特征**都除以流通市值或成交额**（不除以市值就会变成"永远选大票"）。
- `build_factor_matrix` 返回 **32 列 = 6 个透传列**（`date/code/close/high/low/circ_mv`）**+ 26 个特征**；`circ_mv` **不是特征**，只用于过滤与分档。
- 另外还有一套**不用于这 3 档模型**的因子库 `factor_library_v2.py`：**35 个因子 / 7 大类**（价值 6 / 成长 5 / 质量 6 / 动量 5 / 波动 4 / 流动性 5 / 规模 4），服务于多因子筛选与单票回测那条链路。**被问到要分清这两套，别混。**

**预处理口径**
- `method = percentile`（默认）：**按日截面名次映射到 `[-1,1]`** —— `ranks = groupby(date).rank(pct=True)` → `(ranks - 0.5) * 2`。
- **缩尾也是按日截面**：`winsorize = [0.01, 0.99]`，逐日用当日分位裁剪。
- 备选 `zscore`：当日 `(x-mean)/std` 后裁 `±clip_z=5.0`。**两种都只依赖当日截面**，所以都不构成未来函数。
- **缺失值一律留 NaN，绝不填 0**——填 0 会让树模型把"没有资金流数据"当成"资金流为零"，那是两个完全不同的判断。LightGBM 原生吃 NaN。
- `dtype = float32`。
- ⚠️ **训练与推理必须复用同一份口径**：统一走 `data_engine.preprocess_kwargs(config)` 翻译配置。两处各写一遍就会出现"训练用 percentile、打分用 zscore"这种**静默错配**——分数照样出得来，只是全错。
- 顺序硬约束：**先算因子 → 再预处理（只作用于特征列）→ 最后才算标签**（用真实的 close/high/low）。早期版本在 `build_panel` 里就把整表 Z-score 了，`close` 被标准化后再算未来收益 → 标签全是噪声、正样本率 0。

**周度重训（不是"训完就上线"）**

```
周六 20:00（非交易日，作业内再判一次交易日挡住调休）
  → 重训三档 → 逐档回归对比（AUC / RankIC）
  → 过闸门（gate）才原子替换 → 失败自动回滚成完整旧套
  → 报告落 moss_selector/data/retrain_report_latest.json
```

为什么替换路径要写得这么细：服务读模型是按**公开文件名 glob 取最新**。替换过程中若出现"新 joblib 已就位、特征列表还是旧的"这种半套状态，模型照样能加载但**分数全错**。所以"失败要回滚成完整旧套"是显式断言，不靠人眼检查目录。

**自定义板块**：既是**选股范围**也是**归类标签**。两种类型：
- `manual`：手工维护成分股；
- `dynamic`：服务端按规则实时求值（`min_circ_mv` / `max_circ_mv` / `industries` / `exclude_st`）。

**输出字段（`QuantSelectionRun`）**：`trade_date` / `window(open|close|manual)` / `threshold` / `scored` / `selected` / `items[]`（`code, name, score, rank, cap_bucket, circ_mv, sectors[], factors{}, added`）/ `gaps` / `model_detail` / `data_stale`。
展开某一行还能看到**该票的关键因子值**（已做当日截面名次映射到 `[-1,1]`，越接近 1 越靠前）——这是"可解释性"的落地。

**亮点**
- **可解释**：每一行能展开看因子值，能说清"为什么是它"。
- **不越权**：结果只进模块，加自选要人手点。
- **数据滞后可见**：见 2.8。
- **重训有闸门**：`INTERVIEW_STRATEGY.md` 里"如何避免过拟合"的工程答案。

**已知限制（这一节直接决定面试官觉得你"懂不懂行"）**
- **阈值是相对分位**：全市场普跌时照样选出 20 只（"矮子里拔将军"），必须配合情绪周期一起看。实测某日阈值 **0.3569**、打分池 197 只、选出 20 只。
- **回测是样本内的**：官方那份"近一年"回测区间（2025-09-16~2026-09-15）几乎完全落在模型的**测试区间**内 —— 年化/夏普要读作"这个模型在它自己刚训完的那一年上表现如何"，**不能当作样本外业绩**。代码注释里写明了这一点，我会主动讲。
- **`min_listed_days: 120` 未生效**：配置里有这一项，但**全仓库没有任何读取方**——也就是说"上市不足 120 天的新股"实际没有被过滤掉。这是配置与实现的脱节，被问到直接承认。
- **20 亿以下/市值缺失的票会落到兜底档**：`cap_bucket()` 对 `<20亿` 或缺失返回 `""`，而三档目录里没有 `""` 键 → 实际落到 `next(iter(models.values()))`（mtime 最新的那一档）。因为打分阶段不做 20 亿门槛，这个分支确实可能走到。
- 训练用 5 年数据，A 股风格切换会让老样本权重偏高；目前靠分档 + 周度重训缓解，**没做样本加权衰减、没做 walk-forward**。
- 因子计算目前是**逐票 Python 循环**（MACD/布林/箱体都是 `groupby(code)` 里跑），没用向量化——这是下一步的优化点。
- `models/` 目录当前只有带时间戳的 3 份模型，**没有公开名文件**；`retrain_report_latest.json` 那次是 `dry_run: true`（`replaced: false`），所以"原子替换 + 回滚"这条路径**有单测但没有真实生产运行记录**。

### 2.4 竞价选股（11 维打分 + 六式互斥分类器）

**定位**：每日 9:25 集合竞价结束后，从**昨日涨停股**里挑出"今天可以接力"的票，9:27 前出池。

**选股逻辑（六步）**

1. **候选池**：昨日涨停股（权威来源 `limit_ladder()`，实测 47–58 行，全部 `limit_status='sealed'`）。
2. **股票池硬过滤**：非 ST、流通市值 `(30 亿, 110 亿)`、剔除无涨跌幅限制的新股。开盘涨幅 <2% 剔除、主板 >6% 剔除（创业板不做上限——语料里 12% 与 2% 自相矛盾，取了"不硬砍、只在打分里降权"这个更保守的解法）。
3. **竞价特征**：09:15–09:25 逐秒序列（必须按窗口切片——该序列在 eltdx 里覆盖到 14:59，不切会把下午的成交当竞价数据）、承接强度、开盘涨幅、量比、竞价额、未匹配量方向、形态分类。
4. **11 维打分** → 总分 100。
5. **硬性否决**（只放有明确语料出处的规则）。
6. **六式裁定**（互斥，不参与加权）。

**打分逻辑（分层）** —— 11 维，合计 **100**：

| 维度 | 权重 | 衡量什么 |
|---|---:|---|
| `auction_strength` 竞价量能 | **19** | 量比 / 竞价额 / 未匹配量 |
| `price_position` 开盘位置 | 14 | 开盘涨幅的区间口径（越高越好但有上限） |
| `takeover` 承接强度 | 12 | 9:20 后的价格轨迹与未匹配方向 |
| `theme_heat` 题材热度 | 12 | 题材涨停家数 / 连板高度 / 封单 |
| `sentiment` 超短情绪 | 12 | 复用 `market_cycle` 的阶段与温度 |
| `ladder` 梯队位置 | 10 | 连板身位（板块地位） |
| `seal_flow_ratio` 封流比 | 6 | 封单 / 流通市值 |
| `previous_day` 昨日质量 | 5 | 昨日封单 / 成交额 |
| `capital_fit` 盘口适配 | 4 | 流通盘与竞价额的匹配度 |
| `turnover` 换手率 | 3 | — |
| `theme_leader` 题材龙头 | 3 | — |

**总分怎么算（这段最容易被追问，务必背熟）**

```
对每个维度 i：
    value_i = scorer_i(feature)            # 0~1，取不到数据 → None
    if value_i is None:  skip（不补 0！）
    else: weighted += value_i * w_i ;  available_weight += w_i

raw      = weighted / available_weight * 100
coverage = available_weight / total_weight
total    = raw * min(1, coverage / 0.55)      # MIN_WEIGHT_COVERAGE = 0.55
```

两个刻意的设计：
1. **缺席维度从分母剔除，不补 0**——补 0 是"最差"而不是"未知"，会系统性压分数据缺失的票。
2. **但只按已得权重归一化会奖励缺数据**：实测只有 `open_gap_pct` 一个维度可用时它满分 → 总分算出 **100 分**，比数据齐全的好票还高。所以再加一层**覆盖率惩罚**：可用权重占比 <55% 时按比例封顶。

**决策分层（L4）**：

| 条件 | 决策 |
|---|---|
| 有任一否决 | `reject` |
| `total ≥ 60`（`min_total_score`） | `buy` 可参与 |
| `60 - 12 ≤ total < 60` | `watch` 观察（**不进推荐池**） |
| 否则 | `reject` |

**硬性否决（`check_veto`，只放有出处的规则）**：ST / 无涨跌幅限制 / 市值越界 / 开盘涨幅 <2% / 主板开盘涨幅 >6% / 竞价量比 >10（语料：往往见顶出货）/ 强转弱（昨日涨停今日低开）/ 形态为「高开回落」/ **环境否决**（炸板率 >60% 且涨停 <15 只）/ **情绪周期退潮期或冰点**。

**六式分类器（这是整个项目最能讲的设计之一）**

六个战法**互斥**，由**择时（情绪周期阶段）**决定用哪一套：

| 模式 | 所属 | 有效择时 | 标的条件 | 买点 |
|---|---|---|---|---|
| 追击式 | 降龙 | 启动/主升/发酵/加速 | **当前市场最高板** | 次日非爆量接力、下午强力封板 |
| 破冰式 | 降龙 | 冰点/绝对冰点/混沌 | 冰点上**逆势拉板的最高板** | 冰点范畴午后硬顶 |
| 龙回式 | 降龙 | 高位震荡/主升/发酵 | 大龙（≥3 板或最高板） | **回踩低吸**（开盘 −2%~+3%），成交额 ≤13 亿 |
| 无极式 | 反核 | 冰点/启动/发酵/主升/混沌 | **连板断板票** | 次日反包上板（打板） |
| 出水式 | 反核 | 冰点/启动/发酵 | 断板票或人气辨识度品种 | 水下/小红盘拉起，日内了结 |
| 趋龙式 | 趋龙 | 主升/发酵/高位震荡 | **主线总龙/主线龙** | 趋势段跟随 |

**为什么不能加权求和（面试必答）**：同一个冰点节点上，「破冰式」是买点，而「追击式」**恰恰是该避开的时段**（追高在冰点接力会一路 A 杀）。把两个互斥时段的招式加权求和，数学上就是把"该做"和"不该做"平均成一个没有意义的中间值。所以输出是**单一模式 + 该模式内部的机会分（0~100）+ 六式的逐条判定明细**（为什么命中/为什么否决，前端可复盘）。

**两个容易踩的工程细节**
- `eligible=False` 必须**一定有原因**：曾经出现"6 项检查过 5 项、生态那项没过但没写 blocker"，结果不但给不出理由，还因此**输给分更低的模式**（出水式 66.7 压过追击式 83.3）。现在 `finalize()` 统一从失败的 blocking check 兜底生成原因。
- 共振型判据的单项**不能当否决**：原文对冰点四大指标的要求是"多方共振、满足越多越准"，不是"四项都必须满足"。把单项当否决会把"一般冰点"误判成"没到冰点"（实测：跌停 8 家 <10 时四项只过 3 项，破冰式被判不成立）。现在单项 `blocking=False`，过半即成立。

**生态与压力位（用户口径，最容易被问倒的地方）**

- **生态**：把**最近 10 个交易日每天的"当日最高连板"**画成序列，找出波峰：
  - 生态档位取**最高波峰**：`≥8 板 强生态 / ==7 正常 / ≤6 弱生态`
  - **压力位取最后一个波峰**（不是最高波峰）
- **为什么不能只看当天的最高连板**：那是**一个点**，而生态要的是一段曲线的形态。同样"今天最高 5 板"：前 10 天最高也就 5 板 vs 前 10 天到过 8 板后掉到 5 板，操作含义完全相反。
- **波峰的识别规则**（`find_peaks`）：
  - 平台取中：连续相等的段压缩成一个候选，只在**最后一天**记一个波峰（平台的意义是"在这个高度停留"）；
  - 右端（最新一天）：只有当最后一段**是上升的**才算"正在形成的新极值"——这正是用户例子"今天涨停到 6 板"的情形；
  - `[3,5,8,6,4]` 的波峰**只有 8**，6 是下行途中的点不是极值（曾经想把它当波峰，是错的）。
- **规则 1（连板数修正）**：从第一个涨停开始、连续缩量一字板（每天换手 <1.5%）的，连板数**从首次换手 >1.5% 那天算第 1 板**。实现上只剔**开头那一串**——一旦换手超过 1.5%（真实换手发生），后面的板照常累加，中途再出现低换手一字板不回溯剔除。
  为什么：连续缩量一字板**买不到量**，那些板没形成真实筹码交换，算进高度会虚增生态与压力位。
- **规则 2（大/小周期与金叉）**：
  - **大周期** = 窗口内最高连板数（记其日期）；
  - **小周期** = 当 `v[t] ≤ v[t-1]` 时记录一个点，**值取昨天的 `v[t-1]`**（小周期高度描述的是"这一波走到多高"，那是转折前的高点）；
  - **金叉** = 最近两次小周期高度相等 → 门槛 = `大周期 - 3`（≥8→5、7→4、6→3），大周期 <6 时**没有规则就不猜**（返回 None）；
  - **上升期** = 最新一次高度变化 > 0；
  - **新龙头** = 金叉成立（且过门槛）+ 上升期 + 是当日最高板股；**有梯队** = 同题材（**真题材名**）低位连板股 ≥3。

**输出字段**：`market_cycle{stage, temperature, limit_up_count, broken_rate, max_streak, streak2plus, ecology, ecology_peak, resistance, resistance_distance, resistance_level, resistance_meaning, leader_tags{is_new_leader, has_tier, tier_count}}` + `picked[]`（每只带 `mode / mode_score / mode_fits / dim_scores / dim_notes / buy_reason / veto_reasons`）。

**已知限制（必须主动讲，这是加分项）**
- **候选池与招式不匹配**：无极式/出水式做的是**断板票**，而候选池是**昨日涨停股**，所以这两式在实盘竞价链路里**必然判否**。要么扩展候选池来源，要么如实说明——目前是后者，写在 `docs/AUCTION_SELECT.md` 的"模式覆盖与数据缺口"。
- **题材榜的伪题材**：通达信自己生成的**状态标签**（"最近情绪指数 / 昨日涨停 / 昨日首板 / 最近多板 / 最近闪拉"）不是题材概念。不排除的话，几乎所有昨日涨停股都会匹配到榜上第 1 名的"最近情绪指数"，于是每只票的题材热度都顶到 ~1.0，这个维度彻底失去区分度（实测踩到）。现在用 `pseudo_theme_patterns` 正则排除。

### 2.5 超短战法回测（六式的历史检验）

**定位**：把六个战法拿去跑历史，回答"这套打法到底有没有超额"。**回测调用的是实盘同一个分类器**（`modes.classify_mode`），只替换数据源——否则回测出来的是另一个策略，结论不能用来指导实盘。

**选股逻辑（信号生成）**
- 信号日 T 用 T 日收盘后的数据判定；**买入日 = T+1 开盘**（与实盘竞价一致）。
- 候选池两路：**涨停池**（T 日封板股）+ **断板池**（前一日连板 ≥2、当日未封板）——后者是给反核两式用的，实盘竞价链路里没有。
- 逐票跑 `classify_mode`，取出命中的模式。

**打分/统计层次（输出分四层）**

| 层 | 内容 |
|---|---|
| L1 逐笔 | 66 笔（30–200 亿口径）逐笔明细：信号日/买入日/买卖价/卖出原因/持仓天数/单笔收益 |
| L2 分模式 | 每个模式的笔数、胜率、平均单笔、中位数、盈亏比、盈利因子 |
| L3 对照 | **无条件对照**：当日全部涨停股、同样卖出规则、不做仓位裁剪（3090 笔） |
| L4 账户 | 20%/笔、最多 5 笔并发的真实资金曲线：总收益、最大回撤、年化波动、夏普、平均持仓数、暴露度 |

**交易规则（用户口径 + A 股制度）**
- 每笔 = 当时总权益 × 20%，最多 5 笔并发；同日超额按 `mode_score` 降序取，其余记 `skipped`。
- 日内跌破**买入价** 7% → 止损；收盘跌破 **5 日均线**（含当日）→ 清仓。
- **A 股 T+1**：买入当日不可卖（哪怕当天就破止损）→ 记 `breached_entry_day`，**次日开盘**卖。
- **一字涨停买不进** → `buy_blocked`，不建仓。
- **跌停卖不出** → 挂到下一个能成交的交易日开盘（一字跌停可能连挂几天）。

**实测结果（信号日 2026-06-26 ~ 2026-09-16，59 个交易日）**

| 口径 | 笔数 | 胜率 | 平均单笔 | 去掉最好一笔 | 盈亏比 |
|---|---:|---:|---:|---:|---:|
| 出水式 | 29 | 13.8% | −4.42% | −4.86% | 0.66 |
| 追击式 | 7 | 28.6% | −6.66% | −8.51% | 0.25 |
| 无极式 | 26 | 46.2% | **+3.10%** | +1.50% | 2.31 |
| 龙回式 | 4 | 50.0% | −4.56% | −7.33% | 0.24 |
| **全部命中** | 66 | 30.3% | −1.70% | −2.39% | 1.44 |
| **无条件对照**（全部涨停股） | 3090 | 30.7% | −1.67% | −1.71% | 1.39 |
| **账户口径** | 34 | 26.5% | −2.51% | — | 总收益 **−16.33%**，最大回撤 −23.3% |

**三条结论（这就是能讲出来的东西）**
1. **战法选择几乎没带来超额**：全部命中 −1.70%/笔 vs 无条件对照 −1.67%/笔。亏钱的主因是这套**买卖规则本身**（涨停次日开盘买入 + 7% 止损 + 破 5 日线），在这个区间里是负期望。
2. **只有无极式是正的，但它 26 笔在严格模式下全部不会出现**——历史没有逐笔委托数据，无极式的"盘口强势有气质"被降级成记录项（只扣分不否决）才让它成立的。**这个前提没被检验过**，所以那个正收益要打问号（严格模式整体 −3.75%/笔）。
3. **破冰式 0 信号是行情事实**：59 天里没有一天被判为冰点/绝对冰点（33 天是退潮期）。趋龙式因为**没有历史题材榜数据**直接标为"不可评估"，**没有拿 0 笔冒充胜率 0**。

**这份回测里最能体现方法论的三件事**
- **数据缺口的处理分两种，刻意不同**：降级白名单**只有**盘口承接分（无极式 5 条判据里它只占 1 条，剩 4 条仍硬约束）；趋龙式**故意不降级**——它的身份判据全依赖题材榜，降级后会退化成"主升期买任意涨停股"，那个胜率挂"趋龙式"的名字就是错的。
- **报告里单列"有 N 个信号在严格模式下根本不会出现"**，并给出严格模式的对照数字。
- **无未来函数**：每天的周期与生态只用截至该日的数据构建。为此把生态判定从 `build_snapshot()` 抽成纯函数 `snapshot_from_series()`，**实盘与回测共用同一段代码**，并有单测断言"多喂一天就会改变结论"。
- **成本与敏感性**：佣金万 2.5 双边、印花税千 0.5 卖出；敏感性表覆盖股票池 110/150/200 亿三档、滑点 0.2%/0.5%、止损基准（买入价 vs 信号日收盘）、均线 10 日、仓位规格、严格模式共 11 个变体。

**已知限制（主动说）**
- 买入价用日线开盘价，真实竞价成交价会有差异；一字涨停已剔除，但开盘价本身是理想化假设。
- 无极式/出水式的原文买点是"打板/低吸"，回测统一用"次日开盘价"——日内逐笔无历史，做不到判断当天是否封板。
- 样本量小：龙回式/追击式是个位数到十几笔，结论只能当"该区间内的记录"，不能当"这套战法的胜率"。

### 2.6 资金流监控

**定位**：回答"钱在往哪个板块去、板块里谁在被买"。三页签：板块 / 个股 / 拥挤度（按页签挂载，避免后台 60 秒轮询白跑）。

**选股逻辑**

**① 板块层趋势**：单点 = 板块当日净额 `net_amount`（**元**），历史一次取 **730 行日频**再截窗口。默认窗口 **10 个交易日**（接口 `window` 允许 5~30）；**趋势线不做平滑**（无 MA）——看的是原始资金进出。
板块历史取数走**三级口径**（按可靠性降级）：① Tushare 按板块代码 → ② 东财 akshare → ③ **本地聚合**（成分股流通市值前 60 只 × 个股资金流逐日求和，并注明"与东财口径不可逐一对应"）。

**② 个股层排行指标 = `近 N 日主力净额均值 / 流通市值`**
- 分子：Tushare `moneyflow.net_mf_amount`（万元→元）的 **N 日均值**；
- 分母：`daily_basic.circ_mv`（元）；
- **大单/超大单不参与排序**（只是随序列带出）——这点很容易讲错，别把 `buy_lg/buy_elg` 说成排序依据；
- 用比值而不是绝对额：**绝对值排行永远是大市值股票**，比值才让大小盘可比。实测榜首样例：近 10 日主力净额均值 3.27 亿 / 流通市值 79.7 亿 = **4.10%**；
- 缺 `circ_mv` → `net_to_mv = None` → 落入 fallback 组按净额均值排序，**并写进 `gaps`**（不猜）。

**③ "市值 > 30 亿的昨日涨停股"这一档**
- 阈值 `LIMIT_UP_MIN_CIRC_MV = 30e8`。注释给了理由：**30 亿以下的涨停多是几百万资金推动，会淹没真实信号**。
- 涨停判定是**仓库自算**（不是在线接口）：`daily × stk_limit` 内连接后 `high >= up_limit - 1e-6`；"昨日"取命中日期排序后的 `dates[-2]`；只查近 12 个自然日。
- 市值筛选用**仓库日频** `daily_basic.circ_mv`，且这一步发生在**腾讯盘中快照覆盖 `circ_mv` 之前**（口径要一致，不能一半用日频一半用实时）。
- 这一档内部按**涨停当天的连板数**降序排前 10 —— 也就是说它不只是"涨停 + 市值"，而是把**身位**也排进去了。
- 涨停原因列 `limitup_reason` 来自涨停池的"所属行业"，有连板数时拼成 `（N连板）`。**涨停日与原因池必须同源**，否则会出现"股票来自 A 日、原因来自 B 日"。

**④ 榜单拼接顺序**（同一只票只出现一次）：`昨日涨停 → 净流入前 N → 净流出前 N → 其他 → 自选`。

**打分逻辑**：本模块**不打总分**，是**排序 + 趋势可视化**。
> 面试注意：**不要硬说成打分模块**。它的输出是"排名"和"趋势"，编一个总分反而是错的（见第 3 节的范式 d）。

**输出**：板块趋势图 + 个股进出榜（带 `rank_group` 徽标）+ 自选/监控列表（持久化在 `dim_fund_flow_watch`）。

**图表设计（面试可以讲"为什么这么做"）**
三块**共用同一 x 轴、各自独立纵轴**：主图**资金流**（亿元，零轴分正负，占高 50%）、中图 **K线**（价格，30%）、下图 **成交量**（万手，20%）。
- 为什么必须拆轴：三者量纲差几个数量级（亿元 / 元 / 股），塞进同一根轴会互相压扁。
- 交互：滚轮以**光标为中心**缩放、拖拽平移、双击复位、Y 轴随可见窗口重算。
- **缺口不画假线**：`net` 为 null 的点不进线；只有 1 个点时画圆点而不是线段。

**数据与缓存**
| 内容 | 来源 |
|---|---|
| 板块截面（主） | Tushare `moneyflow_ind_dc` |
| 板块盘中覆盖 | 同花顺"即时"（仅在交易/午休/竞价时段叠加，打 `net_realtime=True`） |
| 个股日频 + OHLCV | 本地仓库 `moneyflow` + `daily_basic` + `daily`（**零网络**） |
| 盘中市值/涨幅 | 腾讯批量快照（GBK，亿元×1e8） |
| 涨停池/原因 | akshare 涨停池（**子进程隔离**） |
| 股票名称 | 本地名录（不发网络） |

- Parquet 落盘 `data/cache/fundflow/`：面板按窗口分文件（`stock_frame_{N}d.parquet` + `.caps.parquet`），**增量补数**（只取盘上最大日期之后的自然日）、面板缓存 30 天过期、板块截面按 mtime **5 天**过期。
- 实测文件：`stock_frame_10d.parquet` **52,070 行 / 5,217 只票 / 10 个交易日 / 3.58 MB**。
- TTL：板块历史 30min / 实时 60s / 个股 300s / 成分 6h / 涨停 60s；服务层快照 60s。
- 实测耗时：昨日涨停自算从**3.46s → 0.2s**（窗口缩到 12 自然日）；板块截面在线一次拉 1030 个板块**50 秒量级**，冷启动首屏 **52.94s** → 磁盘优先后"降到秒级"；腾讯快照带上百只票 **0.1~0.3s**。

**已知限制**：资金流是**滞后指标**（当日盘中数据收盘后才定型），不能用它做日内择时；`rank_group` 的文案硬编码成"净流入前10/净流出前10"而实际条数由 `top` 决定（**文案与条数不一致**，是个待修的小 bug）。

### 2.7 板块拥挤度

**定位**：判断某个概念板块是不是"人太多了"——拥挤度越高，踩踏风险越大。

**指标逻辑（完整公式，面试会追问"水位是什么"）**

```
板块每日成交额   = 板块指数日线的 vol × avg_price
全市场每日成交额 = 全部 A 股当日成交额之和（quant_daily.amount，只统计 >0）
原始拥挤度 raw   = 板块成交额 / 全市场成交额
平滑拥挤度 ma5   = raw 的 MA5（min_periods=1）
拥挤度水位 water = ma5 / 该板块自身近 6 年 ma5 的最大值      ∈ [0,1]
```

- **水位不是分位数**，而是"**当前 / 自身历史最高**"的比值。分母是**该板块自己**，不是全市场、也不是跨板块排序。
- 回看 **6 年**（按**日历日** `-365×6` 推算，不是交易日数）；有效样本门槛 **`min_bars = 750`**（≈3 个交易年），不足则 `water_level = None`。
- **未来函数防护**：第 i 天只用第 i 天为止的数据（用 `expanding` 而不是 `max()`）。
- 出口把 `nan` 显式转回 `None`（否则 JSON 里出 `nan`，前端"数据不足"的判断会失效）。

**为什么不直接用成分股聚合**：成分股接口只给**当前快照**，用它回算 6 年历史会有**前视偏差**（今天的成分股不等于当年的成分股）。所以板块成交额改用**板块指数日线** `vol × avg_price`。

**告警分级**：`alert_threshold = 0.8`（橙）、`high_alert_threshold = 0.9`（红）；`water_level IS NULL` **不参与告警**——注释原话：**"不知道和不拥挤是两件事"**。

**存储**（主库 `data/moss_finagent.db`）
- `sector_crowding_daily`：`trade_date / sector_code / sector_amount / market_amount / raw_crowding / ma5_crowding / water_level`，`UNIQUE(trade_date, sector_code)` + 两个索引。实测 **2,170,638 行**，2020-09-16 ~ 2026-09-15，2,510 个板块。
- `sector_meta`：板块元数据 + `is_concept` + **`last_update_date`（增量刷新的水位线）**。
- `sector_member` / `sector_crowding_watch`。
- 短连接 WAL（`timeout=30`、`busy_timeout=30s`、`synchronous=NORMAL`）——理由是**后台线程刷新时 SQLite 连接不能跨线程共享**。

**工程点**
- 提交方式：逐板块提交 **217 万行要 656 秒** → **整批一次提交 80 秒**（**8.2×**）。
- 本地重算（不联网、改参数后用）：**82 秒重算 217 万行**。
- 刷新架构：`POST /refresh_all` 立即返回 `task_id` + 后台线程，前端轮询状态——**不全量同步等待**（项目里踩过 300 秒反代超时）。
- 并发 8 线程（依据：接口限流 500 次/分、单次 0.2s → 8 线程 ≈ 40 次/秒）。

**实测现状（很能说明"阈值要定对"）**
| `min_bars` | 水位 ≥80% 的板块数 |
|---|---:|
| 60 | **218**（其中 ≥90% 有 101 个） |
| **750** | **26**（≥90% 有 6 个） |

`min_bars=60` 时绝大多数告警是"**历史太短所以永远是自己最高**"——一个纯粹的统计假象。提到 750 之后降到 26 个，才是真正值得看的。

**已知限制**：① 改参数后**库里仍留着旧水位**，不重算的话界面继续显示旧口径的误告警；② `is_concept` 只在刷新时写入，改判定规则后必须重跑重分类；③ **不做定时自动刷新、不做消息推送**（要手动触发）。

### 2.8 数据层与调度（面试里最容易被低估、但最能体现工程能力的一块）

#### 2.8.1 数据分层

```
Tushare/akshare/QMT/eltdx
   ↓ 按交易日分区的 Parquet 缓存（可断点续传、增量）
   ↓ scripts/quant_warehouse.py ingest（幂等 UPSERT，建索引）
SQLite 仓库 data/quant/warehouse.db（15.3 GB）
   daily 15,384,650 行 · daily_basic 15,384,481 行
   stk_limit 14,426,310 行 · moneyflow 14,023,030 行
   覆盖 20060104 ~ 最新交易日
   ↓ load_dataset(dataset, *, start, end, codes, columns, root, universe, prefer)
统一取数入口 → (DataFrame, "db:sqlite.quant_daily")
```

**为什么必须把"来源"一起返回**：否则"这次到底查的库还是文件"会变成查不出来的问题——回测复现性直接依赖它。

**`covers()` 为什么必须看最大日期而不是"有没有行"**：入库是按分区键**顺序**进行的，所以库里任何时候都是缓存的一个**前缀**。只用"区间内有没有行"判断，一个灌到一半的数据集会被判为"走库"，于是回测**静默丢掉后半段数据**——净值曲线照样画得出来，只是少了一半样本。这比直接报错危险得多。

**取数性能优化（全部有实测，这是"数据层做过优化"的硬证据）**

| 手段 | 实测 |
|---|---|
| 三种取数方式对比 | Tushare API **66~248 ms** / CSV.gz **10~40 ms** / 数据库 **5~20 ms**（单截面） |
| **列裁剪** | 250 日区间：全列 2908ms → 只取 3 列 **1050ms（快 2.2×）**；"取数耗时几乎全在搬多少列上" |
| **股票池过滤下推到 SQL** | 250 日 + 筛 50 只票：CSV 2313ms → 库 **10.3ms（快 ~225×）**，靠 `(code, trade_date)` 复合索引 |
| **绕过 SQLAlchemy** | 经 `Result` 返回逐行 `Row` 再 `from_records`：5000 行多 ~4ms、125 万行多 **~2.5s**。直接取 `driver_connection` 的 DBAPI 游标 |
| SQLite PRAGMA 调优 | `cache_size=-200000`(200MB) + `mmap_size=1GB` + `temp_store=MEMORY` + WAL + `synchronous=NORMAL` → 宽表扫描**快 ~12%**，且 WAL 允许入库时并发查询 |
| 行数统计改 `MAX(rowid)` | 14.28GB / 8550 万行：`COUNT(*)` 九表合计 **40s+**（第二次 42s→46s，还冲掉页缓存）→ `MAX(rowid)` 全部 **0.00s**，数值完全相等 |
| 面板装配 | 103.9s → **27.3s**（再装配命中缓存 **19.5s**）；端到端 **115.4s → 47.8s（2.4×）**，结果逐位不变 |
| 每个数据集分区只读一次 | 原实现 48 字段 × 171 分区 ≈ **8200 次 gzip 解压 ≈ 92s** → 8 数据集 × 171 ≈ 1370 次 |
| `order=False` | 面板类调用随后要 pivot，顺序无意义，大区间上排序是纯开销 |
| `columns_of()` 先裁剪列 | 请求不存在的列会直接 SQL 报错 → **整条链路退化成 CSV 回退**（"很难发现的性能事故"） |

> **一句可以直接背的总结**：*"入库本身不会让取数变快，快在能把过滤下推到 SQL。"* 这句话解释了为什么值得维护一个 15GB 的本地仓库。

#### 2.8.2 数据新鲜度（这是本会话最有价值的一条）

**事故**：2026-09-18 09:10 手动跑「量化选股」，选出来的日期是 **20260915**。
**根因**：选股取日期只有一行 `latest = str(processed["date"].max())`，即"数据里最新的一天"。而本地仓库里最新就是 0915——**0916/0917 没有任何作业去同步**。选股链路没有错，它忠实地用了"手上最新的一天"。
**为什么危险**：分数、阈值、排名、模型档位**全都算得出来**，界面上看不出任何异常，但它描述的是两天前的市场。

**修法（两层）**
1. **让它可见**：新增 `src/quant/freshness.py` ——
   - `latest_complete_trade_date()`：最近一个**已收盘**交易日。**盘中不算今天**（09:25 时最新可用是昨天），过了 **16:30**（EOD 发布线）才把今天算进来。
   - `freshness(data_date)`：返回 `{expected_trade_date, data_stale, note, checked}`；注意 `checked=False` 表示**没判**，调用方不能读成"确认新鲜"。
   - 接口**读时计算**（不落库）→ 老记录也能被正确重判；前端出「数据滞后」横幅。
2. **从根上补**：新增 `quant_data_sync` 定时作业，工作日 **16:40** 先问仓库当前最新日期、**只补缺的那几天**、下完**必须 ingest**（"下了但没入库"是这一步最容易漏的）。

#### 2.8.3 盘前预热的缓存（120–159s → 0.02s）

**问题**：预热 4 个远端接口，`theme_strength_rank` 一项实测 **139s**。而且 `count=40` **救不了它**——该参数只裁剪返回条数，服务端照样算完整个题材榜。
**为什么反复付**：`scheduler._PREHEAT` 是**进程内**缓存，只按交易日做键 → 每次服务重启、`run_selection` 直接调 `fetch_preheat()`（绕开调度缓存）、手动 force，都要重付一遍。

**做法**（`src/auction_select/preheat_cache.py`，落 `data/cache/auction_select/preheat_<日期>.json`）：
- **键是交易日**（预热内容是"那一天"的函数，跨日一律不命中）；
- **按分项记 ok/失败**：09:15 那次 `limit_ladder`/`theme_strength_rank` 会被 eltdx 以 `ShortlineIndicatorsNotReadyError` 拒绝（"09:25 竞价完成前短线指标未就绪"），那两项**不写进缓存**，下次**只补这两项**而不是整轮 230s；
- **全命中就不碰网络**：连 `session.ensure()` 都不调用 → 数据源挂了也能出池；
- **空结果不入缓存**（写进去就永远不会再补，维度永久空着）；**过期/坏文件/版本不符一律丢弃**。

**实测**：

| | 耗时 |
|---|---|
| 冷启动（真的拉一次） | **120.1s** |
| 暖缓存 | **0.02s**（复用全部 5 项） |
| 服务重启后第一次调预热接口 | `seconds: 0.13`（改前是 `159.45`） |

#### 2.8.4 调度

- **单一事实源**：所有 cron 只允许在 `src/scheduler/registry.py` 声明，禁止散落在代码里的 sleep 循环（Celery Beat 与管理 API 都从这张表生成视图）。
- **窗口判定 + 当日去重**：`quant_select` 的 cron 是 `*/5 9 * * 1-5`（分钟粒度粗一点更抗"服务当时没起来"），真正的 09:25–09:45 边界在**作业内**判断；窗口有 20 分钟、cron 每 5 分钟醒一次，不做去重会连跑 4 轮。
- **判重条件只能是 `status == "done"`**：曾经写成 `record.get("picked") is not None`，这对 `picked = 0` 也成立 → "当天出池为 0 只"会被判成已跑过，之后怎么点都跳过。**"当天是否已成功跑过"是运行记录的问题，与选出几只无关。**

#### 2.8.5 连接器路由与降级（面试爱问的"多源容灾"）

**三级短路（从快到慢）**：`[1]` 进程内 TTL 缓存 → `[2]` 本地持久化 DB（只对**慢变量** + 带过期判定）→ `[3]` 真实 connector 链。任一 connector 成功后**同时回填 DB 和 TTL**。

**路由链（主→备）**：QMT(xtquant) → 本地行情 CSV（仅在配置了目录时）→ akshare → 腾讯日K → Tushare（日线链最后一道在线兜底）→ … → 模拟源（业界惯例：**真实源失败后不回退模拟**，宁报缺口也不用假数据冒充）。

**TTL 分级**（不是一刀切）：月频宏观 24h / 估值与行业 PE 12h / 两融与北向 4h / 实时成交额与换手率 5min / FedWatch 1h / 日线 4h；未匹配的前缀不缓存。

**DB 命中判定不是"有没有"，而是"够不够新"**：`DataFreshnessEvaluator.confidence >= 0.4` 才算可用，否则"DB 里有但过期 → 穿透网络刷新"。

**故障转移的判据是"够不够新"，不是"成功/失败"**（这是最值得讲的一条）：
- 带日期区间的查询**不走 DB 短路**（区间要的是当天形成中的 bar），但仍查一次 DB，把 `db_newest` 当作**新鲜度下限**；
- 链上某源返回成功但最新日期早于下限 → 视为"该源过旧"，继续试下一个源；
- **过旧不记失败冷却**——"这个源本身是好的，只是这份数据旧了"，记冷却会把它连"最新可得的源"都当不成；
- 全部源都比下限旧 → 返回其中**最新的那一份**（而不是报错）；
- **空结果也算"没拿到"**（实测某源被阻断时返回 `[]` 而不是异常），否则会把后面的源挡掉。

**失败冷却**：key = `连接器名:指标`，失败后冷却 **300 秒**；成功即清除；**全部匹配源都在冷却中时返回空列表而不是抛异常**，交给上层的存储兜底。

**防击穿**：per-key `asyncio.Lock` + 持锁二次检查 TTL，保证同一指标并发只发一次网络请求。

**实测容灾**（这是能拿出手的证据）：QMT 在线命中 **7~9ms**；QMT 掉线 **4/4 次**自动切腾讯（90~480ms）；熔断生效后 `should_attempt(qmt)=False`（冷却剩 299s），后续尝试日志里完全没有 QMT；静默等 35s（探针周期 30s）后**自动恢复**到 QMT（10.8ms）。QMT 快照中位 **0.2ms**（读本机终端内存），与在线源差 7~12 倍。

## 3. 打分逻辑总表（横向对比四种范式）

面试官常问"你系统里分数到底怎么来的"。一句话回答：**四种范式，各用在该用的地方**。

| 范式 | 用在哪 | 合成方式 | 缺数据怎么办 | 为什么这么选 |
|---|---|---|---|---|
| **a. 加权求和** | 做T（14 维）、竞价选股（11 维） | `Σ(维度分×权重) / 已得权重 × 100`，再乘覆盖率惩罚 | 从分母**剔除**（不补 0）+ 覆盖率 <55% 封顶 | 维度之间**近似可加**（都是在描述"这只票质量如何"） |
| **b. 互斥分类** | 六式 | 择时闸门 → 生态/标的/买点逐条判定 → 取拟合度最高的**单一**模式 | 拿不到的判据**显式声明**，由各模式自己决定是否降级 | 六式由**择时**决定，互斥；加权求和等于把"该做"和"不该做"平均 |
| **c. 机器学习** | 量化选股 | LightGBM 三档，按流通市值分发；阈值取**当日截面 90 分位** | 特征缺失交给模型自身处理 + 预处理 winsorize/clip | 26 个因子的非线性交互靠规则写不出来 |
| **d. 排序 / 分位** | 资金流、拥挤度 | 不做总分，直接排序或算历史分位 | 不参与排序 | 这两类问题的答案是"排名"和"相对位置"，编一个总分反而是错的 |

**再补一层"闸门"**：所有范式之上都有**一票否决**（ST/市值/涨跌停限制/情绪周期退潮冰点/环境否决）。分数只在通过闸门的池子里比大小。

## 4. 踩坑集（每条都能当独立小故事讲）

> 讲法统一：**现象 → 根因 → 修法 → 可迁移的教训**。

**坑 1｜静默用两天前的行情**
- 现象：09:10 手动量化选股，选出的日期是 20260915。
- 根因：取日期 = "数据里最新的一天"，而本地仓库最新就是 0915；**没有任何作业在同步仓库**。
- 修法：`freshness.py` 算"应该是哪一天"并在接口读时暴露 `data_stale`；新增 16:40 的 `quant_data_sync` 作业。
- 教训：**"算得出来"不等于"算得对"**。凡是结果依赖于"最新数据"的地方，都要能把"最新是哪一天"显式报出来。

**坑 2｜ST 过滤一直空转**
- 现象：`exclude_st: true`，但 notes 里永远写着"剔 ST 0"，看起来像"今天正好没有 ST 涨停"。
- 根因：ST 判定读的是 `limit_ladder()` 的 `name` 字段，而实测这 58 行**`name` 全是空串**；有名字的是另一张表 `daily_price_limits`（5574 行全有）。
- 修法：优先取涨跌停对照表的名字，并回填到候选池（前端显示的股票名之前也是空的）。
- 教训：**同一个字段名在两个接口里不一定都有值**；过滤条件是"静默失效"的最佳藏身处——它不会报错，只会让结果悄悄变多。

**坑 3｜覆盖率归一化奖励了缺数据**
- 现象：只有 `open_gap_pct` 一个维度可用时，它满分 → 总分 **100 分**，比数据齐全的好票还高。
- 根因：只按"已得分的权重"归一化。
- 修法：加覆盖率惩罚（可用权重 <55% 按比例封顶）。
- 教训：**缺失值的默认处理往往是隐含的激励**。剔除分母是对的，但要配一个"信息量不足就封顶"的惩罚。

**坑 4｜`eligible=False` 却给不出原因**
- 现象：追击式 6 项检查过 5 项、生态那项没过但没写 blocker → 不但没有理由，还**输给分更低的模式**（66.7 压过 83.3）。
- 修法：`finalize()` 统一从失败的 blocking check 兜底生成原因；前端靠 blockers 告诉用户"为什么不能用这套打法"。
- 教训：**"不成立"必须自带原因**，否则它会在排序里被当成一个低分而不是一个否决。

**坑 5｜共振判据被当成全部必要条件**
- 现象：跌停 8 家（<10）时四项冰点指标只过 3 项 → 破冰式被判不成立，错过机会。
- 根因：原文要求"多方共振、满足越多越准"，实现成了"四项都必须满足"。
- 修法：单项 `blocking=False`，过半即成立。
- 教训：**读需求要区分"必须"和"加分"**，这类词（共振/多数/倾向）在规则落地时最容易被写成 hard and。

**坑 6｜伪题材把题材维度打满**
- 现象：所有昨日涨停股的题材热度都 ~1.0，维度彻底失去区分度。
- 根因：通达信题材榜前列是"最近情绪指数/昨日涨停/最近多板"等**状态标签**，不是题材概念。
- 修法：`pseudo_theme_patterns` 正则排除。
- 教训：**数据源的"字段语义"要逐条验**，不能看到名字像就拿来用。

**坑 7｜"强制刷新"变成空操作**
- 现象：给预热加了磁盘缓存后，`get_preheat(force=True)` 只清了进程内缓存，`fetch_preheat` 仍然读到同一份磁盘缓存。
- 修法：`force` 一路传到 `fetch_preheat`。
- 教训：**引入第二层缓存时，要回头检查所有"绕过缓存"的入口是否还成立。**

**坑 8｜测试读到了真实缓存，断言全部反过来**
- 现象：加了磁盘缓存后，三个"接口全挂也要返回对象"的用例开始失败——因为它们从本机真实缓存里拿到了数据。
- 修法：`test_auction_select.py` 加 autouse fixture 把缓存目录隔离到 tmp。
- 教训：**任何写文件的缓存，测试里都必须显式指到 tmp**；否则测试会随机器状态漂移。

**坑 9｜并发只解决了"一轮内别串行"**
- 现象：4 个慢接口串行 230s+，并发后 = 最慢那项 ≈139s，但仍然每次都要付。
- 教训：**优化要分清"单轮成本"和"重复次数"**。并发降单轮，缓存降次数，两个维度都要看。

**坑 10｜`count=40` 不省服务端算力**
- 现象：以为缩小返回条数能加速。
- 根因：参数只裁剪返回条数，服务端照样算完整个题材榜（实测传 40 与不传耗时一致）。
- 教训：**优化前先确认成本发生在哪一侧**（客户端/网络/服务端），否则会做一堆无效参数调整。

**坑 11｜回测里买入当日就卖了**
- 现象：早期回测没考虑 A 股 **T+1**，买入当天跌破止损就"卖出"，收益虚高。
- 修法：买入当日不检查；当日触发只记 `breached_entry_day`，次日开盘卖。
- 教训：**制度约束（T+1、涨跌停、停牌）不是细节，是收益率的一部分。** 同理还有"一字涨停买不进""跌停卖不出要挂下一日"。

**坑 12｜未来函数**
- 现象：给回测算生态时，直接用最新序列 → 右端波峰规则看到了"未来一天"。
- 修法：把生态判定抽成纯函数 `snapshot_from_series()`，**实盘与回测共用**，回测逐日喂"截至该日"的序列；单测断言"多喂一天就会改变结论"。
- 教训：**回测和实盘必须是同一段代码**，否则回测的是另一个策略。拆纯函数不只是为了复用，是为了让"未来函数"无处藏身。

**坑 13｜数据源在开盘前拒绝提供短线指标**
- 现象：09:15 预热时 `limit_ladder` / `theme_strength_rank` 报 `ShortlineIndicatorsNotReadyError`（"09:25 竞价完成前短线指标未就绪"）。
- 影响：盘前预热**必然**缺这两项；而 09:25 主任务若重试一次 139s 就会击穿 09:27 的截止线。
- 处理：不自动重试（宁可先出池）；把缺项**只补缺的那几项**写进缓存，下一次调用补齐。
- 教训：**要知道自己依赖的数据源在什么时刻才有值**，并且为"拿不到"设计一条不崩的路径。

**坑 14｜Windows 控制台 GBK 让 `manage.py stop/start` 看起来像失败**
- 现象：命令**已经执行完**，最后一句 `print("✅ …")` 抛 `UnicodeEncodeError`，退出码非 0。
- 修法：`main()` 里把 stdout/stderr 重设为 UTF-8。
- 教训：**"命令成功但退出码非 0"是最容易被误判成故障的一类问题**；脚本的输出编码要显式处理。

**坑 15｜追加语义导致"加了自选但列表里没有"**
- 现象：从量化选股一键加了 20 只，左侧自选列表看不到 → 用户以为加错了地方。
- 根因：自选池是**追加**语义，那 20 只在 43 只里的第 24–43 位，正好在可视区之外；加完**没有任何定位反馈**。
- 修法：加成功后回调父级 → 展开侧栏 → 滚到新票并高亮 4 秒（**不改配置顺序**，用户的排列是有意义的）。
- 教训：**"数据写对了"和"用户看见了"是两件事。** 列表类交互要给"刚刚发生了什么"一个落点。

**坑 16｜同一个 SQLite 绑定参数上限**
- 现象：一键全部加自选要一次标记 1200 个代码 → 单条 `IN (...)` 超过 SQLite 变量上限直接报错。
- 修法：分块（每 400 个一批）。
- 教训：**批量接口的上限要按底层实现的硬限制来定**，不能假设"参数多没关系"。

> 以下 8 条来自做T模块，**都带实测数字**，是面试里最好用的"具体故事"。

**坑 17｜布林轨是"当日分钟"口径，被当成"日线支撑"用**
- 现象：图上出现 11 个红色实心止损倒三角，226 个分时点里 **60 个（27%）** 被判 `forced_exit`。
- 根因：`300308` 当天箱体 804~950、布林轨（当日分钟口径）下轨 902 / 中轨 905.5 / 上轨 909（带宽仅 **0.77%**），而当日最低 **867.44**。低吸线取 `max(804, 902) = 902`，止损 889.76 —— **止损位比当日已经成交过的最低价还高**，于是"开盘即跌破"。
- 修法：布林下轨**只有在现价下方**才算支撑候选（上轨同理）。
- 教训：**同一个指标在不同时间口径下含义完全不同。** 用之前先问"这条轨是用哪一级别的数据算的"。

**坑 18｜固定百分比止损对高波动股形同噪声**
- 现象：高波动股几乎每个点都在触发止损。
- 根因：`300308` 的日线 ATR = 52.8（占股价 **5.8%**），而默认 `stop_loss_pct = 1%` 只有 9 元 → 任何噪声都能打穿。
- 修法：`止损距离 = max(百分比口径, 0.5 × ATR)`。
- 教训：**绝对百分比是"看起来公平、实际上不公平"的参数**——它对低波动股太宽、对高波动股太窄。

**坑 19｜两条护栏相乘恰好等于现价，把信号彻底做死**
- 现象：用户报"该低吸的位置没信号"，实测当天两只票触及低吸线 **0 次**。
- 根因：护栏要求"低吸线必须在现价下方"，实现成了 `price × (1 − 0.003)`；而贴线判定是 `price ≤ low_buy × (1 + 0.003)`。`0.997 × 1.003 ≈ 1` —— **两者相乘正好等于现价**，条件永远不成立。
- 修法：按波动率给真实位置 `现价 − 0.3×ATR`。修完 `603083` 的低吸线 **215.5**，恰好等于当日最低 **215.44**。
- 教训：**两个各自"保守一下"的护栏叠在一起会变成一个死锁。** 加护栏时要算它们的复合效果，不能各加各的。

**坑 20｜用"当前"的止损位去判早盘的 bar**
- 现象：`300308` 09:45 那根 bar 被标成"止损"。
- 根因：回放时用**当前**档位判历史 bar —— 09:45 收盘 867 < 当前止损 872；而**当刻**真实止损是 **853**，价格在它上方 14 元，根本没破位。
- 修法：逐 bar 用当刻档位（`levels_series`）。修完该票当日跌破止损 **0 次**。
- 教训：**回放必须"重置时钟"**，用当时能看到的信息判当时——这就是未来函数的日内版本。

**坑 21｜"触及"用收盘价判定，盘中摸到的全不算**
- 现象：图上明明摸到了低吸线，却没有信号。
- 根因：`600176` 早盘 W 底的最低价正好落在低吸线上，但每根 5 分钟 bar 的**收盘**都在线上方 → 判"从未触及"。
- 修法：图上标记改用**盘中极值**判定（low/high），实时信号仍用现价。修完该票当日实际触及 **9 次**。
- 教训：**"触发"这个词要区分"瞬时触碰"和"收在那边"**——两者的交易含义完全不同。

**坑 22｜第三方库并发调用导致整个进程原生崩溃**
- 现象：用户新加一只票后服务**无 traceback 猝死**（exit code 1，连 Shutting down 都来不及打印）。
- 根因：行情库的两个入口各持一份客户端，都在工作线程里调用；它的下载接口是**原生实现且非线程安全**，原生层出错即解释器消失，**try/except 拦不住**。两次现场都看到它正在打印下载进度条。
- 修法：① 进程级可重入锁包住所有调用；② 下载类操作丢到**子进程**执行（返回值语义是 `(是否成功, 原因)`，**永不抛异常**）。
- 教训：**"能不能 try/except 住"是选隔离方案的分水岭。** 能在同进程里兜住的用异常，兜不住的必须隔离进程。

**坑 23｜数据源的一个字段高估 3.6%，把均价线整体抬偏**
- 现象：VWAP 算出 901 元，而当天真实均价约 869.6 元。
- 根因：该源的分钟线**成交额字段不可信**——逐 bar 求和 161.78 亿 vs 快照口径真实 156.14 亿（高估约 3.6%），用它推导均价自然偏高。
- 修法：该字段置 0，VWAP 回退典型价 `(H+L+C)/3`，实测 869.31（与真实差 0.03%）。另用两次独立源交叉验证（相差 **0.01%**）做护栏。
- 教训：**同一份数据里的不同字段可靠性不一样**；关键派生指标要能换算法并交叉验证。

**坑 24｜"猜一个板块"污染了 14 分权重**
- 现象：随口查一只银行股，它的"板块涨幅排名"按 PCB 概念去排（10/390），还映射到了英伟达。
- 根因：原实现"未在自选里绑定板块 → 回落到配置里的第一个板块"。
- 修法：只认已绑定的板块；未绑定则**板块情绪 + 板块排行两个维度记不可用**（`available_weight = 80/100`），而不是随便套一个。
- 教训：**"给个默认值"是最危险的兜底方式**——它不会报错，只会让结论悄悄跑到别的板块上。宁可让维度不可用。

> 以下来自量化选股（3 档模型）链路。

**坑 25｜阈值写死 0.6，导致"永远选不出票"**
- 现象：选股点了没反应，一只都不出。
- 根因：标签是**稀有事件**（旧口径实测正样本率仅 ~9%），模型输出概率集中在 0.01~0.2（75 分位 ≈0.07、最大 0.55），而阈值写死 0.6 —— **永远不可能达到**。
- 修法：改 `threshold_mode = percentile`（当日截面 90 分位）；绝对下限 `min_score` 默认关到 0（曾经设 0.15，而某日分数区间只有 0.074~0.092 → 又是 0 只）。
- 教训：**分类模型的阈值必须看分数的实际分布，不能照搬"0.5 就是分界"的直觉。**

**坑 26｜漏传一个参数，26 列特征里 13 列静默变 NaN**
- 现象：模型照常训练、照常出分。
- 根因：调因子工厂时漏传 `panel_data=bundle.raw`，而板块截面与情绪序列都在这个"原始面板"里 → 板块 4 列 + 情绪 4 列 + 交叉 5 列全 NaN。
- 修法：把 `PanelBundle.raw` 透传，两处调用点都补上。
- 教训：**"少传一个参数"不会报错**，尤其当那个参数是可选的时候。这种 bug 只能靠"检查特征缺失率"抓。

**坑 27｜分了档，但打分时取的是"目录里最新那个模型"**
- 现象：分档训练做完了，效果和没分档一样。
- 根因：打分仍走 `load_latest_model`（按 mtime 取最新 joblib）→ **等于随机命中一档**，可能用小盘模型给大盘股打分。
- 修法：新增 `load_model_set` / `load_model_for_stock`，按**当日流通市值**选档。
- 教训：**"训练侧做了分档"和"推理侧按档分发"是两件事**，中间那条线要显式写出来并测。

**坑 28｜整批打分失败，上层只看到"打分 0 只"**
- 现象：界面点选股，什么都不发生，日志里也没有。
- 根因：① 逐票打分失败记的是 `debug` 级；② `moss_selector` 的 logger 在服务进程里**没有挂 handler**（`propagate` 也没配）→ 日志直接消失。
- 修法：改 `warning` + `exc_info=True`，并按异常类型统计失败明细；服务侧给它挂一个独立的诊断日志文件；再加一条"打分池为 0"的显式告警。
- 教训：**"静默"往往是两个小问题叠加**（日志级别 + 日志没落地），单看哪一个都不致命。

**坑 29｜用文件名里的时间戳识别"新产物"，跨秒就失效**
- 现象：明明训练成功、模型文件也生成了，重训服务却判定"没有产出"。
- 根因：服务用一个 stamp 去匹配文件名，而训练器**自己生成另一个 `datetime.now()` 时间戳**——只要跨了一秒就对不上。
- 修法：改成"**训练前后目录文件名集合的差集**"来识别新产物，与命名规则解耦。
- 教训：**不要用"猜命名规则"来识别产物。** 前后快照做差集才是稳的。

**坑 30｜备份后缀算错，回滚时还原不回来**
- 现象：一次失败的替换之后，目录里留下一套残缺的文件。
- 根因：备份名按 `f"{Path.stem}.prev{suffix}"` 拼，而 `Path.stem` 对两段式的 `.meta.json` **只吃掉最后一段** → 得到 `core_v1_20-150亿.meta.prev.json` 这种名字，回滚时 `name.replace(".prev","")` 还原不回去。（另一个：`_strip_stamp` 锚定了结尾，对"时间戳不在末尾"的备份名无效，会产出 `.prev.features.prev.features.json` 废文件。）
- 修法：显式 `_with_suffix()` 先去掉已知后缀再拼；正则不锚尾。
- 教训：**备份/回滚这种"只在出错时才走"的路径，必须专门写测试**——正常路径跑一万次也不会暴露它。

**坑 31｜行数统计用 `COUNT(*)`，把整个服务卡了几分钟**
- 现象：`/health` 300 秒超时，服务整体卡住。
- 根因：库 14.28 GB、9 张表合计 8550 万行，`COUNT(*)` 单表 0.46~8.66s、九张表合计 40 秒以上，还会**冲掉 OS 页缓存**（后续查询从 42s 变 46s）。
- 修法：改用 `MAX(rowid)`（写入是"原地 UPSERT 不换 rowid"且从不 DELETE，所以数值与 `COUNT(*)` **完全相等**），并把 `count_mode` 写进返回值。
- 教训：**"统计一下有多少行"这种看起来无害的操作，在大表上是重操作。** 状态接口尤其不能踩。

**坑 32｜路径反推少一层，SQLite 凭空建了个空库**
- 现象：明明配了数据库，却"成功地"去读 CSV，白付 5 秒，**一句日志都没有**。
- 根因：`root` 从 `store.root` 反推少了一层 → SQLite 在错误路径**凭空建出一个空库**并连接成功 → `covers()` 查不到表 → 静默回退 CSV。
- 修法：`root` 由调用方显式传入；未能走库时记 `warning` 而不是 `debug`。
- 教训：**SQLite 会"帮你"建出你写错的路径。** 连接成功不等于连对了库——**必须校验表是否存在**。

**坑 33｜逐日 `as_of` 查询吃掉整轮 47% 的时间**
- 现象：171 个交易日的因子面板要跑 127 秒。
- 根因：财务面板逐日调 `PitPanel.as_of`，等于把 33 万行财务记录过滤/排序/去重 171 遍 —— 单这一步 **59.9 秒（47%）**。
- 修法：改用 `as_of_panel` 一次 `merge_asof`（该步骤 60.4s → **2.0s**）。
- 教训：**先量再优化**——这一条如果只靠"读代码感觉哪里慢"，很可能去优化错的地方。

**坑 34｜用"当日"的箱体判"当日"的突破（自证式）**
- 现象：`box_breakout` 特征异常地"好用"，重要度排第一。
- 根因：当日箱体上沿是用当日最高价算的，用它判"当日是否突破"——**自己证明自己**。
- 修法：改用**前一日**箱体（`shift(1)`）判突破。
- 教训：**特征工程里最隐蔽的泄漏不是"用了未来"，而是"用了包含结果本身的口径"。** 遇到一个特征重要度异常高，第一反应应该是怀疑泄漏。

> 以下来自资金流 / 拥挤度 / 数据层与连接器。

**坑 35｜一个"位置参数 vs 关键字参数"的错误，让整条数据链静默变空**
- 现象：板块资金流整条链路返回空，日志说是"数据源不可用"。
- 根因：`asyncio.to_thread(client.call, api, {})` —— 而函数签名是 `call(self, api, **params)`，只收关键字参数 → `TypeError: takes 2 positional arguments but 3 were given`，**被 except 捕获后归类成"数据源不可用"**。
- 教训：**宽泛的 `except Exception` 会把"程序写错了"和"外部服务挂了"混成同一件事。** 前者应该立刻暴露（代码缺陷），后者才该降级——这个项目的连接器路由后来就明确区分了这两类。

**坑 36｜不传日期参数，返回的是"多天拼接"**
- 现象：板块"当日净额"随机取到几天前，截面日期显示成 20260910。
- 根因：该接口在不传 `trade_date` 时返回**多天拼接**（实测 5000 行含 14/15/16 三天），不按板块去重取最新就会取错。
- 教训：**接口的"可选参数"往往决定了返回结构，不只是过滤条件**。拿到数据先看日期有几个 distinct 值。

**坑 37｜阈值定太小，218 个板块报警——而且全是统计假象**
- 现象：大量板块拥挤度 ≥80%，界面一片告警。
- 根因：水位的分母是"该板块自身历史最高"。样本门槛 `min_bars=60` 时，**历史短的板块天然就是"自己最高"** → 水位恒为 1。
- 修法：门槛提到 **750（≈3 个交易年）**，告警数从 **218 → 26**。
- 教训：**"相对自身历史"的指标必须配足够的样本门槛**，否则它衡量的是"数据有多少"而不是"挤不挤"。而且**改完门槛必须重算已落库的数据**，否则界面继续显示旧口径的误告警。

**坑 38｜把 0 当成有效分母，正常板块被顶成告警**
- 现象：部分正常板块的拥挤度虚高。
- 根因：全市场成交额里零星有 0 值（1538 万行里少量空/0），如果把它当作分母参与计算，**分母被低估 → 拥挤度被高估**。
- 修法：`amount > 0` 才计入。
- 教训：**分母的清洗比分子更容易被忽略**，因为它是"别人的数据"。

**坑 39｜写按偏好、读按实际——换个 Python 环境就"看不见数据了"**
- 现象：用另一个解释器（装了 pyarrow）跑服务，前端显示"11 个数据集 / 0 万行"，因子筛选报"缓存里只有 0 个交易日"。
- 根因：写入时会自适应（有 pyarrow 就写 `.parquet`，否则 `.csv.gz`），但**读取只认一种后缀** → 数据其实躺在 `.csv.gz` 里。
- 修法：**写按偏好，读按实际**（两种后缀都认）。
- 教训：**格式自适应是双向契约**。只做写入侧的自适应，等于给自己埋一个"换机器就丢数据"的雷。

**坑 40｜交易日历默认倒序 + 缓存不记区间，只下了 11 天却报"成功"**
- 现象：请求 2026 全年数据，结果只下载了 11 天，任务状态却是"成功"。
- 根因：① 该接口返回**倒序**，不排序直接 `days[-N:]` 会取错端；② 交易日历缓存**只存"上次请求的那段"**，下次请求更宽区间时被静默缩窄（先冒烟测了 9/1~9/15，随后请求全年）。
- 修法：返回前强制排序；把 `start/end` 写进 manifest，区间不够就按 min/max 扩展重拉。
- 教训：**缓存要记录"它覆盖的范围"**，否则"命中缓存"会变成"覆盖不全"。

**坑 41｜带区间的查询被"本地旧 CSV"挡住更新的数据源**
- 现象：日K面板一直显示两周前的行情，而本地库里其实躺着更新的数据。
- 根因：带 `start/end` 的查询不走 DB 短路，链上第一个成功的源是"本地行情 CSV"（QMT 导出文件，可能停在两周前）→ 把能取到最新日期的在线源挡在门外，而库里更新鲜的数据反而被跳过。
- 修法：把 DB 的最新日期当作**新鲜度下限**——链上某源比它旧就继续试下一个源；全部都比下限旧时返回其中**最新的那份**。（注意：这种"源本身没坏、只是数据旧"的情况**不记失败冷却**，否则一个好好的源会被自己踢出候选。）
- 教训：**故障转移的判据不该是"成功/失败"，而该是"够不够新"。** 返回 200 但数据是两周前的，比报错更危险。

**坑 42｜token 明明配好了，进程却看不见**
- 现象：Windows 注册表里（User/Machine 两处）都写好了 token，但 `os.environ` 是空的 → 取数全部失败。
- 根因：**子进程继承的是父进程启动那一刻的环境快照**。服务比"设置环境变量"这一步更早启动，所以永远看不到。
- 修法：token 三级兜底 —— 环境变量 → `.env` → **Windows 注册表**。
- 教训：**"配置读不到"要先问"这个进程是什么时候启动的"**，别急着怀疑配置本身。另外 token 全程不打印、不落日志，只报长度与首尾 4 位。

**坑 43｜单位不统一就是 10000 倍级错误**
- 现象：不统一就会出"差 100 倍/10000 倍"的诡异结果。
- 根因：不同接口的金额有元/千元/万元、股数有股/万股，比率有百分数/小数。
- 修法：在**下载层一次性归一**（金额→元、股本→股、比率保持百分数），下游只认一种口径，并在模块 docstring 里写明"这里不统一就会出 10000 倍级错误"。
- 教训：**单位问题必须在边界处一次性解决**，散在业务代码里迟早出错——而且这种错往往"数值看起来还挺合理"。

**坑 44｜`create(checkfirst=True)` 只判断表在不在，不补列**
- 现象：新增字段后写入整条失败，**错误信息只提列名、不指向真正的原因**。
- 根因：建表工具只判断"表在不在"，不会给已存在的表补列；INSERT 里引用了新列就在数据库层炸掉。
- 修法：显式用 `PRAGMA table_info` + 幂等 `ALTER TABLE ADD COLUMN` 补列。
- 教训：**"建表幂等"不等于"schema 迁移"**。内联 schema + 补列的写法在多版本迭代里是必须的。

## 5. 面试题库（分类 + 答案要点）

### 5.1 量化 / 策略类

**Q1：你的 Alpha 来自哪里？**
> 三条，按我信的程度排序：① **短周期情绪结构**——超短收益主要来自资金接力，而接力的可行性由情绪周期与生态决定，这部分是可以量化的（涨停家数/炸板率/最高连板/连板家数）；② **竞价的微观信息**——9:15–9:25 的价格轨迹与未匹配量方向包含"今天谁在买"的信息，散户看不到但盘口里有；③ **题材聚焦**——资金在题材内部轮动，龙头与梯队的位置关系可量化。
> 但我要说清楚：**这套东西目前是"筛选器"而不是"印钞机"**——我自己回测的结果是四个战法里三个负期望，所以我不会说我的 Alpha 很强。详见 2.5。

**Q2：怎么避免过拟合？**
> 四层：① **样本外**：`test_ratio=0.2`，标签用 `band` 只留明确样本；② **参数少**：LightGBM `num_leaves=31 / lr=0.05 / min_child_samples=50`，比"深树+小叶子"保守；③ **上线有闸门**：每周重训后逐档对比 AUC/RankIC，**过闸门才原子替换**，不过就保留旧模型；④ **回测用实盘同一套规则**，不另写一套"回测专用逻辑"。
> 不足：没做样本加权衰减、没做 walk-forward 的滚动窗口重训；如果被追问，我会承认这是下一步。

**Q3：如果实盘失效怎么办？**
> 三层熔断：① 打分层的**覆盖率惩罚**（信息量不足直接封顶，不会硬出一个高分）；② **情绪周期闸门**（退潮期/冰点 `t_allowed=false`，直接不做）；③ **一票否决**（ST/市值/环境否决）。另外结果**不自动写自选池**，模型选错不会污染人工决策链路。

**Q4：你用什么回测框架？**
> 自研的日线级回测。原因是**约束条件太特殊**：T+1 不可当日卖、一字涨停买不进、跌停卖不出要挂次日、信号日 T 买入日 T+1、20% 仓位最多 5 笔并发。通用框架要改这些反而更费劲。
> 关键设计是**回测调用实盘的分类器**（`modes.classify_mode`），只替换数据源——否则回测出来的是另一个策略。

**Q5：胜率多少算好？**
> 要看**盈亏比**。超短天然是低胜率高赔率：我实盘回测里无极式是 **46% 胜率 + 2.31 盈亏比**，出水式是 14% 胜率 + 0.66 盈亏比——后者明显是错的，因为低胜率还配低赔率就是稳定亏钱。
> 另外我会同时给**中位数**和**去掉最好一笔的均值**：超短收益分布右偏极重，一笔翻倍就能把均值拉正，只看平均单笔容易被一笔运气误导。

**Q6：为什么不直接买指数/ETF？**
> 这套系统的适用场景是**超短与做T**（持有周期 1–5 天），跟配置指数是两个目标函数。做T的前提是已经有持仓，系统解决的是"今天该不该动手、在哪动手"，不是"该不该持有"。

### 5.2 机器学习 / 因子类

**Q7：为什么用 LightGBM 而不是深度学习？**
> 三个理由：① **样本量与信噪比**：日频截面、5 年数据、26 个特征，树模型在这个规模上比深度网络稳；② **可解释性**：要能展开看每只票的因子值（这是产品需求，不只是技术偏好）；③ **训练成本**：周度重训要能在一台机器上跑完。
> 如果特征变成高频序列（日内 tick），我会换时序模型——但那需要先解决数据存储成本。

**Q8：标签为什么用 band 而不是二分类？**
> 二分类会把"涨了 1%"和"跌了 1%"强行分成两边，但那两个样本其实是同一类——**噪声**。`band` 只留"3 日内最高涨幅 >7%"（正）和"3 日收盘 <-2%"（负），中间地带不进训练。而且用**超额收益**（`use_excess`），剔掉了大盘 beta。

**Q9：为什么要按流通市值分三档训练？**
> 不分档的话，模型很容易学到"市值本身"而不是"这只票好不好"——因为不同市值段的定价机制不同（小盘看资金与情绪、大盘看基本面与流动性）。分档后每档独立训练、独立评估；**推理时按票自己的流通市值分发模型**，而不是先定一个模型再打全市场。

**Q10：阈值为什么取分位数而不是绝对分？**
> 因为模型分的**绝对水平会随行情漂移**：普涨的日子所有票分数都高。取当日截面 90 分位保证"每天都是相对最好的那批"。代价是全市场普跌时也会选出 20 只（矮子里拔将军），所以必须配合市场情绪周期一起看。

**Q11：特征有多少个？怎么防泄漏？**
> 26 个。防泄漏靠三条：① 面板构建时**只用截至当日的**数据；② 预处理是**当日横截面 percentile**（自带"当日排名"语义，不跨日泄漏）；③ 训练与推理复用同一份 `preprocess_kwargs`——**训练喂 Z-score、推理喂原始量纲会让分数整体塌掉**，这是实测踩过的。

**Q12：模型怎么上线？**
> 每周六 20:00 重训（作业内再判一次交易日挡住调休），逐档做回归对比（AUC/RankIC），**过闸门才原子替换**，失败自动回滚成完整的旧套，报告落 `retrain_report_latest.json`。
> 为什么"半套状态"必须被挡住：服务读模型是按公开文件名 glob 取最新，如果出现"新 joblib 已就位、特征列表还是旧的"，模型照样能加载但**分数全错**。

### 5.3 工程 / 性能类

**Q13：15 GB 的本地仓库，取数怎么做到快的？**
> 三条实测有效的：① **列裁剪**（250 日区间只取 3 列比全列快约 2 倍）；② **绕过 SQLAlchemy**（直接拿 DBAPI 驱动连接给 pandas 走快路径，5000 行截面省 ~4 ms、125 万行区间省 ~2.5 s）；③ **`order=False`**（面板随后要 pivot，排序是纯开销）。

**Q14：怎么保证"数据库优先、CSV 兜底"不出错？**
> 返回 `(DataFrame, 来源字符串)`，来源必须显式回传——否则"这次到底查的库还是文件"会变成查不出来的问题。另外 `covers()` **必须看最大日期**而不是"区间内有没有行"：入库是按分区键顺序的，库里永远是缓存的一个前缀，只看有没有行会让一个灌到一半的数据集被判为"走库"，于是回测**静默丢掉后半段数据**。

**Q15：预热从 159s 降到 0.13s，怎么做的？**
> 先定位到成本在服务端（139s 那一项，`count` 参数不省算力），再定位到它被重复付（进程内缓存、重启就没）。做法是按**交易日 + 分项**落盘复用：全命中就一个远端调用都不发，部分命中只补缺的那几项，空结果不写缓存，过期/坏文件一律丢弃。实测冷 120.1s → 暖 0.02s。

**Q16：缓存一致性怎么处理？**
> 三条规则：① **键必须包含"数据的时间维度"**（预热按交易日，跨日一律不命中）；② **"跑了但没拿到"不能写进缓存**（否则永远不会再补）；③ **版本号 + 交易日双重校验**，不符就当没有缓存。

**Q17：定时任务怎么设计的？**
> 单一事实源：所有 cron 只允许在 `registry.py` 声明，禁止散落在代码里的 sleep 循环，Celery Beat 与管理 API 都从这张表生成视图。作业内再做窗口判定与当日去重（cron 粒度故意取 `*/5`，写死单分钟会因为"服务当时没起来"直接漏掉整个窗口）。

**Q18：单测怎么保证统计学上的可信？**
> 会写"反向验证"——先制造故障条件证明测试抓得住这个 bug，再修（见 `INTERVIEW_事件告警500故障复盘.md` 的做法）。另外对**参数契约**写断言而不是对结果写断言：比如 `weights` 合计必须等于 100（曾经因为 YAML 与代码默认值不同步，权重合计变成 116 和 200）。

### 5.4 数据质量 / 风控类

**Q19：拿不到数据你会怎么办？**
> 一句话：**不猜、不臆造，缺口必须显式报出来**。具体分级：
> - 分母 ≤0 或缺 bars → 指标置 `None`（如水位）；
> - 缺一个维度 → 从权重分母剔除 + 覆盖率惩罚；
> - 缺关键输入（涨停价/昨收/均量）→ **放弃这个判断并记 gap**，不用"上一次的值"或"估算值"顶上；
> - 结构性缺失（如历史题材榜）→ 整个模式标为**不可评估**，而不是报 0 笔当胜率 0。

**Q20：怎么发现"静默错误"？**
> 我的经验是：**静默错误都藏在一个"看起来正常的数字"后面**。所以我会给每个关键中间量加一个"它应该是多少"的对照：
> - 数据滞后 → 算"应该是哪一天"（`freshness`）；
> - ST 过滤 → 报出"剔了几只"（发现永远是 0 就说明过滤没生效）；
> - 候选池 → 报出"昨日涨停 N 只 → 剔 X/Y/Z"；
> - 缓存 → 报出"复用了哪几项、落盘时间"。
> 这类"自证清白"的字段比日志更有用，因为它们会随结果一起进数据库和前端。

**Q21：策略亏钱你怎么归因？**
> 把"选股"和"买卖规则"分开算：我的超短回测里，全部命中信号 −1.70%/笔，而**无条件对照**（当日全部涨停股、同样卖出规则）是 −1.67%/笔 → 说明**亏钱的主因是买卖规则而不是选股**。这一步很关键：不分离这两个因素，就会一直去换选股逻辑，而问题其实在止损/止盈规则上。

### 5.5 产品 / 协作类

**Q22：为什么选股结果不自动加自选？**
> 这是用户的明确要求：**模型选错时不能污染做T主链路**。所以结果只落在模块里，用户点「＋加自选」才写 `configs/intraday.yaml`。

**Q23：用户报"加了自选但列表里没有"，你怎么处理？**
> 先查事实再下结论：我直接打了接口，看到返回 43 只、新加的 20 只在第 24–43 位——**数据是对的，问题在可见性**。所以修的是"加完给一个落点"（展开 + 滚动 + 高亮 4 秒），而不是去改数据。中间还发现接口 `limit` 默认 20 会让第一次排查的人误判成"没写进去"。

**Q24：你怎么和用户对齐"这个功能到底要什么"？**
> 把口径**写进代码注释和文档**，并指回出处。比如竞价选股的 11 个权重，注释里写明"权重不是语料里的原始数值，语料只给方向与优先级，这里是我们自己的标定，所以每一项标注出处口径"。这样后面任何一次调参都能查到"当初为什么是 19 不是 15"。

| 25 | 换个 Python 环境就"看不见数据"，为什么？ | 写入格式随"有没有 pyarrow"自适应，读取却只认一种后缀 | 结论：**写按偏好，读按实际**——格式自适应是双向契约 |
| 26 | 你怎么保证**改参数之后**界面不会继续显示旧口径的结果？ | 一般做不到自动，所以我在文档里写明"改完必须重算" | 实例：拥挤度样本门槛从 60 提到 750 后，告警从 218 降到 26，但**库里旧水位不重算就还在报** |

## 7. 能独立讲的亮点（每条 2 分钟，STAR 化）

**亮点 A｜互斥分类器：拒绝加权求和**
- S：六个战法来自三套，资料里没写"怎么合成一个分"。
- T：要么加权求和给一个分，要么找另一种表达。
- A：读原文发现它们的有效择时**互斥**（冰点上破冰式是买点、追击式是禁忌），于是做成"择时闸门 → 逐条判定 → 取最高拟合度的单一模式"，并输出六式的逐条判定明细。
- R：前端能回答"为什么不能用这套打法"；避免把"该做"和"不该做"平均成没意义的中间值。
- **金句**：*"加权求和的前提是各维度可以同时成立；择时不是这样——它在任何时刻只允许一套打法。"*

**亮点 B｜生态不是当天的一个点，而是一段曲线**
- S：最初用"当天最高连板"判生态档位。
- T：用户指出这与实际操作含义不符。
- A：改成最近 10 个交易日"当日最高连板"序列 → 找波峰 → **生态取最高波峰、压力位取最后一个波峰**；处理平台取中、右端只在上升时算波峰。
- R：同样"今天最高 5 板"，前 10 天最高 5 板 vs 曾到 8 板后掉到 5 板，现在能区分开——操作含义完全相反。
- **金句**：*"一个点只能说明今天，一段曲线才能说明环境。"*

**亮点 C｜数据缺口必须显式，且分级处理**
- S：不同数据缺失的性质完全不同。
- T：既不能一缺就崩，也不能用估算值蒙混。
- A：分四级——分母异常置 None；缺一个维度从权重分母剔除 + 覆盖率惩罚；缺关键输入放弃该判断并记 gap；结构性缺失把整个模式标为"不可评估"。
- R：回测报告里"趋龙式不可评估"和"破冰式 0 信号是行情事实"都被明确写出，没有拿 0 笔冒充胜率 0。
- **金句**：*"0 笔和胜率 0% 是两件完全不同的事，报告里不能混。"*

**亮点 D｜行情预热的复用设计（159s → 0.13s）**
- S：盘前预热被 `theme_strength_rank` 一项拖到 139s，且每次重启都要重付。
- T：既不能让它变旧（预热内容是按日变的），又不能重复算。
- A：按交易日 + 分项落盘；只复用"真拿到数据"的项；全命中就不建立数据源连接。
- R：冷 120.1s → 暖 0.02s；服务重启后第一次调用 `seconds: 0.13`。
- **金句**：*"并发降低单轮成本，缓存降低重复次数——我一开始只做了前者，所以 139s 还在。"*

**亮点 E｜回测与实盘共用同一段代码**
- S：回测要按日重放，实盘只算最新一天。
- T：不能为回测另写一套规则（那回测的就是另一个策略）。
- A：把生态判定从有 IO 的 `build_snapshot()` 抽成纯函数 `snapshot_from_series()`，实盘与回测共用；回测逐日喂"截至该日"的序列。
- R：未来函数无处藏身，并有单测断言"多喂一天就会改变结论"。
- **金句**：*"回测的价值全部建立在'它跑的是同一个策略'上。"*

**亮点 F｜A 股制度约束进了收益率**
- S：早期回测买入当日就能卖。
- T：真实交易有 T+1、涨跌停、停牌。
- A：买入当日不检查止损（只记 `breached_entry_day`，次日开盘卖）；一字涨停买不进；跌停卖不出挂下一日开盘。
- R：回测出现"止损-买入当日触发（T+1 次日开盘卖）"这类真实的成交分类。
- **金句**：*"把制度细节漏掉，回测出来的就是另一个市场的收益率。"*

## 8. 别吹过头：诚实边界

面试里**主动划边界**比被追问出来强得多。下面这些要能脱口而出：

| 事项 | 事实 | 怎么讲 |
|---|---|---|
| 实盘收益 | **没有实盘盈利证据**；回测账户口径 59 天 −16.33% | "系统在跑，但我不宣称它赚钱。我宣称的是它把不该做的时段挡掉了、把负面结果如实报出来了。" |
| 无极式的正收益 | 26 笔全部依赖一条**未经验证的降级假设** | 主动说："这个数字要打问号，前提是缺失的盘口承接分本来会通过。" |
| 破冰式 / 趋龙式 | 0 信号 / 数据不可评估 | "这是数据与行情事实，不是模块缺陷；我没有拿 0 笔当胜率 0。" |
| 样本量 | 龙回式 4 笔、追击式 7 笔 | "个位数样本只能当记录，不能当胜率。" |
| 过拟合防护 | 没做样本加权衰减、没做 walk-forward | "这是我下一步要补的。" |
| 资金流模块 | 滞后指标，不能做日内择时 | 主动说，别让面试官发现 |
| 实盘执行 | 没有对接券商下单，没有滑点/冲击成本模型 | 滑点只做了 0/0.2%/0.5% 的敏感性 |
| 数据合规 | Tushare 付费 + 公开源，无内幕数据 | 所有输出带免责声明 |

**"我不知道"的正确用法**：被问到没做过的（组合优化、风险平价、期权对冲、T0 高频），直接说"这块我没做，我的理解是……"，然后把它和做过的连起来（比如"我的仓位规则是固定 20%×5，没做凯利或风险平价，因为超短的收益分布右偏太重，估不准方差"）。
