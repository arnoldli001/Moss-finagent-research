    理由 1：可控的 fan-out / fan-in

    理由 2：失败边界必须显式
    需求：单节点失败吞入 state.errors，不中断整图。
    LangGraph：_node() 内 try/except AgentExecutionError → return {errors: [...]} — supervisor.py:851-856。
    AutoGen：框架接管错误处理，不知道错误是不是被吞了。
    理由 3：状态必须可观测
    需求：前端实时看到"A17 正在追问 A10"、"ReAct 第 2 步"。
    LangGraph：ResearchState 黑板 + live_state 旁路 — research.py:339-341。
    AutoGen：Group Chat 内部状态机，外部看不到。
    理由 4：成本必须可独立控制
    需求：分析层 9 个 Agent 各自有 token 预算，超预算就 fail-fast。
    LangGraph：_node() 内每个 Agent 独立预算检查 — gateway.py:329-336。
    AutoGen：成本是整体，不能 per-Agent 控。

    面试话术

    "LangGraph vs AutoGen 不是'哪个好'——是'你的需求是什么'。

    我的需求是：① 9 路 Agent 并行 ② 失败边界显式 ③ 状态实时可见 ④ 成本 per-Agent 控制。

    LangGraph 的 add_edge 让我能精确控制：哪些节点串行、哪些并发、A17 之前所有 Agent 都完成才进入——这些是显式的、可测的、可优化的。

    AutoGen 的 Group Chat 是黑盒——我无法回答"为什么这个 Agent 现在说话"、"什么时候 A17 综合"，更无法回答"这一轮 token 花了多少钱在哪个 Agent 上"。

    选 LangGraph 不是技术偏好，是需求驱动——架构师选型应该问'我的需求是什么'，不是'哪个框架更潮'。"

def _truncate(self, prompt: str) -> str:
    cap = int(self._settings.llm_input_char_hard_cap or 0)
    if cap <= 0 or len(prompt) <= cap:
        return prompt
    head = int(cap * 0.7)
    tail = cap - head
    dropped = len(prompt) - cap
    return (prompt[:head]
            + f"\n…（中段已省略 {dropped} 字符）\n"
            + prompt[-tail:])

# 实测：分析层加 cap 前 A10/A11/A12 单次输入 23.3 万 tokens

    # src/infrastructure/llm/circuit_breaker.py:42-127

class TimeWindowCircuitBreaker:
    def __init__(self, name, failure_threshold, failure_window_sec,
                 recovery_cooldown_sec, half_open_success_needed):
        self.name = name
        self.failure_threshold = failure_threshold          # 失败阈值
        self.failure_window_sec = failure_window_sec          # 滑动窗口（秒）
        self.recovery_cooldown_sec = recovery_cooldown_sec   # OPEN→HALF_OPEN 冷却
        self.half_open_success_needed = half_open_success_needed  # 半开需成功数
        self._state = "CLOSED"
        self._failures: list[float] = []      # 窗口内失败时间戳
        self._opened_at: float | None = None  # OPEN 起始时间
        self._half_open_successes = 0

    def allow_request(self) -> bool:
        """熔断器准入决策。"""
        now = time.monotonic()
        if self._state == "CLOSED":
            return True
        if self._state == "OPEN":
            # 冷却期满 → 转 HALF_OPEN
            if self._opened_at and (now - self._opened_at) >= self.recovery_cooldown_sec:
                self._state = "HALF_OPEN"
                self._half_open_successes = 0
                return True
            return False  # 仍在 OPEN
        # HALF_OPEN：只放行少量探测请求
        return True  # 探测阶段

    def record_failure(self):
        now = time.monotonic()
        if self._state == "HALF_OPEN":
            self._state = "OPEN"  # 探测失败立即回 OPEN
            self._opened_at = now
            return
        # CLOSED：累计窗口内失败
        self._failures.append(now)
        # 清理窗口外的旧失败
        cutoff = now - self.failure_window_sec
        self._failures = [t for t in self._failures if t >= cutoff]
        if len(self._failures) >= self.failure_threshold:
            self._state = "OPEN"
            self._opened_at = now

    def record_success(self):
        if self._state == "HALF_OPEN":
            self._half_open_successes += 1
            if self._half_open_successes >= self.half_open_success_needed:
                self._state = "CLOSED"
                self._failures = []

    HR 必问："熔断器为什么按 provider 而不是 model 隔离？"

    HR 追问 你的熔断器是按 provider（deepseek / ollama）隔离的，不是按 model（deepseek-v4-pro / deepseek-flash）。为什么不按 model？
    答：熔断的本质是"外部依赖不可用"。同一 provider 的不同 model 是同一个故障域——如果 deepseek 的 API 挂了，deepseek-v4-pro 和 deepseek-flash 一起挂。

    如果按 model 隔离，deepseek-v4-pro 熔断了，deepseek-flash 还能继续——但它们用的是同一个 API endpoint、同一个 key、同一个熔断器。这会让熔断器变假象：deepseek-v4-pro 报熔断，但 deepseek-flash 还能调，结果降级链里 deepseek-flash 也失败，整个降级链断掉，链路 100% 失败。

    所以按 provider 隔离 = 让熔断器的判定和实际故障一致，不是装饰。

    ★ 追问的下一层（2026-10-01 补）：那"按 provider"是不是就够了？不够。 故障域有两个方向：provider 维度（外部依赖挂了）之外还有请求方维度—— 失败是按请求方累积的，却按提供商生效。于是 A 租户 60 秒内 3 次失败， 把 deepseek 桶打成 OPEN，B 租户连 API 都不试（实测现象就是 "一个用户的突发流量让所有用户被拒"）。修法：key = provider × 租户 （deepseek:vip），拿不到租户身份时退回 provider 级全局桶并且仍然熔断 （后台作业走这条，如实退化）。判据里带自证：用"丢掉租户维度"的旧注册表 跑同一条场景，B 必须被拒——同一场景两种机制结论相反，才证明隔离判据不是恒绿。

def _filter_points_for_agent(agent_id, points, *, fallback_limit=200):
    """按 Agent ID 白名单过滤 validated_points（避免无关数据占 token）。"""
    keywords = _AGENT_DATA_WHITELIST.get(agent_id)
    if not keywords:
        return list(points[:fallback_limit])  # 未配置 → fallback

    kws_lower = tuple(k.lower() for k in keywords)
    matched = []
    for p in points:
        ind = str(p.get("indicator", ""))
        ind_lower = ind.lower()
        if any(kw in ind_lower or kw in ind for kw in kws_lower):
            matched.append(p)

            "Agent %s 的白名单过滤后 0 条数据点（fallback 取前 %d 条），"
            "请检查 _AGENT_DATA_WHITELIST 配置", agent_id, fallback_limit)
        return list(points[:fallback_limit])
    return matched

def call_cost_cny(*, provider, model, tokens_in, tokens_out,
                  provider_cache_hit=False, prices=None):
    """一次调用的费用（元）。**唯一的计价实现**。
    
    · provider != "deepseek"（本地 Ollama 等）→ 0 元
    · 未登记价格的模型 → _FALLBACK_PRICE 兜底（宁可高估不可漏记）
    · 计价口径：tokens_in × 命中/未命中价 + tokens_out × 输出价（元/百万 token）
    """
    if str(provider) != "deepseek":
        return 0.0
    table = model_prices() if prices is None else prices
    hit_rate, miss_rate, out_rate = table.get(str(model), _FALLBACK_PRICE)
    in_rate = hit_rate if cache_hit else miss_rate
    return ((int(tokens_in or 0) * in_rate
             + int(tokens_out or 0) * out_rate) / 1_000_000.0)

def reserve_task(self, source="research") -> bool:
    """为一次投研任务预扣额度。"""
    if self._daily <= 0:
        return True
    need = self._task_reserve  # 默认 0.25 元（p90）
    with self._lock:
        if self._ledger.used + need > self._daily:
            return False  # 预算不足
        self._ledger.reserved += need
    return True

def release_task(self, actual_cost=0.0, source="research"):
    """结算：退还预扣 + 记实际消耗。"""
    if self._daily <= 0:
        return
    with self._lock:
        self._ledger.reserved = max(0, self._ledger.reserved - self._task_reserve)
        if actual_cost > 0:
            self._ledger.spent += float(actual_cost)
            self._ledger.by_source[source] = (
                self._ledger.by_source.get(source, 0.0) + float(actual_cost))

def rebuild_max_ma5_table(conn, *, sector_codes=None):
    """重建 max_ma5 物化表。

    · sector_codes=None：全量重建（GROUP BY 一次性扫日线表）
    · sector_codes=[...]：只更新这些板块（refresh 增量场景）
    """
    stamp = _now()
    if sector_codes is None:
        rows = conn.execute(
            f"SELECT sector_code, MAX(ma5_crowding) AS mx FROM {DAILY_TABLE} "
            f"WHERE ma5_crowding IS NOT NULL GROUP BY sector_code").fetchall()
        payload = [(str(r["sector_code"]), float(r["mx"]), stamp)
                   for r in rows if r["mx"] is not None]
    else:
        # 增量：按板块代码分别取
        payload = []
        for code in sector_codes:
            row = conn.execute(
                f"SELECT MAX(ma5_crowding) AS mx FROM {DAILY_TABLE} "
                f"WHERE sector_code = ? AND ma5_crowding IS NOT NULL",
                (code,)).fetchone()
            if row and row["mx"] is not None:
                payload.append((code, float(row["mx"]), stamp))
    if not payload:
        return 0
    conn.executemany(
        f"INSERT INTO {MAX_MA5_TABLE}(sector_code, max_ma5, updated_at) "
        f"VALUES (?, ?, ?) "
        f"ON CONFLICT(sector_code) DO UPDATE SET "
        f"max_ma5 = excluded.max_ma5, updated_at = excluded.updated_at",
        payload)
    conn.commit()
    return len(payload)

    取舍 1 · 不上 React Query

    为什么不上：
    ① 数据形态特殊：本项目有大量带状态机的轮询（任务状态 queued/running/completed/failed），React Query 是为"列表 + 缓存"设计的，不能表达"轮询 + 终止令牌"这种业务语义
    ② WebSocket 已经替代了大部分缓存需求：告警未读 / 情报流已就绪都是 WS 推送，缓存反而成为"假新鲜度"的来源
    ③ 保活面板：事件告警、情报流用 KeepAlive 缓存已挂载状态，React Query 缓存会冲突
    ④ 可控性：useEffect + setInterval 显式控制轮询生命周期，出问题易排查

    代价：每个面板要手写 useEffect + loading + error 三件套，代码冗余——是有意为之的"显式优于魔法"。

    取舍 2 · 不上虚拟滚动（散点图）

    ① 散点图场景特殊：600+ 圆点需要缩放/平移/框选交互——虚拟滚动会让交互事件路径复杂化（要跨组件边界）
    ② 浏览器能扛：实测 600 圆点 + O(n²) 标签避让 = 30ms 渲染，远低于 16ms 一帧，用户无感
    ③ 贪心标签放置：标签 O(n²) 避让是有意保留的——避免硬挤重叠，宁可少标几个（标题里说明"已标 N 个，M 个因空间不足未标"）
    ④ SVG vs Canvas：SVG 交互好开发但性能差；Canvas 性能好但交互差——Demo 阶段 SVG 优先，性能未到瓶颈前不切换

    三档超时语义

    超时档位触发条件语义代码位置
    L1：单次 LLM 调用llm_timeout_seconds=120provider 无响应挂死core/config.py:147
    L2：单次降级链尝试attempt_budget_sec（light 20s / medium 20s / reasoning 45s / decision 60s）"成功但极慢"被中断、自动降级下一跳llm/gateway.py:69-74
    L3：任务级 token 累计llm_token_budget_per_task=200000单任务失控core/config.py:169
    L4：沙箱执行SANDBOX_TIMEOUT_SEC=15生成代码里死循环code_validator.py:59

    为什么是"三档"超时？每档防的问题不同

    L1 单次调用超时（120s）：防 provider 无响应挂死——所有调用
    L2 单次尝试超时（20-60s）：防"成功但极慢"——只对有退路的跳生效（最后一跳不设，因为没退路）
    L3 任务级 token 超时（200K）：防循环异常导致费用失控
    L4 沙箱超时（15s）：防生成代码里死循环——子进程级 kill

    关键：每档超时只防一种问题——不要一档超时解决所有问题。
    这是 "分层防御" 而不是 "一档兜底"。

    实际事故：被自己压测否掉的第一版（缓存方案）

    事故（PROJECT_AUDIT §1.2）：
    背景：第一版 LLM 缓存方案用"遍历 data/llm_cache/*.json 全部文件"做语义索引

    实测：本机 3108 个缓存文件
    · 冷未命中扫描：682.2 ms（进程重启后第一次）
    · 暖未命中扫描：8.9 ms（此后每次未命中）

    问题：
    ① 同步阻塞事件循环——这是 async 服务，9ms 的同步 IO 冻结所有并发请求
    ② 实测事件循环最大停顿 22.3 ms
    ③ 一次投研分析有 7-15 次 LLM 调用，大部分会未命中，N 个用户并发时总阻塞 ≈ N × 9ms
    ④ 随缓存增长而退化：3108 文件 = 10MB，缓存只增不减（过期文件仅在被访问时才 unlink）

    修法（第二版）：
    · 进程内维护 (agent_id, scope) → vector 索引
    · 语义查找变成纯内存计算（微秒级）
    · 索引按 (agent_id, scope) 分桶，先分桶再算余弦
    · 懒加载：首次语义查找时建一次索引

    教训：
    ① "文件遍历 = 同步 IO"在 async 服务是毒药
    ② "缓存只增不减"是退化——需要 lazy build + 容量淘汰
    ③ "被自己压测否掉"是好事——比"上线后才被用户发现"好得多

    端到端时间线（故障复盘视角）

    阶段耗时关键问题修法
    早期（deepseek-flash 全云端）~160sA17 撞 4096 上限 98 次ReAct 增量协议（−91%）
    第八轮后~80-120s信息层串行 95sA05/A06 并行 + A07 改 light
    第九轮后~40-70sA17 3 步 99% 用不上第 3 步max_steps=2（默认）
