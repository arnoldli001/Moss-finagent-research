**几个前端坑**（都是实测）：
- `zoom: clamp(1, 100vw/1780, 1.15)` **不生效** —— Chromium 不解析 `zoom` 里的 `vw`
  （计算值恒为 1），`100%` 又是循环依赖。改用 `@media` 断点阶梯。
- `position: sticky` 要生效，**必须有一个纵向滚动容器**，否则表头不动。
- SVG favicon 里写注释含 `--` 会让浏览器报 `Comment must not contain '--'`，
  整个图标渲染失败。最终**去掉全部注释**。

### 1.2 主线挖掘：成分股提纯（`src/mainline/relevance.py`）

**要解决的问题**：`ths_member` 概念归集很松。实测 `885959.TI PCB概念` 236 只成分股，
抽查前 12 只只有 3 只主营业务真与 PCB 有关，其余是 TCL 科技、铜陵有色、中钨高新。

**规则**：一只股票要留在某概念板块里，该概念必须落在**它自身最相关的前 3 题材**内。

```
走势相关性 60%   市场把这只股当什么在炒     ← 定排序与权重
主营业务   40%   公司实际做什么（LLM 判定） ← 证伪，剔除巧合
```

外加三条硬门槛：**总市值 < 30 亿**、**ST/退市**、**统计/事件/地域型假板块**。

**5 张表**（都在 `data/mainline_cache.db`，与主线主库同一个文件）

| 表 | 行数 | 内容 |
|---|---:|---|
| `ml_company_business` | 6,294 | 主营描述缓存（`stock_company` 一次拉取，1.8s） |
| `ml_member_corr` | 110,605 | 逐 (股票, 板块) 走势相关性（240 交易日日对数收益率 Pearson） |
| `ml_stock_theme` | 14,985 | 逐股票前 3 题材 + 分项得分 + `prompt_sig` 缓存签名 |
| `ml_theme_board` | 1,910 | 题材 → 各分类体系板块代码映射 |
| `ml_member_clean` | 137,030 | 逐 (板块, 股票) 的相关性结论 |

**关键设计：相关性离线、市值在线**

- 相关性（走势 + 主营）依赖当前成分股快照与最新一期主营描述，本质静态 → **离线**批算
- **市值和 ST 按运行日现取**（`quant_daily_basic.total_mv` / `quant_stock_directory.name`）
  —— 写死会让回测用今天的市值筛过去的成分股

**统一集成点只有一处**：`service.py` 的 `member_map`。下游资金流聚合、景气度、
筹码、两融、北向、龙头识别全部读同一份，不会出现"某个维度还在用全部成分股"的口径分裂。

**批处理入口**（分 4 段，各自幂等可续跑）

```bash
python scripts/mainline_relevance.py --stage all              # 全流程
python scripts/mainline_relevance.py --stage score --force    # 强制重打分
python scripts/mainline_relevance.py --explain 002050         # 看单只判定明细

### 1.3 LLM 基础设施（`src/infrastructure/llm/`）

| 问题 | 修法 |
|---|---|
| 投研分析报"全部模型调用失败（链: deepseek-v4-pro→deepseek-flash）" | `.env` 补 key（根因：System-scope 环境变量为空，而进程环境在 spawn 时已固定） |
| decision 层 fallback 与主模型**同 provider** → 熔断时主备一起被拒 | `decision.fallback` 改为 `local_medium`（跨 provider） |
| 缺 key / 401 / 402 / 403 被计进熔断 → 3 次就 OPEN，病因被 `circuit_open` 淹没 | `LLMGatewayError(count_as_failure=)` 分类，配置类错误不计熔断 |
| token 预算 30,000 不够一轮分析（实测需 38,207） | 提到 200,000（`llm_token_budget_per_task`） |
| 输出上限 4,096 被推理链吃光 → **空响应** | 打分调用显式 `max_tokens=32768`；硬上限 4096→32768 |
| **空响应被写进缓存** → 所有重试命中空缓存 | 空内容不算命中、也不写入 |
| 单只卡死无感知 | `stall_seconds` 卡死守卫（心跳 + 超时抛错，已落库部分保留） |

## 二、踩坑记录（面试主战场）

> 每条按 **现象 → 根因 → 修法 → 可迁移教训** 写。面试官问"遇到最难的问题"就从这里挑，
> **一定要讲出"我一开始判断错了"** —— 这比一次做对更有说服力。

### 坑 1：走势相关性只算出 1,035 对（应为 110,605）

**现象**：14.4 万个"股票×板块"组合，只有 1,035 个能算出相关性。

**我的三次错误假设**（这段是加分项，展示排除过程）：
1. 以为窗口起点算错 → 写诊断脚本，发现起点是对的
2. 以为板块日历稀疏 → 对比两边交易日历，重叠 451 天，数据本身没问题
3. 以为要"各自取末尾 240 个再求交" → 改完**仍是 1,035**

**真根因**：`ml_board_bar` 数据**残缺**。近 12 个月（255 交易日）里只有 **48 个板块**
K 线完整，1,305 个只有 50~119 根，243 个完全没有 —— 板块数据要么止于 `20251128`，
要么从 `20260915` 才开始。两条序列**时间段不相交**。

**关键判断**：我怀疑是接口限制，于是**直接探针** `ths_daily` 请求
`20260101~20260918`，返回 174 行正常 → 排除接口限制，确认是上次同步 `partial`
（`511 项未取到`）后没续跑。补数后完整度 48 → **1,074 个板块**，
相关性 1,035 → **110,605 对**。

**代码侧防御**：`_common_tail()` 取两条序列**共同日期**的最后 N 个，
而不是"各自末尾 N 个再求交集"。这样无论哪条序列何时断掉，
都能拿到真正重叠的那段历史。

**可迁移教训**：
- **卡住时不要继续推理，要加仪器**。三个假设全错，每次都是诊断脚本推翻自己。
  决定性的一步是加计数器拆解：`no_stock=7880 no_board=524 short=109339 ok=1035`
  —— 一眼看出真凶是 `short`。
- **区分"接口不能" 和 "我们没取"**：一个 3 行探针就能定性，比读 200 行同步代码快。

### 坑 2：LLM 输出上限把约 20% 结果静默吞掉

**现象**：约 20% 的打分调用返回**空字符串**，且**重试同样失败**（不是抖动）。
没有重试就表现为"这只股票没有记录"（贵州茅台就这么丢过一次记录，而它显然该有"白酒"）。

**排查路径**（这条路径本身值得背）：
1. 空响应 → 打日志看失败原因，发现是"解析不出条目"
2. 打印 gateway 响应的 `tokens_out` 字段 → **所有失败都是 4096，正好等于上限**
3. 结论：DeepSeek 的**推理 token 计入输出上限**，4096 全被思维链吃光，正文一个字没输出
4. 抬到 32768 → `tokens_out` 落在 890~7,653，失败率 20% → **0.1%**

**中途踩的两个次级坑**：
- 改 `max_tokens` 覆盖时**顺序写反**（先覆盖、再被硬上限截回 4096），表现为"改了没用"
- 修好之后**仍然失败**，最后用**单变量对照**定位：

```
use_cache=True  → len=689   out=4096  cache_hit=True    ← 缓存的旧截断响应
use_cache=False → len=998   out=6604  cache_hit=False   ← 真实的新响应
```

**真凶是缓存**：网关把那条空响应**写进了缓存**，此后每次重试都命中它并立刻返回 ——
而且因为命中缓存耗时变短，看起来完全不像缓存问题。清掉 1,312 条被污染的空缓存后，
失败率才真正降到 0.1%。

**可迁移教训**：
- **空结果不是结果**。缓存层必须把"空"当失败，否则一次故障会被固化，
  故障从"偶发"变成"永久"。
- **怀疑某个因素时只改它一个**。我对 `max_tokens` 推理了一整轮，一行 A/B 对照就结束了。

### 坑 3：板块目录被静默裁掉（同一个 bug 踩了两次）

**现象**：`ml_board` 从 2,232 行掉到 335 行。

**根因**：`config.universe.source == "crowding"` 时 `sync_boards()` 委托给
`import_crowding_pool()`，它只带来 335 个板块；而 `_prune_boards()` **不区分来源**，
把其余 1,800+ 个概念板块当"已不在名录里"删了。

**为什么难发现**：
- 主线打分**只遍历 `ml_board`** → 1,800+ 板块静默退出打分，只有排行榜悄悄变短
- `ml_member` / `ml_board_bar` 数据都在（清理不碰它们）→ "数据看起来齐全"
- 触发源是**后端定时任务**，在跑 LLM 补算期间就把目录裁了，完全静默

**修法**：`_prune_boards(keep, source=...)` 只清理**本名录源自己**的行；
池子 upsert 的 `source` 改成"只写不改"；黑名单改成**读取时过滤**而不是靠删数据；
另加**目录萎缩告警**（一次删超三成就 warn）。

> ⚠️ **这条有个重要后续**：用户后来说明 335 行是**他有意的任务**，不是 bug。
> 所以面试讲这条时，要讲成"我误判成 bug 并做了防护，后来发现是业务预期，
> 于是把防护收敛成'告警 + 可恢复'" —— **这比"我修了个 bug"更成熟**，
> 而且展示了你区分"工程缺陷"与"业务意图"的能力。

**可迁移教训**：
- **任何删除都要能回答"删错了怎么恢复"**。我为此写了 `mainline_restore_boards.py`
  （从本地名录缓存重建，几秒，不需要网络）。
- **进程内的代码修复 ≠ 生效**：后端 16:56 启动、我 23:58 才改代码，
  它一直在跑旧代码。改完必须重启，否则"验证通过"是假象。

### 坑 4：卡死守卫自己有两个 bug

**现象 A**：守卫抛出异常后进程**永久挂起**（pytest 超时 10 分钟）。

**根因**：`asyncio.gather` 在守卫抛错时立刻传播异常，但**其余 worker 任务仍挂在
事件循环里**，而 `asyncio.run()` 退出前会等待所有 pending 任务。

**现象 B**：守卫**从不触发**。

**根因**：守卫用"任务是否全部派完（`index` 到底）"判断退出 —— 但 worker 可能还在跑
最后几只。守卫先退出了，**卡死就再也没人看守**。

**修法**：用 `asyncio.Event` 在**所有 worker 真正退出**时通知守卫；
每完成一只更新心跳；用 `wait(FIRST_COMPLETED)` + 显式 cancel 收尾。

**可迁移教训**：
- **判据要选"事实"而不是"代理指标"**：`index` 到底只是"活派完了"，
  不等于"活干完了"。
- **超时/守卫这类代码本身必须有测试**，否则它只是让你以为有保护。

### 坑 5：我自己的 `--explain` 触发了一次破坏性同步

**现象**：我用 `--explain` 查一只股票的结果，它**默认跑了完整流程**（含数据同步），
把板块目录裁了（同一 bug 的第二次触发）。

**教训**：**任何"顺手看一眼"的 CLI，默认值必须是零副作用**。
改成 `--explain` 只跑 report 阶段。

### 坑 6：提纯结果本身有 3 个已确认缺陷（本会话只做到"发现"）

| 缺陷 | 证据 | 性质 | 后续 |
|---|---|---|---|
| 假板块规则**精确匹配**失效 | `is_fake_board("饮料(A股)")` = False（规则写的是 `^饮料$`）→ 饮料/食品饮料/酿酒商占满茅台前 3 → **茅台归属板块数 = 0** | 实现 bug，几行可修 | 随方案替换一并作废 |
| 41% 板块被**整板剔空** | 1,888 个板块中 782 个 keep=0；物联网 470→0、粤港澳大湾区 490→0、石墨烯 77→0 | 过度过滤 | 新方案改为阈值制，不再整板归零 |
| 规则**方向反了** | 我用"个股前 3"决定板块成员；但"概念→股票映射"要的是每个概念下有哪些股票。一只股票有几十个竞争题材，导致真实相关的板块可能挤不进任何一只股票的前 3 → 整板归零 | **设计问题** | **已由 `ml_member_pure` 的板块侧排名 + 阈值解决** |

**面试怎么讲这三条**：不要回避。可以说"这块我完成了第一版并跑通全量，但自查时发现了
三类问题，其中一类是设计层面的方向问题……" —— **能自己找出设计缺陷是强信号**，
比假装完成要好得多。

### 后续进展（09-21 及之后，**不属于本会话，但要知道结论**）

这套方案后来被**替换**了：新的产物是 `ml_member_pure`，判据从"个股前 3 题材"改成

## 三、面试问答准备

### 3.1 量化开发岗

| 问题 | 你的答法（本项目都有实证） |
|---|---|
| 怎么防**前视偏差**？ | 相关性离线算（依赖当前成分股快照，是已知的 survivorship 局限）；但**市值阈值必须按运行日现取** —— 写死成"今天"，跑 2022 年回测就会用 2026 年的市值筛成分股，**自动选中后来才长大的票**，回测会好得离谱 |
| 用了什么**收益率**，为什么 | 日**对数**收益率 `ln(P_t/P_{t-1})`；相关系数用 Pearson。对数收益率可加、对极端值更稳 |
| 相关性具体怎么算 | 240 交易日，两条序列**按共同交易日对齐**（处理停牌/数据缺失/日历口径差异），样本 < 60 天的丢弃 |
| 信号**数量级**与性能 | 110,605 对，纯本地计算 **24 秒**。先把每个板块的收益率序列缓存成 dict，再按股票角度一次遍历，避免重复查库 |
| 相关性 ≠ 归属，怎么处理 | 这正是双信号设计的原因：`近期解禁` 与三花智控 +0.567、`杭州都市圈` +0.570 都是**巧合/同城共振**，必须靠主营业务判定剔除 |
| 停牌 / 涨跌停 | 共同日期交集天然处理停牌；涨跌停未特殊处理（已记为已知不足） |
| **幸存者偏差** | `ml_member` 是**当前快照，没有历史** —— 这是主线模块的既有局限，我在文档里如实标注而**没有假装解决** |
| 市值加权 vs 等权 | 提纯的目标就是剔除"**大市值但低相关**"的票 —— 它们在市值加权下会主导板块走势，把板块指数变成一只与主题无关的股票 |
| IC / ICIR / Purged Walk-Forward | 项目里已有（`ic_window_days=120`、`min_icir=0.02`、`purge_days=10`）。**这部分不是本会话做的，别往自己身上揽**，但要知道原理 |

**可能被追问的**："60%/40% 这个权重怎么定的？"

→ 诚实答：**基于两个反例定的，没有做网格搜索**。三花智控的案例说明纯主营会砍掉
走势驱动的主线（人形机器人 +0.657 vs 真实主营"家电零部件" +0.547），
所以走势权重要高于一半。**这是明确的下一步工作**（用回测胜率做参数扫描）。

### 3.2 AI 应用开发岗

| 问题 | 你的答法 |
|---|---|
| **模型分层路由** | 4 层：light（本地 1.5B）/ medium（本地 qwen3:8b）/ reasoning / decision。按任务性质路由，支持 fallback |
| fallback 为什么要**跨 provider** | 原来 decision 层是 `deepseek-v4-pro → deepseek-flash`，**同一 provider、同一端点、同一熔断器** → DeepSeek 一挂主备一起被拒，等于没兜底，而本机 Ollama 明明是好的 |
| 熔断器**哪些错误不该计入** | 缺 key / 401 / 402 / 403 是**配置类**错误，重试不会自愈。计进去只会 3 次就把熔断器打开，之后全是 `circuit_open`，**真正的病因被淹没** |
| 缓存怎么设计 | ① 签名缓存（`prompt_sig` = sha256(主营文本 + 候选题材集)）→ 输入没变就跳过，**重跑免费**；② 网关级 prompt 缓存；③ **空内容不缓存** |
| 怎么防**重复烧钱** | 每完成一只**立即落库**（不攒批），中断保留已完成的；重跑命中签名缓存 |
| 并发怎么控制 | **工作池**而不是分批 `gather`。分批的屏障代价：每批都要等最慢那只，而延迟分布 min 26.5s / max 55.2s，每批空等几十秒，累计是数小时级浪费 |
| 并发数怎么定 | 实测 16 路稳定（约 56 只/分钟）；并发过高会压垮提供商（出现过 1,027 只集中返回空） |
| 重试策略 | 单只失败重试 3 次 + 线性退避。**关键区分**："答案为空"是失败（不落库 → 下次补），"答案全 0 分"是合法结果（落盘占位） |
| 结构化输出 | `json_mode=True`（`response_format: json_object`），解析做容错：剥 ``` 围栏、截取首尾 `{}`、空 entries 视失败 |
| 怎么**评测** LLM 输出质量 | 人工抽查 + **跨 tier 交叉验证**（同批股票用 decision / reasoning 各跑一次对比排序）+ **反例检查**（茅台不在白酒 = 明显错误） |
| 成本 | 4,995 只、reasoning 层，约 66 分钟、12~25 元。一轮完整分析实测 38,207 token / 7 次调用 / 约 0.077 元 |
| Prompt 设计要点 | ① 给**打分档位定义**（80-100 / 60-79 / …）而不是让它自由发挥；② 明确要求"必须覆盖全部 N 个题材"；③ 明确列出**要排除的类型**（市场情绪/股价特征/宽泛风格）；④ 只把相关性最高的前 20 个候选交给它（省 token + 降漏答） |

**可能被追问的**："`light` 层为什么不可用？"

→ 实测它对**每个**题材都给 85 分、理由是模板复制（"主营核心业务直接属于该题材"），
而且随机只答 1~6 个（候选有 20 个）。原始输出只有 71 字符。
**快 7 倍但产生垃圾** —— 所以**质量门必须独立于成本门**。

### 3.3 AI 应用架构师

| 问题 | 你的答法 |
|---|---|
| 为什么这套**没用多 agent**？ | 任务**强串行**：本地信号行不行 → 决定要不要上 LLM；LLM 质量行不行 → 决定用哪层；数据残缺不残缺 → 决定相关性算不算得出来。每步的输入是上一步的**结论**。硬拆多 agent 会让每个 agent 缺上下文，把"证据传递"变成新故障源 |
| 什么情况**才该**上多 agent | 子任务**独立**（可并行）或需要**独立视角做验证**。我这套最大的改进空间恰恰是后者：加一个专门唱反调的验证 agent，看到"相关性 1,035 对"时问"这个数量级对吗" |
| 可观测性怎么做的 | ① 每阶段有**活性证据**（心跳、计数、进度条）；② LLM 全链路审计（prompt_hash / token / trace_id / provider_chain）；③ 已知缺陷：同一批调用被记到两个 `trace_id`（重复计数） |
| 幂等与可恢复 | 签名缓存 + 每步立即可重跑 + 离线/在线分离；补数脚本 `--retry` 多轮直到 0 缺口 |
| 副作用可逆 | 提纯只影响打分池，`ml_member` 原始数据**一条不删**；目录可几秒重建；清理只作用于本来源 |
| **最容易出事的环节** | **静默失败**。本会话三个最贵的 bug 全是静默的：空响应被缓存、"数据看起来齐全但榜单变短"、过滤器写了但**什么都没过滤** |
| 数据契约 | 口径写进 `configs/mainline.yaml` + 模块 docstring；`docs/MAINLINE_MINING.md` 记录实测数字与"别再重复踩" |
| 成本/质量/延迟三角 | 用**实测表格**决策而不是感觉（见 3.2 的模型选型） |

### 3.4 通用"深挖型"问题（面试官最爱问）

| 问题 | 答法 |
|---|---|
| **你怎么证明本地方案不行？** | 三条路线全部**证伪**：① 主营子串匹配 —— `半导体概念` 对中芯国际（主营"**集成电路**晶圆代工"）得分 **0**；② 同义词表 —— 2,205 个概念名不可维护；③ 行业字段匹配 —— 全量只有 **16%** 的概念能命中（PCB/CPO/光伏/锂电池/军工/钢铁/房地产全无命中）。根因是**概念题材名与公司主营描述用词体系不同**，是语义问题 |
| **为什么不能批量调 LLM？** | 规则是逐股票排序（"该股所属概念的前 3"），无法跨股票批量，所以是 4,995 次调用 |
| 打分范围怎么定的 | `ml_member` 有 13,116 个 code，但**只有 5,557 个是真实 A 股** —— 其余是导出产生的合成占位码（`00000A`…`00000J`）。加"在股票目录 + 有日线 + 非 ST"后 5,018 只 |
| 一只股票能属于多个概念吗 | 能，这是设计意图。"前 3"是**题材数上限**不是"只能留一个板块"。三花智控同时留在 汽车热管理 + 人形机器人 + 特斯拉 |
| 同一题材多重分类怎么办 | 茅台同时归入 `白酒 881273` / `白酒Ⅲ 884188` / `白酒概念 885525`。全量同名概念 248 组、去后缀后近似重复 **404 组**。所以只对**归一化题材**排序，落库时映射回各体系**全部**板块代码 |
| 怎么验证结果对？ | **反向案例检查**：茅台不在白酒板块就是明显错误（这正是我自查发现缺陷的入口） |
| 全量跑一次多久、多少钱 | 相关性 24 秒（纯本地）；LLM 打分 4,995 只约 66 分钟、12~25 元；总流程约 83 分钟 |
| 测试怎么做的 | 为提纯新增 **88 个单测**（含"空响应算失败"、"守卫不误杀"、"共同日期对齐"等回归）；全量 **2,935 个单测通过** |

## 五、建议补的技术点（按被问概率排序）

| 技术点 | 为什么会被问 | 一句话准备 |
|---|---|---|
| **前视偏差 / look-ahead bias** | 量化必问 | 用"未来信息"构造的因子在回测里必然虚高。本项目防线是"静态量离线算、时变量在线取" |
| **幸存者偏差** | 量化必问 | 用"今天的成分股"回溯历史，等于只保留活下来的票。本项目已知未解决，如实标注 |
| **Purged Walk-Forward + purge/embargo** | 量化高频 | 训练集与验证集之间留 gap，防止标签窗口重叠泄漏 |
| **IC / ICIR / 因子加权** | 量化高频 | IC = 因子值与未来收益的秩相关；ICIR = IC 均值/标准差；用 ICIR 加权、设 `min_icir` 下限防止负权重 |
| **熔断器三态** | AI 应用必问 | CLOSED → 连续 N 次失败 → OPEN（直接拒绝）→ 冷却后 HALF_OPEN 试探 → 成功则 CLOSED |
| **幂等 / 断点续跑** | AI 架构必问 | 每个单元有稳定标识（这里是签名哈希）；重复执行不产生副作用；中断后从已完成处继续 |
| **asyncio 取消语义** | AI 应用可能问 | `gather` 抛错**不取消**兄弟任务；`asyncio.run` 会等所有 pending 任务 → 必须显式 cancel + await |
| **SQLite WAL / busy_timeout** | 可能问（多进程写） | WAL 允许读写并发；`busy_timeout` 避免 `database is locked`；但**多进程同写仍有冲突** |
| **SQLite 变量上限** | 可能问 | 变量上限 999，所以 `IN (...)` 要按 400 分块 |
| **截面分位打分** | 量化可能问 | 本项目用 `percentile_score` 做截面分位，避免绝对阈值不可比 |
