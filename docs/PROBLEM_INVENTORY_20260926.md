# 项目问题清单：根因与解决方案（2026-09-26~27 会话）

> 本文汇总本会话暴露的**全部**问题：用户报障 + 我在实现过程中自己引入的缺陷。
> 每条都带**实测证据**，可复现。
> 涉及模块：投研多Agent链路、数据采集/保留、并发治理、前端面板加载。

---

## 〇、一句话结论

**这套系统的问题几乎全部不是"某个算法写错了"，而是"口径不一致 + 缺少权威单一事实源"。**

同一个判断散在多处、各自漂移；本该被量化的约束留在注释里；
"成功"与"成功但不可用"没有区分。三类根因占了本文 80% 的条目：

| 根因类型 | 表现 | 本文条目 |
|---|---|---|
| **A. 同一判断多份实现 / 缺单一事实源** | 5 处指标元信息各说各话；两条告警删除路径 | P1-2、P2-1、P2-6、P3-1 |
| **B. 只判"失败"不判"慢/空/旧"** | 降级链永不触发；空响应被缓存；慢模型占着主位 | P2-4、P2-5、P2-7、P4-1 |
| **C. 上限与口径不在代码里** | 无并发闸门；无成本上限；保留期只在配置注释里 | P1-1、P3-2、P3-4 |

## 一、质量与正确性：数据根本查不到

### P1-1 「AI产业链龙头估值数据缺失 / valuation_calc=数据不足」

**症状**：用户问"对当前A股AI产业链各细分行业龙头的估值及10月走势分析预测"，
系统回"估值无任何输入数据"。

**根因**（三层，缺一不可）：

1. **LLM 规划器返回裸指标名**。实测它对这条问题的真实输出：
   ```json
   {"analysis_type":"macro","target":"",
    "indicators":["us_fed_rate","stock_close","PE(TTM)","PB","资产负债率","流动比率"]}
   ```
   `PE(TTM)` 是**裸名字**，而个股指标**必须拼 6 位代码**。
   实测 A01 拿裸名字去 fetch：
   ```
   PE(TTM)      -> DataFetchError   0 ms      ← 没有任何连接器 supports
   PE(TTM):300308 -> 1096 点      302 ms
   ```
2. **`target` 为空** → 下游补不出后缀。
3. **`_PLANNING["full"]` 只含 `["CPI","PPI"]`** —— 即使 target 有代码，
   `full` 类型也**不会**带个股指标（只有 `stock` 类型才带）。

**关键事实：本地库根本不缺这些数据**：
```
fact_data_points: 1,996,561 行 / 749 个指标
  PE(TTM):  覆盖 82 个标的，最新 2026-09-24
  PB:       覆盖 80 个标的，最新 2026-09-24
  ind:sw_third_pe_ttm:all  1645 行（申万335个三级行业PE截面），最新 2026-09-22
```

**解决**：新增 `sanitize_indicators()`（`src/orchestration/supervisor.py`）
在 LLM 规划之后**确定性修正契约**：

| 情况 | 处理 |
|---|---|
| 有 6 位代码 + 裸指标 | 补后缀 `PE(TTM)` → `PE(TTM):300308` |
| 无代码 + 裸指标 | **丢弃**，换成行业估值截面 `ind:sw_third_pe_ttm:all` 等 |
| 已带后缀 | **原样保留**（不能用 target 覆盖 LLM 明确指定的标的） |

第三行是**测试抓出来的**：我最初写成"有 target 就覆盖"，于是
`PE(TTM):600519` 被改写成 `PE(TTM):300308` —— 静默把"分析茅台"变成
"分析 target 那一只"。

**为什么"换成行业估值"而不是静默丢弃**：丢弃后 A10 仍无估值素材，
还是输出"数据不足"；换成行业截面（有真实数据源与入库作业）至少让分析有据可依。

### P1-2 数据目录缺失：5 处元信息、零一致性校验

**症状**：路由决定"要不要打网络"时没有权威目录可查，只能靠前缀硬编码猜 ——
一漂移就出现"库里明明有当天数据却仍打网络"。

**根因**：指标元信息散在**五处**、各自独立维护：

| 位置 | 知道什么 |
|---|---|
| `planner.py` `INDICATOR_CATALOG` | id + 描述 |
| `data_freshness.py` `_FREQ_BY_PREFIX` | 更新周期 |
| `router.py` `_DB_QUERY/SKIP_PREFIXES` | 要不要查库 |
| `router.py` `_TTL_BY_PREFIX` | 进程内缓存 TTL |
| `scheduler/registry.py` `JOB_REGISTRY` | 采集作业，**但不声明产出哪些指标** |

**而且没有任何测试校验这几处互相一致**（搜遍 `tests/`，零命中）。

**实测后果**：`mkt:cybkcb:` **完全不在新鲜度规则里** → 落到默认月频 (30/90/365)，
被当成"30 天前的都算新鲜"；而它实际是**盘中每 5 分钟**采的实时数据。
两处口径互相矛盾。

**解决**：新增 `scripts/data_lifecycle.py` —— 把四处口径**并排打出来**，
`--check` 模式专门列"有定期作业但分析时仍绕过数据库"的指标。
它当场查出 **6 个"有需求但完全没定期作业"** 的指标。

> ⚠️ 这是**只读视图，不是目录**。真正的修法是建
> `configs/data_catalog.yaml`（单一事实源），让五处消费方都从它派生，
> 并补一条一致性测试。**这条仍未做**，见 §五。

## 二、性能：为什么慢，慢在哪

### P2-1 「每次都先从互联网采集，耗时非常长」

**根因**：13 个指标里 **5 个"查库=是"但库里明明有当天数据，仍然走了网络** ——
因为 `_should_query_db()` 把"实时型"指标**一律拒绝查库**。

而 scheduler 已经在**盘中每 5 分钟**采它们（`market_intraday_snapshot`、
`board_cyb_kcb_intraday`）—— 库里就是几分钟前的数据。

**实测代价**（单指标）：
```
fed:rate_prob:next        23.44s   ← 外网不可达，等满硬超时
mkt:cybkcb:spot_summary   11.96s   ← 分页拉两板全部个股
mkt:turnover:hist          3.22s
mkt:turnover_rate:all_a    2.61s
```
A01 用 `asyncio.gather` 并发 → **墙钟 = 最慢那个 = 23.4 秒**。

**解决**：新增 `_DB_REUSE_FRESH_DAYS = 1` 容忍窗口 ——
库里有"当天的"数据就直接用。

**实测效果**：
```
                         改造前     改造后
mkt:turnover:total       0.12s  →  0.03s   ✓库命中
mkt:turnover_rate:all_a  2.61s  →  0.01s   ✓库命中
mkt:cybkcb:spot_summary 11.96s  →  0.01s   ✓库命中
13 指标 gather 墙钟      23.28s →   0.01s（预探后）
```

### P2-2 外网为什么不可达：CME 被阻断，FRED 可达

**根因（实测矩阵）**：
```
DNS   www.cmegroup.com     -> 108.160.165.211（Akamai 边缘，被阻断网段）
TCP   www.cmegroup.com:443 -> ✗ 不通（curl 等满 21.3s 才报错）
TCP   api.stlouisfed.org   -> ✓ 通
HTTP  FRED CSV             -> ✓ 200  1.1~1.3s
HTTP  TradingView/Investing -> ✗ 均超时
```

**关键**：DNS **能解析**但 TCP 连不上 —— 所以**不能用 DNS 判断可达性**。

而 `cme_fedwatch` 库内部要等满 21.3s 才抛错，没有失败记忆。

**解决**（三层）：
1. **FRED 兜底源** `fed:policy_range` —— 实测 1.17s 拿到
   **目标区间 3.75%~4.00%、有效利率 3.88%（最新 2026-09-25）**。
   这同时修掉了另一个问题：AkShare 的 `us_fed_rate` 最新有效值
   **停在 2025-07-31**（陈旧 14 个月）。
2. **TCP 可达性预检**（`connectors/net_probe.py`，新增）：
   2 秒超时 + 60 秒结论缓存。不可达就直接返回空，省掉 21 秒等待。
3. **失败冷却**（`connectors/source_cooldown.py`，新增）：
   60 秒内不再重试，指数退避封顶 900s，成功立即清除。

**实测**：连续 5 次 fetch **117s → 23.3s**；冷启动 **23.4s → 4.08s**；
启动预探后用户感知 **0.0s**。

### P2-3 信息层 3 个 Agent 硬串行

**根因**：`g.add_edge("verify_info","extract_events")` → `("extract_events","sentiment")`。
但这是**实现选择的产物，不是数据依赖**：
- A05 可信度评分（输入：原文）
- A06 事件提取（输入：**原文**，要求 `evidence_quote` 逐字来自原文）
- A07 情绪量化（输入：**事件表**）

**A06 真正依赖的只是原文**；A05 的分数只是被当作前置过滤。
唯一有真依赖的是 A07 → A06。

**解决**：信息层并行化（A05/A06 同时跑，A07 等 A06）。
**状态：未实施**（见 §五）——因为下面 P2-4 的收益大一个数量级。

### P2-4 信息层挂本地模型，慢 4 倍（**本会话最大根因**）

**根因**：A05/A06 挂 `medium` 层 = **本地 Ollama qwen3:8b**。审计实测：
```
A05_verifier     tier=medium     单次中位 33.7s
A06_extractor    tier=medium     单次中位 36.8s
A07_sentiment    tier=reasoning  单次中位  1.5s   ← 同一系统里快 24 倍
```

我用 A06 真实 prompt 做对照实验（3 次取中位）：
```
现状 medium (Ollama qwen3:8b)   45.7s
改 reasoning (DeepSeek-Flash)   11.1s   ← 4.1×
reasoning + effort=none          2.1s   ← 21×
```

**更根本的机制缺陷**：降级链**只在失败时前进**，"成功但极慢"不算失败：
```python
resp = await provider.chat(...)   # 本地模型"成功"了，哪怕花了 45 秒
return resp                        # 快 4 倍的备模型永远轮不到
```
`models.yaml` 的备模型配得对，**但触发条件不对**。

**解决**：新增**单跳延迟预算** `attempt_budget_sec`，
**只对链上还有退路的那几跳生效**（最后一跳设预算会把"慢但正确"变成"必然失败"）：
```python
_ATTEMPT_BUDGET = {"light":20.0, "medium":20.0, "reasoning":45.0, "decision":60.0}
```
超时**不计入熔断**（慢 ≠ 坏，计进去会把它标成"故障"）。

**实测**：
```
默认 20s 预算 -> 22.2s 落到 deepseek-flash  fallback=True
手动  5s 预算 ->  7.2s 落到 deepseek-flash  fallback=True
（改造前：本地模型独自跑完 45.7s，备模型从未被使用）
```

### P2-5 A17 决策层模型选型：`pro` 是纯延迟成本

**根因**：A17 挂 `decision` = `deepseek-v4-pro`，审计实测 **每任务 2.06 次 × 34.5s = 78.3s**
（占整条链路 LLM 时间 68%）。

**实测对照**（同一 A17 prompt，真实 6 维上游输入）：
```
现状 decision = deepseek-v4-pro   20.2s   out 2299
改 reasoning  = deepseek-flash    11.7s   out 2781   ← 更快且输出更长
+ effort=none                      2.6s   out  383
```
`configs/models.yaml` 选 `pro` 的理由是"决策层要质量"，但实测 `flash`
**输出更长**的结构化结果 —— 这个假设值得重新评估。

**另一处细节**：`max_tokens=2048` 对 decision 层的结果是**空响应**
（`out=2049 空!`）—— 思维链先吃光预算，正文一个字都没输出。
**降延迟只能降 `reasoning_effort`，不能砍 `max_tokens`。**

### P2-6 双创板块指标缺 TTL，每次全量重拉

**根因**：`mkt:cybkcb:spot_summary` 抓一次要**分页拉创业板+科创板全部个股**
（东财 clist，~16 次分页请求，实测 13.4s），而它**不在任何 TTL 规则里**
→ `_cache_ttl()` 返回 `None` → **每次分析都重新全量拉**。

**解决**：给它 5 分钟 TTL（与 scheduler 的 `board_cyb_kcb_intraday` 周期一致），
并把更具体的 `mkt:cybkcb:spot_summary` 规则**排在** `mkt:cybkcb:val` 之前
（前缀规则是首个命中即返回）。

**同时修掉新鲜度误判**：`mkt:cybkcb:` 显式加入日频段。

---

### P2-7 空响应被写进缓存 → 故障永久化

**根因**：某次调用因 `max_tokens` 被思维链吃光而返回**空 content**，
这条空记录被写进缓存后，**后续每一次重试都命中这条空缓存并立刻返回** ——
表现为"确定性失败、重试无用"，而且因为命中缓存耗时更短，
**看起来完全不像缓存问题**。

**解决**（两处对称判断）：**空响应不算命中** + **空响应不写缓存**。

---

### P2-8 语义缓存在事件循环上同步阻塞

**根因**：`_get_semantic()` 在**每次未命中**时遍历 `data/llm_cache/*.json`
**全部 3108 个文件**，逐个 `read_text` + `json.loads` 才能读到
`agent_id`/`scope` 做过滤（**过滤发生在解析之后**）。

**实测**：
```
cold 未命中扫描:  682.2 ms   （进程重启后第一次）
warm 未命中扫描:    8.9 ms
事件循环最大停顿:  22.3 ms
```
它是**串行累加**的：N 个并发用户的总阻塞 ≈ N × 9ms。

**解决**：`_SemanticIndex` —— 按 `(agent_id, scope)` **两级分桶**存 3-gram 向量，
懒建 + `put()` 增量更新；新增 `aget()` 走线程池；`warm_up()` 供启动预热。

**为什么分桶是重点**：语义复用必须**同时满足** agent_id 与 scope
（防 `light` 层小模型结论被 `decision` 层复用、防 A05/A06 输入重叠串台）。
原实现是"解析全部文件→丢掉 99%"，分桶让过滤变成"直接取桶"。

**实测**：并发 8 次查找 **2155.7ms → 2.5ms（847×）**，事件循环滞后 22.3ms → 2.2ms。

### P2-9 前端：预加载只在登录动作里触发

**症状**：「热点&研报小作文、事件告警 每次打开这个界面不能预加载到浏览器吗，
切界面还是会有 2 秒延迟」。

**根因**（三层）：
1. **预加载只写在 `useAuth.login()` 里** —— 而绝大多数访问是
   **带 remember-me Cookie 刷新页面**，走 `probe()` → `authApi.bootstrap()`，
   **那条路径从不预取**。所以每次刷新后缓存都是冷的。
2. **缓存有 TTL**（告警 5 分钟 / 情报 10 分钟），放着就过期。
3. **面板被卸载重挂** —— `App.tsx` 用三元链渲染，切走即卸载，
   `useState` 全归零（连展开的卡片、滚动位置、筛选档位都丢）。

**解决**：
- `panelPrefetch.ts`（新增）：挂在**已登录状态**上，立刻预取 + 每 4 分钟
  后台续期（< 最短 TTL 5 分钟）+ 页面隐藏跳过 + 回前台补 + 失败静默。
  续期必须 `force=true` 绕过 60 秒去重，否则缓存**永远停在第一次**。
- `KeepAlive.tsx`（新增）：保持挂载、`display:none` 显隐、惰性挂载。

**已实测的载荷**（@51KB/s 隧道）：
```
事件告警 /alerts      100条  明文 109,526B  gzip  1,870B (1.7%)   2139ms → 37ms
情报流 /intel/feed     60条  明文  62,657B  gzip 16,994B (27%)    1224ms → 332ms
```
⚠️ 情报流压比只有 27%（告警 1.7%）—— 因为情报的 `summary` 是**每条都不同的
中文长文本**。**所以 gzip 对情报的收益远小于告警，客户端缓存才是必需的。**

## 三、并发与成本治理

### P3-1 完全没有准入控制

**根因**：`research.py` 就是 `asyncio.create_task(_run())` 裸起，
**没有信号量、没有队列、没有并发上限**。而单条 full 管线是
7~15 次 LLM 调用 + 最多 20 个指标并发采集 + 20 万 token 预算。

**三重放大**：
1. **LLM 配额**：超限调用在 provider 层失败 → 触发**全局三态熔断器**
   （deepseek 60s 内 3 次失败即 OPEN）→ **一个用户的突发流量让所有用户一起降级**；
2. **成本**：`llm_token_budget_per_task` 是**单任务**预算，无全局上限；
3. **线程池**：`asyncio.to_thread` 用 `min(32, cpu+4)`，被占满后
   连健康检查都排队（`core/executors.py` 记录过 `/health` 要 144.5s 的历史故障）。

**解决**：四层治理（按代价从低到高）
```
① 结果缓存命中 → 直接返回（0 成本）
② 同问合流 → 复用 leader 的 task_id（不新起管线）
③ 日成本预算 → 预扣 0.25 元/任务，不足则 503
④ 准入闸门 → 信号量，等 30s 拿不到名额返回 503
```
第 ② 层堵的是"检查缓存未命中 → 管线跑完才写缓存"之间**整个管线时长**的击穿窗口
（10 人同时点同一个热门问题 = 10 条完整管线）。

**实测**：提交 32 个任务、闸门 4 → **峰值在飞数严格 = 4**。

---

### P3-2 20 元/天预算：投研不是烧钱的那个

**根因**：原来只有 `llm_token_budget_per_task`（**单任务** 20 万 token），
它防"单个任务失控"，**完全不防"很多任务累加"**。

**按 agent 分账的实测成本**（审计 43104 条记录）：
```
mainline_relevance      484.11 元   ← 主线相关性逐股打分
mainline_member_pure    117.25 元
A17_recommend             7.28 元
投研分析合计（80 次）      8.62 元   ← 单次中位 0.0527 元
总计                    617.53 元   其中 2026-09-20 单日 487.57 元
```

**关键洞察：投研分析单次 0.05 元，而主线相关性打分一天能吃掉 487 元。**

**两个天花板必须分开看**：
```
并发天花板 = 闸门 ÷ 单任务时长 = 4 ÷ 36.2s = 6.6 任务/分钟 = 3960 次/天
成本天花板 = 日预算 ÷ 单次成本 = 20 ÷ 0.0527 = 379 次/天
                                              ↑ 这个先撞到（紧 10 倍）
```

**解决**：新增 `src/core/budget.py` —— 按日累计、**预扣+结算**、按来源分账。
预扣是必须的：突发时所有任务都还没产生 token 消耗，只看已花费会集体放行、
集体超额（TOCTOU）。

**实测**：`0.046 元`（30k 输入 + 4k 输出 × flash 价）与手算一致；
预算 0.10 元时提交返回 503 且**不占并发名额**；任务结束后预扣归零。

### P3-3 TaskStore 内存泄漏

**根因**：`_tasks` / `_tokens` / `_handles` **只增不减** ——
只在 lifespan 关停的 `cancel_all()` 里 clear。
实测 200 个任务跑完后：`任务残留=200  live残留=0  token残留=200`。
按每次产出几十 KB 报告估算，**1 万个任务就是几百 MB 常驻**。

**解决**：TTL（默认 1 小时）+ 容量（默认 200）双阈值淘汰，**四表同步回收**；
**在飞任务永不淘汰**（有测试守着 —— 淘汰在飞任务会让轮询 404、取消失效）。

### P3-4 告警保留期：两个机制都不满足需求

**需求**：「事件告警的信息最多保留三天，超过3天的信息自动溢出删除。」

**根因**：
| 机制 | 改动前 | 问题 |
|---|---|---|
| `_expire_due`（读路径懒过期） | 置 `status='expired'` | **只是列表不显示，行永远留在库里** |
| `retention_alert_days` | 默认 **365 天** | 一年才删 |

即"最多保留三天"**一条都没实现**。

**解决**（⚠️ 这里我中途纠正了一次设计错误）：
我最初在 `run_retention` 里**新增**了一段删除调用，但走查后发现
**已经有一条更完备的路径**：`retention_passes` 的 `fact_alerts` 档，
它带**级联删 `user_alert_read`** —— 而我的新路径没有。
两套并存时谁先跑谁生效：我的路径先跑会留下**引用不存在告警的孤儿"已读"记录**。

**正确落法是改保留期数值，而不是新开删除路径**：
```python
alert_expire_days: int = 3        # 7 → 3     读路径据此置 expired
retention_alert_days: int = 3     # 365 → 3   真正 DELETE + 级联
```
两者取同一值是刻意的：到期即删除，不留"已过期但还占着库"的中间态。
**危险组合是"删除期 < 过期期"** —— 会删掉还没到期、列表上还该显示的告警
（有测试守这个不变式）。

`prune_alerts_before()` 保留为**显式 API**（供运维按任意截止日清理），
但不参与每日作业。

## 四、我自己引入的缺陷（AI 首轮编码）

> 这部分单独成节，因为它和"项目原有问题"性质不同：
> 它们是**我在本轮实现中制造、又自己发现**的。详见配套 skill。

### P4-1 编辑操作破坏语法（3 次，同一类）

| 次数 | 操作 | 后果 |
|---|---|---|
| 1 | `edit` 替换 docstring 结尾时把 `"""` 一起替换掉 | 后续中文散文变成裸代码 → `SyntaxError` |
| 2 | 在 `JOB_REGISTRY` 插入新条目时误删了 `name="tech_industry_daily",` | 该作业字段缺失 |
| 3 | 在 `App.tsx` 三元链里删/加分支时丢了 `? (` 与 `)}` | **连续 3 次编译失败**才定位 |

**为什么危险**：`py_compile`/`tsc` 能报，但**同一类错误在 `.md`/`.ps1`/`.json`
里是静默的**（本项目已有先例：`.ps1` 丢 BOM → 解析失败即退出，
`LastTaskResult=1` 却一行日志都不写）。

**教训**：编辑"成对分隔符"（引号/括号/大括号/JSX 标签）时，
替换串必须**包含**这些分隔符的完整配对，并且改完立刻编译。

### P4-2 我用启发式脚本"验证"自己 → 6 个假告警

**经过**：我用一个自写的正则脚本检查 15 个 Mermaid 图的引号平衡，
它报了 6 个 `ODD-QUOTES`。我差点去"修"那 6 处。

**根因**：脚本用 `^\s*</div>` 找块结束，但 Mermaid 块嵌在
`<div class="fig">` 里 → **提前截断**，把 HTML 文本的引号算进了图里。
换成正确的块边界后：**15 个块 0 问题**。

**教训**：**自己的检查脚本必须先证明它是对的**（用一个已知答案的输入试），
否则"脚本报错"与"代码有问题"无法区分。

### P4-3 测试断言写错了，差点去"修"正确的代码

**经过**：我写了个测试断言"1 天前的孤儿事件应被删除"，测试失败。
第一反应是去改实现 —— 但**实现是对的**：未超期的孤儿事件**必须保留**
（它可能还没轮到被分析，删掉等于丢掉一条还没被评估的线索）。

**教训**：测试失败时先问"**是我想要的语义吗**"，再问"代码错了吗"。
把**语义**写进测试的 docstring，这样失败时能立刻分辨是语义问题还是实现问题。

（同一处还踩到：`fact_events.created_at` 是**入库时刻**，
测试里造的"5 天前事件"实际 `created_at` 是今天 —— 用它判"事件有多旧"是错的。
真正该用 `publish_time`。这也是**先写测试才发现的**。）

### P4-4 一次"顺手重构"把风险放大了 20 倍

**经过**：改 `AlertsPanel` 时我把"发两个请求"合并成一个、顺手调整了分支 ——
原本 10 行能改完的事变成改 `App.tsx` 的三元链，**连续 3 次编译失败**。

**正确做法**：先做**注入式**最小改动（在现有 `load()` 里加 2 行读缓存），
确认通过后再考虑重构。

**教训**：**修复的最小化**是一项纪律，不是审美偏好。
改动规模每翻一倍，回归面积翻一倍以上。

### P4-5 一次不可逆操作没先确认

**经过**：我在多轮编辑 `App.tsx` 时，把 `? (` 连同周围内容一起替换掉，
且**没有先备份**。发现问题后想回滚，发现该文件不在我的备份清单里
（备份是上一轮针对 5 个文件做的）。

**教训**：**破坏性编辑前先复制一份**（哪怕只是 `Copy-Item` 到 temp）。
本项目工作区有大量未提交改动，**回滚成本远高于备份成本**。
