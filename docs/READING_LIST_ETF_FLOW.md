## 3. `configs/etf_flow.yaml`（279 行）🔴

**为什么读**：面试常问"这个阈值哪来的、改了会怎样"。**每个数都要能说出

**必须记住的阈值及其含义**：

| 配置 | 值 | 含义 / 改了会怎样 |
|---|---|---|
| `percentile_window` | 34 | 位置分位回看交易日。**调小更灵敏但趋势中会飙升** |
| `percentile_mode` | rank | 百分位排名（对极值稳健）；`range` 会被插针压扁 |
| `opportunity.max_percentile` | 0.30 | 机会信号要求分位 ≤30%（低位） |
| `opportunity.min_share_change_1d` | 0.03 | 份额日环比 >+3% |
| `risk.min_percentile` | 0.70 | 风险信号要求分位 ≥70%（高位） |
| `resonance.min_etfs` | 3 | 同系列 ≥3 只同向才算共振 |
| `regime.window` | 120 | 环境窗口（≈半年），与 34 日分位窗口互补 |

| `regime.opportunity_allowed` | `[bear]` | **机会信号只在熊市放行** |
| `regime.risk_allowed` | `[bull, range]` | 风险信号排除熊市 |

2. `linkage.enabled` 为什么默认 false？（未经回测的联动会让分数无法归因）
3. `apply_to_scoring` 与 `regime_multiplier.enabled` 为什么是两个开关？

## 4. `src/mainline/etf_flow.py:297` `adjust_share_splits` 🔴【最难，必须默写不变式】

**为什么最重要**：这是本次修复里**唯一需要推导**的部分，也是最容易被追问的。

**必须默写出来的不变式**：

```
份额比 s = 拆分后份额 / 拆分前份额
可流通份额变了 s 倍 ⇒ 拆分后 1 份 = 拆分前 1/s 份

约束 A：份额列必须显示原始存量（当前份额要匹配券商）
约束 B：变化率必须跨拆分连续（不能把机械翻倍算成 +96% 申购）
⇒ 当前行不能动，历史行折算到新基准：原始份额 × ∏(之后各拆分日的 s)

验证：1,200,859 × 1.9629 = 2,357,197 ≈ 拆分日真实存量 2,357,118
      （差 0.003% = 当天真实申赎）⇒ 拆分日日环比 ≈ 0 ✓
```

**必须能说的三个实现细节**：
1. **检测必须用原始序列**（不能边改边测，否则同一位置被重复识别成拆分）；
2. **是乘不是除**，**改的是拆分日之前的行**（这两点我都错过一次）；
3. 只动内存序列，**不回写 `ml_etf`**（库里是原始托管数据，要能对账）。

**读完必须能回答**：
1. 三个判据条件各去掉一个会怎样？
2. 一次拆分同时伴随真实大额申购会怎样？（真实申购被吸收进份额比、被归一化）
3. 分红为什么不触发这个判据？（分红改净值不改份额）
4. 扩募该不该被归一化？（不该——那是真实流入，且价格不会同比例反向跳变）

## 5. `src/mainline/etf_flow.py:390` `index_percentile` + `:527` `apply_regime_policy` 🔴

**为什么读**：这两个函数决定了"信号何时触发、何时被降级"。

**`index_percentile`**：
- `rank` 模式：`小于等于当日的天数 / 窗口长度`（默认，对极值稳健）；
- `range` 模式：`(close - min) / (max - min)`——分子分母都由两个极值决定，
  **一根插针就能把整段分位压扁**；
- 样本不足 `max(window, 5)` 时返回 `None`（**不是 0**——"不知道"不是"低位"）。

**`apply_regime_policy`**：
- 读 `regime.opportunity_allowed` / `risk_allowed` 白名单；
- 不在白名单 ⇒ `gated = True`，等级降为 `weak`，**但不丢弃**（仍进观察列表）。

**读完必须能回答**：
1. `rank` 和 `range` 在震荡市的差异？（两者差异明显，默认 rank）
2. 为什么"降级 ≠ 丢弃"？（直接丢弃会让用户以为"今天没信号"，
   而降级能同时表达"有异动"和"但环境不支持"）
3. 分位为 `None` 时信号会怎样？（不会触发——极端区判据不成立）

## 6. `src/mainline/etf_flow_backtest.py:497` 循环边界 + `:272` `collapse_signal_runs` 🟠

**循环边界**（面试爱问"回测到哪一天"）：

```python
total = len(calendar) - max_horizon     # max_horizon = 34
while cursor < total:
```

⇒ 回测**结构上**评估不到最近 34 个交易日——因为每条记录要记 T+34 的
**实际**收益，"未来还没发生"。

**`collapse_signal_runs`**：
- 同一 `(code, kind)`、相邻触发日间隔 ≤ 7 自然日 ⇒ 同一事件，只留首日；
- 输出 `repeat_days`（连报天数）与 `repeat_until`；
- ⚠️ **合并必须先于截断**（先取尾部会把同一事件的中间几天当独立样本）。

**读完必须能回答**：
1. 为什么明细最后一天必然早于今天？
2. 为什么在展示层去重而不是信号层？（信号层逐日触发是有意的"持续性确认"）
3. `by_kind` 的样本数按日还是按事件？（按日——所以和明细行数不等）

## 7. `src/mainline/datastore.py:2214` `sync_etf_shares` + `:2163` `_write_etf_rows` 🟠

**为什么读**：这里藏着本次最核心的 SQL 设计判断。

**`sync_etf_shares` 的三条不变式**：
1. 只 `UPDATE ... WHERE shares IS NULL`（已有份额一个都不动）；
2. **永不插入新行**（"插一行行情有、份额无的记录"正是出事的机制）；
3. 重试只针对接口**明确标为 ETF** 的代码（`== "ETF"`，不是
   `types.get(code, "ETF")`——后者会把场外基金又捞回来，实测一次 1373 只）。

**`_write_etf_rows` 的注释要看懂**：
- `ON CONFLICT ... CASE WHEN excluded.shares IS NOT NULL` 保护**对新插入行无效**；
- `fund_daily.amount` 口径是**千元**，本表统一存**元**（不换算会让下游按元
  设的门槛高 1000 倍，实测把 37 只 ETF 里的 34 只全过滤掉）；
- 份额映射的键必须是 `(ts_code, trade_date)` 二元组（历史上按单一键存过，
  导致逐只回填路径永远取不到份额）。

**读完必须能回答**：
1. 为什么补份额不能插新行？
2. `ON CONFLICT` 的 NULL 语义为什么救不了新行？
3. 金额单位错换算会造成什么现象？（**分数是横截面分位，整体放大后排序不变，
   界面上看不出异常**——只有绝对金额荒谬到扎眼）

## 8. `src/mainline/etf_flow.py:559` `build_indicators` 🟠

**三个字段的关系**（面试容易问混）：

| 字段 | 含义 |
|---|---|
| `trade_date` | 行情所属交易日 |
| `shares` | 份额（万份），**可能来自更早的交易日** |
| `shares_date` | `shares` 实际取自哪天——与 `trade_date` 不同说明当天份额未发布 |

**三件它做的事**：
1. 先过 `adjust_share_splits` 还原口径，再算 1/5/10/20 日变化率；
2. 最新日份额为 NULL 时**回退到最近有份额的交易日**并标注 as-of；
3. 份额窗口不足时字段留 `None`（**不补 0**——0 表示"份额没变"，
   与"不知道"完全是两回事）。

## 9. `src/mainline/etf_share_guard.py`（366 行）🟡

**状态机五态**（面试问"你怎么区分正常和故障"就答这个）：

| 状态 | 含义 |
|---|---|
| `fresh` | 一切正常，**零网络请求** |
| `filled` | 补拉成功 |
| `unpublished` | 份额确实还没发布——**正常时序，不告警** |
| `stale` | 补同步后仍落后 |
| `offline` | 数据源不可用——**要人查** |
| `no_calendar` / `no_data` / `failed` / `skipped` | 各类跳过/降级 |

**两个关键口径**：
- `recent_closed_days`：`trade_date <= 今天` **且当天 15:00 之前不算已收盘**；
- `MISSING_RATIO_FLOOR = 0.30`：为什么不是 0？（场外基金长期不发布，
  实测齐全那天全表仍缺 18%，真缺口是 64%）

## 10. `src/mainline/etf_flow.py:730` `evaluate` 🟡

**三类信号的判定顺序与等级规则**：

| 类型 | 触发条件 | 等级 |
|---|---|---|
| 机会 | 分位 ≤30% 且份额日环比 >+3% | 中；同系列 ≥3 只同向 → 强 |
| 风险 | 分位 ≥70% 且份额日环比 <-3% | 中；共振 → 强 |
| 行业反转 | 份额 5 日累计 >+10% | 中 |
| （弱信号） | 份额日环比超阈值但分位不在极端区 | 弱，**从不告警** |

**⚠️ 最容易被问倒的一点**：判定"会真正告警"必须同时满足
`gated=false` **且** 等级为强/中。**只看 `gated` 会把观察项算成告警。**

### 三个不变式（默写）

```
① 份额折算：新基准历史份额 = 原始份额 × ∏(之后各拆分日的 s)
   （改拆分日之前的行；是乘不是除；检测必须用原始序列）

② 补份额：UPDATE ... WHERE shares IS NULL，永不插新行
   （幂等 + 不可破坏；插新行正是出事的机制）

③ 信号口径：会告警 = gated=false 且 等级 ∈ {strong, medium}
   （只看 gated 会把观察项算成告警）
```

### 三句话的"范围声明"

> 1. 「模块架构与信号定义是项目原有的，我做的是数据质量专项。」
> 2. 「我把 5 类问题定位、修复、验证了：份额 T+1 缺口、拆分误读、伪重复、
>    明细截断方向、展示层口径。」
> 3. 「修 bug 的验收条件是**结论不变**——门控对照 66 条 +9.18%/83.3% 全程一致。」
