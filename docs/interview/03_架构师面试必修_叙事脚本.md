## 专题 1 · 为什么 LangGraph 不用 AutoGen / CrewAI

### 30 秒版
"我需要的是**可控的图**：A08-A16 八九个分析 Agent 并行、汇合到 A17 再串行审计，失败要按节点隔离、取消要贯穿全链。AutoGen 的 group chat 是黑盒——控不了并发度、控不了失败边界、控不了取消传播。LangGraph 的 StateGraph 给了我三样东西：显式边、operator.add reducer 的并行写聚合、节点级异常吞入 state.errors 不拖垮整图。"

### 3 分钟版
1. **编排语义**：我的链路是 DAG 混合并行（信息层 A05∥A06、分析层扇出）+ 串行依赖（A17 等全部前驱）。StateGraph 的 add_edge/add_node 是显式声明；AutoGen 的 group chat 靠 LLM 自由对话路由，**调度本身不确定**——对投研这种"每一步都要可审计"的场景不可接受。
2. **状态语义**：并行节点写同一个 state 键时，LangGraph 用 reducer（operator.add）聚合而不是覆盖——实测 200 个并发任务封存审计哈希链，链完整、seq 全唯一（55.6ms）。AutoGen 没有等价的声明式状态合并。
3. **失败语义**：节点级 try/except → errors 列表，单 Agent 失败不中断整图；取消令牌在节点入口检查。这套"失败边界"在 group chat 里只能靠提示词约束，那是靠不住的。
4. **代价（主动说）**：LangGraph 的样板代码更多（节点工厂/payload_fn）、build_research_graph 曾经 587 行——后来拆成模块级工厂函数（可单测、不重建闭包）。图编排的复杂度是买可控性的成本，不是白付的。

### 追问防御
- **Q：19 个 Agent 是不是过度设计？** "是职责分层不是 19 个服务：单进程注册、接口无状态、Planner 按任务挑子集（实测 full=10、stock=8、macro=3 个 Agent 被唤醒）。而且 A12 合规我正在改成纯规则——Agent 数量由任务语义决定，该减就减。"
- **Q：那为什么不自己写个轻量调度器？** "差一点就自己写了。LangGraph 给了我三个我本来要自己造的东西：reducer 语义、checkpoint/恢复的演进路径、社区验证过的并发正确性。自己写的真正成本在边界情况（部分失败恢复、取消传播），不在 happy path。"
- **Q：图构建函数怎么测试？** "节点工厂抽成模块级纯函数（_build_analyze_payload_fn、_liquidity_ctx_node），不依赖闭包状态——可以直接 await 单测。这本身就是一次重构教训：587 行的大闭包没法测。"

### 金句
> **"多 Agent 编排选型的标准不是'谁的 demo 好看'，是谁把失败边界、取消传播、状态合并这三件事做成了一等公民。"**

## 专题 2 · 成本治理方法论（44,213 条审计归因）

### 30 秒版
"我的方法论是**先归因、后优化、再闭环**。先把 14 天 44,213 条 LLM 审计逐条折钱——结果推翻直觉：三大 Agent 功能合计不到 4%，**95% 的钱花在一个没人看的离线批量脚本上**（¥200.98/14天）。然后把交互链路用三层成本模型压到趋零（告警 ¥0.32→¥0/轮），最后把账单按功能/租户/天做成管理员界面。Token 优化的前提是知道钱花在哪。"

### 3 分钟版
1. **观测底座**：网关逐次落审计（tokens_in/out、模型、延迟、cache_kind、provider_chain）。没有这层，一切成本讨论都是猜。
2. **归因漏斗**：总量 44,213 → 剔除缓存命中（60.4%）→ 真实付费 16,343 次 ¥211.72（≈¥15/天）→ 按功能分组。关键发现：**主线挖掘离线脚本 15,860 次付费调用 ¥200.98（94.9%）**，投研 ¥7.79、告警 ¥0.32、热点 ≈0。
3. **治理分两轨**：交互链路走三层成本模型（专题 4）；离线脚本先让它"可见"（llm_cost.py 把 ops.script 单列，不混进前端功能账单），再上日预算闸（下一个 OKR）。
4. **闭环**：llm_cost.py 按 HTTP path 精确归属新数据；历史行没有 path 字段（44,213 条里 0 条，AccountingMiddleware 是后加的）就按 agent_id 推断——**界面上如实标注"这是推断不是账单"**。
5. **教训**：离线脚本为什么能烧 200 元才被发现？因为它没有页面入口、没有预算、没人看审计。**成本治理的本质是给每个调用方装电表，而不是给系统装一个总闸。**

### 追问防御
- **Q：为什么不一开始就上预算闸？** "预算闸是'止血'，归因是'诊断'。不诊断就上闸，闸会打在错误的地方——比如把离线脚本砍了，而它其实是主线的核心信号源。正确顺序：账单可见 → 定额 → 超限降级。"
- **Q：60.4% 缓存命中率怎么算的，水分大吗？** "逐条统计 cache_hit 字段。要说清构成：大部分命中是'同 Agent 重复跑同一任务'（精确层），真正的语义泛化少——3-gram 在长 prompt 下区分度下降。它救的是重复调用不是语义理解，改进路线是 embedding 索引进内存。"
- **Q：为什么 semantic cache 用 3-gram 不用 embedding？** "Demo 期零依赖选择：无向量库、无模型依赖、确定可复现。已知局限明确记录（长 prompt 区分度下降），并配了保守阈值 0.85——宁可不命中不能错命中。这是'轻量实现+诚实边界'，不是'自研向量库'。"

### 金句
> **"我最重要的成本发现，是钱根本不在我以为的地方——94.9% 花在一个离线脚本上。所以 Token 优化的第一步永远是把审计折成钱，而不是改 prompt。"**

## 专题 3 · 故障语义与三档超时（500 故障复盘）

### 30 秒版
"一次真实 500 故障：读路径里藏了一次懒过期 UPDATE，主库被多条链并发写，连接参数又游离在项目范式外（裸 connect 默认 5s）——三因叠加。我第一版修复是'把超时调大到 20s'，本地单发完美，**被自己的占锁压测否掉**：4 连请求全部超时，局部错误升级成全局阻塞。最终方案是超时按业务代价分三档：关键写 20s 排队、交互读写 2s 快速失败、懒过期 0.4s 只试一次可降级。"

### 3 分钟版
1. **定位过程**（体现方法论）：16 组参数探测全 200（排除参数问题）→ 日志抓完整 traceback（读路径里的 UPDATE）→ 全日志 85 处 database is locked（说明共享资源长期紧张）→ 逐仓储核对连接参数（两个游离在范式外）。**先建事实，不猜。**
2. **三因叠加**：读路径藏写 × 多写者竞争 × 连接参数不统一。为什么"之前能用现在不行"？并发写者变多了（二期加入量化/做T/资金流），偶发窗口变成扫描时必撞。
3. **方案 A 为什么错**：把错误变成了延迟；单事件循环 + 默认线程池下，每个排队请求占死一个线程——占锁 12s 压测 4 连超时，健康检查都挂。**它把局部错误升级为全局阻塞。**
4. **方案 C 的三档表**（背下来）：

| 场景 | 等待 | 理由 | 失败行为 |
|---|---|---|---|
| 关键写（事件/告警入库） | 20s + 3 次退避重试 | 丢一条告警 = 丢推送+邮件，值得排队 | 只重试锁错误 |
| 交互读写（列表/详情/已读） | 2s | WAL 下读几乎不被阻塞，不该为写锁排 20s | 快速失败，前端重试 |
| 懒过期（读路径顺带清理） | 0.4s 只试一次 | 必须 < 前端 1.5s 轮询间隔 | 返回 False 降级，下次自然补 |

5. **验收**：8 条锁竞争回归（真占锁）+ 红绿验证（还原旧实现必红、报错与生产一致）+ 运行日志连续 200。占锁场景 500 → 200（0.52s 内返回）。

### 追问防御
- **Q：为什么 retry_on_locked 只重试锁错误？** "locked/busy 是瞬时可重试；no such table 是确定性失败，重试只会拖延暴露。重试集合必须等于瞬时错误集合。"
- **Q：为什么不用 PostgreSQL？** "根因是连接参数与读路径藏写，不是 SQLite 能力问题——换库是拿架构变更掩盖工程问题。真要演进：先写入收敛（单写者队列），再换库，且 DATA_BACKEND 工厂已抽象好。"
- **Q：懒过期为什么不改成后台任务？** "那是更干净的方案 B，但要引入后台任务生命周期，改动面从仓储扩散到应用装配。止血阶段选最小爆炸半径；'懒迁移+幂等+可失败'三性质守住后它就是安全的。已记录为演进方向。"

### 金句
> **"修并发问题的第一反应不该是'把超时调大'，而要问三件事：这个等待值得吗？谁在为它付费？失败能不能降级？——先定义失败语义，再谈等待时长。"**

## 专题 4 · LLM 网关红线 + 三层成本模型

### 30 秒版
"架构红线：**所有 LLM 调用必须过网关，禁止 Agent 直连模型 API**——这是把成本、可靠性、审计从'散落在 19 个 Agent 里'收口成一个控制面。网关六步：取消检查 → 保头保尾截断 → 两级缓存 → token 预算 → 按层降级链（熔断按 provider 计数）→ 审计落盘。上面再叠三层成本模型：L0 规则（默认）→ L1 本地模型 → L2 云端三闸门。"

### 3 分钟版
1. **为什么是红线**：没有收口的后果是具体的——成本不可见、失败无留痕、模型名散落、缓存无法统一键控。红线写进模块 docstring + code review 把关。
2. **六个步骤每个都防一种真实事故**：取消检查防"用户点停止还在花钱"；保头保尾防"schema 被切掉→必然失败的重试成本翻倍"；两级缓存防重复调用（全站命中 60.4%）；token 预算防单任务失控（200K/任务 + max_tokens 双层上限防配置写 100k）；降级链防"主模型挂了全链失败"（熔断按 provider——v4-pro 和 flash 同端点，model 级熔断等于没兜底，实测踩过）；审计链让一切事后可查。
3. **三层成本模型**（网关之上的调用方策略）：
   - **L0 规则**：关键词/正则/计数/排序——精确、免费、可复算。绝大多数情报需求在这层结束（"哪个板块被提及最多"丢给模型既贵又不可复算）。
   - **L1 本地**：8B/1.5B——语义任务零 token 费（只吃电）。事件打分、倾向抽取、摘要。
   - **L2 云端**：三闸门同时满足（显式 allow_cloud + 单任务 8000 token 预算 + 当日 20 次上限，计数从审计链读），任一不过**降级 L1 而非报错**——情报降级只是质量略降，报错是功能不可用。
4. **local_only 钉在配置层**：靠每个调用点记得传参数靠不住（实测事件告警阶段一 0.0196 元就是这么漏的）；钉在 models.yaml 让新调用方默认安全。

### 追问防御
- **Q：网关成为单点怎么办？** "进程内单例但无状态（缓存目录+审计文件外置即可多实例）；熔断器各 worker 独立计数会让实际阈值×N——宁可宽松不可误熔断，可接受，未来收敛到 Redis。"
- **Q：语义缓存会不会返回错误的答案？** "按 agent_id+scope 隔离防结论串台；0.85 保守阈值宁缺勿错；已知 3-gram 在长 prompt 区分度下降，命中构成以'同 Agent 重复跑'为主——它救重复调用不救语义理解，这话我主动说。"
- **Q：L0 规则的准确率怎么保证？** "L0 只做'原文这么说'的归类（多空词计数），不做平台判断；置信度封顶 0.9；有测试钉住词表行为。规则的可复算性本身就是验收标准——用户能自己验算。"

### 金句
> **"网关红线的本质是把'调用模型'从自由行为变成受控动作——每一次调用都必要、都带必要的信息、都一次成功、都留痕。"**

## 专题 5 · 并发评估：准入 / 合流 / 状态外置路线图

### 30 秒版
"并发评估的结论是：**链路的并发正确性过关（状态隔离、reducer、per-key 去重、哈希链 200 并发实测），但资源仲裁缺位**——没有准入控制、语义缓存在事件循环上同步扫描、结果缓存有击穿窗口、TaskStore 永不淘汰。安全并发 2~4 个 full 任务，超出后是'所有人一起变慢'。P0 四项落地后 15~20；再往上必须状态外置，那是'从 Demo 到服务'的分界线。"

### 3 分钟版
1. **测量先行**：整机 CPU 仅 6~13% → 饱和根因是**重复计算与同步阻塞**，不是核数——据此**否掉加实例方案**（进程内状态会让加 worker 立刻出现"任务提交后查不到"）。
2. **P0 四项（都已是小改动）**：① 准入信号量（MOSS_RESEARCH_MAX_INFLIGHT=4，按 LLM 配额定不按用户数定，满员明确报"队列已满"）；② 同问合流（qhash 占位 + Future，10 个并发同问 → 1 条管线）；③ 语义缓存 aget 走线程池（冷 682ms/热 9ms 的同步扫描移出事件循环）；④ TaskStore TTL+容量淘汰（实测 200 请求残留 200 份完整报告）。
3. **P1 路线图（状态外置）**：结果缓存/TaskStore/熔断器/预算 → Redis；数据层 → PostgreSQL（工厂已支持）；租户级日配额。解锁能力：**可以加 --workers、可以多实例**。
4. **P2 可观测**：research_inflight / queue_wait / event loop lag / cache_scan_ms 四个指标——"事件循环滞后"是发现同步阻塞的唯一直接信号。
5. **防护栏（主动说清现状）**：token 预算是单任务口径，无全局/租户上限；API 层无令牌桶。这些在路线图上有明确位置。

### 追问防御
- **Q：为什么不直接上 Kubernetes 多实例？** "状态外置没做完之前，多实例是负优化（缓存命中率 1/N、任务 404、预算失效）。我的顺序是：先让单实例把该省的计算省掉（P0），再外置状态（P1），最后才是水平扩容。跳步会把分布式问题引入单机就能解决的场景。"
- **Q：4 这个数怎么定？** "按 LLM 配额反推：DeepSeek RPM/并发限制 ÷ 单任务平均调用数（8~15）≈ 4，压测后调。旋钮交给环境变量，容量决策数据化。"
- **Q：同问合流的缓存失效怎么做？** "结果缓存 600s TTL + 500 条容量 + force_refresh 绕过；投研结论带数据时点（trade_date 钉死），过期重算——宁可多算不可给陈旧结论。"

### 金句
> **"并发正确性是'写不错'，资源仲裁是'排得动'——前者我靠 reducer 和锁做到位，后者是我从 Demo 到服务要补的课，每一步都有实测基线。"**

## 专题 6 · 前端取舍辩护（无 React Query / 无虚拟滚动）

### 30 秒版
"三个手写缓存（alertsCache/intelCache/useAuth 内联）确实该统一，React Query 在 roadmap 上。但当时每一次手写都在解决一个**真实的报障**：告警 2 秒、情报切页丢状态、预取路径不全——而它们的方案核心（localStorage SWR + keep-alive 预取 + seq 收敛）与数据量级（列表 ≤100 条、清单 554 行）是匹配的。取舍点在于：引入 React Query 要重写三套缓存并回归，而当时的优先级在并发 P0 与后端事件循环阻塞这些用户真正卡住的地方。统一数据层的触发条件我已经写进 roadmap。"

### 3 分钟版
1. **先摆事实（数据量级决定必要性）**：情报流 60 条/页（服务端 500 条池筛选）、告警 ≤100 条、拥挤度清单 554 行（前端排序过滤）。虚拟滚动解决的是 1000+ 行 DOM 的渲染压力——**当前量级下整表渲染 16ms 以内**，引入 react-window 是为不存在的问题付复杂度。
2. **React Query 的真实代价（不只是引包）**：三套手写缓存各自带**业务语义**——告警的 60 秒新鲜度去重 + force 续期、情报的"refreshing 强制 false"（切回不该进等 WS 补拉的状态）、按 filter|sort|direction 分键（防"切到高可信档拿到全部的列表"）、登出清空（防换账号串数据）。迁移 = 把这些语义逐条翻译成 queryKey/staleTime/invalidation 并回归——**这是 1~2 天 + 全量回归的改动，收益是删代码，不是修 bug**。优先级排序输给了并发 P0（用户实际卡住的点）。
3. **已经做对的（不卑不亢）**：SWR 语义（先画缓存再后台核对）、两路预取（登录+刷新，第二次报障根因）、4 分钟续期 < 最短 TTL、KeepAlive 惰性挂载、体积守卫测试（载荷膨胀是静默的）、**14 条源码结构守卫 + 反向验证**（没有测试框架时的务实护栏）。
4. **改进路线（具体到触发条件，不是敷衍）**：
   - **SWR/React Query 统一数据层**：触发条件 = 第四个需要缓存的页面出现，或任一缓存语义需要跨页失效。步骤：先抽 useSwrCache() 钩子统一读写协议 → 逐页迁移 → 删手写缓存。
   - **虚拟滚动**：触发条件 = 清单 &gt;1000 行或低端机实测掉帧。方案：@tanstack/react-virtual 只包告警表 body，表头用 sticky——半天工作量，随取随用。
   - **vitest**：触发条件 = 结构守卫测试开始误报（源码结构变化导致的脆弱断言）。把结构断言迁为行为测试。
5. **主动交底**：这是"单维护者 + AI 工作流"下的优先级取舍——**每一行手写缓存代码背后都有一个真实报障编号**；技术债在 roadmap 上有名字、有触发条件、有预估工作量。这就是我理解的负责任的取舍。

### 追问防御
- **Q：三套缓存有没有出过不一致的 bug？** "出过一次'假象'：intelCache 被动态导入+静态导入两次，看起来分了包其实没有——Vite 警告，改成静态导入。语义不一致没出过，因为缓存键协议（feedCacheKeyOf）有测试对齐预加载键逐字一致。"
- **Q：为什么不用 Next.js/路由库？** "单实例内网工具，无 SEO 无 SSR 需求；hash 路由 + 白名单解决'刷新回到默认页'的真实问题，代码量 30 行。框架是手段不是简历关键词。"
- **Q：如果明天要支撑 1000 并发用户？** "前端不是瓶颈（静态资源 + CDN/反代缓存）；瓶颈在状态外置（专题 5 的 P1）。我不会为了'看起来现代'在前端先动手——架构动作要对着瓶颈数据。"
