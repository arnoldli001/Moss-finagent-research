## 专题 1 · 行情"为什么不刷新"——挖出了两个独立 bug

### 30 秒版

用户报"今天已经开盘了为什么行情里个股没刷新"+"9:25 集合竞价结束就应该显示在分时图上"。**我没当成一个问题查**。拆成两个表现：**watchlist 不显示开盘涨幅**（后端闸门误杀） + **分时图第一根 bar 是 9:30**（前端没画 9:25 锚点），**根因不同，分别修**。后端那道闸门是 `is_trading_day()` —— 它用行情时钟 tick 判定节假日，但**指数在集合竞价期没成交**，tick 不前进，于是把真交易日 9:25 误判成"非交易日"，整段跳过整表重算。修法是在 9:15-9:30 这 5 分钟**不调这个判据**，让 watchlist 9:25 撮合后立刻拿到开盘价。

### 3 分钟版

1. **拆症状**：用户说"不刷新"，我先列清单——watchlist 没显示 9:25 开盘涨幅、分时图没 9:25 数据。这两个**根因不同**，不能合并查。
2. **后端根因**：`src/intraday/service.py:_watchlist_refresh_loop` 有两道闸门。第一道 `watchlist_refresh_window()` 正确放行 9:15-9:30（含集合竞价期）；第二道 `is_trading_day()` 想拦节假日，但它**用指数 tick 的 timetag**（`live_session_date()` 探的是 `qt.gtimg.cn` 指数的 31 位时戳）判定"今天"。问题：**A 股指数没有集合竞价**，9:15-9:30 tick 不前进，指数时戳停在昨天 15:00，`live_session_date()` 返回昨天 → `is_trading_day()` 把真交易日判成"非交易日"。于是 9:25 撮合那一帧，watchlist 静默地不刷新。
3. **修法（Plan A）**：把"是否查 `is_trading_day()`"做成**条件**——9:15-9:30 不查，9:30 之后查。代码 `now_moment.hour*60 + now_moment.minute < MORNING_OPEN` 决定 `in_call_auction`，`holiday_check = allowed and not in_call_auction and not _is_trading_day_for_refresh()`。**取舍**：节假日工作日的 9:25-9:30 多空跑一轮（48 只 × 3-5s ≈ 150s CPU），但下一轮到 9:30 市场时钟追上，闸门恢复。比"集合竞价看不见开盘价"轻得多。
4. **前端根因**：`sessionMinute()` 把 9:30 之前的 ts 都映射为 `minute=0`，分时线第一根落在 09:30:00 —— 而分时数据源（腾讯 / 新浪 / 东财）的 `fetch_trend` 返回的 `data.data` 数组**首条就是 09:30**。9:15-9:25 那 10 根 call-auction bar 没有免费替代（`AGENTS.md` 已登记"竞价链 fallback=none"），但 `quote.open` 在 9:25 撮合后**立刻可用**（腾讯快照第 5 位）。
5. **修法（Plan B）**：不扩 `view.start`（避免挤压 240 分钟窗口）、不改 `sessionMinute`（避免对所有分时点的 X 轴映射产生连带影响），而是**在分时线最左单独画 9:25 锚点**：一根红色虚线（向右 42px）+ 三角 + `09:25 开盘` 文字标签 + tooltip 显示撮合价 + vs 昨收涨跌幅。触发条件分四道：`openPrice > 0 && prev_close > 0 && view.start <= 0`。**`view.start <= 0`** 决定用户缩放到 10:00 之后锚点自动让位给分时。

### 追问防御

- **Q：为什么 9:15-9:30 多空跑一轮能接受？** "48 只 × 3-5s ≈ 150s CPU，下一轮 9:30 市场时钟追上立即恢复。修这个 bug 的业务价值是让 9:25 撮合价立刻可见（开盘定方向），省下的 150s 不如这个价值大。**两个错方向选错的那个**：误判成'非交易日'→ 漏掉开盘价 = 用户看不见决策关键帧；多跑一轮 CPU = 浪费算力但**数据正确**。"
- **Q：为什么不直接 `is_holiday()`？** "本项目没有这个函数，硬编码节假日表 AGENTS.md 已强调会过期（春节/国庆调休每年变）。用日历表误判方向的代价更大 —— 把真交易日的 9:25 漏掉比节假日多烧一轮 CPU 严重得多。"
- **Q：为什么不扩 `view.start` 到 -10 把 9:25 画成普通点？** "`view.start` 影响所有分时点的 X 轴映射，9:30 起的连续竞价那 240 分钟会被挤压，**分时图本身就是靠那 240 分钟的颗粒度判断冲高/无承接/止跌**。改它的爆炸半径远大于收益。Plan B 把它做成独立的视觉元素 —— 不参与轴映射、不参与尺度计算。"
- **Q：quote.open 在 9:25:00 当真就立刻可用吗？** "腾讯 `qt.gtimg.cn` 第 5 位 `open` 是**今开价**字段，实测 9:25 撮合后 1 秒内即可拿到。第 32 位 `change_pct` 是基于 (current - prev_close) 计算的，9:25 时 current = open，所以 change_pct 也是 9:25 撮合价相对昨收的涨幅。**不需要二次计算**，直接读字段。"

### 金句

> **"用户报'行情没刷新'的时候，先把每一个观察到的表现单独列成一行 —— 因为根因往往不是同一个。一个症状 + 一次诊断 = 一个答案，但用户常常把两个症状揉成一句话。"**

> **"节假日闸门和'集合竞价该不该跑刷新'是两个问题，**用一道闸门解决两个问题**的结果就是两边都被卡住。闸门是单维度的，问题是多维度的 —— 任何'一道闸门解决两件事'的代码都是埋雷。"**

## 专题 2 · AI 编程的三条反模式（本轮自检）

### 30 秒版

本轮我犯了三个 AI 编程的典型错误：① **把诊断当回答**（用户问"为什么不刷新"，我回"怎么看日志"而不回"怎么修"）—— 用户已经看到了 stale 数据，他要的是 fix path；② **把两个症状当一个症状**（watchlist 不刷新 + 分时图没 9:25 锚点，根因完全不同，我只查了第一个）；③ **commit 时不验 staged 集**（第一次 commit 把别人预 staged 的 3 个文件一起带走了）。每条都有具体修法 + 防御纪律。

### 3 分钟版

1. **诊断 ≠ 修复**：第一轮我列了 3 步排查（点强制刷新 / 看数据源健康 / 等源恢复），**没修任何东西**。问题不是排查步骤错 —— 是用户已经看到了现象，他不需要我教他排查，他要的是"如果根因是 X 就改这里"。**纪律**：诊断型回复必须附带"如果你判断根因是 X，修复路径是 Y"，否则等于把"找根因"的负担从 AI 移到了用户头上。
2. **多症状 = 多根因**：用户一句话报了 2 个症状，我只查了 1 个。**为什么 AI 会这样**：找到第一个能解释的现象会触发"完成感"（loss aversion 的镜像），于是停。**纪律**：列清单 → 每个查独立根因 → 找到多个根因时分别修，不合并到同一个 commit。
3. **commit 不验 staged 集**：`git add my_files && git commit -F msg` —— AI 默认 `git commit` 等价于 `git commit my_files`，**实际等价于 `git commit --staged`**（包含所有已 staged 的内容）。**事故还原**：第一次 commit 多带了 `.gitignore` + `src/api/routes/auction_select.py` + `src/api/routes/quant_select.py` 三个别人预 staged 的文件。**修法**：`git diff --staged --name-only` 必须在写 commit message 之前跑一遍；不在本次范围的文件 `git restore --staged` 踢出去。

### 追问防御

- **Q：这三个错误算什么严重程度？** "① 是用户感知最直接的（用户被教回去自查，挫败感最强）；② 是最容易漏的（用户的话天然是'揉'过的）；③ 是最容易修复的（一条 `git diff --staged` 命令就防住）。三者都是**流程层**的 bug，不是知识层 —— 知道与做到之间差的是纪律。"
- **Q：怎么防止下次再犯？** "① 把'列症状清单'和'每个症状分别查根因'写进 `skills/intraday-call-auction-data-pipeline/SKILL.md §7`；② 把 `git diff --staged --name-only` 写进 AGENTS.md 的 commit checklist；③ 每次 commit 前我会**先复制这次踩坑的事故还原**贴进自己的 working notes（不是文档，是会话内自留的复盘）—— 'AI 不到黄河心不死'，把同一坑踩过的现场留着，下次同型 bug 触发的瞬间能认出来。"
- **Q：是不是应该让 AI 在动手前先读 skills？** "对，但 AI 的 skills 加载是**按需**的，不是预读。正确做法是**触发词匹配** + **报错时自检**：用户报"行情不刷新 + 时间不对"，触发 `intraday-call-auction-data-pipeline` skill；如果 AI 第一轮没出修复路径，自检 §6.1（诊断当回答）是否触犯。本轮的复盘让下次同型 bug 的首轮直接给 fix path。"

### 金句

> **"AI 在'找根因'这件事上有 loss aversion 的镜像 —— 找到第一个能解释的现象就停。纪律是'每个症状分别查'，不是'找到第一个就好'。"**

> **"commit 之前不跑 `git diff --staged --name-only`，等同于不打开后备箱就开车。你以为你知道装了什么，实际连别人塞进去的行李也一起开走了。"**

## 专题 3 · 时间窗口 + 数据链的边界感（"免费源拿不到"那一类）

### 30 秒版

修这个 bug 的过程中我对 A 股免费行情源做了一次完整的"能拿到什么、拿不到什么"清单：分时 trend 首条都是 9:30、分钟 bar 没有 9:15-9:25、指数没有集合竞价。**免费源覆盖的是连续竞价（9:30-11:30 / 13:00-15:00）这 240 分钟**，集合竞价 10 分钟是付费区。9:25 的"开盘价 + 集合竞价涨幅"是免费的（腾讯快照字段），9:15-9:25 的"逐分时轨迹"是付费的（只有 QMT tick）。**这种"边界感"决定了哪些 bug 是该修的、哪些是数据天花板**。

### 3 分钟版

1. **数据链的边界**：`AGENTS.md` 已经登记"竞价链 fallback=none"，但只在改配置时才会被读到。修 bug 的时候再读一遍是为了确认"这次能不能拿到 9:25 的分时数据" —— 答案是不能（免费源都没有），所以 Plan B 退而求其次画一个 9:25 锚点（用 `quote.open` 单一价格），不做完整的分钟轨迹。
2. **指数 vs 个股 的差异**：A 股**指数没有集合竞价**，所以指数 tick 在 9:15-9:30 不前进。**这是 `is_trading_day()` 误判的物理根源**。任何依赖指数时钟的判据（节假日判定、市场活跃度判定）在集合竞价期都要做"指数还没动"的特殊处理 —— 不只是 `is_trading_day` 一个函数。
3. **代码与数据的分工**：`sessionMinute()` 的 `if (minutes < morningOpen) return 0` 把所有 9:30 之前的 ts 都映射到 0，**这是设计选择不是 bug**。改它需要重新设计 X 轴刻度，对所有分时点的映射都有连带影响。**Plan B 不改它**，而是把 9:25 锚点做成独立视觉元素 —— **这种"不擅自动共享函数" 的纪律是改代码的核心**，不是"能改就改"。
4. **腾讯快照字段的语义**：`qt.gtimg.cn` 字段 31 是行情时戳（YYYYMMDDHHMMSS）、字段 5 是今开价、字段 32 是 `change_pct`（基于 (current - prev_close)）。**9:25 时 current = open，所以 change_pct 也是开盘价相对昨收**。这两个字段是免费的，且**9:25:01 就可用**（撮合完成后第一秒即返回）。

### 追问防御

- **Q：为什么不直接买一个付费数据源？** "QMT 终端可以拿 tick 逐秒数据，但本项目**短期无法恢复 QMT 行情权限**（AGENTS.md 已强调：终端失去行情权限、不再运行、连接超时 4~5s）。**不依赖付费源、不依赖 QMT 是**所有"自由数据链"的硬约束。在这个约束下，9:15-9:25 逐分时是无解的 —— Plan B 给的是**锚点**，不是轨迹。"
- **Q：免费源拿不到 9:25 那为什么 `is_trading_day()` 错得这么离谱？** "它依赖的是指数 tick 时戳，**指数没集合竞价**所以 tick 在 9:15-9:30 不前进。这是 A 股市场结构的硬约束，不是 bug —— bug 是设计者没意识到这一点。这个 lesson 已经写进 skill §6 的"闸门是单维度的，问题是多维度的"那条。"
- **Q：sessionMinute 不动它怎么解决 9:25 显示问题？** "不动 `sessionMinute` 是**设计取舍**：改它要扩 `view.start`、连带改 view 计算函数、改 domain 函数，爆炸半径 200 行。Plan B 只在 SVG 层加一个独立 `<g>` 元素，触碰面 35 行。**改代码的纪律不是'改到对'，是'改到刚刚够'**。"

### 金句

> **"免费行情源的覆盖边界是 9:30-11:30 / 13:00-15:00 这 240 分钟连续竞价。集合竞价那 10 分钟是付费区，知道这条边界就少走 50% 弯路。"**

## 简历亮点 bullet（可直接用）

> ★ 数字与路径可复现（复现方式见 `skills/intraday-call-auction-data-pipeline/SKILL.md` §5）。

- **修 A 股交易系统开盘前 5 分钟数据缺口**：定位 watchlist 不刷新 + 分时图无 9:25 锚点两个独立 bug，分别修。后端在 `is_trading_day()` 闸门上加"集合竞价期不查"的豁免（条件 6 行），让 watchlist 在 9:25 撮合后立刻看到开盘价 + 集合竞价涨幅；前端在分时图最左加 9:25 锚点（35 行 SVG），不动共享函数 `sessionMinute`、不挤压 240 分钟窗口。

- **AI 编程纪律三条（自检）**：① 把诊断当回答 → 必须附 fix path；② 把多症状当一症状 → 列清单、每个查独立根因；③ commit 不验 staged 集 → `git diff --staged --name-only` 必跑。三条都已沉淀到 `skills/intraday-call-auction-data-pipeline/SKILL.md` §6 + AGENTS.md。
