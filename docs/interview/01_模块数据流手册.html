关键决策（为什么不用备选方案）

决策理由（可当场讲）
LangGraph StateGraph，不用 AutoGen/CrewAI需要可控的 fan-out/fan-in（A08-A16 并行汇合到 A17）与失败边界；group chat 是黑盒，控不了并发度、取消传播与 reducer 语义。StateGraph 的 operator.add reducer 让并行写状态天然安全。
分析层白名单 + 空结果兜底审计实证 5 个 Agent 收完全相同全量（tokens_in=25,149 一致）；白名单按 indicator 关键字过滤，过滤后 0 条必须兜底取前 200 条——否则 Agent 全部走"无数据拒绝分析"静默跳过 LLM（集成测试抓到过这个回归）。
A17 用最贵的 v4-pro跨源冲突仲裁是全链路唯一不可降级环节；且 compact+增量协议后其成本占比已从 55% 大幅下降；空结论回退单次直答保可用性。

比 AI 深一层：追问卡

Q1：LangGraph 里并行节点怎么保证状态不互相踩？
三个隔离层：① 每请求独立 ResearchState（无跨请求共享可变状态）；② 并行写同一键的字段（agent_outputs/errors）走 operator.add reducer，LangGraph 聚合而非覆盖；③ 全局资源（审计链）用 threading.Lock + seq 续链，实测 200 并发封存链完整、seq 全唯一（55.6ms）。
Q2：Planner 用 1.5B 会不会规划错？
会，所以有三道护栏：① sanitize_indicators 修正常见的"裸指标名"契约错误；② append_liquidity_indicators 用规则确定性补齐 LLM 漏掉的流动性指标；③ 规划失败整体回退 plan_run 纯规则路由。规划错一个 Agent 的代价远小于每轮省下的 15 秒云端等待。
Q3：准入上限为什么是 4？
按 LLM 配额定，不按用户数定：DeepSeek RPM/并发限制 ÷ 单任务平均 LLM 调用数（8~15 次）≈ 4；满员时明确返回"队列已满（N/4）"而不是无限排队——排队不可见比报错更伤体验。

关键决策

决策理由
熔断按 provider 而非 modelv4-pro 与 flash 同端点同 key——model 级熔断在 provider 故障时主备一起失败=没兜底。实测踩过：投研报"全部模型调用失败（链: v4-pro→flash）"，decision 层 fallback 随即改为 local_medium（跨 provider）。
截断保头保尾而非只保头只保头会把尾部的 JSON schema 切掉 → 模型输出非法 JSON → 修复重试（use_cache=False、prompt 更长）成本翻倍，且重试仍被同样截断。实测修这一个点省掉一类"必然失败的重试"。
local_only 钉在 models.yaml 配置靠每个调用点记得传参数靠不住——实测事件告警阶段一 0.0196 元就是这样花掉的。配置层钉死，新调用方默认安全；真要付费云端必须显式 local_only=False。

比 AI 深一层：追问卡

Q1：语义缓存为什么按 agent_id 隔离？跨 agent 复用会怎样？
A05 核验与 A06 抽取的输入大量重叠，跨 agent 复用会"结论串台"——A06 拿到 A05 的核验输出当抽取输入，错误静默传播。0.85 阈值是保守值：宁可不命中，不能错命中。已知局限：字符 3-gram 在长 prompt 下区分度下降，命中里大部分是"同 Agent 重复跑"，真正的语义泛化少——改进路线是 embedding 向量库（roadmap P2），且长 prompt 场景先关语义层只留精确层。
Q2：语义缓存在事件循环上同步扫描的问题你是怎么发现和修的？
并发评估实测：冷启动未命中扫描 3108 个缓存文件 682ms、稳态 9ms/次——同步跑在事件循环上且串行累加（N 个并发用户 = N×9ms 全站延迟），缓存还单调增长。最小修法是 aget() 把扫描挪到 to_thread；彻底修法是把索引（agent_id/scope/向量）建进内存，未命中从 O(文件数) 降为纯内存计算。两步都做了/规划了。
Q3：网关是单点吗？
是进程内单例，但无状态（状态只有缓存目录与审计文件）——水平扩容时缓存换 Redis、审计进管道即可；熔断器状态是唯一的多实例不一致点（各 worker 独立计数，实际阈值×N），宁可宽松不可误熔断，可接受。

  • 解释为什么 max_tokens 要双层上限

比 AI 深一层：追问卡

Q1：为什么宁可报缺口也不给模拟数据？
这是刻意的工程主张：假数据进了投研建议，比"这次没数据"危险得多——用户会把编的数字当成真的。代价是演示偶尔"没数据"、需要人工补数据源，我把这个取舍写成明确的价值主张而不是藏起来。配套：DataGapResolverAgent 让系统自己补连接器（LLM 生成代码 → AST 白名单校验 → 子进程沙箱 15s 冒烟 → 双通过才落库复用），把"等开发者"变成"自愈"。
Q2：QMT 为什么排最后且默认关？
本机 QMT 终端失去行情权限，放在任何位置都贡献一次必然失败的连接等待（实测 4~5s）。两个坑：顺序与开关表达同一个意图，两处都要改对——健康分在样本<3 次时照抄配置顺序当先验，只改开关不改顺序，QMT 仍会顶到链首。这是"配置顺序=默认顺序"的隐性耦合。
Q3：健康分怎么防止一次抖动把好源打下去？
健康分基于滑动样本统计而非单次成败；且样本不足时回到配置先验——新源/低频源不会被一两偶然失败永久压底。

比 AI 深一层：追问卡

Q1：批大小 6/8 是拍脑袋吗？
是实测算出来的：本地 qwen3:8b 每条事件输出 330~400 token（思考型模型，思考也占 num_predict 预算），4096 上限扣 ~600 思考 → 可用 ≈3500 → 3500/400≈8，取 6/8 留余量；时间上限 6 条 ≈2400 token ÷ 44 t/s ≈ 55s < 120s 超时。生产日志实证过 30 条一批的下场：Unterminated string 从字符串中间截断，整批退回兜底。分批代价只是多几次调用——本地模型不按 token 计费。
Q2：告警为什么从"每次 0.32 元"变成"0 元"？讲讲决策链。
用户质疑"信息是网上抓的，为什么要花 token"→ 审计归因：53 次调用 0.32 元，其中阶段二写死 reasoning 层而 reasoning 的 primary 是付费 deepseek（28×调用 ¥0.30）——先花钱，本地模型闲着。修复分两层：调用点换层 + local_only=True 钉进配置（不靠人记参数）。验收：3 条真实事件本地跑 23s 出分且区分度良好（政策利好→机会 60/把握 0.7；暴雷→风险 85/0.9；花絮→双低 15/0.3）。
Q3：LLM 挂了告警还能用吗？
分批失败只丢那批；阶段一整批失败退关键词分类+中性情感（功能可用质量降级）；阶段二失败该批无评估但其余批次照常；评分越界丢单条不丢整批。fail-open 在"质量"维度、fail-fast 在"越界伪造"维度——两个方向是刻意分开的。
盲测自检：
  • 默写两阶段的批大小及推导过程
  • 画出"截断抢救"的处理分支
  • 讲清 FR-6 为什么丢弃而不是钳制

比 AI 深一层：追问卡

Q1：抽股票为什么放弃模型？
实测（2026-09-25，160 条真实快讯）：1.5B 两批只抽出 1 只还是港股，且有一批连 JSON 都没输出——快讯里 A 股名字稀疏，小模型在这种输入上是抛硬币。而"谁被提到了"根本不需要语义：名录字符串匹配精确、免费、可解释（能给出在哪条里提到）。模型只留给它真正擅长的：一句话摘要与倾向归类。这是"能用确定性求解的绝不进模型"的典型案例。
Q2：分段抽取是被什么逼出来的？
一条 3452 字的会议纪要按旧逻辑只取两头 591 字——"天岳先进""第三代半导体"在被切掉的中间 2500 字里，实体字段全空。不是模型失败，是它没看见那段原文。改为按句边界切段逐段调用+确定性合并，实测平均 1.9 段/条；成本可控（本地零 token 费），调用次数有 MAX_EXTRACT_SEGMENTS=6 上限防失控。
Q3：feed 冷启动返回空壳，前端怎么收敛？
全局递增 seq：后台建完 seq+1 并 WS 推送；前端比较"手里的 seq < status.seq"决定是否重拉——任何一次重建都会收敛，不依赖推送必达（WS 断线有短轮询兜底 /feed/status，那条接口只读进程内计数器，被高频调用所以必须微秒级）。

  • 默写 L0/L1/L2 三层各自解决什么、闸门条件是什么

Q1：读接口为什么要加 SELECT 守卫？

Q2：水位分母为什么是"近 6 年最高"而不是分位数？

Q3：为什么散点图只画清单内板块？
全市场 2517 个板块全画不可读；清单是"该看哪些板块"的唯一真相源（服务端持久化，两面板共享单所有者），删的是看板显示、历史数据仍保留——可逆。

比 AI 深一层：追问卡

Q1：为什么 retry_on_locked 只重试锁错误？
locked/busy 是瞬时、可重试的；no such table / schema 错误是确定性失败，重试只会拖延暴露问题。重试范围必须等于"瞬时错误"的集合，这是失败语义的一部分。
Q2：为什么不用连接池？为什么不上 PostgreSQL？
连接池：sqlite3 默认 check_same_thread 不跨线程，与 to_thread"每操作一连接"模型天然匹配；池要额外处理 WAL 事务边界与跨线程归还，收益不明确。换库：项目定位是 SQLite 零依赖单机可跑，故障根因是连接参数与读路径写操作，不是 SQLite 能力问题——换库是"用架构变更掩盖工程问题"；真要演进，先做写入收敛（单写者队列）再谈换库。
Q3：懒过期为什么放读路径而不是后台定时任务？
方案 B（后台任务）语义最干净但要引入后台任务生命周期（启动/取消/幂等），改动面从仓储扩散到应用装配——止血阶段优先最小爆炸半径；把"懒迁移+幂等+可失败"三个性质守住后，读路径里的它是安全的。这个权衡我明确记录为后续演进方向而不是拍死。
盲测自检：
  • 默写三档表（数值+理由+失败行为）
  • 讲清"反向验证"怎么做、为什么它比"测试通过"更可信

逐条统计 cache_hit 布尔字段（44,213 条）。可信但要说清构成：大部分命中是"同 Agent 重复跑同一任务"（精确层），真正的语义泛化命中少——所以它救的是重复调用，不是"语义理解"。3-gram 的局限（长 prompt 区分度下降）与改进路线（embedding）都如实讲。
