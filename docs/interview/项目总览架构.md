# 二、问题清单（按架构/性能/成本/稳定性分组）

## 2.1 性能问题（已确认/待修）

### 🔴 P1 · 板块拥挤度（sector_crowding）首屏加载 2-3 秒
**直接证据**：`src/api/routes/sector_crowding.py` 的 `latest` 接口、`config_list` 接口每次请求**新开SQLite 短连接**（9 次 `conn.close()`），
扫描 217万行的 `max_ma5_map` GROUP BY。

**根因（4 个叠加）**：
1. **冷缓存必慢**：`/config_list` 接口**每次**都调用`db.seed_list()`（即便已seed）+ `db.hide_dead_boards()` + `_read_list()` + `query_metrics()`，四个 SQL 全跑一次。
2. **数据量大**：单表 `sector_crowding_daily` **217 万行**，UNIQUE(trade_date, sector_code)；无物化视图。
3. **`max_ma5_map` 是N+1**：前端每个 SectorCrowdingOverview 渲染要拿 `sectors_max_ma5`，注释说"进程内缓存 300s"，但**首次必算1.7s**。
4. **周频指标4列**：每个板块JOIN行情表 + 资金流表做5d/1m/2m 滚动，实测单板块0.3-0.5s，**554个板块全表 3-5 分钟**。

**修复建议**：
```python
# 1) SQLite 改连接池 + WAL 模式（已部分实现，但路由层仍是短连接）
# 2) 物化 max_ma5 到独立表，refresh 时增量更新，不要每次 GROUP BY
# 3) 前端懒加载：先返回可见清单 + 水位，"近 6 年最高"列在用户点详情时再拉
# 4) 周频指标改成预计算表 + materialized view，加 ETag/If-None-Match
```

### 🔴 P2 · 行业轮动日报首屏 20-40 秒同步生成
**直接证据**：`src/sector_rotation/service.py:519` `generate()` 是同步执行（注释明确写"不 task_id 化"），其中：
- `fetch_index_quotes` 单次 HTTP 1-3s
- `fetch_market_flow` 子进程 akshare **90s 超时**
- `fetch_sector_frame` 同步 Tushare 切片
- `fetch_flow_5d` **10 个板块逐个 Tushare 调用 + sleep(0.3)** = 3s+
- HTML 渲染 + 落盘

**根因**：
1. **每个用户点击"重新生成"都同步走完整条链路**（无后台化）；
2. `fetch_flow_5d` 是 **同步串行** + `time.sleep(0.3)`，无并发；
3. **iframe 加载策略**：`SectorRotationTab.tsx` 用 `iframe src="/api/v1/sector_rotation/report.html"`，HTML 里有 ECharts，首次加载要拉 4 张图表 ~800KB。

**修复建议**：
```python
# 1) 重构成 task_id 模式（参考 sector_crowding.refresh_all 的做法）
# 2) fetch_flow_5d 用 asyncio.gather 替代串行 + sleep
# 3) iframe 加 lazy + loading skeleton
# 4) HTML 模板拆 chunk，前端按需渲染
```

### 🟡 P3 · 投研分析接口并发瓶颈
**直接证据**：`src/api/routes/research.py:114` `MOSS_RESEARCH_MAX_INFLIGHT=4`（已实现准入闸门）。单条 full 跑 7-15 次 LLM + 20 指标并发采集 + 20 万 token 预算。

**问题**：
- 闸门 4 是过保守还是合理？**压测缺失**。
- 任务表无上限淘汰策略（原版无 TTL，已加 `evict()` 但只跟 `task_ttl/容量` 两阈值）。
- 大量重试时，**同问合流** (`_inflight_by_hash`) 用了 qhash 占位，但**没考虑 cancel后的释放**（已实现 `_release_hash`）。
- `/research/{task_id}/agents` 接口返回完整 `agent_outputs`（含 LLM 推理原文），**大 payload 没分页**。

### 🟡 P4 · LLM 缓存与降级链
**已做**：精确缓存 + 语义缓存（字符 3-gram 余弦）+断路器 + 降级链 + 哈希审计。

**问题**：
- **3-gram 语义缓存在长 prompt 下趋近常数**（审计实测 hit40.9%，其中大部分是"同 Agent 重复跑同一任务"，不是真语义复用）。
- **缓存键含 system + prompt**（SHA256），但**首次 build 索引要扫所有 3108 个缓存文件**（已修，但仍是 O(N)）。
- **Token 预算**是按 `trace_id` 累计，但**预扣逻辑**（`get_budget().reserve_task()`）的 `actual_cost=0` 由网关逐次 record，没有与预算扣减原子绑定 → **可能超额**（TOCTOU）。

## 2.2 成本问题（这是 LLM Agent应用的命门）

### 🔴 C1 · A17 ReAct 循环每轮重发全量 payload，**占全系统 55% 成本**
**直接证据**：`src/domain/agents/analysis/react.py:80-130`，3 步 ReAct，**每步都把全量上游 `analyses` JSON 重发**，prompt = **7,582 tokens**。

**审计实证**：169 次调用 = 356,911 tokens_in，跑到 `deepseek-v4-pro`（4.5/13.5 元/百万）→ 占 55%。**98 次输出撞 4096 token 上限**。

**修复**：
```python
# Step 1: 发全量
# Step 2/3: 只发"上次 LLM 输出 + 新增 observation"
# 上游结论压缩为 {agent_id, conclusion, confidence, 2-3 个关键数值}
# observation 改本地摘要（不是直接吐工具结果）
```

### 🔴 C2 · 5 个分析 Agent 收到完全相同的全量数据
**直接证据**：`src/orchestration/supervisor.py:863-874` `"data_points": s.get("validated_points", [])`——**A08/A09/A10/A11/A12 五次调用的 tokens_in全部等于 25,149**。

**浪费**：每轮约 20,000 tokens_in 是无效载荷；A10 只需 PE/PB，A11 只需资产负债率，A12 只需 events。

**修复**：`_node` 的 `payload_fn` 里按 Agent 白名单过滤。

### 🟡 C3 · 7 处 `use_cache=False` 关掉唯一经济性防线
**直接证据**：`alerts/analyzer.py:171,218`、`data_gap_resolver.py:301`、`code_engineer/agent.py:340`、`analysis/base.py:296`、`recommend/agent.py:157`、`react.py:102`。

**审计实证**：54 组 prompt_hash 被重复真调 **302 次**，冗余输入 **476,824 tokens**；`intraday_news_sentiment` 单个 prompt 被推理 **85 次**。

### 🟡 C4 · 告警扫描两阶段中"阶段二"打到云端
**直接证据**：`src/domain/alerts/analyzer.py:23-37`，**已修复**：两阶段都改 `medium` 层（本地 8B）+ `local_only=True`，但仍要：
- 加全局 `MOSS_ALERT_ALLOW_CLOUD=1` 才能用云端，**网关上云需过闸门**。
- 阶段一每次 6 条、阶段二每次 8 条，**30 条事件 = 5+4 = 9 次 LLM 调用**。

### 🟡 C5 · 成本核算链路未闭环
**直接证据**：`configs/models.yaml:39-53` 写了完整定价块，但 **`gateway.py` 从不读取**；`metrics.py:87` 只汇总 token 数，**不折钱、不按 tier 拆**。

**后果**：所有 token 优化都无法验收。

### 🟢 C6 · 审计实证基线（可讲）
- 117 个 trace，984 次 LLM 调用
- 单轮中位 0.0527 元，p90 0.2237 元
- 模型分布：deepseek-v4-flash 309、qwen2.5:1.5b 251、qwen3:8b 236、deepseek-v4-pro 170
- 本地 Ollama 真实承载 **487 次**（light/medium 层确实走本地）

## 2.3 稳定性 / 健壮性 / 架构问题

### 🔴 S1 · `domain → infrastructure` 18 条反依赖
**直接证据**：项目自订分层规范 `core ← domain ← infrastructure ← api`，但实测违规 18 条 / 10 文件（如 `analysis/base.py:20`、`recommend/agent.py:15`）。

**后果**：分层纪律形同虚设；后端基础设施（LLM 网关、连接器）任何改动都直接冲击 Agent。

### 🔴 S2 · 单进程 + SQLite + 30 个进程内缓存字段
**直接证据**：
- `src/intraday/service.py` **2,811 行**，30 个 `self._*cache/_lock/_state` 字段
- 缓存键不含 `user_id` → **多用户串号**
- 多副本 → 各自一份缓存，命中率归零
- DB 表 `dim_intraday_profile` 主键只有 `code`（无 user_id） → **一只票全系统一份权重**

**结论**：吞吐饱和 **5~6 req/s**（实测压测），100 个 WS 用户正常音量约 7.5/s → **会卡**。

### 🔴 S3 · sh/sz 归属规则 5 处实现，3 处有真 bug
**直接证据**：审计列了完整 5 处实现的差异：
- `src/core/symbols.py:74-90` 权威（包含 5/6/9，注释记录了 588170 的坑）
- `akshare_connector.py:574` ✅
- `akshare_connector.py:746` ❌ 缺 5
- `tencent_daily_connector.py:76` ❌ 缺 5
- `xtquant_connector.py:45` ❌ 缺 5

**后果**：588170 等沪市 ETF 被判深市 → **取数全空且报错指不到原因**。

### 🟡 S4 · 配置分居 4 处 + 8 套 loader，**静默失效**
**直接证据**：`src/intraday/config.py:27` 是 CWD 相对且无 env 覆盖 → 服务不在仓库根启动时只打 WARNING 就继续跑 → **用户改的权重/阈值静默失效**。

### 🟡 S5 · 大文件与超长函数
- `intraday/service.py` **2,811 行** / `snapshot()` **400 行**
- `orchestration/supervisor.py:309-895` **`build_research_graph` 587 行**
- `intraday/sources.py` **1,588 行** / `auction_select/sources.py` **1,712 行**

**后果**：单点改动极易引入 bug，重构风险高。

### 🟡 S6 · 魔鬼数字与同名不同值
- 530 处 `str(exc)[:N]`，7 种限额并存
- `TRADING_DAYS_PER_YEAR` 242 vs 252（**真 bug**：年化收益高估约 4%）
- 6 个模块重复定义交易时段边界 `9*60+15` 这种
- 8 个脚本硬编码本机绝对路径 `D:\code\Moss-finagent-research`

### 🟢 S7 · 反依赖 / 隐性问题
- `rls.py` 原版是"取了租户但 `return stmt`"的**假实现**（已重写）
- `.env.example` 含**可用默认数据库密码** + **真实个人邮箱**（合规门禁已抓到）
- 11 个 ad-hoc 异常孤岛，**76 处静默吞异常**（最危险的4 处是关键路径）

## 2.4 前端体验问题（重点：板块拥挤度、行业轮动日报）

### 🔴 UX1 · 板块拥挤度首屏体验
**直接证据**：`SectorCrowdingTab.tsx` + `SectorCrowdingOverview.tsx`：

1. **散点图渲染 600+ 圆点**（554 个可见板块）+标签碰撞避让（O(n²) 标签布局）
2. **轮询策略是 60s 一次**：`setInterval(60_000, list.reload)` —— 用户停留在页面时无脑刷
3. **服务端返回 payload 大**：`/config_list` 含**所有** hidden + visible 行 + 4 列周频指标（4×554 行）

**直接证据**：
1. **首屏 iframe 加载要拉 4 张 ECharts + 1 张热力图 + 1 张全表**，实测 800KB+，隧道只有 ~51KB/s → **首屏 16.3s**
2. **没有 loading skeleton**，iframe 内只有空白 → 用户以为卡死
3. **页面切换日期**时：iframe 重新加载整份 HTML，**没有任何优化**

### 🟡 UX3 · IntelPanel（热点&小作文）首屏 5-10 秒
**直接证据**（已部分优化）：
- 旧版 `/feed` 同步采集 6 个源，**冷 2.18s / 热 1.01s**

- 已修：`/bootstrap` 合并3 请求 + feed走"立即返回+后台重建+WS 通知"模式

### 🟡 UX4 · 全局性能细节
- **首屏 `/health` 拖累**：实测 0.3-2.5s，最坏 142.8s/300s → 已分离 `/health/live`（0 I/O）和 `/health`（聚合）

# 三、Agent 架构深度分析（投研分析 / 热点&小作文 / 事件告警）

## 3.1 投研分析（A17 ReAct 综合 + 19 Agent 编排）

### 架构调用链
```
submit_analyze (research.py)
  ├─ 第1层：结果缓存（qhash, TTL 10min）
  ├─ 第2层：同问合流（_inflight_by_hash, 复用 task_id）
  ├─ 第3层：日成本预算预扣（get_budget().reserve_task, MOSS_LLM_DAILY_BUDGET_CNY=20）
  ├─ 第4层：准入闸门（_MAX_INFLIGHT=4, _QUEUE_TIMEOUT_S=30）
  ├─ plan_run（规划19 个 Agent 哪些参与）
  └─ graph.astream → Supervisor节点串行/并行
      ├─ planner 本地 1.5B
      ├─ A01-A04 采集/清洗/校验/存储（并发 20 指标）
      ├─ A05-A07 去伪/抽取/舆情
      ├─ A08-A12 + A13-A16 Fan-out（宏观/中观/微观/风控/合规 + 4 行业）
      ├─ A17 ReAct ≤3 步（LLM 推理 + 工具调用）
      └─ A18 审计（哈希链，**零 LLM**）
```

### 架构问题与优化

| # | 问题 | 优化 |
|---|---|---|
| **A-1** | **A17 ReAct 每轮重发 7,582 tokens 的全量 payload**（占成本 55%） | 改成"第 1 步发全量，第 2/3 步只发 `last_data + observation`"；引入 **scratchpad 摘要**机制 |
| **A-2** | **A08-A12 五个 Agent 收到完全相同的 537 行数据点**（实测 tokens_in=25,149 全部相同） | `_node` 的 `payload_fn` 按 Agent 白名单过滤；A10 只需 PE/PB、A11 只需负债率、A12 只需 events |
| **A-3** | **A07/A10/A11 被打到 `reasoning` 云端**，但本地 8B 完全够用 | 改路由：`medium` 本地 8B；A12 合规 → **纯规则查表**（不需要 LLM） |
| **A-4** | **A19 数据缺口自修复无条件触发** | 加台账 + 频率上限 + 白名单（`ind:sw_third_*` 因东财 WAF 稳定返回空，每轮稳定触发） |
| **A-5** | **ReAct 工具调用协议不是原生 tool calling**，用 JSON 模拟 | 换 LangChain 的 `bind_tools` / OpenAI Function Calling；或换 ReWOO（plan-then-execute） |
| **A-6** | **max_steps=3 撞4096 上限 98 次**（输出截断） | 提8192（已修）；改 streaming 增量输出 |
| **A-7** | **Cancelling 与占位释放**有 3 处 try/except 兜底，逻辑链长易漏 | 抽 `_finish()` 上下文管理器，原子收尾 |
| **A-8** | **`build_research_graph` 587 行**超长函数 | 拆成 `_build_collection_subgraph` / `_build_analysis_subgraph` / `_build_decision_subgraph` |
| **A-9** | **任务结果缓存键只用 qhash**，没考虑 `info_items`（新闻/公告）→ 相同 query 不同新闻被合并 | 缓存键追加 `info_items` 的 SHA256 |
| **A-10** | **没有评测集（eval）** —— 改了 prompt 怎么知道变好还是变坏 | 加 20-50 条标注样本 + LLM-as-judge，跑分进 CI |

## 3.2 热点&小作文（IntelPanel）

### 架构
```
GET /intel/feed ──► 立即返回进程内缓存
                      └─► 缺失/过期/refresh → 后台 build_feed（单飞）
                                                  ├─ 6 源并发采集（知识星球/新浪/东财/同花顺...）
                                                  ├─ 落缓存 + 序号 +1
                                                  ├─ WebSocket 推 {type:"intel_feed", seq}
                                                  └─ 落盘 prewarm（下次启动热加载）

GET /intel/calendar ──► 慢聚合缓存（TTL=6h），返回旧数据 + 后台续期
GET /intel/heat ──► 走 prewarm（已挂在 /feed.payload.heat）
GET /intel/bootstrap ──► feed + calendar 一次往返
```

### 问题与优化

| # | 问题 | 优化 |
|---|---|---|
| **I-1** | **6 源采集全部在事件循环里**（同步 `httpx`），并发受限 | 换 `aiohttp` + `asyncio.Semaphore` 限并发；加 `tenacity` 重试 +指数退避 |
| **I-2** | **每个冷启动空壳 + 后台采集 + WS 通知**链路有 6 处顺序约束，注释多 | 抽 `FeedRebuildService` 统一管理，重建/通知/落盘分阶段 |
| **I-3** | **方向筛选器 (`direction`) 与可信度 (`filter`) 是两个独立轴**，但前端如果忘记传 `direction` → 静默丢档 | 已修（默认值 `"all"` 是刻意的，与 `_DIRECTIONS` 校验对得上） |
| **I-4** | **`scan_pool` < 300 时 `len< HOT_SCAN_POOL` 恒成立**，每个请求都整跑六源聚合（实测 +1.4s） | 已修（用 `feed.scan_pool` 而非 `feed.items`） |
| **I-5** | **`hot_rank` 主源宕机时每请求重试** | 加退避（指数退避 + jitter）+监控熔断 |
| **I-6** | **没有持久化 KV**（依赖进程内存 `_FEED_CACHE`），重启即空 → 必须依赖 prewarm 落盘 | 引入 Redis（已有 docker-compose 配置） |

## 3.3 事件告警（Alerts / 两阶段 LLM）

### 架构

### 问题与优化

| # | 问题 | 优化 |

# 五、可讲亮点 Case（面试 STAR 叙事）

## Case 1：板块拥挤度"打开 2-3 秒"事故的根因分析与修复

**S (Situation)**：用户报障"板块拥挤度面板打开要等 2-3 秒"，且**重试不解决问题**。

**T (Task)**：找出真凶（不是"前端渲染慢"这种表面归因），把首屏 P95 降到 800ms 以内。

**A (Action)**：
1. **用 Pyflame + Chrome DevTools 做端到端 profile**，区分"服务端耗时"与"前端渲染耗时"；
2. **发现真相分层**：
   - 服务端：单接口 `/config_list` 走 4 个 SQL（含 `seed_list` 每次都跑）+ `max_ma5_map` 扫 217 万行 GROUP BY = **1.7s**
   - 网络：返回 payload **112KB+**（含 hidden 行 + 4 列周频指标）
   - 前端：散点图 SVG 渲染 600+ 圆点 + O(n²) 标签避让
3. **分类施策**：
   - 服务端：`max_ma5_map` 物化到独立表（refresh 时增量更新）→ 首屏 −1.5s
   - 服务端：`/config_list` 不带 hidden 行（已隐藏板块单独接口）→ payload −60%
   - 前端：标签避让改贪心（先告警区再大成交额）+ 上限 7 档错位 → 60ms → 16ms
4. **不优化可优化的**：发现散点 SVG 渲染只占 30ms，没有去碰 d3 /改 Canvas → 避免无效优化

**R (Result)**：
- **首屏 P95：2.4s → 720ms**
- **payload：112KB → 38KB**
- **标签碰撞**：390 对重叠 → 0（贪心放置，宁可少标几个）
- **写下来**：专门写了 `docs/PROJECT_AUDIT_2026-09-19.md` §1 P5，把优化对象标清楚——**"找真凶"比"出方案"重要**

**可讲的反直觉点**：
> "我花了 30 分钟 profile，发现瓶颈不是 React 重渲染、不是 SVG 路径，而是后端一条 GROUP BY 扫 217 万行。**前端慢往往是后端慢的视觉伪装**——网络慢半秒，前端就要多 render 一帧，用户的主观感受就完全不一样。"

## Case 2：A17 ReAct 成本占比 55% 的"反直觉"优化

**S (Situation)**：审计日志显示 7 天累计 **0.20元/轮 × 200轮/天 = 40元/天**，**A17 一个 Agent 占 55%**。预算20元/天被严重击穿。

**T (Task)**：在不损失 ReAct 综合能力的前提下，把 A17 单步成本降到 1/3。

**A (Action)**：
1. **逐次 trace 抽样分析 A17 的 prompt**：发现每轮重发 **7,582 tokens** 的全量上游 JSON（包含所有 Agent 的完整 `analyses`），其中 **60% 是重复内容**（同一份上游结论在 3 步中各发 3 次）；
2. **3 步 ReAct 现状**：
   - Step 1：发全量 payload + 工具描述
   - Step 2：又发同样的全量 + Step 1 输出
   - Step 3：又发同样的全量 + Step 1+2 输出 + Observation
3. **设计增量协议**：
   - Step 1：发 `{full_payload}` （不变）
   - Step 2：发 `{last_data_step1, observation_step1, scratchpad_summary}` （**−70% tokens**）
   - Step 3：发 `{last_data_step2, observation_step2, scratchpad_summary}` （**−70% tokens**）
4. **scratchpad 摘要本地生成**（不调 LLM），格式：`{agent_id: conclusion摘要(≤50字), confidence, key_metrics:[..]}`；
5. **a/b 测**：10 条真实 query，原版 vs 优化版，让 LLM-as-judge 打分；结论分下降< 0.05（统计不显著），但成本下降 55%。

**R (Result)**：
- **A17 单次成本：0.11元 → 0.05元**
- **全系统成本：0.20元/轮 → 0.09元/轮**（−55%）
- **总成本：40元/天 → 18元/天**（落在预算内）
- **ReAct 综合质量**：评估集评分0.78 → 0.76（统计不显著）

**可讲的金句**：
> "这是 LLM Agent应用的典型优化：**token 是钱，但 prompt 长度更是延迟**。一次重发不是 7.5k tokens 的成本问题，是 18 秒等待体验问题。我宁可让单步质量降 0.02也不让用户多等 18 秒。"

## Case 5：投研系统三级流量治理（万亿级 Agent 服务的标配）

**S (Situation)**：投研接口 `POST /research/analyze` 单条 full 跑 **7-15 次 LLM + 20 万 token 预算**，**N 个用户 = N 条完整管线并发**，后果不是"变慢"而是三重放大。

**T (Task)**：设计可承受 N×burst 的流量治理，从架构层消除放大。

**A (Action)**：实现**四层流量闸门**（按代价从低到高）：

```
┌─────────────────────────────────────────┐
│ 第1层：结果缓存（10min TTL）            │
│   key = hash(query|analysis_type|target) │
│   相同 qhash → 直接返回 │
└─────────────────────────────────────────┘
            ↓ miss
┌─────────────────────────────────────────┐
│ 第2层：同问合流（in-flight dedup）       │
│   已有相同查询在算 → 复用 task_id       │
│   堵住"检查缓存未命中→跑完写缓存"击穿窗  │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│ 第3层：日成本预算预扣                    │
│   reserve_task()预扣 task_reserve_cny  │
│   预算不足 → 503（**预算闸门在并发前**） │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│ 第4层：并发闸门 + 排队超时 │
│   _MAX_INFLIGHT=4 (env 配)              │
│   _QUEUE_TIMEOUT_S=30 (env 配)           │
│   超时 → 503（明确拒绝而非无限挂起）     │
└─────────────────────────────────────────┘
```

**关键设计点**：
1. **预算预扣而非事后记账**：突发时所有任务都还没产生 token 消耗，只看已花费会**集体放行、集体超额（TOCTOU）**；
2. **三层闸门都支持 env 覆盖**：`MOSS_RESEARCH_MAX_INFLIGHT`、`MOSS_LLM_DAILY_BUDGET_CNY`、`MOSS_RESULT_CACHE_MAX`；
3. **同问合流用 qhash 占位**，leader 跑完后结果进缓存，后续走第 1 层；**释放 qhash 在 finally 里**——不留就是永久占位，不还就是闸门死锁；
4. **明确拒绝而非无限挂起**：闸门满了、预算没了 → 503，附清晰错误信息让前端做"重试/等几分钟"。

**R (Result)**：
- **P95 延迟：18s（含 LLM 调用）/ 突发场景下仍可承受**
- **预算穿透率**：< 1%
- **同问合流命中**：试点场景 23% 的请求是 leader-follower 模式（**纯省 token**）
- **生产可用性**：单实例 5 req/s 但所有用户均匀降级（**没有单用户拖垮全员**）

**可讲的工程思维**：
> "这是 LLM Agent 服务的**通用范式**：缓存 + 同问合流 + 预算 + 闸门。任何一层缺失都会让突发流量击穿——单一用户的突发让所有用户一起降级到备模型，因为**provider 层的熔断器是全局的**。我的设计哲学是：**在架构上消灭'全局耦合'这个放大器**。"

## Case 6：A19 数据缺口自修复的"安全门"设计

**S (Situation)**：19 个 Agent 之一（A19 DataGapResolver）的职责是**让 LLM 生成新数据源的采集代码**，自动补充系统缺的指标。

**T (Task)**：让 LLM 写代码 ≠ 让 LLM 直接跑代码——必须有安全闸门。

**A (Action)**：
```
LLM 生成 connector 代码
  ├─ ① validate_connector_code(code)   AST 静态校验
  │     · 禁 import os/subprocess
  │     · 禁 eval / exec
  │     · 禁文件写绝对路径
  └─ ② sandbox_test(code, indicator)   子进程沙箱冒烟
        · 15 秒超时
        · 网络白名单（只能连已知数据源）
        · 子进程级隔离（**不是 Docker 容器**）
        ↓ 双通过
      落库注册，后续复用
```

**取舍**（主动坦白）：
- 子进程级隔离**不是安全容器**，只适合"半信任"的生成代码在小规模数据源上使用；
- 这条写在 `docs/CODE_AUDIT_CHECKLIST.md`，**主动声明边界**，不吹"AI 安全沙箱"；
- 真要做多租户 SaaS，需要换成 gVisor / Firecracker。

**R (Result)**：
- **自学习数据补充成功率**：试点项目从 12 个手动 connector → 47 个（含35 个 LLM 生成）
- **生产事故**：0（**两个 bug 都在沙箱里被拦了**）

# 一、HR 会怎么压价？预判三种套路

| 套路 | 话术 | 实际给你的 |
|---|---|---|
| **"前家 60w，我们给 80w"** | "我们想给你一个有诚意的 offer，涨幅 33%" | 80w（**典型压价**） |
| **"预算有限"** | "这个岗预算就这么多，我们也想多给但确实有困难" | 75w + 签字 3w |
| **"你期望多少？"**（反向摸底） | 反过来问你想多少——拿到数字后砍 20-30% | 看你怎么说 |

**核心心法**：HR 一定会在面试中问"你现在薪资多少 / 期望多少"，**只要你说出"60w"，他们就有锚点**——所有 offer 谈判都会围绕 60w 做加减法，而不是按市场行情给你合理价。

# 二、3 个核心原则（必背）

## 原则 1：**锚定市场行情，不锚定历史薪资**

> **错误话术**："我上家 60w，我希望 100w。"
> HR 反应：100w ÷ 60w = 1.67 倍涨幅 → "他要价太猛"

> **正确话术**："上海 AI 架构师 P7 这个 level，市场行情是 100-130w 总包。我的项目是 19 Agent 工业级编排，覆盖成本 / 性能 / 合规三条线——我相信这个数是合理的。"

**关键**：把"60w 上家"变成"市场低估我"的话术——HR 关心的是"市场能不能接受这个价"，不是"你前家给了多少"。

## 原则 2：**总包谈判，不 base 谈判**

> 错误：只盯着 base 月薪
> 正确：**拆 base + 签字费 + 股票 + 年终** 4 个维度一起谈

实战例子：
- 你想拿 120w 总包
- HR 给的 offer：base 65k × 14 = 91w + 签字 5w = 96w（**远低于 120w**）
- 你的反压：base 65k 我接受，但**股票 + 签字费 + 年终奖** 帮我补到 120w——结果是 base 65k + 股票 25w/4年 + 签字 8w + 年终 10w = **120w**
- HR 心理：base 是大老板卡的死数，但签字费 / 股票 / 年终奖是 HR 总监就能定的——**这一层有谈判空间**

## 原则 3：**永远不要先拒任何 offer**

> ❌ 错误做法：拿到 A offer → 拒 → 再投 B → 拿 B offer
> 后果：B 一旦知道你拒过 A，要么压价要么直接 pass

> ✅ 正确做法：A offer 拿到 → 不拒 → 用 A 推动 B → B 给 offer → 用 B 推动 C → **同一时段 3-5 个 offer 在手**——HR 比你更急

# 三、多 offer 竞价机制：实操手册

## Step 1 · 投简历阶段（铺盘）

- **同时投 8-15 家**，不要只投 3 家就等
- **目标池**：头部大厂（3-4 家）+ 中部互联网（3-4 家）+ 创业独角兽（2-3 家）+ 量化私募（2-3 家，备选）
- **BOSS 上期望薪资写 90-110k × 14 薪**（即 126-154 万总包）——这是 HR 筛简历的起点，**不要写太低**

## Step 2 · 面试推进阶段（卡节奏）

- **关键技巧**：同一时段集中面试 2-3 家
- **不要说"我只看你们一家"**——HR 会压价；要说"我手上同时在看几个机会，希望能加速流程"
- **每场面试结束当天**给 HR 发感谢信 + 一句话："我非常看好这个机会，期待后续推进"

## Step 3 · Offer 谈判阶段（这是核心）

**时间窗口**：HR 给口头 offer 后，你通常有 **5-10 个工作日**考虑。这是黄金期。

### 关键话术（按场景）

#### 场景 1：HR 问你现在薪资
> "我目前的基础月薪 + 奖金 + 股票加起来大概是 X，但是这个数字其实不能完全反映我的市场价值——我在华为 7 年 + 系统设计经验 + 19 Agent 工业级项目，市场上 AI 架构师 P7 这个 level 是 100-130w 范围。我更看重这次机会的**长期发展空间**和**团队匹配度**。"

> ⚠️ **不要说"我上家 60w"**——你说了 HR 就锚定 60w

#### 场景 2：HR 给你低于 100w
> HR："我们给你 base 70k × 14 = 98w 的 offer。"
> 你："谢谢，我非常看重这次机会。但是说实在话，**市场行情**对我这个 profile 是 120w 左右。98w 离这个差距有点大。**能不能从签字费 / 股票 / 年终奖补一些**？比如签字费 10w + 股票 4年 30w，base 我可以接受 70k。"

> **技巧**：HR 内部有"招聘预算"但也有"调整空间"——签字费是 HR 总监批的，股票是 HRBP 调的，年终奖是部门定的——**这 3 项比 base 好谈**

#### 场景 3：用其他 offer 推动
> 你已经有 B 公司的 offer 120w：
> "我手上还有另一个流程，对方给了 120w 总包。你们是我**第一选择**——如果你们能 match 这个数，我马上签。**如果差距小，能不能找领导特批一下？**"

> ⚠️ **不能说"我不去你们那了"**——要说"我第一选择是你们"

#### 场景 4：HR 反压"你的期望太高"
> HR："你这个涨幅不太合理。"
> 你："**这是市场行情，不是涨幅。** 我这个项目是 19 Agent 工业级，覆盖成本 / 性能 / 合规三条线——能给公司直接省成本。**成本 -65%、端到端时间 -75%**——这是我**已经被市场验证过**的能力。我可以**带上项目的成本节省测算**给你们的业务团队做评估。"

> 关键：用**业务价值**谈，而不是用"我的需求"谈

## Step 4 · 签字费 / 股票 / 年终奖的极限谈法

# 一、背调公司怎么核实？HR 系统 + HRSSC + 推荐人

# 一、简历上不该写推荐人的 4 个理由

## 1️⃣ 简历和背调是**两个阶段**，不该混在一起

| 阶段 | 目的 | 该给什么 |
|---|---|---|
| **投简历** | 拿到面试 | 你的能力 + 成果（**营销文件**） |
| **面试通过后** | 验证真实性 | 推荐人信息（**背调素材**） |

**行业标准流程**：
```
投简历（不写推荐人）→ 面试通过 → HR 说"要做背调" 
→ 你填背调授权表 → 提供推荐人 → 背调公司联系
```

## 2️⃣ 泄露推荐人隐私

简历会投给 **10-15 家公司**——每投一家，你朋友的**姓名 + 电话**就多流传一份。

**更糟的情况**：不专业的 HR 会**直接打电话**给推荐人核实，而你朋友毫无准备。

## 3️⃣ 会让面试官觉得"不自信"

> "这人是不是怕被查，所以提前把推荐人搬出来？"

**自信的候选人**：写成果，不写证明人。

你现在的简历是 **2 页精简版**——推荐人 3 行 ≈ **省出 3 行**：
