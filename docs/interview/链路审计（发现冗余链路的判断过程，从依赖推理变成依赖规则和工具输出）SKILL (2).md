# 链路审计 skill：把「发现冗余」从依赖推理变成依赖规则和工具输出

> **一句话**：AI 写代码时看到的是「代码现在长什么样」，不是「业务实际需要什么」。
> 它看到 `for sector in ALL`，不会追问「消费端到底要几个」。
>
> 本 skill 把「找出来」交给工具，只把「能不能动」留给人/AI 判断。

---

## §0 · 先划边界：这里有**三种**不同的审计

| | ① 静态死代码 | ② 运行时白算 | ③ **准备态错配** |
|---|---|---|---|
| 特征 | 写了但**从未被调用** | 每次都在跑，输出**没人读** | **准备了，消费概率极低，成本持续发生** |
| 消费集 | 封闭、可枚举 | 封闭（固定渲染出口） | **开放、不可枚举**（用户/Agent 自由提问） |
| 证据 | 引用图 | 执行计划 / 计数对比 | 调用埋点 + 成本账 |
| 工具 | vulture / knip / CodeQL | **没有现成的，必须自己写** | 血缘图 + 埋点 |
| 结论 | 可能删除 | **可能收口** | **分层：热/温/冷/死** |

**③ 是 AI/Agent 系统特有的，也是传统前后端审计最容易判错的一类。**
在 Agent 系统里，数据预处理脚本、skill、爬虫调度都是「随时准备被调用」的状态——
**"今天没被调用"不等于"明天不会被调用"**。

⚠️ 本 skill 最大的风险是**工具本身出错**（§6 记录了 10 次真实误判，每次都让结论反向）
和**消费集判错**（§6.9/§6.10）。**没做完这两项核对，不许出结论。**

## §1 · 三种准备态资产，成本结构完全不同

> 来源：用户 2026-09-27 提出的框架。**先分类，再审计**——混在一起必然判错。

### ① 活跃消耗型 Active
定期爬取、定时调度、每日 ETL。**不管有没有人消费，成本都在发生。**
- 判据：用「最近 N 天消费次数」量化，连续 30 天零消费 = 明确候选
- 例：每天凌晨爬全部板块资金流并落库

### ② 惰性存储型 Passive
已落库的表、已注册的 skill、写好的脚本。不调用就不耗算力，只占存储。
- 判据：**不能只看调用次数**，还要看「是否增加了 Agent 的选择噪声」
- 例：写了但没有任何 Agent 调用的 `fetch_xxx.py`

### ③ 半活跃依赖型 Semi-active
被其他 skill 间接依赖。A 没被直接调用，但 B 调 A，B 偶尔被调用。
- 判据：**传递闭包**分析，不能只看直接调用
- 例：`normalize_quotes.py` → 被 `calc_rolling.py` 引用 → 后者每周被 Agent 调一次

**有效使用率**（这是核心公式）：

```
effective_usage_rate(node) = max(usage_rate(d) for d in all_downstream(node))
```

一个表被三个 skill 读，其中两个零调用、一个每周一次 → 有效使用率是**每周一次**，不是零。

## §2 · 四阶段工作流

### 阶段一：Orient —— 枚举资产 + 建血缘图

**第 0 步（强制）：枚举消费方类别。** 漏掉任何一类，"前端没调"就会被误读成"没人用"。

| 消费方 | 怎么找 |
|---|---|
| 前端页面 | `web/src/**` 里构造的请求路径 |
| **Agent / 管线** | `runtime.agents.get(...)`、Agent 类里的 service 调用、**system prompt 里的工具清单** |
| **调度器 / 定时任务** | `src/scheduler/`、各模块 `scheduler.py`、cron / Airflow DAG |
| **运维 / 脚本** | `scripts/`、`manage.py`、`docs/OPS_GUIDE.md` |
| 外部调用者 | OpenAPI 对接、Kafka topic、外部 API、监管流程 |

```bash
# 调度资产
grep -r "cron\|schedule\|airflow\|DAG\|dagster\|prefect" --include="*.py" --include="*.yaml" --include="*.toml"
# skill 注册 / 工具定义
grep -r "@tool\|register_skill\|SKILL.md\|tool_registry\|skill_registry" --include="*.py" --include="*.md"
# ETL / 爬虫
grep -r "requests.get\|spider\|crawl\|fetch_\|etl_\|extract_" --include="*.py"
# 枚举常量与循环边界（"要算多少个"的落点）
grep -rn "ALL_\|_SECTORS\|_CODES\|universe" src/ configs/
grep -rn "for .* in \|executemany\|iterrows" src/
```

**血缘图**（不用一次建全，近似图就够第一轮）：

```
[爬虫脚本] → [原始表] → [预处理脚本] → [特征表] → [skill] → [agent]
```
每个节点挂两个属性：**成本**（CPU 秒 / 存储 GB / 请求数 / 调度频率）、
**最近 N 天消费次数**。

三种解析方式合并：
* `sqlglot` / `sqllineage` / **LineageX** → SQL 列级血缘（LineageX 不需执行查询，适合 CI）
* Python `ast` → 脚本的 import 与文件读写
* skill 注册表的 `downstream_tables` 字段补全

### 阶段二：Instrument —— 先埋点，再审计

> 🔴 **没有消费数据时，任何冗余判定都是猜测。** 若系统没有埋点，
> 本 skill 的**第一个输出就是"先加埋点"**，而不是一份审计报告。

每次 skill 调用 / 脚本执行 / 数据读取都产生一条结构化日志：

```json
{
  "event": "skill_invoked",
  "skill_id": "fetch_sector_flow",
  "agent_id": "main_line_miner",
  "timestamp": "2026-09-27T10:23:11Z",
  "input_params": {"sector_codes": ["BK0001"], "window": "5d"},
  "downstream_tables_read": ["quotes_daily", "moneyflow_daily"],
  "duration_ms": 420
}
```

**关键字段是 `downstream_tables_read`** —— 它把「skill 被调用」和「数据被消费」连起来。
没有它，你只知道 skill 跑了，不知道它读了哪些表、用了哪些板块。

聚合查询：
```sql
SELECT skill_id, count() AS invoke_30d, max(timestamp) AS last_invoked,
       sum(duration_ms) AS compute_ms
FROM skill_invocations WHERE timestamp > now() - INTERVAL 30 DAY
GROUP BY skill_id
```

### 阶段三：Audit —— 运行时证据，不读代码

按可靠性从高到低：

| 手段 | 适用 | 要点 |
|---|---|---|
| **A. 计数对比** | 通用，最容易做 | 产物表行数 vs 清单表行数；**必须记"改前/改后"** |
| **B. 任务台账** | 有任务对象 | `task.total` / `rows_written` / `seconds` 就是现成埋点；翻历史实测记录比重跑省事 |
| **C. 执行计划** | Spark/Flink/PG | `EXPLAIN (ANALYZE)`；对比 Scan 实际行数，不看代码结构 |
| **D. 依赖闭包** | 半活跃型 | 用 `effective_usage_rate`，不是直接调用数 |
| **E. 埋点指纹** | 兜底 | 连续 N 次运行的输入指纹相同 → 偏差是持续的，不是偶发 |

## §3 · 输出不是「删除清单」，是**分层策略表**

> 这是 Agent 系统审计与传统前后端审计**最大的区别**。
> 传统场景：554 算 140 用 → 改成 140 算就行。
> Agent 场景：**不能因为"最近 30 天没调用"就删掉一个 skill** ——
> 未来某个 Agent 可能突然需要它。

| 层级 | 判定条件 | 策略 |
|---|---|---|
| **热路径** | 最近 7 天消费 ≥ 5 次 | 保持全量更新、实时调度 |
| **温路径** | 最近 30 天消费 1–4 次 | **降频**（每日→每周）或改按需触发 |
| **冷路径** | 最近 90 天消费 0 次，但**仍被注册为可用** | **懒加载化**：不预计算，调用时实时算 |
| **死路径** | 最近 180 天消费 0 次，**且无下游依赖** | **归档**（非删除），从注册表移除 |

### 关键动作：冷路径的「懒加载化」

把「每天预计算全量」改成「消费时按需计算所需部分」。
**不是删掉计算逻辑，而是让它从"预计算"变成"按需计算"** ——
从**持续成本**变成**偶发成本**。

> 这一步直接解决「未来可能被问到，但现在没人问」的两难：
> 能力保留了，成本不常态发生。

## §4 · 安全门禁（不可绕过）

建议任何**归档/移除**前，强制四查，任一未过则降级为「标记但保留」并写明原因：

1. **注册表检查** —— 该资产是否被注册为可调用 skill / tool？
2. **Prompt 引用检查** —— 是否有 Agent 的 **system prompt 里引用了它**？
   > Agent 的行为由 prompt + 工具列表共同决定。**prompt 里写了但从不调用，
   > 问题在 prompt 设计，不在这个 skill。** 这条防止把"prompt 写了没人用"误判成代码冗余。
3. **隐藏依赖检查** —— 是否有非代码路径的消费者（外部 API、Kafka、在线特征存储、监管/合规流程）？
4. **Git 历史检查** —— `git log --follow`：是否近期被**有意保留**？（找 `kept for backward compat` 之类注释）

### 硬规则

| 规则 | 依据 |
|---|---|
| 「零导入者 ≠ 死代码」 | 这是**猜测**，不是**发现**；必须 git history 调查 |
| 「零使用 ≠ 零价值」 | 可能支撑外部 API / 流 / 监管流程 |
| 「LLM 不计算爆炸半径」 | 爆炸半径从血缘图**确定性计算**，不由 LLM 猜 |
| 「先加埋点再审计」 | 没消费数据时任何判定都是猜测 |
| **「从不自动执行删除」** | 只输出**有证据的提案**，交人工审批 |

## §5 · 前沿工具（已核实，2026-09）

> ⚠️ 下列条目**逐条联网核实过**。标注「论文」的是可查证研究，
> 标注「黑客松/社区」的**不要当生产产品引用**。

### 死代码检测
| 工具 | 性质 | 用法 |
|---|---|---|
| **DCE-LLM** | 论文（[NAACL 2025](https://aclanthology.org/2025.naacl-long.501/)、[arXiv 2506.11076](https://web3.arxiv.org/abs/2506.11076)） | LLM 缩小搜索范围 + 静态分析交叉确认 |
| `vulture`(Py) / `knip`(TS) / CodeQL unreachable / semgrep | 生产工具 | **确定性基线**，先跑它们出候选 |
| **CodeGraph**（[MCP server](https://mcprepository.com/codegraph-ai/codegraph-vscode)、[HelgeSverre/codegraph](https://github.com/HelgeSverre/codegraph)） | 社区 | 代码知识图谱 / 影响面分析。⚠️ 具体工具名与置信度评分**未核实**，引用前先看其文档 |

**结论**：静态工具产出候选清单 → LLM 只判「候选里哪条能安全移除」。
混合方法（静态做基线 + LLM 处理条件性死代码）在行级性能与召回率之间最平衡。

### 数据血缘与管道治理
| 工具 | 性质 | 要点 |
|---|---|---|
| **LineageX** | 论文+开源（[arXiv 2505.23133](https://ar5iv.labs.arxiv.org/html/2505.23133)、[sfu-db/lineagex](https://github.com/sfu-db/lineagex)） | SQL **列级**血缘，**不需执行查询** → 适合 CI |
| `sqlglot` / `sqllineage` | 生产库 | 解析 SQL 血缘 |
| DataHub / OpenMetadata | 平台 | 企业级血缘 + 影响分析 |
| **FlowJury** | ⚠️ [**devpost 黑客松项目**](https://devpost.com/software/flowjury) | 设计思路值得借鉴（见下），但**别当生产产品引用** |

**FlowJury 值得借鉴的 4 个设计决策**（作为设计参考，不是工具背书）：
1. **零使用 ≠ 零价值** —— 数据集零查询也可能支撑外部 API/Kafka/监管流程
2. **Skeptic Review** —— 高风险建议由独立节点挑战验证
3. **爆炸半径确定性计算**，不由 LLM 猜
4. **Never auto-disable** —— 只生成有证据的提案供人审批

### Agent 可观测性

## §6 · 工具与建模的 10 个坑（**全部真实踩过**）

> 这一节是本 skill 存在的主要理由。**每一条都曾让结论完全反向。**

### 6.1 只看"绝对路径"，漏掉 `PREFIX + 相对路径`
```ts
const PREFIX = "/api/v1/auction_select";
fetch(PREFIX + path)            // path 来自 request("/today")
```
`"/today"` 不以 `/api` 开头、也不含模块名 → 整组接口被判"没人用"。
**修法**：本文件的 `/api/...` 常量 × 相对路径字面量做**笛卡尔积超集**。宁可多认，不可漏认。

### 6.2 段全是变量时被丢掉
`/users/${id}/approve` 整段替换成占位符后若**丢弃**该段，段数就对不上（6 vs 5）。
**修法**：整段是变量时**保留成参数段**。

### 6.3 段尾拼接没归一
`` `/alerts${suffix}` `` → `alerts{p}` ≠ `alerts`。**修法**：比较前剥掉段内占位符。

### 6.4 用「最后一段」当特征串
`state`/`list`/`watch`/`today` 满仓都是 → 89 个孤儿全判成"到处被引用"，等于没判。
**修法**：特征串**至少两段**（`auction_select/state`）。

### 6.5 把构建产物也索引了
`web/dist-pilot/**` 是打包 JS，含全部接口字符串 → "前端有没有引用"**恒真**。
**修法**：排除 `dist*`/`node_modules`/`.venv`；注意按**路径分量**判，别按字符串前缀。

### 6.6 没去注释、没排除常量声明
文档里提的接口、`const PREFIX = "..."` 都被算成调用点 → 真 BUG 被假阳性淹没。
**修法**：去行/块注释（保持行号）+ 排除"整行右边就是一个字符串字面量"。
⚠️ **不能**简单排除所有 `const` 开头的行（`const rows = await get(...)` 是真调用）。

### 6.7 段边界 lookahead 漏了 `/`
`` `/item/${hash}` ``、`/board/${code}` 匹配不上 → 5 个**在用**接口被误报。
**修法**：lookahead 含 `/`：`[/?#`'"\s]|$|\$\{`。

### 6.8 只把「前端」当成消费方 —— **建模错误**
本项目里 `code-engineer/*`（A19 编码实现 Agent）、`intraday/auto-select`（调度器）
被列成"疑似可删"。**"前端不调用"是零决策价值的信号**，除非已枚举过 §2 阶段一那五类。
📌 报告里**禁止写"没人用"**，只能写「**前端未消费**（其余消费方：…）」。

### 6.9 ⛔ 「算了没人读」**不等于**冗余 —— 但要分清**哪一层**

> 用户原话（投研场景）：
> 「用户未来可能会问到的一些宏观产业行业数据，当下没被用到，不代表明天不会有
> 用户问到。如果问到了，就优先从数据库查询，比直接网上到处搜索更快更靠谱。」

| | 封闭消费集 | **开放消费集** |
|---|---|---|
| 典型 | 固定页面/报表 | 用户/Agent **自由提问**、按需下钻、RAG |
| 可枚举吗 | 能 | **不能** |
| "当下没人读" | **强冗余信号** | **什么也不意味** |
| 做法 | 按渲染范围收口 | **当预物化保留** |

**在投研/研究型系统里，覆盖度本身就是产品价值。**

### ⚠️ 但 6.9 最容易犯的次级错误：把「原始数据」和「派生指标」混为一谈

> **这条是我自己踩过的。** 我引用了原代码「以后想看行业拥挤度不用重跑 6 年」
> 来论证"派生指标也要全量预计算"—— **引用错了，那句话说的是原始数据。**

| 层 | 重算代价 | 要不要全存/全算 |
|---|---|---|
| **原始数据**（行情、资金流、成交额） | **贵**：要重新联网抓 6 年 | ✅ **全存**，与渲染范围无关 |
| **派生指标**（滚动、水位、聚合列） | **便宜**：本地重算，实测全库 217 万行 **91 秒**、零网络 | 按**重算代价**决定，可以按渲染范围收口 |

**判据要分两层问：**
1. **原始数据要不要留全？** → 看消费集是否开放 → 开放就留全（这层别省）
2. **派生指标要不要预算？** → 看**重算一次多少钱** → 便宜就按需，贵才预物化

把这两层混起来，会得出"什么都不能收"或"什么都能删"这两种都错的结论。

**正解往往是 §3 的冷路径懒加载**：
热路径（真被渲染的）预计算，冷路径**按需算** —— 能力一点没少，
因为原始数据还在，重算只要几秒。

📌 **连带陷阱**：加黑名单后，**"恢复/新增"通路必须能撤销它**。
本项目 `POST /config_list` 与 `/restore` 只写 `visible=1`、不碰剔除清单 →
接口回 `{"restored": 1}` 而板块**不出现**，静默失败。

### 6.10 把「可能被渲染」当成「默认渲染」
看板 554 个可见板块，其中 262 个概念板块；「只看概念板块」**默认勾上**。
按 554 收口 → 292 个仍白算。
**判据必须是"默认渲染集合"，不是"可能被渲染的集合"。**

📌 **连带陷阱**：加黑名单后，**"恢复/新增"通路必须能撤销它**。
本项目 `POST /config_list` 与 `/restore` 只写 `visible=1`、不碰剔除清单 →
接口回 `{"restored": 1}` 而板块**不出现**，静默失败。

## §8 · 铁律

1. **工具负责"找出来"，AI 只负责"能不能动"。** 不让 AI 读代码猜冗余。
2. **没有运行时计数，不许说"冗余"。**
3. **工具自己会错，而且错得反向。** 出结论前抽 3~5 条人工复核。
4. **区分"全量落库"和"全量计算"。** 落库常是**故意**的（"以后想看不用重跑 6 年"）——
   收的是**计算**，不是存储。
5. **收口必须可回退 + 有防呆。** 范围为空时**退回全量并告警**，
   绝不能算成"本周 0 条"—— 那会落成 0 行却报成功、**不抛任何异常**。
6. **加黑名单必须同时设计"怎么加回来"。**
7. **报告要写清置信度档。**不同置信档不能混在一张表里。
8. **报告里禁止写"没人用"**，只能写「**前端未消费**（其余消费方：…）」。
9. ⛔ **先判消费集是开放还是封闭**（§6.9）。开放消费集里的"当下没人读"
   **不构成任何收口理由** —— 那是预物化。
10. **投研/研究型系统默认按"开放消费集"处理。** 覆盖度就是能力；
    要省就省**单次成本**（缓存/增量/本地重算），**不要省覆盖范围**。
11. **输出分层策略，不是删除清单。** 冷路径懒加载化，死路径归档，
    **从不自动执行删除**。

**判据不是"当下有没有人读"，而是：**

> **再算一次的边际代价  vs  少答一类问题的代价**

## §9 · 实战案例

### 案例 A：板块拥挤度周频指标（**收口正确，但我一度想反悔、而且反悔错了**）

| 项 | 值 |
|---|---|
| 后端实际计算 | 1479 个板块 |
| 前端默认渲染 | 262 个（`visible=1` 且 `is_concept=1`） |
| 表面"冗余" | 82.3% |
| **真实节省** | **3.4 秒/周**（262 板块 3.37s vs 554 板块约 7s） |
| **结论** | ✅ **收口正确**：派生指标只花 3.4 秒，且**原始日线一行没动** |

* 根因：① 接口契约里没有"范围"入参 → 后端默认全量成为事实口径；② 驱动侧以全量表为准
* 真该收的是另一批：**用户自己移除的 671 个**（`visible=0`，已决策的封闭集合）

⚠️ **我自己在这上面又错了一次，值得记：**
我先说"82.3% 是白算"（**错**：开放消费集里当下没读≠冗余），
改成"应回退到 554 保住行业指数"（**又错**：引用的"不用重跑 6 年"说的是**原始数据**，
而周频 4 列是**派生指标**，本地全库重算只要 **91 秒**、零网络）。

**最终正确表述**：
* **原始数据层**（6 年行情）→ 开放消费集 → **全存**，与渲染范围无关
* **派生指标层**（周频 4 列）→ 重算只要 91 秒 → **按渲染范围收口是对的**
* 缺的是"按需补算单个板块"的通路，**不是**把范围改大

**→ 这就是 §3 冷路径懒加载的标准形态：热路径预算、冷路径按需。**

### 案例 B：接口层审计净结果 —— **零可删**

215 个后端接口全量配对：全仓零引用 0 / 前端未消费 22（Agent·调度·运维在消费，**全部保留**）/
路径没配上 44（置信度低，不动）/ 前端调了后端没有 11（全是解析残渣）。

### 案例 C：水位分母的样本量偏差（**"收缩估计"被自己的回测证伪**）

* 水位 = `当前平滑拥挤度 / 该板块近 6 年最大值`，分母是**样本最大值**，
  `E[M_n]` 随 n 单调上升 → 历史短的板块水位**系统性虚高**（曾有 218 个板块误报 ≥80%）
* 原方案用二值门槛 750 堵 → **只把悬崖挪了个位置**（750~1460 根有 1033 个板块，仍不等价）
* 第一方案「向同类中位数收缩」→ **截断回测证伪**：越收越偏（k=0 偏差 +0.047 → k=250 时 **+0.099**）
  原因：`M_peer` 是横截面中位数，向它收缩会把**高于中位**的板块分母**调小**，水位反而更高
* **最终方案（已验证）**：尺度校正 `denom = M_n · r(n)`，`r(T)=median(M_full/M_T)`

| T | r(T) | 朴素偏差 | 校正后偏差 | MAE 改善 |
|---:|---:|---:|---:|---:|
| 60 | 2.6207 | +0.3502 | **−0.0612** | **54.3%** |
| 250 | 1.7021 | +0.1801 | −0.0241 | 27.0% |
| 750 | 1.0000 | +0.0470 | +0.0470 | 0% |

* 验收：32/33 短历史板块救回，**告警率 0%**（对照满窗组 6.1%），中位数对齐 0.372 vs 0.351
* ⚠️ **教训**：`r(T≥750)=1` 是**实测结论**不是设的；而"收缩"这个听起来更高级的方法
  在数据面前是错的。**先做截断回测，再选方法。**

> 三轮审计里，**机械工具连错 10 次**（§6.1–§6.10），孤儿接口数在
> 118 → 89 → 109 → 86 → 69 → 92 → 91 → **22** 之间反复横跳；
> 其中**第 8 个是建模错误**（§6.8）、**第 9 个是判断错误**（§6.9）——
> 后两个比前八个严重得多：工具错给出**错答案**，判断错给出**看起来很对但方向反了**的答案。
> **所以 §6 不是附录，是正文。**
