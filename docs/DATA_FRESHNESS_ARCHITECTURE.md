# 数据新鲜度评估架构设计

> 面试亮点版 | 2026-09-15 | 实现参见 `src/core/data_freshness.py`

---

## 一、为什么需要这个模块？

### 1.1 旧系统的硬伤

| 问题 | 症状 | 后果 |
|------|------|------|
| **硬编码月阈值** | "宏观 >12 月过时，行业 >6 月过时" | 长周期船舶数据 18 个月被误杀；日频 PE 断档 7 天却还放行 |
| **无行业周期感知** | 所有指标用同一套阈值 | 半导体（中周期 30 个月）和消费电子（短周期 12 个月）用一样的过期判定 |
| **全有全无过滤** | 过期要么展示要么删除，没有中间态 | LLM 看到 24 个月前的行业数据，不知道该信几分 |
| **与 Prompt 脱节** | 过滤逻辑在数据层，Prompt 层没有时效标注 | LLM 不知道 "2025-10" 的半导体出货量同比该信几分 |

### 1.2 新系统解决什么

1. **发布频率分类**：日/周/月/季/年/长周期——每种有独立的 warn/filter 阈值
2. **行业周期倍数**：短/中/长/超长——衰减速度随行业自然变化
3. **指数衰减置信度**：连续评分，不是跳级
4. **硬截止 vs 软权重**：两层分离——过期不能绕过，新鲜度有中间态
5. **Agent/Prompt 全链路对齐**：Router DB 判定、_build_context 行内权重、LLM 时效红线——三处用同一套 evaluator

## 二、核心设计：两层分离

### 2.1 硬截止层（filter_days）

**业务决策**——什么叫"完全不可用"，超过这个天数的数据**不进 LLM prompt**、**不进 Router DB 命中**。

```
┌──────────────────────────────────────────────────────────┐
│  指标前缀              │ 发布周期 │ filter_days            │
│  ──────────────────────┼─────────┼────────────────────── │
│  PE(PB/换手率/FedWatch) │   1 天   │ 30 天 （日频）         │
│  weekly_inventory      │   7 天   │ 90 天 （周频）         │
│  CPI/PPI/M2/社融        │  30 天   │ 365 天 （月频）        │
│  季度营收/产能利用率     │  90 天   │ 540 天 （季频）        │
│  渗透率/研发投入         │ 365 天   │ 1095 天 （年频）       │
│  船舶订单/核电装机       │  90 天   │ 1440 天 （长周期）     │
└──────────────────────────────────────────────────────────┘
```

**为什么 exp 不能代替 filter_days？**

```
λ=0.5, CPI 月频(cycle=30) → exp(-0.5*365/30) = exp(-6.08) ≈ 0.002
λ=0.5, PE 日频(cycle=1)  → exp(-0.5*30/1)   = exp(-15)  ≈ 3e-7

如果用 conf < 0.1 当硬截止：
  CPI 只有 ~138 天有效期
  PE 只有 ~4.6 天有效期
这和业务常识完全不符——CPI 半年前的数据仍然有参考价值！
```

所以 **filter_days 是独立于指数衰减的业务决策线**，不是数学推导的结果。

### 2.2 软权重层（指数衰减 confidence）

**分析决策**——在有效期内，数据越旧权重越低。

```
confidence = exp(-λ × days_since / (publish_cycle_days × industry_multiplier))

λ = 0.5（默认，可配置）
```

#### 五级分级（与 confidence 绑定）

| 区间 | 状态 | 图标 | 权重 | LLM prompt 里的表现 |
|------|------|------|------|-------------------|
| 0.9-1.0 | fresh | ✅ | 1.0× | 正常展示，全权重 |
| 0.7-0.9 | normal | ✅ | 1.0× | 正常展示 |
| 0.4-0.7 | lagging | ⚠️ | 0.7× | 标注 "数据可能滞后" |
| 0.1-0.4 | stale | 🔶 | 0.3× | 标注 "数据陈旧，仅供参考" |
| < filter_days 硬截止线 | expired | ⛔ | 0.0× | **完全不进 prompt** |

#### 行业周期倍数怎么放大衰减差异

| 行业 | 倍数 | CPI 365 天 conf | PE 15 天 conf | 说明 |
|------|------|-----------------|---------------|------|
| 消费电子（短周期） | 1.0× | 0.002（硬截止外） | 0.0006（硬截止内→stale） | 消费电子一年前数据确实过时 |
| **半导体（中周期）** | **1.5×** | 0.05 | 0.0009 | 半导体 18 个月数据仍有参考 |
| **船舶（长周期）** | **2.0×** | 0.14 | 0.002 | 船舶 24 个月数据 lagging 而非过期 |
| 铜（超长周期） | 2.5× | 0.29 | 0.003 | 大宗商品大周期 |

## 三、全链路对齐

### 3.1 三个消费点共用同一个 Evaluator

```
┌─────────────────────┐
│   DataFreshness     │
│   Evaluator         │
│   (纯函数+配置查找) │
└──────┬──────────────┘
       │ 三处消费，同一口径：
       │
       ├──────────────────────────────┐
       ▼                              ▼
┌──────────────┐              ┌──────────────┐
│ Router       │              │ Agent        │
│ _is_db_fresh │              │ _build_context│
│              │              │              │
│ conf>=0.4    │              │              │
│ → DB 可用    │              │ 每行带       │
│              │              │ icon/conf/   │
│              │              │ weight/标注  │
└──────────────┘              └──────────────┘
       │
       ▼
┌──────────────┐
│ LLM prompt   │
│ 时效红线     │
│ （硬约束）   │
└──────────────┘
```

### 3.2 Router DB 判定

```python
def _is_db_fresh(points, indicator, today=None) -> bool:
    """DB 最新点 conf >= 0.4（lagging 以上）才算可用。"""
    fe = DataFreshnessEvaluator.evaluate(
        indicator, newest_period, today=today
    )
    return fe.confidence >= 0.4
```

PE stale（conf < 0.1）→ DB 命中也会**穿透到网络刷新**，不会假装旧数据是新的。

### 3.3 Agent Prompt 展示

```
### 当前日期锚定：2026-09-15
### 输入数据：42 条展示（45 总 / 3 过期已过滤）
### 新鲜度机制：指数衰减 exp(-0.5×d/(周期×行业倍数))
### ⚠️ 以下指标新鲜度下降：ind:半导体PE(TTM)(⚠️ lagging)

- PE(TTM):300308 ✅ | 期间 2026-09-14 | 值 50.28 | 来源 百度 | 置信度 0.98
- 半导体出货量同比 🔶 | 期间 2025-10 | 值 24.1 | 来源 行业协会 | 置信度 0.18 | 权重×0.3 | [数据陈旧，仅供参考]
- 申万一级 ⚠️ | 半导体 | PE=35.2 | 成份85个 权重×0.7
```

### 3.4 Prompt 时效红线（防幻觉）

```
### 🔴 时效红线（最高优先级）
当前日期是 2026-09-15。你只能使用上方「输入数据」中展示的数据点。
严禁引用你训练数据中任何年份、任何时间点的外部信息或历史数值。
所有数据引用必须能在上方「输入数据」找到对应 period_date 和数值。
如果上方没有某数据，就说「未获取到」，然后只依据有的数据给结论。
引用数据时必须带 period_date。
```

## 四、设计决策与权衡

### Q1: 为什么 filter_days 不能让行业倍数调？

**文档建议**：行业倍数影响"有效期倍数"。但如果让倍数同时影响 filter_days，会导致船舶的 filter_days 变成 1440 × 2 = 2880 天——8 年的行业数据都算可用。

**我的选择**：行业倍数**只影响衰减速度**，不影响硬截止线。理由：
1. 硬截止线是**独立的业务判断**——"一个指标超过 X 年绝对不能用了"，这个判断不应被行业类型左右
2. 行业周期通过**软权重**起作用——船舶 24 个月的季度产能数据 conf≈0.14（lagging, 权重 0.7），比消费电子同周期的 conf≈0.002（过期）有参考价值，但也不会被当成新鲜数据
3. 两层分离让调优路径清晰——想调"什么时候过期"改 filter_days，想调"衰减多快"改 λ/行业倍数

### Q2: 为什么 λ 固定 0.5？不做自适应？

**答**：MVP 阶段固定 0.5。原理是指数衰减的半衰期：`half_life = cycle × multiplier × ln2 / λ`。λ=0.5 时：
- CPI (cycle=30) 半衰期 = 30 × 0.693 / 0.5 ≈ **42 天**（半年内衰减一半）
- PE (cycle=1) 半衰期 = 1 × 0.693 / 0.5 ≈ **1.4 天**（2 天内衰减一半）

这和金融市场常识吻合——日频数据半衰期短、月频数据半衰期长。未来可以做"根据历史数据的最佳 λ"拟合，但 MVP 先用合理默认。

### Q3: 行业周期倍数硬编码，不做动态识别？

**答**：MVP 硬编码 12 个典型行业。动态识别（从行业名 → 关键词 → multiplier）容易误判，且对分析质量影响有限。当前命中率：
- "半导体" → multiplier=1.5（命中）
- "光模块" → 没在表里 → 默认 1.0（安全退化）
- 用户可以在 `_INDUSTRY_MULTIPLIERS` 加行业名扩展

### Q4: 为什么 industry Agent 用 self.industry_name 当 hint？

```python
# analysis Agent：从 payload.focus/user_query 提取 hint
industry_hint = payload.focus or payload.user_query

# industry Agent：直接用 self.industry_name（更准确）
industry_hint = self.industry_name
```

industry Agent 在初始化时就知道分析哪个行业（`tech / cyclical / healthcare` 等子类），比从 query 里猜更准。

## 五、与面试相关的核心亮点

### 亮点 1："硬截止 + 软权重"两层分离

面试官会问："你怎么决定数据该不该过滤？"
→ 回答 filter_days 是业务决策（拍板"什么叫不可用"），exp confidence 是数学工具（算权重），两者分离避免了"数学推导结果恰好符合业务需求"这种巧合问题。

### 亮点 2：全链路口径对齐

面试官会问："数据过滤在哪里做？会不会上层过滤了下层又忘了？"
→ 回答三处消费（Router/Agent/Prompt）共用同一个 evaluator，**没有散落的 if-else 阈值判断**，新增指标只要在 `_FREQ_BY_PREFIX` 加一行。

### 亮点 3：prompt 时效红线是硬约束

面试官会问："LLM 幻觉怎么防？"
→ 回答两层联动：数据层 filter_days 先过滤 → Prompt 层时效红线再硬约束。不是靠 prompt 提示"请不要用外部信息"就完事，而是让 LLM 根本**看不到**过期数据。

### 亮点 4：行业周期感知让长周期行业不死

面试官会问："你的系统怎么处理船舶/核电这类行业？"
→ 回答行业倍数让长周期行业的衰减更慢，船舶 24 个月前的数据 conf=0.14（lagging），而消费电子同周期 conf=0.002（expired）。这不是硬编码判断"船舶数据特殊"，而是统一框架自然推导的结果。
