# 面试复盘：首屏加载从 220 秒到 1.4 秒

> 本文只覆盖 **2026-09-18 ~ 09-24 这一段结对开发会话**（用户报障"每次前端启动加载数据都很慢，大概1分钟，
> 优化目标 10 秒内"→"首屏做到 1~2 秒级"）。这份是**讲稿 + 题库**，不是设计文档；
> 设计细节在 `src/intraday/service.py` / `src/intraday/hot_cache.py` 的注释里。
>
> ⚠️ 诚实前提：这些改动是我和 AI 结对做的。面试时**只讲你能自己推导、能白板画出来、
> 能回答追问的那几条**。本文"你必须能讲清楚的最小集"一节就是划这条线。

## 0. 一句话结论（面试开场用这句）

> 一个多 Agent 投研平台（FastAPI + React）重启后前端要等 220 秒才有数据。
> 我用"按浏览器真实并发序列打接口 + 采样事件循环主线程栈"定位到**不是某个接口慢，
> 而是事件循环被启动期的自选池整表重算饿死**（连只返回静态字典的接口都要 25 秒），
> 用**限并发+批间让路**把最长占用从 36.5s 压到 0.4s，再用**分层的落盘热加载 +
> 口径指纹 + 占位降级**把重启首屏做到 **1.4 秒**（自选 0.5s / 当前标的快照 1.4s），
> 全程"旧值必带时间戳、缺口显式标注"，不伪造新鲜度。

**能立刻震住面试官的两个数字**：

| | 修复前 | 修复后 |
|---|---|---|
| 重启首屏（主面板可用） | ~220s | **1.4s** |
| 只返回静态字典的 `/agents/meta` | 25.5s | 0.5s |
| 事件循环最长连续被占用 | **36.5s** | **0.4s** |
| 整表重算（48 只票） | 198s | 113s |

## 1. 你做的功能（按"能讲的价值"排序）

### 1.1 首屏性能治理（主菜）
把"重启后等 1 分钟以上"变成"1~2 秒"，并且**把为什么讲得清楚**：
- 冷启动请求级耗时表（每个接口修复前后的秒数）；
- 事件循环饿死→限并发→占位降级→落盘热加载的完整链路；
- 三层缓存（进程内 TTL → 落盘热加载 → 数据源），每层的失效策略与"为什么这层能撒谎/不能撒谎"。

### 1.2 做T（T+0）辅助模块的稳定性修复
- `sell_points`：分时卖点（冲高回落无承接/尾盘放天量/零轴长影见顶）整条链路**静默失效**的修复；
- 自选池刷新语义：单飞、stale-while-revalidate、报价快车道（5 秒）与打分（60 秒）双节奏解耦；
- 占位列表：无缓存时先给"代码+名称+板块"，数字留空（前端显示 "—"），价格由快车道在 5 秒内贴上。

### 1.3 平台级"慢链路"治理（顺带）
- 数据健康度预热**错峰**（它要遍历 3.5 万个分区清单 + 扫 14GB SQLite，6~28s I/O）；
- `/health` 的同步阻塞代码（建 SSL 上下文连 Ollama、审计链校验、连接器能力探测）挪进专用线程池；
- Ollama 探针改"读缓存 + 后台重探"（原来是 2 秒超时，前端 20 秒轮询一次就一直等满）；
- 板块接口的同步 SQL（名录表 5,562 行 ≈1.4s）挪出事件循环。

### 1.4 度量与可观测性（面试加分，很多人没有）
- 新增 `scripts/first_screen_probe.py`：固定复现"浏览器首屏那一组并发请求"，逐条报耗时，>10s 告警。
  **这类"可复现的性能探针"是面试官最想听到的东西** —— 说明你会把性能变成回归防线，而不是"感觉快了"。
- 事件循环阻塞定位器：看门狗线程每 0.2s 采样主线程栈，聚合出"责任帧"。

## 2. 定位方法（面试必问"你怎么知道是它"）

### 2.1 第一步：量，而且要在**冷进程**里量
在线服务是热的（各种进程内缓存都命中了），量不出问题。做法：
- 另起一个进程（换端口，不动在用的实例）；
- 按前端挂载时的**真实请求集合并发**打一遍；
- 逐条记录耗时 + 响应体大小。

结果（冷进程）：
```
agents/meta（纯静态字典）      25.5s   ← 关键异常
intraday/watchlist（有热缓存！） 22.0s
intraday/snapshot               219.6s
health / weight-profiles        211s / 208s
```

**推理**：一个只返回字典的接口要 25 秒 ⇒ 不是"哪个接口慢"，是**所有请求都在排队**。

### 2.2 第二步：采样事件循环主线程栈（不猜代码）
看门狗线程每 0.2s 抓一次 `sys._current_frames()[主线程]`，聚合"落在项目里的最近调用者"：

```
features.py:163 build_intraday_features
features.py:83  resample_bars
features.py:428 replay_totals
features.py:96  _expanding_zscore_by_day
indicators.py:170 macd / 221 kdj / 138 bollinger
service.py:2404 _bars_frame
sources.py:184  _normalize_bars
```

再配合"同一帧连续出现 >1.2s 就打印完整栈"，量到**最长连续占用 36.5s**。

### 2.3 根因（一句话）
启动后 `_watchlist_refresh_loop` 立刻对 ~50 只票做 `asyncio.gather(轻量快照)`：
- 每只票 3~5 秒的**同步 pandas 计算**（特征/指标/逐bar回放/引擎）跑在事件循环上；
- 同时几十个档位拟合走 `asyncio.to_thread`，几十个线程抢 GIL；
- ⇒ 事件循环长时间拿不到执行权，所有 HTTP/WS 请求排队。

**第二条独立根因**：热缓存不可用时（首次部署 / 快照超 24 小时 / 自选池大改），
`/watchlist` 会在**请求路径上**现算整表 200 秒。

## 3. 五个可以深挖的故事（STAR 结构，背下来）

### 故事 A：静态字典接口要 25 秒 —— 事件循环饿死
- **S**：用户说"每次重启前端加载要一分钟"。
- **T**：先定位是哪个环节（不能靠读代码猜）。
- **A**：冷进程并发探针 + 栈采样；发现是整表重算把事件循环按住了。
- **R**：最长占用 36.5s → 0.4s；总耗时不变（那本来就是跑不掉的 CPU 时间）。

**追问必答**：为什么限并发到 1 不是 2/4？—— 实测三档：

| 并发 | 整表耗时 | 事件循环最长被占用 |
|---|---|---|
| 50（原来 gather 全部） | 198s | **36.5s** |
| 2 | 193s | 4.2s |
| **1（现在）+ 批间 sleep(0.05)** | 200s | **0.4s** |

**总耗时几乎不变**（CPU 时间单核跑不掉），但事件循环从"被按死"变成"随时能插空服务"。
并发不是越高越好：这是 CPU-bound 任务，`gather` 只让它们**更凶地抢 GIL**。

### 故事 B：没有缓存时，绝不能让请求等整表重算
- **S**：热缓存会因"首次部署 / 超 24 小时 / 自选池大改"而不可用，此时 `/watchlist` 挂 200s。
- **T**：首屏目标 10s 内。
- **A**：三件事——
  1. **占位列表**（只有代码/名称/板块，数字留空，前端显示 "—"）**立刻返回**；
  2. 整表重算转后台，**启动宽限期 20 秒**内先不跑（把 CPU 让给"当前标的的完整快照"）；
  3. 宽限过后起后台重算并**最多等 3 秒**（`asyncio.wait_for` + **`asyncio.shield`** 保证超时后任务继续在后台跑，算完写回缓存并由 WebSocket 推送补齐）。
- **R**：`/watchlist` 219.8s → **0.5s**。

**追问必答**：
- 为什么用 `shield`？—— `wait_for` 超时会**取消**内部协程；加 `shield` 只放弃等待，不取消计算。
- 占位数据算不算"骗用户"？—— 不算：字段本来就是 Optional，空值前端显示 "—"；并且状态里带 `warming=true`，
  前端写"⟳ 首次重算中：先给自选清单与现价，分数稍后补上"。**宁可标"还没有"，不给假数字。**
- 为什么不用"后台线程慢慢算，前端轮询"？—— 已经有 WS 推送，不需要前端轮询；且轮询会让多标签页放大取数。

### 故事 C：一个 DataFrame 的真值判断，让整条业务链路静默失效
- **S**：日志里每分钟几十条 `分时卖点计算失败（降级）：The truth value of a DataFrame is ambiguous`。
- **A**：`sell_points._points()` 写的是 `for item in trend or []`，而 `trend` 传进来是 **pandas DataFrame**：
  - `trend or []` 先对 DataFrame 求布尔值 → 直接抛 `ValueError`；
  - 就算不抛，`for item in df` 迭代的是**列名**，字段全取不到。
  被上层的 `except` 吞掉 ⇒ **卖点面板永远是 null**，还刷日志洪水。
- **R**：新增 `_rows()` 用鸭子类型显式处理 DataFrame（`to_dict(orient="records")`）/ list / pydantic / None，
  并补了回归测试（断言"传 DataFrame 与传 list[dict] 结果完全一致"）。

**这个故事面试价值极高**：它同时展示了
① 读日志的敏感度；② 对 pandas 真值语义的掌握；③ "异常被吞掉=业务静默失效"的工程直觉；
④ 修完补回归测试。可以主动引申：**"降级分支必须可观测"** —— 降级可以，静默不行。

### 故事 D：落盘热加载 + 口径指纹（首屏 1~2 秒的关键）
- **S**：即使事件循环不堵了，冷启动第一次 `/snapshot` 仍要真取一遍全链路（QMT 在 6.8s，关掉后 11.1s）。
- **A**：把每次算好的**单票完整快照**按代码落盘（68KB JSON，原子 `os.replace`），重启后**第一次**请求：
  1. 先返回这份旧快照（毫秒级）；
  2. 同时排一次后台真算（单飞、`force_refresh=True` 绕过数据源 TTL）；
  3. **只在"本进程还没算过这只票"时**吃缓存（`_snapshot_fresh_at`）—— 稳态下重复快照只要 ~3 秒，没必要拿旧数据糊弄热进程。
- **正确性的三道闸**（这才是重点）：
  1. **口径指纹**（`sha1(config.snapshot() + 板块/海外/同业绑定)`）：用户改了权重（YAML 是按 mtime 热重载的，
     不重启）⇒ 旧快照的分数不再是当前口径的分数 ⇒ 整份作废。防的正是"改了权重但分数没变"。
  2. **不伪造新鲜度**：`generated_at` / `trade_date` / `health.stale` 原样保留，另在 `health.gaps`
     写明"本面板是上次运行缓存的快照（N 分钟前），正在后台刷新"。
  3. **降级快照不落盘**（判据：有分时序列 + 有行情）：落盘的这份是下次启动首屏的**第一帧**，
     空图占首屏比多等一次真算更糟。
- **R**：重启首屏 自选 0.50s / 快照 1.36s / 全部就绪 **2.27s**；三轮冷启动一致（1.61/1.63/1.36s）。

### 故事 E：测试污染了生产的缓存文件
- **S**：修完缓存后，自选概览热加载总报"快照条目与当前自选池**无交集**（配置改动较大）"，整份被丢弃。
- **A**：打开文件一看，里面是 `['600000','600001','600002']` —— 那是**单测替身返回的假代码**。
  原因：替身调 `watchlist(force=True)` 会真的落盘，而热加载按"代码交集"校验 ⇒ 假代码把真缓存顶掉了。
  现象极具欺骗性：**跑完单测后重启服务，前端自选分数一直空着**（要等 200 秒整表重算）。
- **R**：在根 `tests/conftest.py` 加 autouse 夹具把 `hot_cache.DEFAULT_CACHE_DIR` 重定向到临时目录
  （与仓库里既有的 `_isolate_health_caches` 同套路，那个坑是"测试把生产的仓库健康度缓存写成 MySQL 不可用"），
  再补一条"替身不许写仓库缓存"的回归断言。

**这个故事讲的是工程成熟度**：同类问题在仓库里已经踩过第二次，所以处理方式是"提到根 conftest 做成 autouse"，
而不是"逐个测试记得清理"。

## 4. 踩坑清单（每个都能当"你遇到过什么困难"的答案）

| # | 坑 | 现象 | 教训 / 修法 |
|---|---|---|---|
| 1 | 同步代码跑在 asyncio 事件循环上 | 连静态字典接口都要 25s | 任何 >50ms 的同步调用都要 `run_in_executor`/`to_thread`；用栈采样定位而不是猜 |
| 2 | `asyncio.gather` 用在 CPU-bound 任务上 | 并发越高越糟（抢 GIL），最长占用 36.5s | CPU-bound 要**限并发**并主动让路；`gather` 不等于加速 |
| 3 | 请求路径上做重活 | 无缓存时 `/watchlist` 挂 200s | 慢链路一律 stale-while-revalidate + 有界等待（`wait_for` + `shield`） |
| 4 | `pandas.DataFrame` 参与布尔判断 | `truth value is ambiguous`，被 except 吞掉后链路静默失效 | DataFrame 的 `if`/`or`/`in` 全是雷；降级必须可观测 |
| 5 | 读失败被缓存成"空结果" | 档案库抖一下，5 秒内有档案的票按全局口径算分（错分数），还把缓存指纹带偏 | **失败不要写缓存**；失败只影响这一次 |
| 6 | 缓存没有失效维度 | 改了权重但面板分数没变 | 落盘缓存必须带**口径指纹**（配置+绑定）与版本号 |
| 7 | 缓存了"降级结果" | 数据源全挂时缓存一屏空白图 | 落盘前加"是否算全了"的判据 |
| 8 | 测试污染生产落盘路径 | 单测跑完，服务重启后自选分数空 4 分钟 | 落盘缓存路径必须由 autouse fixture 重定向，不能靠"记得清理" |
| 9 | 测试用真实服务但不隔离配置热重载 | `_reload_config` 因深拷贝导致身份不等 → 每次重建子组件 → **静默联网**，单测 17s | 替身必须 override `_reload_config`；单测里出现秒级耗时先怀疑联网 |
| 10 | `asyncio.run` 结束时取消后台任务 | 断言"任务还在跑"永远失败 | 要在协程内部断言 `not task.done()`，别在 `run` 之后断言 |
| 11 | conftest 把方法 patch 成 no-op | 新测试静默测了个空 | 导入期先取一份真实方法引用（`_REAL = Class.method`），用例里换回来 |
| 12 | 自己的实验脚本自递归 | 测出来"0 只票、3.7 秒"，全是假结论 | 覆盖方法后内部要调用**保存的原始引用**；实验脚本先自检输出是否合理 |
| 13 | Windows PowerShell 5.1 + 非 ASCII 脚本 | 脚本被按 GBK 解码 → 中文变乱码 → 解析报"字符串未终止" | 临时脚本一律**只写 ASCII** |
| 14 | `Get-Content -Raw` + `Set-Content -Encoding utf8` 改文件 | UTF-8 被当 GBK 读 → 文件整篇乱码（我用它改自己的测试文件，只能重写） | 改文件用编辑器/工具，别用 PS 的编码往返 |
| 15 | 采样器写错属性名 | `frame.lineno` 应为 `f_lineno`，采样线程直接崩，采到 0 个样本 | 探针自身要能自证在工作（打印样本数，0 就是坏了） |
| 16 | 只看在线（热）服务 | 一切看起来都很快（warm 0.3~1s），量不出问题 | 性能问题必须在**冷进程 + 真实并发序列**下量 |
| 17 | 环境/日期相关的既有失败 | `test_connector_router` 因"今天"变化而失败 | 先证明"不是我造成的"（`git diff` 该文件为空 + 直接调用被测定值验证），再决定修不修 |

## 5. 需要掌握的知识（按三个岗位方向）

### 5.1 量化开发方向
**数据与时序**
- **未来函数 / look-ahead bias**：指标只能用截止当前 bar 的数据；逐 bar 回放（replay）必须因果。
  本项目里"逐bar档位序列"就是为这个存在的（拿当前档位横贯全天会误判破位）。
- **PIT（point-in-time）**：财务/估值要按发布日期对齐，不能用修订后的数据回填。
- **前复权/后复权**：比较、回测、画图口径不同；混用会导致收益率错。
- **交易日历**：节假日、半日市、盘前/集合竞价/午休的时段判定；"市场时钟"要与系统时钟区分
  （本项目用行情源自己的 timetag 反推市场日期，避免节假日误判）。
- **A 股微观结构**：T+1、涨跌停、集合竞价（09:15–09:25）、做T的摩擦成本
  （佣金+印花税+滑点 ≈0.2% ⇒ 档位差 <1.5% 的信号会被成本吃光，所以有 `min_band_pct`）。

**因子与回测**
- IC/IR、分层回测、换手率、容量、样本外（walk-forward）、参数过拟合；
- 命中率 vs 平均前瞻收益 vs 与"随机时点基准"的超额（本项目阈值回测就是这么做的：全样基准对照）；
- 交易成本建模（手续费/印花税/滑点/资金闲置收益）；
- 分位/标准化要跨票可比（如 MACD 的 DIF-DEA 用 ATR% 归一化）。

**数据工程**
- 多源路由 + failover + **失败冷却**（避免每次白等超时）；EWMA/中位数延迟统计（样本 <3 不给结论）；
- 缓存分级：进程内 TTL → 落盘 → 上游；**缓存穿透/击穿/雪崩**（单飞、per-key lock、TTL 抖动）；
- SQLite 实务：WAL、`-wal/-shm` 陈旧索引导致 `disk I/O error`、checkpoint、`os.replace` 原子替换、
  **大表别 `COUNT(*)`**（14GB 库会卡几百秒，用 `MAX(rowid)`）、读写分离/只读连接。

### 5.2 AI 应用开发方向
- **多 Agent 编排**：Supervisor / StateGraph（LangGraph）、分层 Agent（数据→信息→分析→行业→决策→审计）、
  标准 JSON 消息、MCP 工具调用、**无状态接口**便于演进成微服务。
- **LLM 网关**：多 provider、超时与降级链、prompt/response hash、token 计量、
  P50/P95/P99 与慢调用、缓存命中率、降级率（本项目有完整的 LLM 审计与指标）。
- **本地 vs 云端模型分工**：Ollama 跑小模型做"消息面情绪"这类低价值高频判断（零 token 成本），
  重推理走云端 API；**模型常驻（keep_alive）** 解决冷启动 28s 的问题。
- **成本与延迟工程**：只在必要时调 LLM（新闻没变就复用上次打分）、分层模型、批处理、缓存。
- **幻觉治理**：数据溯源（`source_url`/`publish_time`/`fetch_time`/`raw_content_hash`）、
  结论必须引用数据 ID、**缺口显式标注（gaps）而不是编造**。
- **可观测性与合规**：审计链（哈希链，可验证未被篡改）、多租户 RLS、免责声明、审计日志保留期。

### 5.3 AI 应用架构师方向
- **分层与边界**：端口/适配器（repo/connector 抽象）、fail-open vs fail-closed 的选择
  （数据源失败要降级继续，健康检查不能因此 500）。
- **"诚实数据"原则**（本项目反复强调，面试很加分）：
  旧值一定带时间戳；缺口写清楚；占位不冒充真值；降级要可观测。
- **性能预算与首屏契约**：把"首屏 ≤10s"变成可测指标 + 固定探针 + CI 告警。
- **错峰与优先级**：后台预热/定时任务必须与服务首屏错开（本项目把板块预热延后 600s、
  数据健康度预热延后 20s、竞价调度延后 60s）；**关键路径专用线程池**避免被业务线程挤死。
- **优雅关停**：lifespan 里 cancel 任务 → 关连接池 → SQLite checkpoint → 关线程池；
  **每一句都各自兜异常**（一句 AttributeError 会让整个收尾中断，导致下次启动读到脏 WAL）。
- **子进程隔离**：第三方原生库（py_mini_racer）会让整个进程崩，必须用子进程隔离，
  并且**取消路径也要 kill + wait**（只 kill 不 wait 会留僵尸 + 管道让事件循环关不掉）。
- **可演进性**：单进程分层 → 保留拆微服务的路径；配置热重载（mtime）与缓存失效的联动。

## 6. 高频追问与标准答法

**Q1：为什么不用多进程/进程池把 CPU 活搬走？**
A：计算里大量是小粒度 pandas 操作，进出进程要序列化 DataFrame（成本可能超过计算本身），
且这些函数依赖大量进程内状态（provider 缓存、配置、拟合缓存）。这里真正的目标是**不让事件循环被饿死**，
限并发 + 让路已经达到 0.4s 的占用上限；如果单只票的计算再重一个量级，下一步才是进程池/离线预计算。

**Q2：为什么用 SQLite 不用 PostgreSQL？**
A：演示阶段要"零依赖、克隆即可跑"，PG/Redis 作为可选后端（`DATA_BACKEND=postgres`）保留了口子。
代价就是上面那些 SQLite 实务坑（WAL 一致性、大表 COUNT），所以专门做了启动自愈与关停 checkpoint。

**Q3：热加载旧数据，用户看到旧分数怎么办？**
A：三条：① 时间戳原样展示（"更新 14:31:02（快照 14:30:58）"）；② `health.stale` 与页面上的"非当日"警告；
③ 面板顶部 `gaps` 里一句话写明"这是上次运行缓存的快照，正在后台刷新"。**先给能立刻给的 + 明确标出它多旧**。

**Q4：怎么保证缓存不会永远失效/永远命中？**
A：失效维度显式化 —— 版本号（结构变了）、TTL（时间）、口径指纹（配置/绑定变了）、
代码交集（自选池变了）。命中条件写成"取交集"，并且**每次命中都排一次后台真算**，所以就算判错了也会很快自愈。

**Q5：你怎么证明优化真的有效？**
A：`scripts/first_screen_probe.py` 固定请求集合 + 冷进程 + 逐条耗时 + >10s 告警，三轮复测一致
（1.61 / 1.63 / 1.36s）。**不是"感觉快了"，而是可复现的数字 + 可回归的脚本。**

**Q6：如果让你继续优化，下一步做什么？**
- 单只票的冷快照仍是 7~11s（首取链路的固有延迟）→ 盘前/启动后**预热当前标的**（错峰）；
- 整表重算 113s > 60s 循环间隔 ⇒ 分数刷新实际是 ~2 分钟一轮：可以把"轻量快照"真正做轻
  （自选列表只需要分数+信号，不必跑档位拟合/逐bar回放），或按自选数量做分级（只对前 N 只精算）；
- 把事件循环占用做成**常驻指标**（loop lag 直方图）进 `/metrics`，防止这类回归再次悄悄发生。

## 7. 你必须能讲清楚的最小集（别超纲）

**能白板画出来**：
1. 冷启动时间线：进程启动 → 端口可连（~4-7s）→ 浏览器并发请求 → 各接口耗时；
2. 三层缓存与失效维度（进程内 TTL / 落盘热加载 + 指纹 / 数据源）；
3. `asyncio.gather` 50 并发 vs 1 并发 + 让路 对事件循环占用的差别（时间轴图）。

**能口述**：
1. "静态字典接口 25 秒"的推理链（不是接口慢，是循环被占）；
2. `wait_for` + `shield` 的语义差别；
3. DataFrame 真值判断为什么炸、为什么被静默吞掉；
4. 为什么落盘缓存必须带口径指纹；
5. 为什么"降级快照不落盘"。

**不要主动吹**（容易被追问翻车）：
- 不要说"我做了分布式/多进程削峰"——没有；
- 不要说"首屏 1.4 秒"而不加限定 —— 准确说法是"**有热缓存的常规重启** 1.4s；
  **完全首次启动**（无任何缓存）要真取一次约 7s，之后每次都 1.4s"；
- 不要声称所有计算都无 GIL 阻塞 —— 提取到线程池的是 I/O/部分释放 GIL 的数值计算，
  纯 Python 的 CPU 活仍然争 GIL，这也是限并发的原因。

## 8. 一分钟自我介绍模板（可直接背）

> 我最近在做一个多 Agent 的 AI 投研平台（FastAPI + React + SQLite/可选 PG，LLM 走云端 + 本地 Ollama）。
> 我负责的一块是**做T辅助模块的性能与正确性**。用户反馈"每次重启前端要等一分钟才有数据"，
> 我先用"按浏览器真实并发序列打接口"的探针在冷进程里量，发现连只返回静态字典的接口都要 25 秒 ——
> 说明不是某个接口慢，而是**事件循环被启动期的整表重算饿死**：50 只票的同步 pandas 计算
> 一次性压进事件循环，同时几十个拟合线程抢 GIL，最长连续占用 36.5 秒。
> 我用限并发 + 批间让路把占用压到 0.4 秒，再给"无缓存"这条路径做了占位列表 + 有界等待
> （`wait_for` + `shield`）避免请求阻塞；最后补上**按标的的完整快照落盘热加载**，
> 带**口径指纹**（权重/阈值/绑定变了就作废）和降级快照不落盘的闸门，
> 把重启首屏做到 **1.4 秒**（全程旧值必带时间戳，不伪造新鲜度）。
> 期间还修了一个让分时卖点整条链路**静默失效**的 bug（pandas DataFrame 参与布尔判断被 except 吞掉），
> 以及一个"单测把假代码写进生产热缓存、导致重启后自选分数空 4 分钟"的测试隔离问题。
> 我习惯把性能做成可复现的探针和回归测试，而不是靠感觉。
