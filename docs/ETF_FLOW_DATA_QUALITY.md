## 问题 1：份额缺口导致面板空白

### 现象

「核心宽基 ETF 份额」9 只卡片中 7 只的份额、1/5/10/20 日变化率、
对应指数分位**全部显示为「—」**，并带红字「数据缺口」标签。

### 根因

一条完整的因果链，每一环单独看都不像 bug：

```
份额由交易所 T+1 发布（次日 8:30），而 ETF 日线当晚就有
  → 当晚 17:50 的全市场同步（fund_daily + fund_share）给最新交易日
     写入 2138 行，其中只有 765 行拿到份额，其余 shares = NULL
  → 该行的 ON CONFLICT「NULL 不覆盖旧值」保护**对新插入的行无效**
     （没有旧值可保护）
  → 面板以 SELECT MAX(trade_date) 为锚点，只读**最后一行**的份额
  → shares=None ⇒ 份额为空；变化率 _pct_change(None, ...) 全为 None
  → 指数分位依赖 resonance 数组，而 resonance 要靠份额判方向 ⇒ 也空
```

实测证据（`ml_etf` 按交易日统计）：

```
20260918 → 364 行，364 行有份额（全齐）
20260921 → 2138 行，只有 765 行有份额   ← 缺口
```

### 方案

**分两层，都在数据层而不是展示层**——因为"插一行行情有、份额无的记录"
正是出事的机制本身，在展示层兜底会掩盖它。

**① 定向补份额 `sync_etf_shares()`**（`src/mainline/datastore.py:2214`）

```sql
UPDATE ml_etf SET shares=? WHERE code=? AND trade_date=? AND shares IS NULL
```

- 只更新 `shares IS NULL` 的行：**已有份额一个都不动** ⇒ 幂等且不可破坏；
- **永不插入新行** ⇒ 不会制造新的"行情有、份额无"脏数据；
- 两条取数路径：先 `fund_share(trade_date=day)` 一次性拿全市场（实测 1762 行），
  再对仍缺的**场内 ETF** 逐只兜底重试；
- ⚠️ 重试只针对接口**明确标为 ETF** 的代码（`types.get(code) == "ETF"`）。
  不能用 `types.get(code, "ETF")` ——那样"接口压根没提过的代码"会被当成 ETF
  去重试，恰好把要避开的那批场外基金（`158008.OF` 等，实测一次缺 1373 只）
  又捞回来，在 5000 积分档的频次限制下足以拖垮启动自检。

**② 启动自检 `ensure_etf_shares()`**（`src/mainline/etf_share_guard.py:170`）

挂在 API lifespan 的后台任务（延迟 3 秒，不阻塞首屏）。判定逻辑：

| 情形 | 动作 | 状态 |
|---|---|---|
| 最新已收盘日份额齐全 | 不发任何请求 | `fresh` |
| 最新日份额成片为 NULL | 一次调用尝试补拉，补齐则 | `filled` |
| 份额确实还没发布 | 如实记录，不反复等 | `unpublished` |
| 本地落后于必然已发布的交易日 | 整段补同步（回看 10 天） | `filled` / `stale` |
| 数据源不可用 | 降级，不拦启动 | `offline` |

**关键设计判断**：

- **日历口径 `recent_closed_days()`**（`etf_share_guard.py:136`）：
  `trade_date <= 今天` 且**当天 15:00 之前不算已收盘**；只认
  `ml_calendar` 里 `is_open = 1` 的日子，不用工作日近似。
  少了这条，每天开盘后都会误报一次缺口。
- **判据贴着展示口径**：阈值取"缺口**比例**"而非"有没有 NULL"，
  因为 `ml_etf` 里混着 `158008.OF` 这类**场外基金**——它们的份额长期不发布，
  实测份额齐全那天全表仍缺 377/2138 ≈ 18%。真缺口是 1373/2138 ≈ 64%，
  阈值 30% 落在两者之间。
- **区分"没数据"与"数据源坏了"**：`unpublished` 是正常时序（不告警），
  `offline` 是要人查的故障。混成一种，运维会为一个正常现象每天收到一条
  看起来像故障的记录。

**③ 展示层回退**（`etf_flow.py:559`）：最新日 `shares` 为 NULL 时，
回退到**最近一个有份额的交易日**，并在 `shares_date` 字段与界面上
如实标注 as-of 日期，避免"拿昨天的份额配今天的收盘价"。

### 验证

```
实时场景注入（库副本）：注入 2138 行 20260922 行情（份额 NULL）
  → state=unpublished，回填 767 行，耗时 0.39s，不阻塞启动
正常场景：state=fresh，耗时 0.03s，零网络请求
补拉后 9 只全部有份额/变化率/分位（实测 9/9）
```

### 实现踩坑（自省记录）

- **`_write()` 走 `executemany`，参数为空的行集合会让整条语句一次都不执行**。
  测试里 `DELETE FROM ml_calendar`（无参数）静默失效，导致测试"什么都没验证"。
  改为带参逐行删。
- **键名歧义**：`etf_share_coverage()` 原来把「已覆盖比例」
  （`with_share / rows`）命名为 `ratio`，调用方按直觉当「缺口比例」用——
  分母对、分子反了，判据恒为"没缺口"，自检永远不补数且不报任何错。
  已改名 `share_ratio` 并加测试锁死。

## 问题 2：份额拆分被读成巨额申赎（产生假信号）

### 现象

半导体设备 ETF（`159516.SZ`）在 2026-03-30、04-01、04-02、04-03
连续触发 4 条「行业反转警示」，看起来像"三月跌完之后的低位买入信号"。

### 根因

`2026-03-30` 该 ETF 做了 **1 拆 2**：

```
价格   1.660 → 0.852        -48.67%
份额   1,200,859 → 2,357,118  +96.29%
份额×价格  1,993,426 → 2,008,265   只差 0.74%   ← 总市值一分没变
```

系统没有"公司行为"概念，把**机械换股**读成了史上最大的一次申购。
「行业反转」判据是"份额 5 日累计 > +10%"，于是直接吃下这个 +96%。

**影响范围**（扫观测清单 9 只 ETF 的 2018-2026 全历史，共 3 次）：

| 代码 | 日期 | 真实事件 | 系统读成 |
|---|---|---|---|
| `512100.SH` 中证1000 | 2022-09-05 | 份额合并（-64% / +176%） | 巨额**赎回** |
| `159516.SZ` 半导体设备 | 2026-03-30 | 1 拆 2（+96% / -49%） | 巨额**申购** → 4 条误报 |
| `512170.SH` 医疗 | 2021-02-25 | 1 拆 2（+193% / -68%） | 巨额**申购** |

且**污染会持续 5 个交易日**——5 日窗口一直带着这个跳变。这正是"连续四条"的
机制：不是四次异动，**是一次拆分被数了四遍**。

### 方案

新增 `adjust_share_splits()`（`src/mainline/etf_flow.py:297`），在算变化率之前
把份额序列还原成可比口径。

**识别判据**（三个条件同时成立，缺一会把真实申赎误判）：

1. 份额跳变 ≥ 15%；
2. 价格**反向**跳变 ≥ 10%（拆分必然一涨一跌）；
3. `份额比 × 价格比 ≈ 1`（市值不变，允许 ±15% 容忍拆分当天的真实涨跌）
   —— 这条排除"真实申购 + 恰好当天大跌"。

**还原不变式**（这是本问题最关键的一段推导）：

```
份额比 s = 拆分后份额 / 拆分前份额
可流通份额变了 s 倍 ⇒ 拆分后 1 份 = 拆分前 1/s 份

两个约束方向相反：
  约束 A：份额列必须显示原始存量（当前 2,357,118 要和券商一致）
  约束 B：变化率必须跨拆分连续（不能把机械翻倍算成 +96% 申购）

⇒ 当前行不能动，于是**历史行折算到新基准**：
   新基准下的历史份额 = 原始份额 × ∏(该行之后每个拆分日的 s)

验证：1,200,859 × 1.9629 = 2,357,197，而拆分日真实存量 2,357,118
      —— 差 0.003%，正是当天的真实申赎 ⇒ 拆分日日环比 ≈ 0 ✓
```

### 验证

```
跨拆分连续性（修复后）：
  20260326  2,357,707
  20260327  2,357,118
  20260330  2,357,118   ← 1 日变化 +0.0000%（修复前 +95.41%）
  20260331  2,361,518

4 条误报的 5 日累计（判据 > +10%）全部不再触发：
  20260330: -0.45%   20260331: -2.18%   20260401: -2.00%
  20260402: -0.33%   20260403: +1.60%

全量信号数：1253 → 1242（-11 条），且**精确落在这 3 只上**：
  159516.SZ  83 → 78 (-5)     512170.SH 105 → 100 (-5)
  512100.SH 419 → 418 (-1)    其余 6 只：0 变化

门控对照（验收条件）：修复前后完全一致
  opportunity_live   66 条  +9.18% / 83.3%   ← 未受影响
  opportunity_gated 223 条  +0.52% / 52.9%   ← 未受影响
```

### 实现踩坑（自省记录，两轮方向都错过）

**第一次：改错了对象。** 把"拆分日**及之后**"的行乘以份额比 →
真实存量被又放大一倍（2,357,118 → 4,626,692）。

**第二次：乘除方向反了。** 改成"拆分日**之前**的行**除以**份额比 →
得 611,790，与 2,357,118 差 3.85 倍，5 日累计算出 +283%。

**为什么会连错两次**：边改边测，而检测循环读的是**已被修改**的序列，
同一位置被重复识别成拆分，把真实错误掩盖成"看起来在收敛"。

**方法论的收获**（比修好这个 bug 更重要）：

> 时序数据的变换不能靠试。**先把不变式和基准确定下来再写代码**——
> 哪个方向是"当前"、要动的是哪一段、是乘还是除。这个错误不抛任何异常，
> 只让数字静默失真（+1.6% 变成 +283%），测试不覆盖就永远发现不了。

现在这段推导已写进函数文档，并由 8 个测试钉住两个方向。

## 问题 3：伪重复导致样本量虚增 4.8 倍

### 现象

回测明细里同一只 ETF 的同一类信号**连续出现十几行**：

```
20260716 159516.SZ 行业反转警示  T+34 = -3.20%
20260715 159516.SZ 行业反转警示  T+34 = -3.66%
20260714 159516.SZ 行业反转警示  T+34 = -3.57%
...                                 （连续 11 行）
```

### 根因

**判据用的是存量指标的累加值。** 「行业反转」要求"份额 **5 日累计** > +10%"，
而份额是**存量**——一次资金流入发生后，接下来 5 天的累计值**天天都超标**。

```
实测最近 300 条明细的事件/条数比：
  512100.SH 风险信号     43 条 → 只有 9 个独立事件（最长连报 12 天）
  159516.SZ 行业反转     41 条 → 只有 4 个独立事件（最长连报 21 天）
  510050.SH 风险信号     37 条 → 只有 6 个独立事件（最长连报 18 天）
  510500.SH 风险信号     34 条 → 只有 9 个独立事件（最长连报 12 天）

300 行明细 → 63 个独立事件    放大约 4.8 倍
```

**这在统计上是伪重复（pseudo-replication）**：一次事件被当成 N 个独立样本
计入统计，样本量虚增、胜率被单一事件主导。

**对交易的含义**：如果信号连续三天触发就买三次，等于把仓位放大三倍
押在**同一个事件**上。

### 方案

新增 `collapse_signal_runs()`（`src/mainline/etf_flow_backtest.py:272`）：

- 同一 `(code, kind)` 且相邻触发日间隔 ≤ 7 **自然日**的，视为同一事件；
- 只保留**首次触发**那天（那是真正可行动的日子）；
- 在 `repeat_days` 字段里如实给出这段连报了多少天，`repeat_until` 给结束日；
- 落库时启用（`to_dict(collapse_runs=True)`）；
- ⚠️ 合并必须**先于**截断：先取尾部 300 条会把同一事件的中间几天当成独立样本，
  合并后数量远小于 limit，等于白截。

**刻意不动的部分**：
- `report.records` 本身（`by_kind` / `by_etf` 等统计仍按日计样本）；
- 实时信号与告警（那个按 `alert_id = 日期+代码+类型` 逐日触发是**有意**的：
  资金还在流入就该每天提醒，这是"持续性确认"而不是重复）。

### 验证

```
明细 300 行 → 合并掉 666 条重复（全样本口径），前端展示 135/300 行带 ×N日 标记
前端列头标注「×N日」并可 hover 查看起止日期
```

## 问题 4：回测明细"全是 2018 年的老数据"

### 现象

「信号明细」表的日期范围是 2018-04 ~ 2020-09，用户看不到近期样本。

### 根因

```python
"records": [item.to_dict() for item in self.records[:record_limit]]   # 取头部
```

而 `records` 是按回测日历**从旧到新**逐步追加的（`while cursor` 循环里 append）
⇒ `[:300]` 拿到的是**最早**的 300 条。

实测：20180102~20260918 共 1252 条，前 300 条的日期上限只到 2020-09。

### 方案

```python
recent = self.records[-max(int(record_limit), 0):]      # 取尾部 = 最近
rows = [item.to_dict() for item in reversed(recent)]    # 倒序 = 新的在前
```

**倒序这一步不能省**：前端只渲染前 200 行，若最旧的排在最前，
那 200 行会截在"最近 300 条里较早的一半"，等于又丢一次近期数据。

`record_count` 保持**全样本总数**不变——它是"明细被截断"这句话的来源，
改成截断后的长度会让用户以为回测只跑出这么点信号。

### 验证

```
修复前：明细日期范围 20180418 ~ 20200930
修复后：明细日期范围 20260105 ~ 20260804（单调递减 ✓）
record_count 保持 1253（不变）
```

### 附带发现：回测明细**结构上**到不了最新交易日

```python
total = len(calendar) - max_horizon     # max_horizon = 34
while cursor < total:
```

每条明细要记录 T+5/10/20/34 的**实际**收益，而最近 34 个交易日
"未来还没发生"，所以回测只评估到「最新交易日往前 34 个交易日」。
实测明细到 2026-08-04，最后可评估日是 08-06（且 8/5~8/6 恰好没触发信号）。

**这个截断是对的（不能算未来），但界面完全没提示**，用户会以为工具坏了。
已在前端补上说明。

## 问题 5：展示层口径混淆与名额挤占

这一类是"数据正确但让人读错"，共性根因是**排序 + 截断 + 默认值的方向搞反**
——不报错，只让用户看到错误的东西。

| 问题 | 根因 | 修法 |
|---|---|---|
| 明细列「1日」被读成价格涨跌 | 该列是**份额变化率**，而右边 T+5~34 是**价格收益**，两者口径完全不同（-18.91% 配 +7.00% 并不矛盾） | 列名改「份额1日」，浮盈/浮亏加「价格」前缀 |
| 门控行 + 弱信号铺满默认视图 | 1253 条信号里真正会告警的只有 66 条（5%），其余是观察项与门控项 | 默认只显示"要行动的"，观察项/门控项改为主动切换 |
| 「风险信号 **且** 弱信号」纯噪声 | 它同时占了两条不成立的理由：分位没到 70% 的"高位" + 从不告警的弱等级 | 该组合不再显示（中/强风险信号与弱机会信号保留） |
| 同一 ETF 先报机会、后连报风险被当成自相矛盾 | 34 日分位在区间内来回穿越（实测中证1000：4/7 分位 11.8% → 4/8 41.2% → 4/20 97.1%）；两个信号在数学上不可能同时成立 | 界面补口径说明；并指出**短窗口在趋势里会飙升**是已知局限 |
| 板块名显示两遍（「电子 电子」） | 榜单层 `FlowEntity(code=name, name=name)`——拿不到东财 `BKxxxx.DC` 真代码 | 抽 `nameCell()`，`code !== name` 时才补代码 |
| 自选票挤占排行榜名额 | 自选被塞进同一个 `stock_rank`（实测 12 行里 10 行是自选，`top=10` 的净流入榜只显示得出 2 只） | 分离成 `stock_watch` 单列一节，两段互斥 |
| 「昨日涨停股」保送入榜 | 涨停股不论资金流排第几都硬塞进榜，把**排序榜**变成"排序 + 打板池"混合体 | 取消该类，改回纯排序（涨停股凭资金流自然入榜） |

**验证（自选分离）**：


## 通用教训（本报告的结论）

1. **"排序 + 截断"类 bug 的共同形态是方向搞反**：取头部 vs 取尾部、
   升序 vs 降序、默认显示 vs 默认隐藏。这类 bug 不报错，只让用户看到错误的东西。

2. **时序数据的变换先定不变式，再写代码**。份额折算连错两次方向，
   根因是"边改边测 + 没有先把基准说清楚"。错误不抛异常，只让数字静默失真。

3. **判据要贴着展示口径**。"份额有没有缺"不能按全表判（场外基金长期不发布），
   要按**面板真正展示的那些代码**判——否则自检天天误报，久了没人再看日志。

4. **区分"没数据"与"数据源坏了"**。前者是正常时序，后者要告警。
   混成一种，运维会对正常现象脱敏。

5. **存量指标做判据会产生伪重复**。用"5 日累计"这类累加值触发信号，
   一次事件会连续多日超标；统计与展示都必须按事件去重。

6. **修 bug 不能改变有效结论**。本次每次修复后都复核门控对照
   （66 条 +9.18%/83.3%）保持不变——这是验收条件，不是附带检查。
