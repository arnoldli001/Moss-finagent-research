# 数据源总览与优先级路由（实测）

> 本文回答三个问题：**项目里到底有多少数据源**、**谁快谁慢（实测）**、
> **按什么顺序取数、互为备用怎么切**。所有延迟数字都是 2026-09-15 在本机实测。
>
> ---
>
> ## ⚠️ 2026-09-22 重大变更：**全量替换 QMT 为数据源**
>
> **本机 QMT 终端已失去行情权限且不再运行**（`127.0.0.1:58610` 拒连），
> 因此项目做过一次**全量取数链替换**。本章以下的 QMT 测速数据保留作为
> "它曾经多快"的历史记录，但**不再代表当前链路的优先级**。
>
> ### 替换后的实际链路
>
> | 用途 | 原链路（QMT 在链首） | 现链路 | 实测 |
> |---|---|---|---|
> | 日线（个股/ETF/指数） | QMT → 本地CSV → AkShare → 腾讯 → Tushare | **AkShare → 腾讯 → Tushare → baostock → [本地CSV 开关] → [QMT 开关] ** | 14/14 组合通过，最新=当前交易日 |
> | 分钟K / 分时 / 快照 | **QMT** → 腾讯 → 东财 → 新浪 | **腾讯 → 新浪 → 东财 → [QMT 开关]** | 腾讯 快照52ms / 分时~85ms / 分钟K~95ms |
> | 全市场全量下载 | `download_qmt_data.py`（写进 QMT 私有库） | **`scripts/download_market_data.py`**（写进项目 `data/quant/prices*/`） | 19 只 / 7956 行 / 2.8s |
>
> ### 关键改动
>
> 1. **QMT 代码全部保留，但默认关闭**：`QMT_ENABLED=0`（`src/core/config.py`）
>    与 `data.qmt_enabled=false`（`configs/intraday.yaml`）。
>    有权限的部署改这两个布尔值即可恢复原链路 —— 顺序**不需要**再动：
>    `intraday_sources` 里 qmt 仍写在最前（`health.rank` 在样本 <3 次时照抄配置
>    顺序当先验，所以"配置顺序 = 默认顺序"），关闭时它被直接从候选池摘掉。
> 2. **停更的本地 QMT 导出 CSV 退到在线源之后**：它停在 2026-08-31，
>    原来排在在线源前面会把 AkShare/腾讯/Tushare 挡在门外
>    （实测现象："日K面板停在 8-31，而腾讯当天明明有数据"）。
> 3. **市场时钟探针不再只依赖 QMT**：原 `live_session_date()` 只问 QMT
>    tick，QMT 一失效就恒返回 `""`，导致**新鲜度闸门整段失效** ——
>    陈旧数据不再被判失败，"昨天的完整分时"会顶着今天的名头画出来。
>    现改为 腾讯快照 → 东财 trends2 → QMT（仅启用时）。
> 4. **修掉三处"直连 QMT"的旁路**：`quant/price_panel.py`、`intraday/sources.py`
>    的 `fetch_quotes`（硬编码先打 QMT，不看配置）、以及 `Quant` 面板取数，
>    全部改走统一的 `build_daily_connector_chain()`。
> 5. **盘中"当天形成中bar"改由腾讯日K提供**（2026-09-23）。
>    QMT 关闭后，当天那根未收盘的日线bar没了来源，日K做T面板盘中也停在昨天。
>    实测腾讯 `fqkline` 的一个关键行为：**只要请求里带日期区间（含 end 锚点），
>    它就不返回当天这根形成中bar**，只有完全开放的 `day,,,N,qfq` 才给。
>    所以 `tencent_daily_connector` 改为"要最新的请求第 1 页发不带区间的形式"
>    （历史区间不变，回测不会吃到未收盘的bar）；
>    同时日线链加了**调用方声明的 `min_date` 下限** —— 盘中日历源自己走到今天，
>    "只到昨天"的源不再被当成合格数据（否则链上第一个返回昨天的源会把
>    带当天bar的腾讯挡在门外）。详见 `docs/INTRADAY_T_DESIGN.md` §11.3c。
>
> ### 各替代源在本机的**实测**能力（2026-09-22）
>
> | 源 | 个股日线 | ETF日线 | 指数日线 | 分钟K | 分时 | 快照 | 结论 |

> | 腾讯 | ✅ 641根/次，可日期翻页（**带区间时不含当天形成中bar**，见关键改动 ⑤） | ✅ | ✅ | ✅ 1m~60m | ✅ | ✅ 批量 | **主力**，免 token |

### 2.1b 复测（2026-09-16，QMT mini **重开之后**，每项 20 次采样，逐源直测）

上一轮测速期间 QMT mini 被关闭过，QMT 的样本不可信。重开后逐源重测
（直测而非走回退链 —— 走链路只会测到排第一的那个源，永远测不出亚军）：

| 用途 | 源 | 成功/失败 | 中位 | p90 | 最小 | 最大 |
|------|----|----------:|-----:|----:|-----:|-----:|
| quote | **QMT** | 20 / 0 | **0.2 ms** | 0.3 ms | 0.2 ms | 115.6 ms |
| quote | 腾讯 | 20 / 0 | 53.6 ms | 61.7 ms | 47.6 ms | 100.8 ms |
| bars(5m) | **QMT** | 20 / 0 | **8.0 ms** | 11.9 ms | 7.0 ms | 13.1 ms |
| bars(5m) | 腾讯 | 20 / 0 | 97.5 ms | 104.9 ms | 89.7 ms | 127.8 ms |
| trend | **QMT** | 20 / 0 | **15.5 ms** | 18.0 ms | 15.1 ms | 20.7 ms |
| trend | 腾讯 | 20 / 0 | 75.8 ms | 126.8 ms | 63.5 ms | 233.8 ms |
| bars/trend | 新浪 | **0 / 20** | — | — | — | 见下方「新浪 IP 被封」 |
| bars | 东财 | **0 / 20** | — | — | — | 本机网络阻断（RemoteDisconnected） |

排序器据此给出的回退链（用 `SourceHealthTracker.rank` 自己的逻辑，不是人工写死）：

```
quote → qmt(0ms)  ▸ tencent(54ms)
bars  → qmt(8ms)  ▸ tencent(98ms) ▸ sina(无样本/永久失败) ▸ eastmoney(无样本/永久失败)
trend → qmt(16ms) ▸ tencent(76ms) ▸ sina(无样本)
```

**QMT 三个用途全部第一**，且与腾讯的差距是 7~12 倍，不是"略快"。
QMT 快照中位 0.2 ms 是因为它读的是**本机终端内存**，没有网络往返；
最大 115.6 ms 出现在首次调用（xtquant 懒加载 + 建连），这也正是排序用
**中位数**而不是 EWMA 的原因（见 `SourceStat.median_ms` 的注释）。

### 2.2 真实运行负载下（做T面板连续 9 次快照，中位数）

| 源 | 用途 | 中位 | EWMA | 说明 |
|----|------|-----:|-----:|------|
| QMT | 快照 | 49 ms | 43 ms | 并发调用在 `qmt_guard` 锁上排队，比隔离测试慢 |
| QMT | 分钟K | 22 ms | 56 ms | 同上 |
| QMT | 分时 | 60 ms | 86 ms | 同上 |

**两个数字都真实，含义不同**：隔离测试代表"单请求极限速度"，运行中位数代表"并发下的实际体验"。
面板展示的是后者（真实记录），排序也用它 —— 这样一旦某源在负载下变慢，排序会自动调整。

### 2.3 容灾切换实测（端到端，逐项验证）

用"必然失败的 QMT 客户端替身"注入故障（替身抛真实场景原文
`XtMiniQmt 未运行或未登录`），因为真关掉 QMT 无法精确控制失败时刻、且只能测一次：

| 场景 | 结果 |
|------|------|
| ① QMT 在线 | 命中 QMT，7~9 ms；链 `qmt ▸ tencent ▸ sina ▸ eastmoney` |
| ② QMT 掉线 | 4/4 次全部自动切到腾讯（90~480 ms）；尝试日志保留 QMT 的失败原因 |
| ③ 熔断生效 | `should_attempt(qmt)=False`（冷却剩 299s）；**后续请求的尝试日志里已完全没有 QMT** —— 是真跳过，不是"再试一次又失败" |
| ④ 自动恢复 | **静默等 35s（探针周期 30s）、不手动重置**：下一次请求自己探测 QMT 并命中（10.8 ms），链自动回到 `qmt ▸ …` |
| ⑤ 双源同时不可用 | 如实抛 `分钟K线全部数据源失败`，并逐源列出原因（不静默返回空数据） |

另有一层不联网的确定性验证（9 项全通过）覆盖半开探测的机制细节：
熔断后降到末位 → 探测到期置顶 → 放行一次 → 成功则闭合熔断并把本段成功率
恢复到 100%（终身成功率仍如实显示 66.7%）→ 探测名额每周期只放行一次。

**实测代价（如实记录）**：`explore_refresh` 每 60s 会把一个"证据过期"的源插到链首
刷新一次，代价是那一次请求可能多花 ~350ms（实测东财连接中断 427ms vs 直接命中腾讯 90ms）。
这是为了让"因一次异常被降级的源"有机会翻身的必要成本，不是 bug。

## 三、结论：QMT vs Tushare 谁更适合做T

| 维度 | QMT | Tushare |
|------|-----|---------|
| 实时行情 | ✅ tick + 五档，中位 0 ms | ❌ **没有**（实时分钟/实时日线是单独收费权限，未购买） |
| 当日盘中数据 | ✅ | ❌ 当日 15:00~16:00 后才入库；实测盘中/晚间调用 `daily`/`daily_basic`/`stk_limit` 返回 **0 行** |
| 历史分钟 | ✅ 1m/5m/15m/30m/60m | ❌ 需单独 2000 元/年权限 |
| 成本 | 免费（券商提供） | 5000 积分 = 500 元/年 |
| 财务/估值/资金流 | ❌ 极简模式财务表为空 | ✅ 强项（100+ 字段 + 全市场横截面） |
| 稳定性 | 依赖本机终端在线 | 依赖公网 API + 积分限流 |

**结论：做T的实时链路以 QMT 为第一优先，腾讯为第一备用，新浪逐笔兜底；
Tushare 不参与做T实时链路，只做盘后校验与因子/财务数据源。** 两者不是"互为备用"的关系，
而是**分工**：QMT 管盘中实时，Tushare 管盘后基本面。真正互为备用的是 **QMT ↔ 腾讯**（都是实时源）。

## 四、优先级路由怎么实现（测量驱动，不写死）

`src/intraday/source_health.py` + `IntradayDataProvider`：

1. **记录**：每次源调用记录耗时/成功/失败，保留最近 20 次样本 + EWMA（仅展示）；
2. **排序** `rank(sources, method)`：`可用 → 实测中位延迟升序 → 配置先验顺序`；
   - 失败冷却中的源排到最后（但**保留在候选里**，避免"全部冷却时无源可用"）；
   - **样本 < 3 次不给结论**：冷启动的一次慢调用不该改变排序；
3. **用中位数不用 EWMA 排序**（实测教训）：QMT 首次调用要懒加载 xtquant 并连终端（~1.2s），
   EWMA(α=0.3) 会把这个值带很久 —— 面板显示"QMT 110ms"、排序把快源排到慢源后面。
   中位数把它吸收掉（EWMA 仍展示，用于观察趋势）；
4. **自动容灾**：QMT 掉线 → 记失败 + 冷却 → 排序自动让位腾讯；QMT 恢复 → 回到第一；
5. **可视化**：前端「运行指标」页新增**数据源健康度**面板（能力矩阵 + 实测延迟表 + 回退链排序），
   「量化交易」页底部健康度区也内嵌了紧凑版。

### 4.1 当日新鲜度：QMT 不会自动写当天分钟bar（2026-09-16 实盘事故）

**现象**：09:52（开盘 22 分钟）打开招商银行 600036，分时图画的是
**2026-09-15 09:30~15:00 一整条完整曲线**，工具栏只有一行小字「· 非当日」。

**根因**（逐源实测）：

```
fetch_trend("600036") → 迅投QMT，241 行，全部是 2026-09-15，无今日数据
600036.SH 当天 1m = 26 行   ← 本进程此前对它做过一次订阅/补下载
601988.SH / 000001.SZ / 600519.SH = 0 行   ← 从未触发过
```

QMT **不会**自动把当天分钟bar写进本地库；未触发订阅/补下载时
`get_market_data_ex` 只返回上一交易日的数据。而 `_trend_sync` 把"数据里最新的一天"
当成当日切片，于是昨天整天顶着"今日分时"的名头被画了出来。

**修法（两层，缺一不可）**：

1. **读之前先订阅当日数据** —— `QmtMinuteSource.warm_today()`：
   `subscribe_quote(code, period=period, count=-1)` 实测 1 秒内把**当日 + 历史**
   一起推入本地库（全新标的，订阅前为 0 行）：

   | 标的 | 订阅前 | `subscribe_quote('1m', count=-1)` 1s 后 | `('5m')` 1s 后 |
   |---|---|---|---|
   | 601318.SH | 当日 0 行 / 覆盖 0 天 | 当日 38 行 / 覆盖 **133** 天 | 当日 8 行 / 覆盖 **172** 天 |
   | 000002.SZ | 当日 0 行 / 覆盖 0 天 | 当日 38 行 / 覆盖 **133** 天 | 当日 8 行 / 覆盖 **172** 天 |

   为什么不用 `download_history_data`：做T链路有一条硬性约定
   （`tests/unit/test_qmt_guard.py` 直接断言）**绝不允许进程内调用它** —— 它曾在
   无锁并发下原生崩溃、连 traceback 都没打印就带走整个服务进程（见 `qmt_guard`
   顶部事故记录）；而隔离子进程版本要 **2.34s 且全程持有全局 QMT 锁**，
   会把 0.2ms 的实时快照读取阻塞两秒多。订阅属于与 `get_full_tick`/
   `get_market_data_ex` 同一类接口，既快又把历史一并带下来（于是下面那条
   「覆盖交易日不够就补历史」的隔离下载在绝大多数情况下不再触发）。

2. **新鲜度闸门** —— `IntradayDataProvider._try_source(..., min_date=...)`：
   **传输成功但日期陈旧**的源判**失败**（`SourceAttempt.ok=False`，detail 写明
   `分时未更新至当前交易日（最新 2026-09-15，当前交易日 2026-09-16）`），
   让链上有当日数据的源（腾讯/新浪）接手；全部源都陈旧时（停牌/休市/源整体滞后）
   才回退到**最新**的那份，同样显式标注"非当日"，且**不写缓存** ——
   源一旦恢复，下一次请求立刻切回。

   "当前交易日"取的是**市场自己的时钟**：上证指数 tick 的 `timetag`
   （实测 0.2ms），而不是"今天是不是工作日"。因为春节/国庆等**工作日但休市**的
   日期里，上一交易日的完整分时就是正确数据，按日历判会把唯一可用的数据也拒掉；
   节假日时市场时钟自动停在上一交易日，判断天然正确。时钟取不到时**放行**
   （fail-open）：真正会陈旧的是 QMT 本地库，而 QMT 不可用时它的读取本来就会失败。

**验证（新进程、从未被任何探针碰过的标的）**：

```
trend 601398（工商银行）: 迅投QMT 39 行  最新 2026-09-16   0.06s
trend 000858（五粮液）  : 迅投QMT 39 行  最新 2026-09-16   0.23s
bars  601398            : 迅投QMT 824 行 / 18 个交易日 / 尾 10:10   0.05s
snapshot(600036)        : trade_date=2026-09-16  health.stale=False
                          分时 09:30 → 10:05，全部来自迅投QMT
```

顺带修掉的两个问题：

- **分钟K线历史被"当日数据"顶掉**：原来只判断"本地是否为空"，订阅刚把当天几根bar
  写进本地库后库就不空了，历史于是永远补不上（实测 600030 的 5m 只回 7 根，
  而它本可以有 800 多根；分钟指标与阈值回测都会因此失真）。改为判断
  **覆盖了几个交易日**，并按 (标的,周期) 以 600 秒去重 —— 次新股历史天生不够，
  不能每次都背一次 2.34s 的隔离子进程开销。
- **界面误导**：分时图上方现在会在"盘中却拿到非当日分时"时给出醒目的红色警示
  （原来只有工具栏一行 `· 非当日` 小字，用户看到的仍是一整条"像今天"的曲线）。
  节假日/盘前的"展示上一交易日"则用中性提示，不甩锅给行情源。

## 六、已知边界

- **东财在本机被阻断**（`push2his`/`push2` 域名 RemoteDisconnected），
  所以"分钟K/板块分时"的东财兜底实际不可用，链路实际是 QMT → 腾讯 → 新浪；
- **新浪已封本机 IP**（2026-09-16 实测）：请求返回 **HTTP 456 + HTML「拒绝访问」页**，
  页面自称"IP 存在异常访问…已被新浪安全部门封禁，停止异常访问一段时间后
  (5~60 分钟)会自动解封"。后果是**第三级兜底当前是空的** ——
  QMT 与腾讯同时不可用时，做T链路会真的失败（⑤已验证它是如实报错而不是返回空数据）。
  代码已把这类失败单独识别为"返回非 JSON（限流/封禁）"，
  不再混进误导性的"无可取交易日"文案；
- QMT 的 **L2（十档/逐笔委托/逐笔成交）需券商单独开通**：接口已就绪
  （`get_l2_quote`/`get_l2_order`/`get_l2_transaction`），实测当前报"请检查Level-2服务器"；
- QMT 本地日线**当日可能尚未落库**（实测 9/15 拉到的是 9/14）→ 做T的日级因子用昨日日线，
  属于正常口径（当日盘中本来也拿不到当日收盘日线）；
- 腾讯/新浪是**免费公有源**，没有 SLA；重要信号建议同时看 QMT 与腾讯两个源的快照是否一致；
- **只有两层可靠兜底**（QMT、腾讯）。要真正做到三级容灾，需要引入一个
  不被本机网络/限流影响的源（例如自建行情代理，或开通 QMT L2 后的同源多路），
  而不是继续依赖免费公有接口 —— 新浪这次封禁就是实证。
