# 股票做T辅助模块 设计文档（Intraday T-Assist）

> 模块位置：`src/intraday/`（后端引擎）+ `web/src/components/Intraday*.tsx`（前端四面板）
> 配置：`configs/intraday.yaml`（策略参数，mtime 热重载）
> 接口：`/api/v1/intraday/*`、`WS /api/v1/ws/intraday`
> 免责声明：本模块输出为多因子量化打分的机械结果，不构成投资建议；做T为高风险短线操作。

---

## 一、模块定位与四个面板

对持仓个股做**日内做T辅助决策**：实时多因子打分 → 输出低吸/高抛/止损信号 → 手机推送提醒。

### 1.0 界面骨架：自选改为**左侧滑动窗口**（2026-09-17 用户报障后改版）

原布局把自选池做成工具栏下方**一行横向平铺的胶囊**，问题很直接：
一只票一个胶囊，十几只就是两三行，每加一只再挤一行 —— 分时图被一路往下挤
（用户报「容不下较多自选股」）。

改版（参考同花顺持仓栏）：

| 区域 | 实现 | 关键取舍 |
|---|---|---|
| 左：自选滑动窗口 | `.intraday-drawer`（`flex: 0 0 246px` + `position: sticky`，列表内部 `overflow-y: auto`） | 票再多也**不再影响图的高度**；收起时用 `margin-right: -258px` 让出宽度（不是 `display: none`，保留过渡动画） |
| 右：个股工作面 | `.intraday-main`（`flex: 1 1 auto; min-width: 0`） | `min-width: 0` 是必需的 —— 少了它，宽表/长代码会把这一列撑爆并溢出到抽屉下面 |
| 口径切换 | `日内分时 / 日K做T` 从工具栏移到**走势图正上方**的 `.mode-bar` | 它决定下面整块图与打分是分钟级还是日线级，贴着图更好理解 |
| 窄屏（<1180px） | 抽屉改 `position: absolute` 浮层 + 半透明遮罩；点选一只票自动收起 | 窄屏没有横向空间再分两栏；`window.innerWidth` 在点击时判一次，不引入响应式状态 |

展开状态记在 `localStorage`（`moss.intraday.watchDrawer`），窄屏首次进入默认收起；
窗口缩到 1180 以下会自动收起（但**不会**自动展开 —— 用户刚收起就被弹开很烦）。

自选行显示 `名称 / 代码 / 涨跌幅 / 总分 / 信号徽标`，与抽屉头部的
`⟳ 报价 5s · 打分 60s` 状态同一份数据（两条节奏分开标，避免把 60 秒前的信号当此刻）。

模块分两种模式（走势图上方「日内分时 / 日K做T」切换）：

| 模式 | 回答的问题 | 时间尺度 |
|------|-----------|---------|
| 日内分时 | 今天在哪一档动手 | 5分钟K线 + 分时 |
| 日K做T | 这只票处在主力四阶段的哪一步、该用哪套战法 | 日K线（量价体系，见第十一节） |

| 面板 | 位置 | 回答的问题 | 前端组件 |
|------|------|-----------|---------|
| ① 估值空间 | 左上 | 当前是「上涨空间」还是「估值透支」 | `IntradayValuation.tsx` |
| ② 分时图与提示点 | 中上 | 何时动手、在哪一档动手 | `IntradayChart.tsx` |
| ③ 多指标合成打分 | 下半部（核心） | 现在该不该动手（总分与阈值） | `IntradayScore.tsx` |
| ④ 消息面与市场情绪 | 底部 | 板块/大盘/消息面是否支持做T | `IntradaySentiment.tsx` |
| ⑤ 日K做T | 日K模式 | 量柱体系 / 高量柱攻防 / B1-B15 / S1-S6 | `IntradayDailyPanel.tsx` + `DailyCandleChart.tsx` |

数据频率：**5分钟K线**为基准周期（分时图用1分钟明细）；刷新：WebSocket 服务端每 15 秒推送。

### 1.1 分时图坐标轴策略（参考同花顺/东方财富）

**踩过的坑**：早期把关键价位线（箱体上沿/下沿）一并纳入 Y 轴 min/max，
实测某票箱体 804~1009 而当日只在 858~884 波动时，Y 轴被拉到 205 点宽，
价格线只占图高的 **8.0%**，几乎是一条水平线 —— 用户反馈「坐标轴太大看不清」。

现行策略（`IntradayChart.tsx`）：

| 规则 | 说明 |
|------|------|
| Y轴按**分时数据**定标 | 以昨收为中心、取可见区间 |最高-昨收| 与 |最低-昨收| 的较大者对称（×1.08），
完全排除箱体等远档位 |
| 可见档位才入图 | 图外的档位改在下方「档位清单」里显示（含距现价百分比 + 「图外」标注），
既不糊图也不丢信息；勾选「纳入远档位定标」可切回全貌视图 |
| 止损线必须可见 | 高抛/低吸/止损三条**可执行**档位允许把 Y 轴拉伸最多 1.6×（`MAX_LEVEL_STRETCH`），
超过则放弃 —— 止损线是最该看见的一条线 |
| 整齐刻度 | 按 1/2/2.5/5×10ᵏ 取步长，避免出现 861.8342 这类标签 |
| 双刻度 | 左轴价格、右轴涨跌幅（同花顺/东财都是双轴） |
| 缩放/平移 | 滚轮以光标为中心缩放时间轴、拖拽平移、双击复位；**Y轴随可见时间窗自动重算** |
| 成交量独立刻度 | 底部 36px 小柱，只按可见区间定标，不与价格争高度 |

实测效果（中际旭创，昨收 873.00，当日 858.00~883.73）：

| | Y轴范围 | 宽度 | 分时波动占图高 |
|---|---|---:|---:|
| 修复前 | 712.40 ~ 1033.60 | 321.20 | **8.0%** |
| 修复后 | 851.64 ~ 894.36 | 42.72 | **60.2%** |

日K线图（`DailyCandleChart.tsx`）共用同一套坐标轴策略，另加：蜡烛红涨绿跌、
**高量柱以橙色描边高亮**（量柱分析是这套体系的核心，必须一眼看见）、
均线可开关、高量安全线/风险线与止损保护线水平标注。

## 二、核心引擎：多指标合成打分

### 2.1 总分公式

```
总分 = Σ(因子得分 × 权重)       因子得分 ∈ [-1, 1]，权重合计 = 100 → 总分 ∈ [-100, 100]
```

前端表格每一行的「贡献分」逐项相加**恰好等于总分**（`engine.compose_scorecard` 与
前端渲染同口径，不留四舍五入裂缝）。

| 因子 | 权重 | 计算方式 | 关键参数 |
|------|-----:|---------|---------|
| 箱体/压力位 | 17 | 现价在近 N 日箱体中的位置 p → `-sign(p-0.5)·\|2(p-0.5)\|^2.5` | `lookback_days=20`、`exponent=2.5` |
| VWAP偏离 | 11 | `clip(-z / 3)`，z 为「现价相对当日VWAP偏离率」的当日标准化值 | `z_scale=3.0` |
| 布林带 | 8 | `clip((0.5 - %B)×2)`，收口时打 `squeeze_damp` 折 | `window=20`、`squeeze_damp=0.6` |
| MACD | 6 | 5分钟与日线 DIF-DEA 相对价格偏离 + 新交叉加成，按 0.6/0.4 融合 | `gap_scale_pct=0.008` |
| KDJ/RSI | 6 | 30分钟与日线 `mean(clip((50-J)/50), clip((50-RSI)/40))`，各占一半 | `kdj_n=9`、`rsi_n=14` |
| 市场情绪 | 6 | `0.5×(2×涨跌家数占比-1) + 0.5×clip(相对板块强度/2%)` | `rs_scale_pct=2.0` |
| 消息面 | 3 | `0.6×LLM情绪分 + 0.4×clip(3×(多-空)/(多+空))` | `llm_weight=0.6` |
| 指数量能 | 6 | `方向 × (0.5 + 0.5×量能强度)`（见下） | `change_scale_pct=1.0`、`volume_scale=0.5` |
| 板块涨幅排行 | 4 | `0.6×排名分位分 + 0.4×板块涨跌幅分` | `rank_weight=0.6`、`change_scale_pct=2.0` |
| 海外映射 | 4 | 美股隔夜0.75 + 韩股盘中同步0.25，按标的权重加权 | `scale_pct=3.0` |
| **缠论结构** | 12 | 最后笔中枢位置分 `(1-w)` + MACD背驰分 `w`，`w=0.5`（见 §2.4） | `overshoot=0.5`、`area_ratio_max=0.85` |
| **筹码量能结构** | 8 | `clip((0.5-位置)×2) × (0.5+0.5×量能强度)`；换手<1% 打七折 | `volume_ratio_scale=1.0` |
| **市场情绪周期** | 6 | 温度分段线性映射（50 为原点），退潮/冰点另走闸门 | 阈值见 `market_cycle.THRESHOLDS` |
| **股性适配** | 3 | `-clip(偏离 / (该股日ATR×0.35)) × (0.5+0.5×震荡性)` | `atr_scale=0.35` |

> **权重口径变更说明（v3，2026-09-16）**：本次把交易技能库的四个维度接进来，
> 原十因子按 **0.71** 等比缩放（24→17、16→11、12→8、8→6…，合计 71），
> 新增四项合计 29（缠论12 / 筹码8 / 情绪周期6 / 股性3）。
> 保持「箱体仍是单项最高权重」与总分区間 [-100,100]、±20/±30 阈值语义不变。
>
> 三批因子的演变史：
> — v1 七因子（箱体30/VWAP20/布林15/…）；
> — v2 十因子：原七因子 ×0.8，新增指数量能8/板块排行6/海外映射6；
> — v3 十四因子（当前）：原十因子 ×0.71，新增技能库四因子。
>
> **想回到旧口径**：前端权重编辑器一键切 `legacy` 模板
> （四因子置 0、其余恢复 24/16/12/8/8/8/4/8/6/6）。
> 三批因子的逐条技能出处、阈值来源、以及**哪些内容刻意没有量化**，
> 见 `docs/SKILL_TO_T_FACTORS.md`。
>
> 注意：若你手改 yaml 只写了原有 10 个权重，加载会因合计≠100 而报错，
> 错误信息会直接提示补上 `chan/chip/cycle/character`。

### 2.0 新增三维度（市场环境）的口径

需求原文：① 所属指数（上证/创业板/科创板）当日**成交预测量能**相比昨日增量还是缩量；
② 最相关板块的盘中涨跌幅 + 板块在**全A板块中的涨幅排行**；
③ 个股映射的**美股**（英伟达/美光/台积电/日月光/谷歌/英特尔/甲骨文/康宁…）昨夜涨跌幅
+ **韩国SK海力士**。

**① 指数量能** —— `方向 × (0.5 + 0.5×量能强度)`

- 方向 = `clip(指数涨跌幅 / 1%)`；量能强度 = `clip((量能比 - 1) / 50%)`
- 量能比 = **全天预测量** / 昨日全天量；全天预测量 = 当前累计量 / 已交易时间占比
  （9:30–11:30 + 13:00–15:00 共 240 分钟，盘中任意时刻都可比较；收盘后即为当日实际量）
- 语义：**量能只放大或衰减方向分，不单独给方向** ——
  放量上涨 +1（流动性支持做多）／缩量上涨 0（"上涨无量=见顶"）／
  放量下跌 −1（放量杀跌）／缩量下跌 0（卖压不足）
- 指数归属：688→科创50、300/301→创业板指、000/001/002/003→深证成指、其余→上证指数
- 数据源：腾讯指数快照（含成交额）+ 腾讯指数日线（昨日量）

**② 板块涨幅排行** —— `0.6×排名分位分 + 0.4×板块涨跌幅分`

- 排名分位 = `1 - (名次-1)/(总数-1)`，直接取同花顺板块快照自带的「涨幅排名 10/390」
  → 线性映射到 [-1,1]；板块涨跌幅按 ±2% 给满分
- 实测：PCB概念 `0.58% 排名10/390 家数119/115`、PET铜箔 `1.72% 排名1/390 家数31/18`

**③ 海外映射** —— `0.75×美股隔夜分 + 0.25×韩股盘中同步分`

- 单条映射：`clip(加权均涨跌 / 3%)`；各标的权重可配（默认英伟达1.5、台积电1.2…）
- **韩股SK海力士（kr000660）单独处理**：韩股 09:00–15:30 KST 与A股同时开市，
  它是**盘中同步信号**（实测 14:30 仍在更新），不是隔夜信号 —— 所以给独立权重而非混入美股
- 实测：英伟达 −3.36%、美光 −5.25%、日月光 −6.06%、台积电 −3.52%、SK海力士 −0.41%
  → 隔夜均 −4.38%、合成 −0.78（明显偏空）
- 映射来源优先级：**个股 `overseas`** → **所属板块 `boards[].overseas`** → 空（记缺口）。
  不在自选池的股票**不会**随便套用别的板块映射 ——
  实测踩过：曾让招商银行回落到 PCB 板块映射，出现「招行映射英伟达」这种无意义组合。

**符号约定**：得分 > 0 对「低吸做T」有利（超跌/超卖/情绪暖/消息多），< 0 对「高抛做T」有利。

### 2.2 与目标截图的口径对齐（回归基准）

需求给出的参考截图（箱体70%位 / VWAP偏离-0.337% z=-0.85 / 布林%B≈0.405 / MACD偏多 /
KDJ-RSI微空 / 板块19-33家上涨且跑输1.02% / 偏多5偏空10 / 总分2.6）已被固化为
**golden 测试** `tests/unit/test_intraday_factors.py::test_golden_reference_screenshot_total`：

| 因子 | 截图得分 | 本实现 | 说明 |
|------|--------:|-------:|------|
| 箱体/压力位 | -0.10 | **-0.101** | `exponent=2.5` 由该口径反解标定 |
| VWAP偏离 | +0.28 | **+0.283** | `clip(-z/3)`，z=-0.85 → 0.283 |
| 布林带 | +0.19 | **+0.190** | %B=0.405 反解 |
| 市场情绪 | -0.18 | **-0.179** | 19/33 家上涨 + 跑输1.02%，等权 0.5/0.5 |
| 消息面 | -1.00 | **-1.000** | `clip(3×(5-10)/15)` |
| **总分** | **2.6** | **2.70** | 差值来自截图四舍五入 |

> 结论：本实现的打分核可**逐项复现**目标截图；总分 2.7 落在提示线 ±20 以内 → 与截图
> 结论一致（震荡区间，不建议大动）。

### 2.3 数据覆盖度护栏

因子数据缺失时 `available=False`、贡献分置 0、原因进 `gaps`，并从有效权重中扣除。
`有效权重 < 70` 时**禁止实心正式信号**（自动降级为空心软提示并说明原因）——
防止「缺了最高权重因子却照样打满分」。

### 2.4 技能库四因子（2026-09-16 接入）

需求原文：「把今天输出的所有经验文档和 skill，加入到分时做T和日线做T的决策因子中，
作为权重之一」。

落成四个新维度，**完整口径、阈值出处、以及哪些内容刻意没有量化**见
`docs/SKILL_TO_T_FACTORS.md`。这里只记三条与本文件相关的工程要点：

1. **逐bar重放必须同步**（本模块最容易踩的坑）：
   分时图上的三角标记与 `score_series` 走的是 `features.replay_totals` 里**另写的一份算术**，
   不是复用 `compose_scorecard`。新增因子只改 `factors.py` 会**静默漏掉标记与总分序列** ——
   实测验证方式是比对「面板总分」与「`score_series` 最后一点」，两者必须相等。
   四因子里：
   - `cycle` 是纯当日常量 → 加进 `score_constants` 的常量循环即可；
   - `chan` 中枢上下沿当日常量、位置分随价格逐bar变化 → 常量带出 `chan_zd/zg/div_signed`，
     逐bar复用同一支 `chan_score_from`；
   - `chip` 量比按 **as-of 累计成交量**算（`截至当前bar累计量 / (近5日均量 × 已交易时间占比)`），
     不能用全天量（那是未来函数）；
   - `character` 的日ATR/趋势效率是常量，偏离用逐bar的 `dev_pct` 重算。

2. **情绪周期的闸门与打分分离**：`cycle` 因子分只表达「今天做T环境好不好」；
   退潮/冰点/一票否决另走 `t_allowed` 闸门（面板红字 + 禁止低吸方向）。
   刻意**只禁低吸、不禁高抛减仓** —— 退潮期的正确动作就是减仓，
   「禁止做T」不该被读成「禁止卖出」。这是实现者的解读，已在该文档显式标注。

3. **降级必须留下痕迹**：四因子任一取不到都走「`available=False` + `gaps`」而不是填 0。
   特别是情绪周期：它在 `MarketCycleProvider` 里**只缓存当日结果、绝不返回上一次的旧值**，
   因为周期阶段错一天会导致「退潮期被当成震荡期」，这是会造成实际亏损的那类错误。

## 三、信号触发机制

### 3.1 关键价位

| 档位 | 计算 | 说明 |
|------|------|------|
| 低吸线 | 箱体下沿，与布林下轨取**较高者** | 两个支撑中更早被触及的那条先动手 |
| 高抛线 | 箱体上沿，与布林上轨取**较低者** | 两个压力中更早被触及的那条先动手 |
| 止损位 | 低吸线 × (1 - `stop_loss_pct`%) | 默认低吸线下方 1%，**硬约束底线** |

**档位差护栏**（`min_band_pct=1.5%` / `max_band_pct=8%`）：

- 过窄 → 围绕原档位中点对称**扩张**：做T一轮双边成本约 0.2%（佣金0.05 + 印花税0.05 +
  滑点0.1），档位差只有零点几个百分点时信号再准也会被摩擦成本吃光；
- 过宽 → 围绕**现价**对称**收缩**：20日箱体在趋势股上可达 25% 宽，
  此时箱体边界离现价太远、做T永远等不到；收缩必须围绕现价，否则现价贴近箱体下沿时
  会出现「低吸线高于现价」这种永不触发的档位（已有测试覆盖）。

### 3.2 触发规则

| 条件 | 信号 | 图形 |
|------|------|------|
| 价格 ≤ 止损位 | 强制卖出警告 | ⛔ 且**禁止一切低吸信号** |
| 触及低吸档位 且 总分 ≥ 动手线(30) | 正式低吸做T | 实心绿三角 |

### 3.2d 图上看不到档位线 / 没有十字光标（2026-09-17 用户报障）

用户报「分时图没有画出低吸、高抛、止损虚线，鼠标移进去也没有十字轴和数值」。
三个独立原因，全部修掉：

| # | 原因 | 修法 |
|---|---|---|
| 1 | **SVG 没有显式 `stroke`**：档位线只给了 `className="lv-sell|lv-buy|lv-stop"`，而 CSS 里写的是 `.lv-sell line { stroke: … }`（**元素**选择器）。漂移曲线是 `<path>`，匹配不上 → 按 SVG 默认 `stroke:none` 渲染 = 一个像素都不画 | 漂移 `<path>`、参考 `<line>`、标签 `<text>` 一律**内联 stroke/fill**；CSS 同时补 `.lv-sell path` 等规则（两道防线） |
| 2 | **档位线被 Y 轴裁掉**：定标只允许 1.6× 拉伸，止损（ATR 口径下离现价 5%+）落在域外。实测 300308：昨收 907.8、分时 867.44~917.50、止损 860.40 → 旧域 `856.61~958.99` 能容下，但换一组数据就会被裁 | ① 参考线现在**始终画**（在范围内画虚线 + 左右标签）；② 在范围外时在上/下边缘画**贴边指示线**：`止损 860.40（−5.19%）↓在图下方`；③ 档位清单每条加**显示开关**（默认全开）；④ 「图外档位也纳入Y轴」的勾选框保留 |
| 3 | **只有纵十字线、没有横线**：旧实现只在数据点上画一条竖线 + 一个圆点，鼠标 Y 位置完全没用上 | 十字光标改为**纵线吸附分钟点 + 横线跟随鼠标**，两端带轴标（左=价格、右=涨跌幅、下=时间），读数条新增 `光标 <价> <涨跌%>` 与「光标价距三条档位线的百分比」 |

### 3.2e 档位**神经网络拟合**（2026-09-17 新增，`src/intraday/level_fit.py`）

需求原文：「优先使用筹码量能结构、箱体/压力位、缠论结构、VWAP偏离、布林带、MACD、
KDJ/RSI 这些**客观数据**做神经网络拟合出低吸、高抛、止损的合适价格线，拟合目标是
在**过去 10 个交易日做T成功率 80% 以上**。然后再根据指数量能、消息面、市场情绪、
市场情绪周期、海外映射、板块涨幅排行、股性微调。默认参数值，每个个股都要通过
神经网络拟合一下。」

#### 一、口径落点：网络学的是"尺度的混合"，不是三个神秘价格

三条线在数学上是**分位数**（"跌到过去 10 天里最深的 10% 那种位置"），
逐票不同、无法预先写死的部分是「**怎么把 7 个客观维度组合成对该股合适的尺度**」：

```
低吸线 = Σ_k w_k × 分位数锚点_k(P05…P30)      ← w 由网络拟合
高抛线 = Σ_k v_k × 分位数锚点_k(P70…P95)
止损位 = Σ_k u_k × 分位数锚点_k(P97…P99.5)
锚点 = 该股自己「每根 bar 相对当日均价的偏离幅度」的经验分位数
```

- 锚点天然带该股波动尺度（≈ATR 口径），**可追溯**："低吸=P15 档"；
- 混合权重 `w/v/u` 是网络拟合出的参数（15 个数），另外一层
  `7→hidden→3` 的小网络做**逐 bar 微调**（当前状态适合把线放宽还是收紧，±15% 夹紧）。

实现约束：项目没有 torch/sklearn，网络是手写前向/反向的 numpy MLP
（tanh + Adam + L2，全批量），单票拟合 0.5~5 秒，按 (代码, 交易日) 缓存。

#### 二、成功率怎么算（全模块最关键的诚实点）

| 口径 | 定义 | 为什么要报 |
|---|---|---|
| 触及 | `bar_low ≤ 低吸线` | 分母**只算触及过的样本** —— 把线画到天边不能刷成功率 |
| 成功 | 触及后 H 根 bar（默认24=2小时）内**先**到高抛、且全程不破止损 | 与"做T一轮"的实际动作一致 |
| 失败 | 先破止损 / 时间到没到高抛（时间止损） | 后者只亏摩擦成本 |
| **样本内** | 在**训练的那些天**上的成功率 | 用户问的"过去 10 个交易日成功率" |
| **留一日** | 留一天、用其余天拟合、在留出日上统计（leave-one-day-out） | **只看样本内一定会过拟合**：480 根 bar 上做到 100% 太容易 |

**前瞻窗口不跨交易日**：做T当日事当日毕，允许跨日会把隔夜跳空算成做T成功。

#### 三、启用闸门 + 可达性上限（两条防止自欺的机制）

1. **闸门**：`留一日成功率 ≥ 目标 80%` 且 `触及样本 ≥ 20` 才允许把拟合档位
   用在信号判定上；否则**回退规则口径**，并把两个数如实报出来。
   宁可告诉用户"这只票拟合不出 80%，我用规则口径"，也不能拿过拟合的 80% 指导下单。
2. **可达性上限**：正式搜索只在 5×5×3 个锚点里选，用户看到 30% 会问
   "是没搜到，还是这只票本来就不行"。于是再扫一遍更宽的组合
   （低吸 0.1~2.0% / 高抛 0.2~4.0% / 止损 1.5~8.0%），报出窗口内的**上限**：
   - 上限 < 目标 → 行情结构决定的上限，调参解决不了；
   - 上限 ≥ 目标 → 机会存在，是拟合没泛化到它。

实测（300308，2026-09-17，8~10 个交易日 / 320~435 根 5 分钟 bar）：

| 指标 | 实测值 |
|---|---|
| 样本内成功率 | 34~39% |
| 留一日成功率 | 30~38% |
| 放宽搜索上限 | 71~80%（最优点常落在"低吸 1.4% / 高抛 1.6% / 止损 4%"，仅 35 次触及） |
| 闸门 | **未通过** → 档位仍走规则口径 |
| 单次拟合耗时 | 0.8~4.9 秒 |

结论（写进面板的 notes）：这只票在这段行情里**不存在稳定可复制的 80% 做T结构**；
把目标线压到 80% 会要求止损放得很宽、样本极少，那种 80% 是过拟合不是能力。

#### 四、拟合之后的 7 个"调整项"

其余 7 个维度**不参与拟合**，按作用面归并成三个有界乘数（各夹在 0.5~1.5）：

| 分组 | 维度 | 作用 |
|---|---|---|
| `structure` | 指数量能、股性适配 | >1 = 适合更宽的波段（线放远） |
| `environment` | 市场情绪、情绪周期、海外映射、板块排行 | >1 = 环境偏暖（低吸适度提前） |
| `micro` | 消息面 | >1 = 消息面偏多（整体微调） |

为什么归并成三个而不是"每维各调一条线"：7 个维度各调一次会互相打架
（消息面看多 + 情绪周期退潮 = 抵消成噪声），也无法解释。打分核与打分卡**同一批函数**，
所以面板改权重，乘数跟着动，不存在两套口径。

#### 五、接线位置与性能

- 拟合在 `service.snapshot` 里、**打分卡之前**执行（`apply_level_fit`），
  并在 `replay_levels` 的逐 bar 曲线上同样套用 —— 否则会出现"曲线在 892、
  右上角标签写 898"两个口径打架；
- 结果按 (代码, 交易日) 缓存在 `_fit_cache`（默认 1800 秒），
  盘中每 15 秒的快照**不会**重训；
- 接口 `GET /api/v1/intraday/level-fit?code=&refresh=`，面板「重新拟合」按钮按需触发；
- 5 分钟 bars 的取数窗口由 `_intraday_days = max(6, sessions)` 决定：
  腾讯单次上限 320 根（≈6.6 天），拿不到 10 天时拟合侧**按实际天数如实标注**
  （实测拿到 8~10 天 / 320~435 根）。

### 3.2f 顶部提示条不消失 + 回调身份引发的连锁（2026-09-17 用户报障）

用户报：「做T辅助界面以下提示一直悬浮无法关闭 —
`已保存权重档案并生效：分时权重 board_rank=4, ... 阈值 action=20, hint=15；档位 ...`」。

两个独立问题，都修了：

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 提示条常驻、且**没有关闭入口** | `notice` 被当成永久状态：`setNotice(text)` 之后**没有任何地方清它**（只有下一次加/删自选才被覆盖）。保存权重是一次性动作，成功文案却挂到用户手动刷新为止 | ① 提示条右侧加「×」；② **9 秒自动消失**（`NOTICE_TTL_MS`）；③ 切换标的时清空（它讲的是上一只票的事）；④ 用 `{id, text, level}` 代替纯字符串 —— 连续两次同一条消息也能重新计时 |
| 2 | 顺手修掉一个我上一轮引入的隐患 | 拟合面板的 `onFitted` 回调是在 JSX 里内联的箭头函数，父组件每次渲染（快照每 15 秒一推、hover 都会触发）都新建一个；它进了子组件 `useCallback` 的依赖 → `run` 身份每 15 秒变一次。当前没有 effect 依赖 `run`，所以没真的自旋，但**只差一个依赖就会变成「快照更新 → 回调变 → 重新拟合 → 快照更新」的死循环** | 回调放进 `useRef`（子组件）+ 父组件用 `useCallback` 固定身份（`handleFitted`） |

教训：**一次性动作的提示必须自带生命周期**（自动消失 / 可关闭 / 切换上下文清空）；
以及**传给子组件的回调要么稳定、要么通过 ref 读取** —— 否则"父组件高频重渲染"
会顺着 `useCallback` 依赖链扩散成子组件的重复请求。

### 3.3 止损硬约束（安全关键）`decide_signal` 的判定顺序即优先级：**止损分支在最前，低吸分支根本不会被求值**。

参数化测试 `test_stop_loss_overrides_every_score` 覆盖 总分 = {+100, +60, +30, 0, -100}
× 价格跌破止损位的组合，全部断言得到 `forced_exit` 且 `blocked_by_stop_loss=True` —
杜绝「越跌越买、越套越深」的路径。

**但"止损位本身算错"会让这条安全约束反过来制造噪声**（2026-09-16 实盘事故）：

> 用户反馈："几乎每个股都有红色实心倒三角出现止损信号，而实际都是很好的低吸位置点。"

逐字段拉真实快照后定位（300308，14:44）：

```
箱体 804.02~949.73(20日)   布林 下902.06 中905.55 上909.04（带宽仅 0.77%）
当日开盘 869.02   当日最低 867.44
→ 低吸线 = max(箱体下沿804, 布林下轨902) = 902   ← 布林是**当日分钟bar**算的
→ 档位差护栏再围绕中轨扩张 → 低吸 898.75 → 止损 = 898.75 × 0.99 = 889.76
→ 早盘 226 个分时点里 60 个（27%）被判"已跌破止损"，图上画出 11 个红色实心三角
```

三处修正（都在 `engine.compute_levels` / `engine.build_markers`）：

| # | 修正 | 原因 |
|---|------|------|
| 1 | 布林下轨只有在**现价下方**才算"支撑"候选 | 强势股刚突破时 20 根bar带宽可窄到 1%，下轨会跑到当日开盘价上方 —— 那不是支撑，取 max 只会把低吸线抬到现价之上 |
| 2 | 低吸线必须在现价下方（跳空高开时退化为现价下方的防守位） | "低吸"的语义是跌到支撑才买；高于现价说明这条支撑已失效。它同时保证**止损必然低于现价** |
| 3 | 止损距离 = max(固定百分比, `atr_stop_mult`×ATR) | 300308 的日线 ATR=52.8（占价 5.8%），固定 1% 只有 9 元 —— 任何噪声都能打穿；600036 的 ATR 只占 1.7%，1% 是合适的 |
| 4 | **图上止损标记必须是一次真实破位**：收盘价跌破"**本bar之前**的最低价" 0.3% 才算 | 回放用的是**当前**这份 levels，而止损位会随行情上移；只判 `close <= stop_loss` 会把早盘低点追认为破位（这正是那 11 个三角的来源） |

修正后实测（同一批标的、同一时刻）：

```
300308: 止损 889.76 → 872.29（ATR 口径）   止损标记 11 个 → 1 个（且落在当日最低点）
600176: 止损 46.18 → 45.17                止损标记 3 个 → 0 个
600036: 止损 40.19                        止损标记 → 0 个（只剩 1 个低吸提示）
三只票的实时信号全部 none（无伪止损）
```

止损位现在还带 `stop_basis`（如「低吸线下方 0.5×ATR（ATR=52.82…）；当日最低 867.44」），
面板可直接说明这条线是怎么来的 —— 用户看到数字没法判断该不该信它。

### 3.4 个股微调：一套参数不可能适配所有票

同一份实测揭示了另一件事：**波动率差一个数量级的两只票，不该共用一组参数**。
`configs/intraday.yaml` 支持按代码覆盖：

```yaml
overrides:
  "300308":
    weights: {boll: 8, vwap: 20}        # 高波动突破股：降低布林权重、提高VWAP偏离
    thresholds: {action: 35, hint: 25}  # 波动大 → 阈值抬高，减少噪声信号
    levels:
      stop_loss_pct: 2.0                # 止损距离下限 2%
      atr_stop_mult: 0.8                # 且不小于 0.8×ATR（高波动股的关键）
      min_band_pct: 2.0                 # 低吸~高抛最小档位差，否则被摩擦成本吃光
```

只写要覆盖的项，其余沿用全局；**字段名写错直接报配置错误**（不是静默忽略 ——
"改了却没生效"是最难查的一类问题）。生效时面板会在缺口区显示
「已应用个股微调（overrides.XXXXXX）：…」，避免两套口径混着看。
`GET /api/v1/intraday/config` 也会返回 `overrides`，前端可展示"这只票改了什么"。

> **2026-09-16 更新**：现在有两条个股口径，优先级为
> **数据库权重档案 > YAML `overrides` > 全局配置**。
> YAML 这条路继续可用（手工编辑、可版本化），但**主档案已改为数据库**
> （前端可编辑、按个股股性保存、下次直接复用）—— 见 §十三。
> 两条路都能覆盖 `weights` / `daily_weights` / `thresholds` / `levels` 四类参数，
> 面板会明说是哪一份在生效。

## 四、数据层：多源容灾

### 4.1 为什么独立于 ConnectorRouter

分钟数据是**多字段 OHLCV 的 bar 序列**，而项目既有 `DataPoint` 契约是「一个指标一个标量」；
且分钟数据每分钟都变，若走路由会被逐次写入 SQLite（单只票每次 320 根 bar 造成无意义库膨胀）。
因此 `src/intraday/sources.py` 自带取数与 TTL 缓存。
**日线上下文仍然复用项目既有采集链**（QMT→本地CSV→AkShare，经 `daily_bars_from_points`
归一化其两种 `extra` 列名口径），估值 PE/PB 序列同样复用该链。

### 4.2 源优先级与实测结论（2026-09 于本机）

| 优先级 | 源 | 能力 | 实测 |
|-------:|---|------|------|
| 1 | 迅投QMT(xtquant) | 5分钟/1分钟K线、逐笔快照，可回补长历史 | 需 XtMiniQmt 运行登录；未启动时明确报错并回退 |
| 2 | 腾讯行情 | 一次请求即回 320 根5分钟K线 / 全天分时 / 实时快照(含PE/PB) | **可用**，免Key稳定 |
| 3 | 东方财富 | 分钟K线 | `push2his.eastmoney.com` 本机被阻断（RemoteDisconnected），保留在链上待网络恢复 |
| 4 | 新浪财经 | 全天逐笔（约4500笔）→ 聚合为分钟bar | **可用**，作为最深兜底 |

全部失败即抛 `DataFetchError` → 写入 `health.gaps`，**绝不使用模拟数据**
（与项目「真实源失败不回退 simulated」的硬约束一致）。

> **兜底路径的可用性是演练出来的，不是假设出来的**：2026-09-15 实测中「QMT未启动 +
> 腾讯网络抖动」同时发生，新浪逐笔兜底抛 `KeyError: 'ts'`（逐笔原始帧的列是
> `ticktime/price/volume`，没有 `ts` 列，却被直接喂给了要求 `ts` 列的聚合函数），
> 导致唯一能兜住的来源也失效、分钟K线整条链路报缺口。已修复并补回回归测试
> `tests/unit/test_intraday_sources.py`（17 例，离线锁定该路径）。
> 修复后真实数据实测：新浪逐笔 → 49 根5分钟bar，VWAP = 869.69，
> 与腾讯路径的 869.58 相差 **0.01%** —— 两个独立数据源交叉验证了 VWAP 实现。

### 4.3 两个实测校准（真实数据反解）

1. **腾讯分钟线的成交额字段不可信**：2026-09-15 中际旭创逐 bar 求和为 161.78 亿元，
   而快照口径真实成交额为 156.14 亿元（高估约 3.6%）。若用它算 VWAP，均价会被抬到
   901 元（真实 869.6 元）——足足差 3.6%，会静默给出错误档位。
   **处置**：该字段置 0，VWAP 回退到典型价 `(H+L+C)/3`，实测 869.31 元，与真实值仅差 **0.03%**。
2. **量纲自愈**：不同源的 `volume` 有「手/股」两种口径、`amount` 有「元/亿元」两种口径。
   `vwap_series` 用「额/量 推导价 vs 收盘价中位数」的比值判定是否存在 100 倍手数错配并自动归一，
   避免均价线飘到 100 倍价位上（已有单测）。

### 4.4 关联板块与情绪

| 数据 | 来源 | 说明 |
|------|------|------|
| 板块涨跌幅 / **涨跌家数** / 成交额 / 资金净流入 / 涨幅排名 | 同花顺概念板块快照 | 「板块内 119/234 家上涨」即 f 维度①的数据源 |
| 行业级涨跌家数 | 同花顺行业板块汇总 | 概念板块缺家数时的替补 |
| 板块分时序列 | 东财概念分钟 → **自选同业等权合成** | 见下 |
| 大盘状态 | 腾讯指数快照（上证指数） | 上涨/下跌/震荡三档 |

**板块分时为何要「等权合成」兜底**：东财板块分钟接口在本机被阻断，且当前 akshare 版本
无同花顺概念成分股函数，拿不到成分股清单就无法直接画板块分时。此时用**已配置的自选同业
股票池**等权合成一条日内指数线（各股以当日首个价格为基期归一后等权平均），
并在返回体中标注 `kind="synthetic_peers"` + 前端显式写明口径，**绝不冒充官方板块指数**。

**板块归属：只认「已绑定」，绝不猜（实测踩坑后的硬规则）**

「关联板块」是**用户判断的产业链关联**（如中际旭创 ↔ PCB概念/PET铜箔 是上下游关系，
而不是它的同花顺概念成分），数据源也没有「成分股反查」接口。因此：

| 场景 | `boards_bound` | 板块快照 | 参与打分 |
|------|----------------|----------|----------|
| 该标的已在自选中声明 `boards` | `true` | 即所声明的板块 | ✅ 板块情绪(8) + 板块排行(6) 计入 |
| 未在自选中声明（随口查一只票） | `false` | 配置里的全部板块，仅作**参考板块**展示 | ❌ 两维度记「不可用」，权重从 `available_weight` 扣除 |

原实现是「未在自选就回落到全部配置板块，保证面板不空」，实测后果：随口查 **600036 招商银行**，
面板拿配置里第一个板块（PCB概念）当它的板块，
于是「银行股按 PCB 板块涨幅排名 10/390 打分」——板块情绪 + 板块排行共 14 分权重被无关板块污染，
总分 −7.07 里有 +0.20 来自 PCB 的排名分。修复后该标的 `available_weight = 80/100`，
板块类因子贡献 0 分，并在 `gaps` 写明修复路径：**在「自选」里用「加自选」填写关联板块即可绑定**
（前端顶栏新增「关联板块」输入框，留空不写入，避免把「随便看看的板块」固化成关联板块）。

绑定后板块分时仍会叠加到分时图上（展示不受影响），只是不参与打分。

### 4.5 估值空间（三口径）

| 口径 | 来源 | 作用 |
|------|------|------|
| 个股自身 PE/PB 近三年日频分位 | 项目既有采集链（百度估值，经 ConnectorRouter 复用 TTL/DB 缓存） | 绝对估值水平 |
| 自选同业逐只 PE/PB + 中位数 | 腾讯批量快照（一次请求 ≤60 只） | 同业对比与溢价/折价 |
| 行业中位数 PE | 巨潮「行业市盈率」接口 | 不依赖自选池的权威对标线 |

合成：`估值空间分 = mean(可用分量)`，分量为 分位分量 `(50-分位)/50` 与
各溢价分量 `clip(-(PE/对标中位-1)×100/50)`；五档结论
`ample / moderate / stretched / expensive / unknown`。

### 4.6 消息面 NLP

复用项目既有 `AkshareNewsFetcher`（个股新闻）+ `LLMGateway`（唯一 LLM 入口，
自带语义缓存/熔断降级/审计/token预算）。任务层级默认 `light`（本地 qwen2.5:1.5b-instruct
非推理模型主、deepseek-flash 备）——**这个默认值是实测选出来的，不是拍脑袋**：

| 层级 | 模型 | 单次耗时 | 稳定性 |
|------|------|--------:|--------|
| `light` | qwen2.5:1.5b-instruct（非推理） | **1.1~1.2s** | 2/2 成功 |
| `medium` | qwen3:8b（推理模型） | **72~85s** | 偶发正文为空 |

`medium` 的两个致命问题：
1. **慢**：推理模型的思维链极长，单次 72~85s。新闻情绪只是权重 5 的一个因子，
   为它付 80 秒延迟完全不值得（还会拖垮整个快照）。
2. **偶发正文为空**：同一 prompt 调两次，一次返回合法 JSON（543 tokens），
   另一次 `tokens_out=4096`（=上限）且 `content` 为空 —— 思维链把 token 额度耗光了。
   而网关会把**空返回也缓存 24h**，形成「毒缓存」：之后同一 prompt 每次都命中空响应。
   实测表现为「有些股票有 AI 情绪分，有些永远没有」。

三重防护（`configs/intraday.yaml` → `factors.news`）：
- `news_task_tier: light` —— 换成非推理模型，从根上消除该失败模式；
- `llm_retries: 1` —— 空返回/非 JSON 时重试一次，并在重试 prompt 追加
  「【严格模式】直接输出JSON，禁止思考过程」（prompt 变化同时绕开毒缓存键）；
- **默认 `use_cache=False`** —— 不走网关层缓存，避免被毒缓存钉死；
  重复请求由本模块自己的 `news_cache_ttl`（默认600s）缓存挡住，无需网关缓存兜底。

`gap` 字段会如实区分失败原因（「模型本次未产出正文（输出tokens=4096，疑似思维链耗尽额度）」
vs「LLM输出非合法JSON」），而不是笼统报「非合法JSON」。

**越界不静默钳制**：LLM 返回分数超出 [-1,1] 时判为不可用并记录缺口，
自动降级为「纯计数口径」打分（与 `domain/alerts` 的 `ScoreOutOfRange` 约定一致）。

### 4.7 盘中实时性契约（数据多快能到屏幕上）

结论：**盘中不需要手动刷新**，但"实时"有明确上限，逐层如下（实测 2026-09-15 收盘后）：

| 层 | 机制 | 实测/配置 |
|----|------|-----------|
| 推送 | 前端建 WS，服务端循环「取快照 → 推 → sleep 15s」 | 实测每帧间隔 **18~19s**（15s 间隔 + 3~4s 快照耗时） |
| 降级 | WS 断开/报错自动切 20s 轮询，右上角徽标从「实时推送」变「轮询模式」 | `POLL_FALLBACK_MS = 20000` |
| 现价（当前标的） | 每帧重新取，快照缓存 15s | 滞后 ≤ 15s |
| 现价（**自选列表**） | 报价快车道：批量 tick 每 5s 一轮，由 WS 立即推 | **滞后 ≤ 5s**（见 4.12；实测每轮 1~2ms） |
| 分时线 / 分钟K线 | 缓存 45s（`minute_cache_ttl`） | 滞后 ≤ 45s |
| 分时线的**粒度** | 源本身是 1 分钟 bar（QMT `1m` / 腾讯 1m），5分钟K线同理 | **每分钟才新增 1 个点**，5m bar 每 5 分钟才变 |
| 总分 / 信号（自选列表） | 整表重算每分钟一轮 | 滞后 ≤ 60s（**不要用快车道的价格去推断它的新鲜度**） |
| 板块快照 | 每次快照重取（东财板块分时有失败冷却） | 近实时 |
| 日线 / 估值 / 消息面 | 1800s / 3600s / 600s 缓存 | 分钟级，日频数据本就不需要更快 |
| 手动 | 顶栏「强制刷新」按钮 → `invalidate()` 清空全部缓存后重取 | 需要立刻确认时用 |

因此"实时"的准确说法是：**屏幕上最多滞后 45~60 秒**（45s 缓存 + 一个推送周期），
但分时曲线本身是分钟粒度，所以曲线端点最多落后当前时刻 1 分钟。
非交易时段不会假装实时：`session_state` 为 `closed`/`lunch_break` 时，
分数基于**最近一根已完成 bar**，并在 `gaps` 明确写出「档位仅供参考」。

### 4.7b 做T会消耗 token 吗？——实测账单（2026-09-16）

**结论：正常使用不消耗云端 token。** 做T链路里**只有一处**会调模型：消息面情绪打分
（`NewsSentimentAnalyzer`）。其余全部是免费行情接口（QMT/腾讯/新浪/同花顺/百度估值），
**完全不碰 19 个 Agent**（那条链路才是花 token 的）。

按 `data/audit/llm_audit.jsonl` 逐条核对（做T消息面 278 次调用）：

| provider/model | 次数 | in 合计 | out 合计 | 中位延时 | 计费 |
|---|---:|---:|---:|---:|---|
| ollama/qwen2.5:1.5b-instruct-q4_K_M | 115 | 237,255 | 8,500 | **991ms** | **0 元**（本地） |
| ollama/qwen3:8b-q4_K_M | 161 | 326,058 | 397,638 | **53,752ms** | **0 元**（本地） |
| deepseek/deepseek-flash（fallback） | 2 | 0 | 0 | — | 0 元（熔断记录，非真实调用） |

即 **云端付费 token = 0**：`light` 层主模型是本地 Ollama（`models.yaml`），
而 `news_task_tier: light`。**唯一的例外**是本地模型不可用/超时/熔断时，网关按
`routing.light.fallback = deepseek-flash` 自动降级 —— 那时才计费（单次约 p50
输入 2046 + 输出 ~70 token ≈ 0.002 元）。

**调用频率**（只有第一条会调模型）：

| 触发点 | 调 LLM？ | 频率 |
|---|---|---|
| 完整快照（发分时/日K面板） | ✅ | 每个标的每 `news_cache_ttl=600s` 最多 1 次 |
| 自选整表重算（每分钟 × N 只） | ❌ `light=True` 直接跳过 | 0 |
| 报价快车道（5s/轮）、日K做T、估值/板块/指数 | ❌ | 0 |
| **抓不到新闻**（今天盘中就是） | ❌ 直接走关键词计数兜底 | 0 |

**真正的问题是白烧本地算力**：278 次调用里只有 **28 个不同的 prompt**（重复率 90%，
最热的一个 prompt 被推理了 **97 次**），161 次走 qwen3:8b（中位 53.7 秒），
13% 把 4096 输出额度全烧在思维链上（正文为空 → 重试再烧一次）。

**已实施的优化**：TTL 到期后照常抓一次新闻（本来也要抓），先比**内容指纹**
（标题+发布时间）；没变 → 滑动 TTL 复用上次打分、**不调 LLM**；变了 → 才重跑。
新闻抓取频率不变，所以是纯收益。开关 `factors.news.reuse_when_unchanged`（默认开），
省下的次数可在 `GET /api/v1/intraday/config` 的 `news_llm.reused_calls` 看到。

**还可以做的**（按收益排序，未实施）：

1. **打开网关缓存的"只缓存有效响应"模式**：现在 `use_gateway_cache=False` 是为了
   避免"空返回被缓存 24h"；给网关缓存加 `skip_empty` 后即可打开，跨进程/重启也能命中。
2. **收紧 prompt**：输入 p50 = 2046 token，主要是 `max_items=10 × item_text_chars=180`；
   降到 6 × 120 约省 40%（对 1.5b 的 2048 上下文也更安全）。
3. **彻底禁止云端降级**（若目标是"永不花 token"）：把 `routing.light.fallback` 改成
   本地模型自身，或给消息面加 `allow_fallback=False`；本地挂了就走关键词兜底（已实现）。
4. **坚持 `light` 层**：`qwen3:8b` 是推理模型，做短分类会烧 4096 输出 token、中位 53.7 秒；
   1.5b 非推理模型输出约 70 token、中位 0.99 秒。

### 4.8 QMT 时间口径：ts 整体早 8 小时（实测踩坑）

QMT `get_market_data_ex` 返回的 `time` 列是 **UTC 基准的 epoch 毫秒**，而 DataFrame 的
**索引才是本地时间字符串**（`20260915150000` = 15:00）。早期实现直接
`pd.Timestamp(ms, unit="ms")` 得到 UTC 朴素时间，实测当日最后一根 bar 变成 `07:00`：

- 分时图 X 轴整体早 8 小时（09:30 开盘显示成 01:30）；前端的 `sessionMinute()`
  把「09:30 之前」一律折叠为第 0 分钟，于是**整条分时曲线会被挤到最左侧**；
- 日期部分不变，所以 `trade_date`、VWAP 按日分组、当日/历史切分都"看起来正常"，
  缺陷因此长期未暴露（腾讯源本身给的是本地时间，只有 QMT 主源命中时才触发）。

修复：优先用索引/`stime` 字符串，缺失时才把 `time` 当 UTC 毫秒**换算到北京时间**
（固定 +8，不用系统时区——服务器若设成 UTC 会再次错位）。

**不变式护栏**：`test_timezone_fix_changes_labels_only_not_values` 把同一批 bars 平移 −8h
重算，断言 5分钟特征（VWAP/布林/带宽/MACD）与 30分钟 KDJ 数值逐行相等、NaN 位置一致 ——
即该修复**只换标签、不改分**（30分钟分桶按"当日第几分钟"归属，8 小时恰为 30 分钟的整数倍）。

### 4.9 QMT 并发访问导致服务猝死 → 进程级护栏（本模块最严重的一次事故）

**症状**：用户新加一只票后，服务进程**无 traceback 猝死**（exit code 1，uvicorn 连
"Shutting down" 都来不及打印）；`/intraday/snapshot` 直接连接被重置。
两次现场都能看到 xtquant 正在下载：

```
GET /api/v1/intraday/daily?code=600176 HTTP/1.1 200 OK
  0%|          | 0/5 [00:00<?, ?it/s]     ← download_history_data 的进度条
（进程结束，无任何 Python 异常栈）
```

**根因**：xtquant 有**两个各自持有一份客户端、且都在工作线程里调用**的入口
（项目日线连接器 + 本模块取数层），两侧都没有串行化。用户快速切标的时
`asyncio.to_thread` 会把 `get_market_data_ex` / `download_history_data` /
`get_full_tick` 并发压到同一个 QMT 终端上。xtquant 的下载接口是**原生实现且非线程安全**，
原生层一出错就是整个解释器消失，`try/except` 拦不住（与 py_mini_racer 同一类问题，
但这次是**下载**路径，且发生在服务进程内）。

**修复**（`src/core/qmt_guard.py`，中性层，两侧共用）：

| 手段 | 作用 |
|------|------|
| `qmt_lock()` 进程级可重入锁 | **所有** xtquant 调用（读、tick、下载）都持锁，把"并发访问"这个变量消掉 |
| `download_history_isolated()` | 补下载放**子进程**执行；子进程原生崩溃只死子进程，服务进程照常运行；返回值语义 `(是否成功, 原因)`，**永不抛异常** |

调用方行为变化：本地无数据时先隔离补下载，失败则记缺口并让上层回退（腾讯/项目采集链），
**不再**在服务进程里直接 download。实测三个从未取过的新标的（601398/000651/300750）
首次取数全部正常，服务存活；新标的首次补下载约 19s（一次性成本，有 45s 超时上限）。

**注意**：写盘只修了这两处调用点；若将来新增 xtquant 调用，必须同样 `with qmt_lock():`。

### 4.10 板块名要对上数据源官方名（用户写法 → 官方名自动解析）

用户在「关联板块」里写的是自己能懂的名字，数据源用的是它自己的目录名。实测：
300308 被绑定到 **CPO概念**，但同花顺官方名是 **共封装光学(CPO)** ——
直接拿用户输入去查会 `IndexError`（官方名列表里没有该名），
再退到新浪（全表仅 175 个粗概念板块，**没有 CPO/PCB/铜箔**）也必然失败，
于是「板块情绪(8) + 板块排行(6)」共 14 分权重静默变成不可用。

`board.match_board_name()` 逐级解析（**歧义即放弃，绝不猜**）：

1. 归一化后完全相同（`PCB概念` → `PCB概念`）；
2. 去掉「概念/板块/指数/行业」后缀后相同（`PCB` → `PCB概念`）；
3. ASCII 片段唯一命中（`CPO概念`/`cpo` → `共封装光学(CPO)`；`液冷` → `液冷服务器`）；
4. 双向包含且唯一（`铜箔` → `PET铜箔`）。

歧义示例：`封装` 同时命中「共封装光学(CPO)」与「先进封装」→ 返回 None；
`AI` 命中 11 个 → 返回 None。官方名列表在子进程里取一次并缓存（失败冷却 300s），
解析结果按请求名缓存；面板的 `source_name` 会写明 `CPO概念→共封装光学(CPO)`，口径可见。

另加两道冷却，避免"注定失败的调用"被每 15 秒重放：
板块快照成功结果缓存 `board_cache_ttl=20s`（否则每次 WS 推送都为每个板块起一个子进程），
单板块失败冷却 `source_cooldown_seconds=300s`（实测名字写错时 3 分钟内重跑了 14 次 IndexError）。

### 4.11 自选池每分钟自动刷新（2026-09-16，用户报"自选股要手动刷新"）

**问题**：`watchlist()` 只在**前端挂载**和**增删自选**时被调用，没有任何定时器 ——
自选股的价格/总分/信号一直停在进页面那一刻，必须手动点才动。
上面 4.7 里"盘中不需要手动刷新"的说法对**当前标的**成立，对**自选池**当时不成立。

**修法（服务端循环 + 缓存 + WS 推送三层）**：

| 层 | 实现 | 说明 |
|----|------|------|
| 刷新 | `IntradayService._watchlist_refresh_loop()` | 盘中每分钟重算全部自选（每只票跑一次 `snapshot(light=True)`，把分钟数据取到最新） |
| 窗口 | `watchlist_refresh_window()` | 只在 **09:15~11:30 / 13:00~15:00**；周末直接排除；节假日用**市场自己的时钟**（`live_session_date()`）排除 |
| 缓存 | `watchlist(force=False)` | 概览结果进程内缓存 `watchlist_cache_ttl=60s`，非盘中放宽到 300s |
| 前端 | WS `{"type":"watchlist"}` + 60s 兜底轮询 | WS 只在**版号变化**时推新版（不重复推同一份），断线期间兜底轮询照常 |

**为什么放在服务端而不是前端定时器**：不依赖浏览器是否开着（无人看盘时信号照样推送）、
多标签页只算一次、且与 WS 快照共用同一套数据源缓存。

**窗口判定的两个坑**：

1. **不能用"今天是不是工作日"**：春节/国庆等工作日休市时刷新只是空转。改用市场时钟
   （上证 tick 的 `timetag`）——节假日它自动停在上一交易日。
2. **不能用市场时钟判断 09:15~09:30**：当天第一笔成交之前 tick 的 timetag 不会前进，
   若按时钟判会把用户要求的"09:15 起自动刷新"整段跳过。所以 09:30 之前只看日历。

**其它细节**：

- 刷新时刻**对齐整分钟 +2 秒**（`_seconds_until_next_tick`）：分钟bar在整分钟之后才生成，
  在 xx:59.8 取数拿到的是上一根bar；对齐刻度还避免了误差逐轮累积。
- 循环**不会因为单轮失败而死**：数据源抖动、某只票停牌、配置写坏都只影响这一轮。
- 增删自选/配置热重载会 `invalidate_watchlist_cache()`：否则刚加的票最长 60 秒不出现。
- 前端状态栏直接显示 `⟳ 报价 5s · 打分 60s · 11:52:03` 或 `⏸ 午间休市`（原因文案来自服务端），
  旁边保留「↻ 立即刷新」（`force=true` 绕过缓存）用于盘中临时催一次。
- `watchlist_refresh_seconds: 0` 可整体关掉自动刷新。

### 4.12 报价快车道：现价 5 秒 / 打分 60 秒（两条独立节奏）

**为什么拆开**：整表重算要为每只票各跑一次轻量快照（bars+trend+quote+日线+板块），
9 只实测 **0.95~1.22s/轮** —— 这是打分的成本，跟"价格要多快"无关。
而现价只要一次**批量**快照：

| 层 | 实测（2026-09-16 11:44，9 只自选） |
|----|-----------------------------------|
| QMT `get_full_tick([9只])` | 中位 **0.54ms**（一次调用取全部，本机终端内存读取） |
| 腾讯 qt 批量（一次请求 9 个代码） | 约 **54ms** |
| 稳态每轮耗时（服务层，含覆盖层写入） | **1~2ms** |

所以价格可以比打分快一个数量级，且几乎不花钱。数据层用 `fetch_quotes(codes)`：
**QMT 批量 → 腾讯批量补缺 → 逐只走完整容灾链**（三级都是"尽量一次取全部"，
逐只调用才是性能杀手 —— 会把 QMT 锁与公网 RTT 乘以 N）。

**解耦点**是服务层的 `_quote_overlay`：`watchlist()` 返回时只替换 `price`/`change_pct`
（并带上 `quote_ts`），总分/信号仍是最近一次重算的值。

**必须让用户看得出来两者新鲜度不同**：状态栏写「报价 5s · 打分 60s」，
每个列表项还带 `quote_ts`。否则用户会把 60 秒前的信号当成此刻的信号 —— 那比不做还危险。
快车道没覆盖到的标的**保留原价**而不是清空（清空会让列表闪成 "—"）。

**WS 推送节奏也跟着改了**：循环从"整体 sleep 15 秒"改成"每 1 秒醒一次"——
否则快车道做出 5 秒的数据也会被卡在 15 秒才到屏幕上。完整快照仍按 15 秒推
（它要 0.4s 一轮，不能更密），自选概览则在 `(打分版号, 报价版号)` 任一变化时推。
`quote_refresh_seconds: 0` 可关掉快车道；`watchlist_refresh_seconds: 0` 关掉打分循环。

### 4.13 「刷新异常慢」的两个真凶（2026-09-16 实测定位）

线上连续 20 次 `GET /intraday/snapshot` 的耗时分布是 **19 次 0.28~0.43s、1 次 7.42s**
——而那次 7.42s 的 `health.attempts` 里**所有行情源都只要 62~103ms**。
时间不在行情链上，在**没被计入 attempts 的板块路径**上：

1. **板块快照把 7~25 秒压在请求路径上**
   冷取实测 7.45s（PCB概念）+ 3.56s（PET铜箔）；失败后每 `source_cooldown_seconds`
   冷却到期会**再同步阻塞一次**（子进程超时上限 25s）。而行业汇总那条路更糟：
   **完全没有缓存**，每次快照都同步等。
   → 改法：`_cached_or_schedule()` 统一三种情况（TTL 内命中 / 过期回旧值+后台刷新 /
   **冷取也立刻返回"首次获取中"+后台拉取**），并给冷取失败加 `_cold_retry_after`
   窗口（否则每个请求都会再排一个注定失败的子进程）。
   实测冷启动 `watchlist(force)` 由 **10.55s → 3.55s**，且 12 秒后板块数据自动补上
   （PCB概念 +3.03%、PET铜箔 +2.0%）。

2. **自选概览过期时请求排队等整表重算**
   `watchlist()` 原本在缓存过期时会进 `_watch_lock` 等一次全表重算（~2.3s）。
   → 改为 **stale-while-revalidate**：有缓存就直接返回（价格由报价快车道单独贴），
   过期只是顺手起一个后台重算（去重 + 保留任务强引用）。`/watchlist` 现在恒为 **0.00s**。

3. **前端：每 5 秒的报价推送带着整张图重渲染**
   两个图表原先没有 `React.memo`，且传给它们的 `snapshot?.trend ?? []` 每次渲染都造
   **新数组**（即使 memo 也会被判为 props 变了）。→ 图表加 `memo`，面板里用
   `useMemo` 固定这些数组引用，5 秒一次的自选更新不再重渲染分时图/日K图。

4. **切换自选股卡 2~3 秒**（用户报"分时和日K切换都卡顿，即便数据刚刷新过"）
   三处叠加：`useEffect` 里先 `setSnapshot(null)` 把图清空 → 页面白一下；等 REST
   往返（0.3~1s）；期间 WS 还在重连、首帧又要等一次完整快照。
   → **前端按代码缓存快照**（`Map<code, snapshot>`，WS 推来的也写进去）：
   切到看过的票时**同一帧就把图铺出来**，随后静默刷新覆盖（stale-while-revalidate）；
   只有从未看过的票才清空显示 loading（避免把上一只票的图当成本票的）。
   日K面板用模块级 `Map` 缓存（切到"日内分时"再切回来也不会丢）。
   注意 `load` 的依赖必须是空数组 —— 一旦依赖 `snapshot`，那个依赖 `load` 的 effect
   会在每次 `setSnapshot` 后重跑，变成无限刷新。

## 五、无未来函数与回测

### 5.1 因果性保证

- 全部指标用滚动/指数/扩展窗口（rolling / ewm / expanding），第 i 根 bar 的取值只依赖 ≤ i 的数据；
- **VWAP 按交易日重置**（VWAP 的定义就是「当日」均价，跨日累计会得到没有交易含义的价格中枢），
  且当日 z-score 用当日的扩展窗口——实时打分时「当日至今全部偏离样本」正是同一口径；
- BOLL/MACD/KDJ/RSI 在**连续**分钟序列上计算（跨日累计、含隔夜跳空），这是盘中惯例：
  开盘即拥有完整窗口，不必等到当日第 20 根 bar 才有布林带；
- 30分钟分量按 **as-of 对齐**：只用「结束时刻 ≤ 当前5分钟bar」的已完成 30 分钟 bar；
- 单测 `test_features_are_causal` 用「截断未来数据后重算」对比验证前段数值不变。

### 5.2 分时图三角标记与回测共用同一批打分核

`features.replay_totals` 对历史每根 bar 复用 `factors.py` 的打分核逐元素求值
（单测 `test_replay_totals_uses_same_kernels_as_live` 断言逐位一致），
因此**图上画的点与面板里的分数同源同口径**，回测也在复现同一套逻辑。

一处必须披露的近似：日级因子（箱体/情绪/消息面，合计 45 权重）在当日逐 bar 重放时
按**最新值恒定**（它们本就无分钟级历史），该说明会出现在 `health.gaps` 与前端。

### 5.3 阈值回测（先做回测，再做T）

`src/intraday/backtest.py` 回答三个问题：

1. 总分突破 ±20 / ±30 之后，未来 N 根 bar 的方向性收益（命中率/平均前瞻收益）是多少？
2. 与「全样随机时点」基准相比是否有超额？
3. 按「低吸信号买入 → 高抛信号卖出 → 当日收盘强制平仓（不隔夜）」的机械规则跑一遍，
   累计收益/胜率/最大回撤如何（含双边佣金、卖出印花税、双边滑点）？

**权重口径**：情绪与消息面无历史序列，回测仅覆盖技术面 5 因子（85 权重），
按比例**归一至 100** 以保持 ±20/±30 阈值刻度可比 —— 该口径在 `gaps` 中显式披露。

**样本深度的诚实披露**：腾讯接口单次上限约 320 根5分钟bar（≈6-7 个交易日）；
QMT 在线时可用 `download_history_data` 回补更长历史。

#### 实测结果（2026-09-15，7 个交易日 / 320 根 bar / 前瞻 6 根 bar）

| 标的 | 阈值 | 信号数 | 命中率 | 平均前瞻收益 | 相对基准超额 |
|------|-----:|------:|------:|-----------:|-----------:|
| 中际旭创 300308 | ±30（动手线） | 85 | **48.2%** | **+0.20%** | **+0.21pp** |
| 中际旭创 300308 | ±20（提示线） | 164 | 48.2% | +0.14% | +0.15pp |
| 中际旭创 300308 | 全样基准 | 314 | 44.3% | -0.01% | — |
| 胜宏科技 300476 | ±30（动手线） | 101 | 39.6% | +0.06% | +0.10pp |
| 胜宏科技 300476 | ±20（提示线） | 153 | 43.1% | +0.05% | +0.09pp |
| 胜宏科技 300476 | 全样基准 | 314 | 43.0% | -0.04% | — |

机械做T（含成本、当日平仓不隔夜）：300308 累计 +0.41%（胜率 60%，最大回撤 0.55%）；
300476 累计 +4.21%（胜率 80%，最大回撤 0%）。

**读数（必须诚实）**：±30 档位在两个标的上都跑出**正的前瞻超额**（+0.21pp / +0.10pp），
方向性有效；但**样本只有 7 个交易日、80-100 次信号**，且 300476 的命中率略低于基准
（靠正偏度取胜）。因此结论是「阈值方向被验证」，**不是「阈值已被证明可稳定盈利」**。
要形成可信结论需要更长历史（QMT 在线回补 1-2 年 5 分钟数据）。
回测里可现场调阈值做敏感性扫描（10~50 网格），据此对**单只标的**调参。

### 8.1 前端操作自选（无需改配置文件）

「＋ 加自选 / − 移出自选」直接写回 `configs/intraday.yaml` 的受管段落：

```
# >>> intraday-watchlist:begin（本段由前端「加/删自选」自动维护）
watchlist:
  - code: "300308"
    ...
# <<< intraday-watchlist:end
```

- **两个标记之间的内容才会被重写**，文件其余部分（含每个参数的中文注释）原样保留 ——
  这也是没用 `yaml.safe_dump` 整文件重写的原因：那会把注释全抹掉；
- 写盘走「临时文件 → 校验候选内容（解析 + 权重合计=100）→ 原子替换」，
  校验失败即回滚，原配置纹丝不动；
- 重复添加同一代码按代码去重；移除不存在的代码幂等成功；
- 北交所（8/4/920 开头）在接口层直接 400 —— 数据源不覆盖，写进自选只会让每次快照都在取数层失败。

顶栏两个可选输入框都只在「加自选」时写盘，且**留空不写入**：

| 输入框 | 写入字段 | 留空时 |
|--------|----------|--------|
| `关联板块(可选) PCB概念,PET铜箔` | `boards` | 不写板块 → 该标的 `boards_bound=false`，板块情绪/板块排行两维度不计入总分（面板会提示绑定路径） |
| `海外映射(可选) usNVDA,kr000660` | `overseas` | 不写映射 → 回落到其**已绑定板块**的默认海外映射；板块也没绑定则记为缺口 |

接口 `POST /api/v1/intraday/watchlist` 回显 `boards` / `boards_bound` / `overseas`，
前端据此在提示条里写明「关联板块 X/Y（海外映射 A/B）」，绑定是否生效一眼可见。

### 8.2 性能：交互延迟的三处修复

实测「切换标的」曾一次要等 **54 秒**，前端按钮在此期间是 disabled 的，用户会以为坏了。
三处根因与修复：

| 根因 | 影响 | 修复 |
|------|------|------|
| 每次快照都重新试探已下线的源（QMT 未启动时每次白等 ~4.2s；东财被阻断时 akshare 走完整个分页重试 ~13s，含板块分钟接口的39页分页） | 冷启动 54s | 引入**失败冷却**（`data.source_cooldown_seconds=300`，与项目 ConnectorRouter 同口径），冷却期内直接跳过并在 health 中标注「冷却跳过」；板块分钟接口同样纳入冷却 |
| 消息面 LLM 每次重跑，`news_cache_ttl` 配置写了但没接线；且默认的推理模型单次 72~85s | 每次 5~85s | 按 TTL 做进程内缓存；**任务层级改为非推理模型 light**（详见 4.6） |
| 自选列表为每只标的跑**完整**快照（各含一次 LLM + 同业批量快照 + 板块分时） | 列表 16s，且互相抢数据源 | 新增 `light=True` 轻量快照：只算行情+档位+总分+信号，跳过估值/消息面/板块分时/大盘 |
| 同一标的被并发重复取数（WS推送 + 首屏 + 自选列表同时请求） | 退化到新浪逐笔时被放大 N 倍（39页下载≈20s × N） | `IntradayDataProvider` 加 **per-key 单飞锁**：同键并发只真正取数一次，其余等结果（与 ConnectorRouter 的 per-key Lock 防击穿同思路） |

**实测结果**（QMT 已启动）：

| 场景 | 修复前 | 修复后 |
|------|-------:|-------:|
| 切换标的（进程冷启动首个） | 54.5s | 21.7s（QMT 首次下载历史 + 首次 LLM） |
| 切换标的（其余标的） | 5.3~6.7s | **0.58~2.00s** |
| 切换标的（暖缓存再切） | — | **0.61~0.73s** |
| 自选列表（4只） | 16.1s | **2.06s** |
| 消息面 AI 打分成功率 | 2/5 | **5/5** |
| 6 路并发取同一标的 | 6 次重复下载 | 0.09s（只取一次） |

此外前端不再用 `loading` 禁用按钮：请求期间按钮始终可点，加载状态只做提示，
并用 `requestSeq` 守卫竞态（快速连点只接受最后一次请求的结果）。

### 11.1 三个诚实标注的局限

1. **触发判定用「硬性条件」而非得分**：早期实现用「得分≥0.75 即触发」，
   实测 B4 在核心条件「阴线跌破情绪释放点」为 ✗ 时仍被判触发 —— 已改为
   `SignalCondition.required` 语义：**全部硬性条件满足才触发**；
   位置、待确认项、依赖缺失数据的条件显式标 `required=False` 只参与打分展示。
   测试 `test_b4_not_triggered_when_core_condition_fails` 锁死该行为。
2. **依赖 Level-2 / 竞价数据的规则只做日线可复现的部分**，并在 `gaps` 写明：
   B3 竞价确认与分时三类买点、B15 竞价/封单量、S1 分时三类卖点、
   S2 竞价跳水、§6.5 盘口五单、§6.1/6.2 分时吸筹洗盘特征。
3. **筹码峰用成交量加权价格分布近似**（真实筹码分布需逐笔成交）：
   `chip_peak_valley` 按收盘价分箱、以成交量加权取峰，再取峰下方成交量最低的箱为峰谷。

### 11.2 保护线：止损必须在现价下方（实测踩坑）

需求 §S5 的「筹码峰峰谷」早期被我用「近60日成交量加权均价」代理，
在**高位回落**的票上会得到一个**高于现价**的"止损线"
（实测某票现价 880、算出 1002），于是永远显示「已破位」，毫无意义。

现行实现：
- 候选支撑 = {最近上涨阳线低点, 筹码峰谷, 近20日最低, MA20}，**先过滤到现价下方**；
- 取其中**最高**的那个（最近的支撑）作为止损线；
- 若最近的支撑仍低于「固定止损幅度」（默认5%），说明它没有风控意义 → 回退到固定幅度止损；
- 同时把全部候选支撑列在 `support_candidates` 里，前端可核对。

测试 `test_stop_line_always_below_price` / `test_stop_line_falls_back_to_fixed_pct_when_support_far`
分别锁死这两条。

### 11.3 日线新鲜度（2026-09-16：从"停在昨天"到"当天形成中bar"）

**用户报告**：日K做T界面自选股也是昨天的数据，没有盘中实时刷新。

实测根因**两层**，缺一层都修不好：

1. **QMT 本地库盘中不写当天日线**（与分钟线同一个坑）：

   ```
   600036.SH 1d 末根 = 2026-09-14（当天 09-16，缺两天）
   588170.SH 1d 末根 = 2026-09-15
   subscribe_quote(period='1d', count=-1) 1 秒后 → 末根 **20260916**
   （当天形成中的bar，close=40.71 与实时快照一致）
   ```

   最隐蔽的是"**本地库非空但停在过去**"：原有"空才补下载"的分支根本不会触发。
   修法是读之前先订阅 —— 下沉到中性层 `qmt_guard.subscribe_once()`，
   项目日线链（`xtquant_connector`）与做T链（`intraday/sources.py`）**共用同一份
   去重表**，避免对同一个终端重复订阅（这也是"两个模块都要用"的典型场景，
   与 `qmt_guard` 存在的理由一致）。

2. **采集链会把昨天的日线当成可用数据**：日线指标有 **4 小时 TTL**
   （`router._TTL_BY_PREFIX`），且 DB 里的昨日bar在 `DataFreshnessEvaluator` 里
   只是 lagging（conf≥0.4）→ `_is_db_fresh` 判为可用 → **直接返回，永不穿透网络**。
   所以日K链路改为**显式给日期区间**（`fetch(indicator, start_date, end_date)`）——
   路由在指定区间时跳过 TTL 与 DB。取 500 个自然日 ≈ 340 根交易日，
   覆盖 `lookback_days(250)` + 绘图120 + 缓冲。

**自动刷新**：日线bar在盘中由逐笔驱动、按分钟更新，故按「**数据源更新周期的 3 倍**」
= **3 分钟**（`data.daily_snapshot_ttl: 180`，服务端缓存与前端轮询同值，
由 `config_snapshot.refresh_seconds` 下发，避免两边各写一份）。非盘中降到 10 分钟兜一次
（收盘后日线源补齐当日收盘bar时能自动反映）。

### 11.3b 「不能等着 QMT 启动」—— 区间查询的新鲜度下限（2026-09-17 修复）

**用户报告**：日K面板显示 `日线最新为 2026-08-31（非当日）`，而当天是 09-17。

**根因有两层，缺一层都修不好**：

1. **带区间查询把本地库整段跳过了**。`router._cached_fetch` 里
   `skip_db = skip_db or bool(start_date or end_date)` —— §11.3 引入显式区间是为了
   绕开 TTL/DB 短路去拿"当天的形成中bar"，但副作用是**连"本地库里有更新数据"这件事
   都不知道**。实测：本地 SQL 库里躺着 2026-09-16 的完整数据，却被跳过。
2. **链上"第一个成功的源"就收工，不看它有多旧**。当时链上三源的真实状态是：

   ```
   迅投QMT          （未启动/本地库停在 8-31）
   本地行情CSV      DataFetchError: 本地CSV无行情数据: 300308   ← 该票根本没导出过
   AkShare          东财被阻断 + 新浪回退断连 → 返回空
   ```

   于是 325 根、停在 8-31 的结果被当成了"成功"，后面的源再没机会。

**修法（`router.py`）**：区间查询仍然**不走 DB 短路**，但**要查一次 DB 并把它的
最新日期当作「新鲜度下限」`min_expected_date`**：

| 情况 | 行为 |
|------|------|
| 某源返回的数据**早于**下限 | 视为该源不可用（**记日志、不记失败冷却**），继续试下一源 → AkShare/腾讯就有机会了 |
| 某源**返回空** | 同上，继续试下一源（空结果与"停牌"无法区分，不该挡住后面的源） |
| 所有源都比下限旧 | 采用其中最新的一份，上层再与 DB 比 |
| 网络链整体失败 | **回退本地 DB**，而不是把异常抛给面板 |
| 网络源比 DB 新（当天的形成中bar） | 用网络 —— 这是区间查询的初衷，必须保住 |

**为什么不把"过旧"记进失败冷却**：这个源本身是好的，只是这份数据旧了；
记冷却会让它连"最新可得的源"都当不成，也会污染非区间查询。

**日线链扩到五个源**（`stock_close`）：QMT → 本地CSV → AkShare → **腾讯财经日K** →
**Tushare Pro**。新增的两个都是为了"不等着 QMT 启动"：

| 新源 | 文件 | 口径 |
|------|------|------|
| 腾讯财经日K | `tencent_daily_connector.py` | `fqkline` 前复权；行序是**开、收、高、低**（读反会整体错位）；量单位手；**不返回成交额，置 None 不编造**；北交所不覆盖 |
| Tushare Pro | `tushare_connector.py` | `ts.pro_bar(adj='qfq')`，无 `adj_factor` 权限时降级不复权并在 `extra.adjust="none"` **如实标注**；`vol`(手)→volume、`amount`(千元)→元；原始**倒序** → 统一翻升序 |

两者都放在链尾：前面的源够新就不会打它们，**常态不增加延迟**。

**实测（2026-09-17）**：

```
修复前  带区间 325 根 / 最新 2026-08-31 / 13ms
修复后  带区间 337 根 / 最新 2026-09-16 / 2.12s（跳过了过旧的源）
        日K面板 scorecard.total 从 -1.27 → 25.5（数据口径错了，分数就是错的）
模拟「QMT掉线 + CSV无该票 + AkShare返回空」：
        337 根 / 最新 2026-09-16 / close=907.80 / adjust=qfq / source=Tushare Pro
腾讯日K直连实测：300308 12根/最新09-16/close=907.8、600036 close=40.92（均前复权）
```

> 注：Tushare 需要 token（环境变量 / `.env` / Windows 注册表三级兜底，
> 见 `src/quant/tushare_source.py`）。**没有 token 时连接器构造不失败**，
> 只在真正取数时报"该源不可用"——它只是兜底，不该拖垮采集链装配。
> 指数（`index_close`）与 ETF（`etf_close`）**没有**接这两个新源：
> 那两个接口的点数与复权口径需要单独验证，不做没验证过的扩展。

实测（2026-09-16 12:47，午休时段，用**本会话从未订阅过**的标的验证）：

```
service.daily(300308): trade_date=2026-09-16  bars=120  0.38s  gaps=[]
service.daily(002463): trade_date=2026-09-16  bars=120  0.35s  gaps=[]
二次取（缓存命中）: 0.000s
```

`gaps` 为空即证明"日线最新为 X（非当日）"那条缺口不再触发。面板上仍保留该提示，
并在日线不含当日时显示红色警示 —— 修好不等于以后不会坏，看得到才修得快。

### 11.4 性能

量柱标记是逐 bar 的 Python 循环，全历史（数千根）要跑数秒。
所有规则最多回看 `lookback_days`（默认250）根、绘图只要120根，
因此先切尾部再标记：日K分析从 **7.6~13.8s 降到 0.93~1.25s**。

### 11.5 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/intraday/daily?code=300308&refresh=false` | 日K做T快照（K线+量柱标记+**买卖标记**+锚点+形态+位置+成本线+B/S信号+保护线+纪律+**加权决策总分**）。默认走 180 秒缓存，`refresh=true` 立即重算 |

### 11.5b 日线做T的七因子加权决策总分（2026-09-16 新增）

需求原文：「当前的分时做T和日线做T的决策因子，打分因子…」。日K此前**只有规则布尔信号
（B1-B15 / S1-S6），没有加权总分**，本次补上第二路输出。

| 因子 | 权重 | 计算 | 出处 |
|------|-----:|------|------|
| `trend` 趋势结构 | 20 | price/MA5、MA5/MA10、MA10/MA60、price/MA120 四个分量等权 | `短线交易体系` |
| `chan_daily` 缠论买卖点 | 18 | 日线笔中枢位置 + 背驰（与分时同一支打分核） | `chanlun-trading` |
| `volume` 量价结构 | 16 | 活动量柱状态 + 量价形态方向 + 缩量/大阴扣分 | 量柱体系 |
| `position` 位置与身位 | 14 | 近120日分位 + **连板高度惩罚** + 贴近高点折价 | `打板技巧`/`连板股选龙头` |
| `signal_rule` 规则信号质量 | 12 | 已触发的 B/S 条数与满足度（只算 `triggered=True`，3 条满） | `daily_signals.py` |
| `cycle` 市场情绪周期 | 10 | 与分时同一个温度函数 | `市场情绪周期` |
| `character` 股性适配 | 10 | `clip((t_friendly−50)/50)`，趋势票再 −0.2 | 股性资料 |

三条刻意的设计约束：

1. **与规则信号并列，不替代**。规则信号回答「满不满足某套战法形态」（可解释到每条条件），
   加权总分回答「综合偏向低吸还是高抛」（能容纳"只满足一半"）。
2. **绝不把加权总分接回 `_finish` 的 `triggered` 判定** —— 那会让"三条里满足两条"
   也发正式信号，而 `test_no_signal_is_silently_triggered_without_required_flag`
   专门钉住了这条底线。
3. **阈值比分时更粗**：日线 ±15/±25（分时 ±20/±30）。一天只有一根bar，
   过度敏感会让用户天天改主意。

4. **股性因子必须用本面板的同一份日线**（`daily._daily_character`）：
   日K面板的日线带显式日期区间（绕开 TTL/DB 短路，见 §11.3），
   而服务层的轻量取数走短路口径 —— 两条路在数据源落后时拿到的**末日不同**
   （实测 QMT 未启动时分别是 2026-08-31 与 2026-09-16）。
   若各算各的，会出现"图上是 8/31 的K线、右侧股性却按 9/16 的数据算"的口径分裂。
   实测同一只票两种算法给出 0.08 与 0.34 的股性分（差 0.26 × 权重10 = 2.6 分）。

`protective.broken_stop=True` 时，无论总分多少，verdict 都先说风险
（「保护线已破 → 先处理风险，不做T」）—— 安全关键的优先级高于一切分数。

### 11.6 买卖标记：最近 30 个交易日的**因果回放**（2026-09-16 新增）

**问题**：图上没有任何买卖点标记。根因是 `analyse_daily` 只对**最后一根**bar 跑一遍
`run_daily_signals`，所以只能标出"此刻"，看不到"最近一个月什么时候给过买卖点"。

**做法**：`replay_daily_signals(enriched, params, bars=30)` 逐bar回放。

| 要点 | 说明 |
|------|------|
| 因果性 | 第 i 根bar只吃 `frame.iloc[: i + 1]`：高量柱锚点、位置分位、主力成本线**全部按当日及之前重算**。用未来数据解释过去的买点是"事后打点"最容易犯的错，也最会让用户对策略产生虚假信心 |
| 只记触发 | 未触发项是"差在哪"，属于当前bar明细（`buy_signals`/`sell_signals`），不上图 |
| 连续去重 | 同一信号**连续触发只记首次** —— 实测某票 S6「高量不破」在 30 根里触发 23 次，逐根打点会糊成一片 |
| 三类方向 | `buy`（K线下方红▲）/ `sell`（上方绿▼）/ `risk`（上方橙▼），与分时图的三角标记同一套视觉语言 |
| 开销 | 30 根 ≈ **0.45s**（每根重跑 22 个信号函数 + 锚点/成本线）；不跟绘图bar数（120 根 ≈ 1.8s）走。日K快照本身有 180 秒缓存 |
| 展示 | K线图上打点（带 tooltip：日期/方向/信号编号/建议买点/止损/当日收盘）+ 面板内一张**倒序**标记表 |

**图例与价位标注（2026-09-16 补充）**：用户反馈"图上黄红标注没有图例，也没有买卖价位标注"。
原因是图上只有贴在线上的一行小字（`高量安全线 949.73（08-11）`），没有颜色对应关系，
且标记只画了信号编号：

- 图表 readout 区补齐**颜色图例**：红虚线=高量安全线、黄虚线(`#e0b020`)=高量风险线、
  绿点线=止损保护、▲买点/▼卖点/▼风控，以及"标记旁数字=建议买价/止损位"；
- 每个标记直接标出**可操作价位**：买点给 `entry`（没有则给当日收盘），卖点/风控给 `stop_loss`，
  形如 `B8 1014.87`；文字加深色描边（`paintOrder="stroke"`）保证压在K线上也读得清；
- hover 时 readout 仍显示该bar的完整明细（开高低收/振幅/量/各种量柱标签）。

实测（2026-09-16 12:5x，真实采集链）：

```
600036: 标记=15 覆盖12个交易日 区间 2026-08-06 ~ 2026-09-15  快照 1.01s
   09-02 risk S3 出高量不破（次日不破位）收盘=40.87
   09-15 risk S6 高量不破               收盘=41.10
300308: 标记=21 覆盖15个交易日                              快照 0.82s
   09-10 buy  B8 缩量回调（放量突破） entry=1014.87 stop=864.37
   09-15 buy  B4 涨停回踩企稳         entry=864.01  stop=811.05
```

**局限（不隐瞒）**：回放用的是**当日收盘后**的数据判断，所以标记是"当天收盘时成立"
而非"盘中可执行"；要评估可执行性请看阈值回测（§5.3）与各信号的条件明细。

## 十三、权重自定义与档案库（2026-09-16 新增）

需求原文：「当前的分时做T和日线做T的决策因子，打分因子、低吸和高抛数值计算，
**根据个股股性**，前端要支持用户自定义设置权重的大小，**并保存到数据库，下次直接使用**」。

### 13.1 三层优先级：档案库 > YAML overrides > 全局配置

项目原本已有「个股微调」机制（`config.CodeOverride` + `configs/intraday.yaml` 的
`overrides:` 段），但它有两个硬伤：

1. **没法在前端编辑** —— `overrides` 段连写回函数都没有，只能手改 YAML；
2. **一处笔误全库失效** —— YAML 解析失败会让整个做T模块回退内置默认参数
   （`load_error` 机制），用户辛苦调的一套档案会"整体消失"。

所以档案改存数据库，YAML `overrides` 保留为兼容入口。**两条路径同时存在时，
面板的 `gaps` 里会明说是哪一份在生效**（例：
「已应用权重档案（manual，更新于 2026-09-16T21:03:11）：分时权重 box=20…」）——
同一只票两套参数下结论不同，用户必须知道看的是哪一套。

### 13.2 表结构：`dim_intraday_profile`

落在 `settings.sqlite_path`（默认 `data/moss_finagent.db`），与
`fact_data_points` / `fact_events` / `fact_alerts` 同库。建表方式是项目统一范式：
模块内联 `_SCHEMA` + `CREATE TABLE IF NOT EXISTS` + `PRAGMA table_info` 缺列自动 `ALTER`。

| 列 | 说明 |
|----|------|
| `code` TEXT PK | 6位证券代码（唯一键，天然 upsert 目标） |
| `name` | 证券简称 |
| `weights_json` | 分时14因子权重覆盖（**稀疏差分**，只写改过的键） |
| `daily_weights_json` | 日线7因子权重覆盖 |
| `thresholds_json` / `daily_thresholds_json` | 动手线/提示线覆盖 |
| `levels_json` | **低吸/高抛数值计算**的档位覆盖（`min_band_pct`/`stop_loss_pct`/…） |
| `character_profile_json` | 保存那一刻的股性快照（可复现推荐依据） |
| `template` / `source` / `note` | 用的模板 / `manual`\|`auto_character`\|`import` / 备注 |
| `created_at` / `updated_at` | upsert 时 `created_at` **刻意不更新** |

**为什么放数据库而不是 JSON 文件**：本项目的 `quant/warehouse.py` 已就"档案放哪"
给过结论 —— JSON 做不到跨记录查询（"我调过哪些票"、"哪类股性的票最容易做T"、
按时段筛），只能每次全量读进内存再排。而且 `data/quant/warehouse.db` 是 14 GiB
的行情仓库，"换个库=换数据源"，把用户偏好混进去会出现"我换了个数据库，做T参数全丢了"。

**为什么是稀疏差分**：前端滑杆只动了几项时，不该把另外几十项也固化到这只票上 ——
否则以后改全局默认值，这只票不会跟着变，而用户完全不知道。

### 13.3 权重合计必须=100（两处校验，一处都不能少）

- 全局 `configs/intraday.yaml` 的 `weights`：加载时硬校验（`Weights._sum_is_100`），
  合计≠100 直接 `ConfigError` 并在面板显示「当前使用内置默认参数」；
- 前端保存档案时提交**全量**权重：接口层 `_check_weight_sum` 二次校验，
  合计≠100 返回 400 并说明"只想覆盖某几项请只提交那几项"。

理由：总分区間 [-100,100] 与 ±20/±30 阈值**完全依赖权重合计**。
一旦存进一个合计=120 的档案，这只票的阈值就永久失效，而用户完全看不出来。

> 稀疏差分（例如只写 `{boll: 8}`）不触发合计校验，只做"未知因子名/负值"校验 ——
> 与 `CodeOverride` 的既有语义一致。实现上用 pydantic 的校验上下文
> `context={"allow_partial": True}` 区分这两条路径，而不是把校验整个去掉。

### 13.4 前端：`WeightProfileEditor`

一个 Modal（复用项目既有的 `.modal-backdrop > .help-modal` 范式），入口在两个面板的工具栏：
分时面板传 `mode="intraday"`，日K面板传 `mode="daily"`。

| 区域 | 能力 |
|------|------|
| 模式 tab | 分时做T / 日线做T（两套因子集合完全独立） |
| 因子表 | **按接口给的分组渲染**（前端不写死任何因子名与中文标签）、数字输入 + 滑杆、`from_skill` 打「技能」角标、`source` 作 title |
| 合计校验 | 实时显示 `Σ权重`，=100 绿 / ≠100 红并禁用保存；提供「一键归一化到 100」（最大余额法，精确 100） |
| 权重模板 | 下拉选 `balanced`/`swing`/`trend`/`dragon`/`low_vol`/`legacy`，选中即填入并显示说明 |
| **按股性推荐** | 调 `/intraday/character`，填入推荐权重与档位，并展示画像指标与中文 `notes` |
| 档位 | 分时模式可调 `min_band_pct`/`max_band_pct`/`stop_loss_pct`/`atr_stop_mult`/`touch_band_pct`/`dip_fallback_atr` |
| **预览** | 调 `POST /weight-profiles/preview`，展示新权重下的总分/分档/各因子贡献分（**不落库**） |
| 保存 / 删除 | `PUT` / `DELETE`，成功后父组件清 `snapshotCache` 并强刷（否则界面继续显示旧权重的缓存快照） |

**「保存后必须清三处缓存」**（少一处就是"改了没生效"）：
`service._profile_cache`（档案）、`_daily_cache`（日K快照）、`_watch_cache`（自选概览总分），
外加前端 `snapshotCache`。

### 13.5 预览为什么走完整链路（而不是前端算一遍）

`POST /weight-profiles/preview` 把这组权重作为 `config_patch` 传给服务器端**同一条**
`snapshot()` / `daily()` 链路，因此预览分数与保存后的真实分数**必然同源同口径**。
两个刻意的选择：

- **不用轻量快照**（`light=True`）：轻量模式跳过消息面/指数量能/板块排行/海外映射，
  预览出来的总分与面板上的分数不可比，反而误导；
- **以全局口径为基准**（不叠加该票已有档案）：否则用户看到的是"档案 + 我的改动"的叠加，
  看不出改动本身的效果。

代价是预览要 1~3 秒，前端必须给 loading 态。

### 13.5b 「改动后会变成多少」——解释层（`src/intraday/impact.py`，2026-09-17 新增）

用户拿到滑杆后的第一个问题是「**我把这个因子调到 8，低吸线会变成多少？**」，
而正确答案是「**不会变**」—— 档位线只由箱体/布林/VWAP/ATR 与档位参数决定，
权重只决定总分。这个"两条互不相干的链路"如果不摊开讲，用户会一直以为自己
在调价格线。于是把解释单独做成一层（**只读、无副作用、不参与任何判定**）：

| 产出 | 回答的问题 | 口径来源 |
|---|---|---|
| `level_rows` | 三条线现在是多少、离现价多远、**由谁定的**、触发价在哪 | `compute_levels` + `annotate_level_basis` |
| `level_deltas` | 「改动前 → 改动后」每条线的位移 | 基准档位（前端回传面板此刻值）vs 预览档位 |
| `gates` | 还差多少分、还差多少价、被谁拦住（覆盖度/情绪周期） | `decide_signal` 的判定条件逐个展开 |
| `factor_impact` | 每个因子对总分的影响度（`每+1分权重` = 得分；`权重置0` = −贡献分） | 打分卡逐行 |
| `examples` / `notes` | 「权重不移动价格线」这类必须讲清的前提，以及护栏/缺口说明 | 静态文案 + 配置 |

几条刻意的取舍：

1. **解释层绝不重算档位**。档位是 `compute_levels` 的产物，「同样行情 + 另一套参数
   → 另一条线」只能由 engine 算；在解释层里再实现一遍必然漂移成两套口径。
   `level_deltas` 因此只做**差值与格式化**，两份输入都由 engine 产出。
2. **「改动前」用前端回传的面板此刻档位**（`PreviewRequest.current_levels`）。
   预览本身要 1~3 秒，而档位是时刻量：服务端自己再取一次基准，前后两次 VWAP 会差
   0.1% 量级，于是"变动"列里凭空多出一行 `VWAP −0.10%` —— 用户会以为是自己改出来的。
   白名单只认 `low_buy/high_sell/stop_loss/vwap` 四个键（否则一个预览请求就能篡改基准）。
3. **档位来源标注要说得出出处**：`low_source` 按 engine 内部的 max/min 取候选顺序
   反推（布林下轨 / 箱体下沿 / ATR 兜底），并在档位差被护栏夹过时一并写出
   "护栏前的候选位置"。实测 300308 出现过「候选 902.35~908.52 恰好等于
   `min_band_pct=1.5%`」这种夹与不夹宽度相同、但**两条线都被移动过**的情况 ——
   只比宽度会漏判，所以判据改成「候选位置 vs 最终位置」。
4. **档位来源字段只补到当前档位对象上**（`service.snapshot` 里 annotate 一次），
   逐bar的 `levels_series`（240 个对象，每 15 秒随 WS 推一次）刻意不标。

前端在 `WeightProfileEditor` 的「实时价格线影响」面板消费这些字段：
改一个数字就自动重算（防抖 0.8 秒、`Σ权重≠100` 时不重算、首屏不自动跑），
并显式标注「表单已改动，待重算」这种过期态。

### 13.6 个股股性 → 推荐权重（"根据个股股性"的落点）

`GET /intraday/character?code=` 返回画像 + `weights`（推荐配方）+ `levels`（推荐档位）。
画像口径与阈值见 `docs/SKILL_TO_T_FACTORS.md` §二.4。要点：

- 全部来自日线历史（≥60 根，取样上限 250 根），不依赖任何付费数据；
- 任何一项算不出来都**记 `gap` 并置 `available=false`**，绝不填 0 冒充
  （0 会静默参与 `t_friendly` 加权，把一只活跃票算成钝化票）；
- 推荐权重是在模板基础上做**乘数微调**（如震荡票 `box×1.15`、趋势票 `chan×1.25`）
  再归一化到 100。用乘数而不是重新分配，是为了能对用户讲清
  "箱体权重 ×1.15"这种可追责的话。

## 十、已知局限（不隐瞒）

1. **5分钟历史深度受限**：非 QMT 环境下只有 6-7 个交易日，回测样本偏薄；
   QMT 极简模式启动后可回补更长历史（`download_history_data`）。
   当前模式是「机制验证」而非收益承诺。
2. **板块分时为自选同业等权合成**（官方板块分钟接口不可达），非官方板块指数；
   前端已显式标注口径。
3. **板块成分股清单不可得**：当前 akshare 版本无同花顺概念成分股函数、东财接口被阻断，
   故「板块内涨跌家数」走同花顺概念快照（该字段本身是官方口径，家数真实），
   但**无法按成分逐只核对**。
4. **日级因子在当日逐 bar 重放时按最新值恒定**（箱体/情绪/消息面/情绪周期合计 51 权重），
   图上的历史标记因此是「以当前日级因子近似重放」。缠论中枢上下沿、近5日均量、
   日ATR/趋势效率同属"半常量"：原料当日常量、价格相关的那一半逐bar重算
   （见 §2.4）。
5. **做T回测按日内回转口径**（当日收盘强制平仓、不隔夜）；A股个股实为 T+1，
   本模块假设有底仓，回测不额外计 T+1 约束。
6. **不含交易执行**：只出信号与推送，不接券商下单接口（QMT 实盘交易接口未接入）。
7. **缠论不做线段**：中枢由笔构造，无级别递归、九段升级、三类买卖点分类；
   平顶/平底不产生分型（严格包含的直接后果）。见 `chan.py` 的诚实标注。
8. **委比/内外盘/五档承接取不到**：`Quote` 模型没有档位字段，QMT 与腾讯两处解析
   都在解析层丢弃了五档（`fetch_quote` 的 detail 写着"五档盘口"但 `Quote` 里没有）。
   所以 `chip` 因子只用真能算出来的量价筹码，不用"看起来更专业"的编造字段。
9. **情绪周期依赖 akshare 的东财池接口**（实测单次 0.1~0.2 秒）。接口不可用时
   该维度按"不可用"扣除有效权重，**绝不返回上一次的旧值** ——
   周期阶段错一天会导致"退潮期被当成震荡期"，这是会造成实际亏损的那类错误。
10. **技能库有一批内容刻意没有量化**（心态/纪律、目视盘口、生态定位、龙头卡位、
    一字板形态…），只作为纪律清单展示，不进任何权重。完整清单见
    `docs/SKILL_TO_T_FACTORS.md` §四。
11. **单因子权重是按技能库的定性重要性 + 刻度配平定出来的，不是拟合出来的**。
    想自己调可以用前端的预览与 `POST /intraday/backtest`，
    但请记住项目里已记录过的教训：**单标的参数扫描出 543 个点的收益差异，基本都是过拟合**。
12. **股性画像依赖日线样本 ≥ 60 根**，次新股会直接记缺口、不给推荐权重。
13. **日线源之间可能存在复权口径差异**：链上 QMT/AkShare 东财/腾讯/Tushare 都是**前复权**，
    但「本地行情CSV」在 `configs/data_sources.yaml` 里明确标注为「复权口径未知」，
    Tushare 在无 `adj_factor` 权限时会降级不复权（已在 `extra.adjust` 标注）。
    §11.3b 的新鲜度下限顺带降低了这个风险（本地CSV一旦比 DB 旧就会被跳过），
    但**没有消除**：若某天 CSV 恰好比 DB 新，它仍会被采用。
    彻底解决需要按来源标注复权口径并在切换时做连续性校验，本期未做。
14. **腾讯/Tushare 只覆盖个股日线**：`index_close`/`etf_close` 未接入（口径需单独验证）。
