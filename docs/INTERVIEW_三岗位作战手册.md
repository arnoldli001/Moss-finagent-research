# 一、本会话做了什么（可直接讲的功能清单）

## 1.1 故障定位（工程方法论）

| 动作 | 细节 | 面试价值 |
|---|---|---|
| 接口探测排除业务问题 | 对运行中后端跑 16 种参数组合（type/level/status/limit） | 证明"先排除低级可能"的纪律 |
| 日志取证 | 从 `data/run/backend.log` 全文检索 ` 500 `，打印上下文 90 行 | 拿到精确 traceback，不靠猜 |
| 关联分析 | 统计出 **85 处** `database is locked`，多数来自做T采集的"路由回填" | 把"偶发"变成"系统性资源竞争" |
| 全仓范式比对 | 逐个核对 6 个 SQLite 仓储的 `connect` 参数 | 发现 2 个仓储游离在项目范式之外 |

## 1.2 根因（三因素叠加）

```
A 主库被多链并发写（做T采集/量化仓库/资金流 + 扫描批量写 64 条事件）
        ↓ 产生持锁窗口
B 读接口里藏了一次写：GET /alerts 先做懒过期 UPDATE fact_alerts
        ↓ 抢不到写锁 → 整个请求 500
C 事件/告警仓储用裸 sqlite3.connect()，默认只等 5s（项目规范是 WAL + 15~30s）
```

## 1.3 修复（三档超时分级设计）

| 场景 | 等待 | 重试 | 设计依据 |
|---|---|---|---|
| 关键写（事件/告警入库） | 20s | 3 次退避 | 丢一条告警 = 丢推送 + 丢邮件，值得排队 |
| 交互读（列表/详情/未读数） | 2s | — | WAL 下读几乎不阻塞，不该为写锁排 20s |
| 交互写（标记已读） | 2s | — | 宁可快速失败让前端重试 |
| 懒过期（读路径顺带写） | **0.4s** | **只试一次** | 必须 < 前端 1.5s 轮询间隔；失败无副作用 |
| 幂等 DDL（建表/迁移） | 2s | 3 次退避 | 不让首个读请求长时间排队 |

代码产出：`connect_sqlite()` / `is_locked_error()` / `retry_on_locked()` / `_expire_due()` 可降级 / `_connect_fast()`。

## 1.4 验证（四层证据链）

1. **新增回归测试**（`tests/unit/test_alert_sqlite_lock.py`，8 条）：用另一条连接 `BEGIN IMMEDIATE` 真正占住写锁；
2. **反向验证**：把 `_expire_due` 还原成旧实现 → 2 条用例立刻变红，报错与生产 traceback 一字不差；
3. **分层实测**：占锁时列表接口 500 → **200，仓储层单次耗时 0.52s**，SELECT 不受 WAL 写事务影响；
4. **端到端**：完整 ASGI 栈 + 独立 DB 副本复现验证；运行实例日志连续 200，无新 traceback。
   最终 **70 passed**，`ruff` 全绿。

# 二、踩了哪些坑（面试最值钱的部分）

## 坑 1（核心）：第一版修复把"报错"换成了"全站阻塞"

- **我的第一反应**：给读路径的连接统一加大超时到 20s，"等过去就好了"。
- **单发请求看起来完美**：不再 500。
- **压测把它否掉了**：占锁 12s 期间连续 4 次请求**全部超时**（客户端 30s 超时）。

```
[lock] 已占写锁 12s
[probe 1] HTTP 200  耗时 14.18s
[probe 2] ERROR TimeoutError
[probe 3] ERROR TimeoutError
[probe 4] ERROR TimeoutError
```

- **为什么更糟**：服务是 **单事件循环 + `asyncio.to_thread` 默认线程池**。一个请求阻塞在写锁上就占死一个线程；线程池被打满后，**连健康检查都超时** —— 局部错误升级为全局阻塞。
- **教训（可直接背诵）**：
  > 修并发问题时，第一反应不该是"把超时调大"，而要问三件事：
  > **这个等待值得吗？谁在为它付费（哪个线程/哪条链路）？失败能不能降级？**

## 坑 2：读接口里藏写操作，是设计层面的隐患

"懒过期"（读列表前把到期告警置 `expired`）本身是好设计（未读红点自动消退、无需定时任务），但它让**读路径的可用性绑定了写锁的可用性**。
→ 结论：懒迁移/懒清理必须设计成 **"可失败 + 幂等"**。

## 坑 3：新模块容易游离在既定范式之外

项目里 fund_flow / quant / auction_select / sector_crowding 都规范地用了 `WAL + busy_timeout + timeout`，唯独**事件/告警**和**宏观数据点**两个仓储用了裸连接。
→ 结论：并发范式要有**统一入口**（本次抽了 `connect_sqlite()`），否则后来者一定漏。

## 坑 4：日志里的"次要错误"被忽略了

`路由回填DB失败（不影响本次结果）: ... -> database is locked` 早就刷了 **85 次**，因为"不影响本次结果"一直没人管 —— 它其实是共享资源已长期紧张的先兆信号。
→ 结论：**降级日志要纳入观测指标**，不能因为"不影响结果"就静默。

## 坑 5：测试要能"抓住"原 bug，否则只是心理安慰

写完回归测试后必须做**反向验证**：把修复还原 → 测试必须变红，且报错与生产一致。
→ 结论：`红 → 绿` 才是证据；只有"绿"可能只是写了个必过的测试。

## 坑 6：并发环境的协作风险（本会话真实发生）

排查过程中，另一个进程在并发编辑同一仓库，`src/intraday/service.py` 出现重复函数定义导致 `SyntaxError`，直接打断了集成测试的导入链。
→ 讲这个可以体现：**多人/AI 并行开发时的文件级冲突检测**、以及"发现不是自己的改动先不动手"的克制。

# 三、三岗位追问清单（按岗位分）

## 3.1 量化开发岗

| 追问 | 回答要点 | 备注 |
|---|---|---|
| SQLite 为什么能"一写多读"？ | WAL 模式：读走 WAL 快照，写追加到 WAL，读写不互斥；但 **写-写互斥**，且 checkpoint/模式切换需要独占锁 | 能画 WAL 结构最好 |
| `busy_timeout` 和 `timeout` 区别？ | `timeout` 是 Python 连接参数（默认 5s），`busy_timeout` 是 SQLite PRAGMA，两者共同决定忙等；本次都显式设置 | 本会话实测数据 |
| WAL 下读为什么还会 `database is locked`？ | 读本身一般不受写事务阻塞，但**读路径里藏了写**（懒过期），且 checkpoint/模式切换等需要独占锁的场景会阻塞 | 这是本题的关键洞察 |
| 为什么不用 `BEGIN` 而用 `BEGIN IMMEDIATE` 复现？ | 立即取写锁，避免"读事务升级为写事务"时的锁升级失败（`SQLITE_BUSY_SNAPSHOT`） | |
| 为什么批量入库放一个事务？ | 减少提交次数 = 减少 fsync = 缩短持锁时间；本次扫描一次写 64 条事件 | 需自己量化对比 |
| 幂等怎么保证？ | `event_key/alert_key` UNIQUE + `INSERT OR IGNORE`，重复采集/重复扫描都不产生重复告警 | 项目设计 |
| 告警冷却/去重怎么做？ | 同源 `alert_key` 24h 冷却 + 跨源同文 `content_key` 抑制，双保险防刷屏 | 需自己补代码细节 |
| 多租户隔离？ | 所有查询带 `tenant_id`，参数化 SQL；Postgres 侧预留 RLS | 需自己确认 |
| 1.3 GB 库上的查询性能？ | `ORDER BY trigger_time DESC, alert_id DESC LIMIT ?` + `(tenant_id, status)` 索引；分页/限制条数 | 需自己补执行计划 |
| 量化面试必问（本会话未覆盖，必须补） | 因子构建、IC/IR、回测无未来函数、涨跌停/停牌处理、复权、滑点手续费、样本内外划分 | **见第四部分** |

# 五、三份"自我介绍"式项目陈述（按岗位定制，各 90 秒）

## 5.1 量化开发岗版本

> 我做的是一套本地优先的多 Agent 投研系统，存储用 SQLite（约 1.3 GB 主库 + 独立行情仓库），数据链路是多源降级：AkShare/腾讯/Tushare/baostock/本地 CSV，QMT 因权限问题排在最后并默认关闭。
> 我的主要工作之一是把"事件告警"这条链做稳。它有一次典型故障：扫描后告警列表必现 500。我从日志 traceback 定位到根因是**读接口里藏了一次写**（懒过期 UPDATE）撞上多链并发写主库，而告警仓储的 SQLite 连接参数还游离在项目规范之外。
> 修复我做了三档超时分级 + 清理动作可降级，并补了 8 条锁竞争回归测试（先红后绿）。过程中我第一版"把超时调大"的方案被自己的压测否掉了 —— 它把 500 换成了全站线程池阻塞，这件事让我后来形成了"先定义失败语义，再谈等待时长"的习惯。

## 5.2 AI 应用开发岗版本

> 我做的多 Agent 投研系统里，LLM 的定位是"结构化研判器"而不是"决定器"：事件采集去重后，**只对新事件**调 LLM 产出风险分/机会分/置信度/受益标的/影响路径，再由确定性阈值引擎决定是否生成告警，并做 24h 冷却与跨源同文抑制防刷屏。
> 成本上做了三层约束：已分析事件不重复分析、单轮候选中限 30 条、超限按时间排序下轮继续。可靠性上，LLM 整体失败时**不标记 analyzed**，下轮自然重试；输出用强类型模型约束。
> 可观测性上记录 prompt_hash 与 token 计量、P50/P95/P99 与缓存命中。我最近还处理了一次线上 500，用日志 traceback 10 分钟定位到 SQLite 锁竞争，顺手把降级语义和回归测试补齐了。

## 5.3 AI 应用架构师版本

> 这套系统的架构判断有两个：一是 **Demo 阶段单进程分层（src layout）+ 进程内 Agent 注册**，保留演进为独立 FastAPI 微服务的路径，避免过早分布式；二是**确定性逻辑与 LLM 推理分离**，阈值/冷却/去重这类必须可解释、可复现的部分不进 LLM。
> 我曾经处理过一次由共享资源竞争引发的 500：读路径里混入写操作 + 多写者共享 SQLite + 连接参数不统一。修复的关键决策是**超时按业务代价分级**：值得等待的关键写排队、无副作用的清理快速失败、交互路径宁可失败不可挂起。
> 我第一版是"统一加大超时"，被压测证明会把局部错误升级为全局阻塞（线程池被打满）—— 这个自我否定让我把"失败语义优先于等待时长"写进了团队习惯。
