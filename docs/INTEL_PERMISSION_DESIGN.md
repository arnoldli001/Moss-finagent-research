## 1. 先说结论：开关机制已经现成，只需注册 + 补动作码

我把链路从头到尾核对了一遍，**开通/关闭新功能的成本比预想低得多**：

```
src/domain/platform/config.py  FEATURES = {key: 中文名}      ← 唯一要新增的地方
        ↓
GET /api/v1/admin/platform/permissions-matrix                 ← 矩阵自动多出一行
        ↓
web/src/components/AdminPermissionPanel.tsx                   ← 自动渲染勾选开关，前端 0 改动
        ↓ 保存
PUT /api/v1/admin/platform/tiers/{tier}  {features:{...}}
        ↓ 落盘（临时文件 + 原子替换，整体校验后写入）
configs/platform_tiers.json                                   ← 可进 Git 评审与回滚
        ↓
GET /api/v1/me/features  →  VIEW_FEATURE 映射 → 可见页签清单
        ↓
web/src/hooks/useFeatures.ts → App.tsx 页签渲染
```

**证据**（`AdminPermissionPanel.tsx` 第 2–5 行与第 155–179 行）：矩阵行来自
`platformApi.matrix()` 返回的 `rows`，前端**不硬编码任何功能名**。
所以：**在 `FEATURES` 里加 key，矩阵里就自动多一个开关**。

**这意味着"给各类用户做开关管控"这件事，真正的开发量只有两处半：**

| # | 改哪 | 工作量 |
|---|---|---|
| 1 | `FEATURES` 加 3 个 key + `_default_config()` 给默认值 | 小 |
| 2 | `my_features.py` 的 `VIEW_FEATURE` 加一行（**关键，见 §2**） | 小 |
| 3 | `policy.py` 补 1 个写类动作码 + 1 个封存动作码（**不要 `intel.export`，见 §3.1**） | 中 |

## 2. ⚠️ 必须先处理的一个坑：`VIEW_FEATURE` 是显式白名单

`src/api/routes/my_features.py` 第 40–44 行有一段很关键的注释：

> 与 `platform/config.py` 的 `FEATURES` **刻意分开**：那边是"可售卖的项"，
> 这里是"前端有哪些页签"。两者目前一一对应，但将来可能一个页签对应多个售卖项。

**当前 `VIEW_FEATURE` 里没有 intel 项**。所以如果我只在 `FEATURES` 加 key，
会出现一个很难查的现象：

> **管理员打开"功能权限"矩阵，看到 4 个新开关、勾上、保存成功；
> 但用户那边页签一个都不出现。**

因为矩阵读 `FEATURES`，页签读 `VIEW_FEATURE`，**后者是显式白名单**。
注释里说的"将来可能"就是现在。**必须两处一起加**，否则就是"配了权限但页面还是进不去"
—— 而这句话正好写在同一份注释的上方，说明这个坑项目里已经预见过一次。

**建议**：顺手加一个单测断言 `set(VIEW_FEATURE.values()) ⊆ set(FEATURES)`，
把这个坑变成 CI 能拦住的东西（而不是靠人记得）。

**按你的决定：导入不做，导出也不做。**

## 5. ⚠️ 情报来源保密：这不是权限问题，是架构问题

> **你的原话**：不能暴露我自己的情报数据源来源，会被盗用，失去情报信息差壁垒。

这句话把这件事的性质说清楚了，而且**推翻了我原方案的定位**。我原方案把"看原文"
当成一个**角色权限**（给不给 PM 看），但你的真实意图是：

> **这不是"谁可以看"，而是"任何人都不能看到数据源长什么样"。**

原因很直接：**来源本身就是可复制的资产。**

| 泄漏了什么 | 对手能做什么 |
|---|---|
| 具体数据源（哪个星球 / 哪个号 / 哪个接口） | **自己去订阅**，成本可能只有几百块 |
| API 端点与参数 | 直接爬，**零成本复制**你的采集层 |
| Token 获取方式 | 复用你的账号体系 |
| 采集频率与调度 | 复刻你的时序优势 |
| 作者 / 群组 ID | 精准定位到人，**绕开平台直接联系** |

**结论：来源信息必须是「基础设施级机密」，不能靠开关或角色来管。**

### 5.1 三层防护（缺一不可）

```
第 1 层｜契约层（最关键）
    API 返回体中【根本不存在】以下字段：
      source_url / group_id / author / author_id / topic_id
      token 前缀 / 采集器名称 / 接口路径 / 原始 HTML
    存在哪里？—— 只在服务端内部存储，永不出 API。
    ★ 这一层的意义：前端的 XSS、抓包、爬接口，一律拿不到东西。

第 2 层｜展示层
    对外只暴露【来源大类】的枚举，不含任何可定位信息：
      OFFICIAL  = 交易所/监管/公司公告
      BROKER    = 持牌机构研报         ← 不写是哪家券商
      MEDIA     = 权威财经媒体         ← 不写是哪家媒体
      SELF_MEDIA= 财经自媒体           ← 不写是哪个号/哪个星球
      UNVERIFIED= 未证实内容
    以及「可信度构成」（来源分/内容分/佐证数）—— 这三个数字不泄漏来源。

第 3 层｜运维层
    · 日志与异常文案中的来源标识必须脱敏（复用 src/core/redaction.py）
    · 采集器异常不得把 URL/Token 带进 HTTP 响应
    · .env 中的凭证不进日志、不进审计链、不进错误上报
```

### 5.2 动作码：改名并收紧

原方案的 `READ_INTEL_SOURCE`（读原文）**语义就不对** —— 它暗示"有人可以读原文"。
按你的意图改成：

```python
#: 读原始情报正文（含来源标识）。
#: ⚠️ 默认【任何人】都不授予。仅用于：本地调试、合规取证（需 break-glass 审计）。
READ_INTEL_RAW: Final = "read:intel_raw"
```

| 角色 | 授权 | 说明 |
|---|:---:|---|
| ADMIN | ❌ **不给** | 管理员管套餐与用户，**不需要也不应该看情报原文** |
| RESEARCHER | ❌ 不给 | 研究员看的是**聚合与统计**，不是采集管道 |
| PM / TRADER | ❌ 不给 | 你明确要求 |
| RISK / COMPLIANCE / AUDITOR | ❌ 不给 | 有 `READ_AUDIT` 已足够做合规取证 |
| 本地调试 | ✅ 走 `break-glass` | 限时 + 留痕，不进常规授权矩阵 |

> **`READ_INTEL_RAW` 不进管理台开关矩阵。** 它是一个**调试/取证通道**，
> 不是产品功能。放进矩阵等于给管理员一个"一键暴露命根子"的按钮。

### 5.3 对界面的连带修改

| 位置 | 原设计 | 改后 |
|---|---|---|
| 情报流表格列 | 有 `source_url` 可点 | **无链接**，只有来源大类标签 |
| 弹窗按钮 | 「查看**来源**」 | 「查看**依据**」—— 列出证据类型 + 可信度构成，不含出处 |
| 来源分布图 | 可下钻到具体源 | 只到**大类**，不下钻 |
| 表格里的具体机构名 | 我原稿写"交易所公告/券商研报" | 保留（这是**类别**不是具体源），但**永不出现券商名、媒体名、星球名** |

> **一个必须守住的边界**：`content_hash` 可以留（用于去重与审计），
> 但**不能**和 `source_url` 一起给出去 —— 有了 hash 就能在公开渠道反查同一篇内容。

### 5.4 这一条带来的额外好处

来源保密同时解决了**两个**问题：

1. **盗用壁垒**：客户拿不到来源，就**离不开你**（他无法自己去订阅）
2. **合规减负**：原文不出平台，就不存在"二次分发第三方内容"的版权风险

> 这也解释了为什么 **§3.1 取消导出是对的** ——
> 导出只是把"来源可复制"从接口层挪到了截图层。**一起关掉才闭环。**

## 6. 动作码：写类闸门（`policy.py`）

功能开关解决"**能不能进这一页**"，动作码解决"**进去之后能不能做这件事**"。
两者缺一不可 —— 项目原则（`policy.py` 第 5 行）：

> **单一入口**：业务代码不得自己写 `if user.role == "admin"`。所有判断走 `authorize`。

### 新增动作（仅 2 个）

```python
#: 写类（新增）
WRITE_ALERT_STATE: Final = "write:alert_state"   # 确认 / 忽略 / 指派事件
#: 读类（新增）—— 默认谁都不给，见 §5.2
READ_INTEL_RAW: Final = "read:intel_raw"         # 原始正文与来源标识（调试/取证）
```

| 动作 | 允许角色 | 依据 |
|---|---|---|
| `WRITE_ALERT_STATE` | RESEARCHER / PM / RISK | 研究与投资可处置事件；合规/审计只读，保证可归因 |
| `READ_INTEL_RAW` | **无**（仅 break-glass） | 见 §5.2 |

### 数据分级（`_REQUIRED_DATA_CLASS`）

| 动作 | 最低等级 | 理由 |
|---|---|---|
| `READ_INTEL_RAW` | **RESTRICTED** | 含来源标识，泄漏即失去情报壁垒 —— 比策略源码更敏感 |

> **参照**：既有 `MANAGE_TENANT` 才用 `RESTRICTED`。
> 把 `READ_INTEL_RAW` 定在同一档是刻意的 —— 它就是新的最高敏感级资产。

## 7. 合规红线（任何套餐都不开放）

这三条**不是开关**，是硬编码在数据层与展示层的约束。管理员在界面上**看不到也不能开**：

| # | 红线 | 落地位置 |
|---|---|---|
| 1 | **未证实传闻不对试用开放**：来源为"未证实"的条目，trial 直接**不返回** | `intel` 路由层按 tier 过滤，**不是前端隐藏** |
| 2 | **风险声明强制**：所有情报输出附免责声明，任何套餐不可关闭 | 契约必填字段 + 前端固定渲染 |
| 3 | **不出现目标价/评级/买卖字段**：契约里**根本不存在**这些字段 | 数据结构层面堵死 |
| 4 | **来源标识永不出 API**：`source_url`/`group_id`/`author`/采集器名不在契约中 | 见 §5.1 第 1 层 |

> 第 1 条容易被当成"多此一举"。但**试用账号是最容易外流的账号**
> （临时开给客户、随手分享给同事），把最不可靠的内容放在最不可控的账号上，
> 是合规上的典型错误。宁可试用少看一类，也不给这条开口子。

| 4 | `tests/unit/test_platform_tiers.py`（或同级） | 断言 `VIEW_FEATURE.values() ⊆ FEATURES`；断言深合并补全缺失 feature | — |
| 5 | `web/src/components/AdminPermissionPanel.tsx` | **分组表头**（按你的决定做） | 低 |
| 6 | `src/api/routes/intel.py`（新增） | **契约层剔除来源字段**（§5.1 第 1 层）—— 这是最容易被漏、后果最重的一项 | **高** |
| 7 | `configs/platform_tiers.json` | **无需手改** —— 深合并自动补默认值（下文已实测） | 低 |

**注意第 6 项**：套餐配置是**运行时由管理台写盘**的。
我已实测确认 `configs/platform_tiers.json` **确实已存在**（只含原 9 项功能）。
起初担心"已存在旧配置 → 新功能读不到、默认全关"，但**实测排除了这个风险**：

`PlatformConfigStore.load()`（`config.py` 第 213–255 行）做的是**深合并**：

```
merged = _default_config()                    # ← 先铺出厂默认
for tier, incoming in 文件里的 plans:
    for field in (resources, features, pricing):
        base[field].update(incoming[field])   # ← 再用文件覆盖
```

文件里只写要改的字段，其余**保留出厂默认**（该函数 docstring 明确说明这是
为了修"浅合并导致其余字段全部消失"的缺口）。所以：

> **在 `FEATURES` 加 key 后，`_default_config()` 会带上它，
> 深合并后自动进入有效配置 → 管理台矩阵立刻出现该开关，
> 且默认值就是 §4 表里定的值。无需手改 JSON。**

**但仍有一个管理动作必须提醒**：默认值生效 ≠ 管理员已确认。
建议管理台对"文件中未显式配置的功能"加一个提示：

> 「检测到 3 项新功能沿用默认配置，请确认是否符合你的售卖方案」

理由：默认值是 fail-closed 的（`intel.alerts` 对 trial 默认关闭），
**安全但容易让管理员误以为"功能没做出来"**。

## 10. 验收标准

1. **开关生效**：管理员关掉 `intel.alerts` → 该等级用户的侧栏**立刻**不出现"事件告警中心"（且直达 URL 被服务端拒绝，不只是隐藏）
2. **服务端强制**：把 `intel.radar` 关掉后，直接请求 `/api/v1/intel/*` 返回 **403**（不是前端藏起来）
3. **来源零泄漏（最重要）**：抓包 `/api/v1/intel/*` 的**任何**响应，
   **不存在** `source_url` / `group_id` / `author` / `author_id` / `topic_id` / 采集器名 / Token 片段；
   响应里只有来源**大类**枚举与可信度构成
4. **无导出面**：服务端**不存在**任何情报批量导出接口；前端无导出入口
5. **红线不可开**：管理台**看不到**"来源开关"与"传闻开关"；trial 账号请求含未证实内容时**服务端不返回**该条
6. **不静默失效**：管理台对"沿用默认配置的新功能"有显式提示
7. **CI 拦住白名单漏改**：单测断言 `VIEW_FEATURE.values() ⊆ FEATURES`
8. **CI 拦住来源泄漏**：单测断言情报响应模型的字段白名单（**新增字段必须显式加白名单**，
   防止以后有人往响应里塞 `source_url` 而没人发现）
9. **深合并不回退**：单测断言"文件里缺失的 feature 等于出厂默认"（防 §8.1 第 2 条）

## 11. 你的决策已确认

| # | 事项 | 决定 |
|---|---|---|
| 1 | `intel.export` 定价 | **取消该功能**，导入与导出都不做（§3.1） |
| 2 | `READ_INTEL_SOURCE` | **改名 `READ_INTEL_RAW`，默认谁都不给** —— 真实理由是**保护情报来源不被盗用**，不是角色隔离（§5） |
| 3 | 导出入四眼原则 | **议题消失**（功能已取消） |

### 需要执行时注意的两个额外动作

- **`intel.export` 相关的一切都要清理干净**：`FEATURES` 条目、`pricing` 项、
  `EXPORT_INTEL` 动作码、前端按钮、以及**任何已写进文档的导出流程描述**。
  半留半去最危险 —— 留一个没人维护的导出路径，等于留一个没被测试覆盖的泄漏口。
- **§5.1 第 1 层（契约层剔除来源字段）优先级高于其他所有改动**。
  前 8 项都是"功能"，只有这一项是"资产保护"；
  而且它**必须在情报接口第一次上线前做完** —— 上线后再补，
  历史响应可能已被抓包留存。
