## 0. 结论先说

**放哪**：情报雷达加**第 3 个子页签「投资日历」** + 盘前简报加**「④ 今日日历」**模块。
（理由见 §5：日历的时间尺度与"情报流/热度"都不同，硬塞会让两边都变差）

**数据从哪来**：**不新接数据源**。你已装的 `akshare 1.18.94` 里就有一批可用接口，
本机实测确认了 **7 个能用**（§2）。其中 `stock_yysj_em` 是**最有价值的一个** ——
它给的是**未来的预约披露日期**，不是历史数据。

**"板块个股影响"怎么做**（§4，合规关键）：
不能做"影响判断"（那是投资建议）。改成 **「影响范围」的客观统计** ——
涉及多少家、分布在哪些行业、占比多少。**这比"利好/利空"更有用，而且合规。**

## 1. 先明确：日历 ≠ 情报

| | 情报流 / 舆情热度 | **投资日历** |
|---|---|---|
| 数据性质 | 第三方观点（**概率性**） | 已公布的日程（**确定性**） |
| 时间方向 | 已发生 | **未来** |
| 可信度模型 | 需要打分（来源差异大） | **不需要** —— 日程是事实 |
| 会不会错 | 会（传闻、误读） | 可能改期（公司变更披露日），但**有变更记录可查** |

**这个差异决定了设计**：日历**不需要可信度环**，需要的是**变更追踪**
（`stock_yysj_em` 一次变更/二次变更/三次变更日期三个字段就是干这个的）。

## 4. ⚠️ "板块个股影响"怎么做 —— 合规关键

你说的是"影响映射分析"。**"影响"这个词很危险** ——
一旦输出"某某事件利好半导体"，就是投资建议。

### 4.1 改成「影响范围」的客观统计

> **原则：描述「哪些公司被这个事件覆盖」，不描述「它们会涨还是跌」。**

| 三层映射 | 数据来源（全部客观） | 输出示例 |
|---|---|---|
| **① 事件 → 范围** | 受影响公司的**行业分布 + 家数 + 金额占比** | 「2026-09-28 解禁覆盖 40 家，半导体 6 家；该行业解禁市值占其流通市值 **3.2%**」 |
| **② 事件 → 个股** | 该公司**已披露公告**（确定参与） | 「中芯国际 · 预约披露日 2026-10-25（已变更 1 次）」 |
| **③ 事件 → 历史统计** | 同一类型事件的**历史样本统计**（只做板块/指数层面） | 「近 20 次该宏观数据发布日，板块指数当日涨跌：+8 / −12，样本 20」 |

### 4.2 两个必须守住的边界

**边界一：行业分类用申万，不用"概念板块"**

- 可用：「半导体设备（申万二级）6 家」
- **不可用**：「苹果概念 12 家」← 概念板块是**人为归类**，用它做映射等于替用户下判断，而且在合规上更接近"推荐"

**边界二：历史统计只做板块/指数，不做个股**

| ✅ 可做 | ❌ 不可做 |
|---|---|
| 「该板块指数在近 20 次同类事件当日涨跌分布」 | 「该股在同类事件后 5 日上涨概率 68%」 |
| 附**样本量 + 区间 + 方法** | 不附样本量 |

> 第二条是硬的：**给个股标注"上涨概率"就是变相的买卖建议**。
> 板块指数的统计是研究材料，个股的胜率是荐股。

### 4.3 用真实数据做的示例（实测数字，不是编的）

**示例 A · 限售解禁（2026-09-28）**

```
解禁家数     40 家
解禁市值     591.1 亿元
行业分布     半导体 6 家 · 医药生物 5 家 · 电力设备 4 家 …
行业占比     半导体解禁市值 / 半导体流通市值 = 3.2%
变更/提示    —（解禁日由交易所规则确定，不涉及改期）
```

**示例 B · 财报预约披露（2026 三季报）**

```
已预约       2320 家
最近一周     有研新材 10-13 · 川投能源 10-14 · 金盘科技 10-14
改期提示     首次预约 → 一次变更 → 二次变更（字段已有，直接可用）
行业密集度   电子 已预约 187 家 / 行业 421 家 = 44.4%
```

**示例 C · 海外财报传导（跨市场时间差）**

```
2026-09-30  美光科技(MU)  美东时间发布2026年四季报及年报
2026-09-30  捷普(JBL)     美东时间盘前发布
```

> **注意这张卡的信息价值**：9-30 是 A 股**国庆前最后一个交易日**，
> 而美光财报是**美东时间**（= 北京时间 10-01 凌晨）。
> **A 股在财报出来之前就休市了 —— 这意味着节后开盘才反映。**
> 这是纯粹的**时间事实**，不含任何判断，但对使用者极有价值。
> **这类"时间差事实"是日历模块最该做的事。**

## 5. 放哪：情报雷达加子页签 + 盘前简报加模块

### 5.1 为什么加子页签而不是塞进现有页

| 维度 | 情报流 | 舆情热度 | **投资日历** |
|---|---|---|---|
| 时间方向 | 过去 | 当下 | **未来** |
| 对象 | 单条信息 | 板块聚合 | **日程事件** |
| 核心操作 | 读 | 看趋势 | **提前准备** |

三者**心智模型完全不同**：前两个是"看发生了什么"，日历是"准备迎接什么"。
硬塞会把两边都做糊。

### 5.2 盘前简报加「今日日历」模块

盘前简报的定位是"今天要面对什么"，日历正好补上这个缺口：

```
④ 今日日历（新增模块）
 ├─ 今日事件      3 项（宏观 1 · 解禁 1 · 财报 1）
 ├─ 未来 7 天     折叠列表
 └─ 本周变更      财报改期 2 家 ← 这个比"有什么"更重要
```

> **"变更"比"有什么"更重要** —— 一家公司把披露日从 10-25 改到 10-28，
> 本身就是一条值得注意的信息（`stock_yysj_em` 的变更字段直接给了）。

## 6. 附带价值：顺手修掉一个真实缺陷

实测发现 `tool_trade_date_hist_sina` **已包含节假日**（9-30 → 10-08 跳过国庆）。

而你平台现有的 `src/core/trading_session.py` **只判周末**：

```python
if moment.weekday() >= 5:          # ← 只判周六周日
    return "closed", SESSION_LABELS["weekend"]
```

**后果**：国庆、春节这些交易日，所有定时任务会**照常执行** ——
采集照跑（浪费配额）、盘前任务照出（产出无意义内容）、告警照弹。

**修法**：把这张交易日历表落库（`dim_trade_calendar`），
`session_state()` 增加一个"是否交易日"判定。
这本来在 `MAINLINE_CALENDAR_REPAIR.md` 里已经出现过（说明你之前遇到过同类问题），
**这次正好一起收口**。

## 7. 定时任务（新增 2 个 JobSpec）

| 任务 | cron | 频率 | 说明 |
|---|---|---|---|
| `intel_calendar_sync` | `0 6 * * 1-5` | 每日 06:00 | 拉取全部日历源，落库 + 算行业分布 |
| `intel_calendar_weekly` | `30 6 * * 1` | 每周一 | 重算未来 30 天视图 + 历史统计缓存 |

**为什么放在 06:00**：早于所有盘前任务（08:05 起），
保证盘前简报生成时日历已经是热的，不会挤占 08:28 硬超时窗口。

**为什么不频繁拉**：日历是**低频变化**数据 ——
预约披露日一天可能只改几家，解禁日程提前数月就定了。
每天一次足够，**passive 拉取比实时轮询更合适**。

## 8. 契约设计

```json
{
  "event_id": "yysj_600206_20261013",
  "event_type": "earnings_schedule",
  "event_date": "2026-10-13",
  "confirmed": true,
  "title": "有研新材 · 三季报预约披露",
  "scope": {
    "kind": "company",
    "codes": ["600206"],
    "industries": ["有色金属"],
    "company_count": 1
  },
  "changes": [
    { "field": "首次预约时间", "value": "2026-10-13" }
  ],
  "metrics": {
    "release_value": null,
    "float_ratio": null
  },
  "evidence": {
    "provider": "东方财富",
    "reliability": "可靠",
    "fetched_at": "2026-09-25T06:00:12+08:00"
  }
}
```

### 三个设计要点

1. **`confirmed` 字段区分确定性**：
   "预约披露日"是**公司预约**（可能改期，`confirmed=false` + `changes` 记录）；
   "解禁日"是**交易所规则确定**（`confirmed=true`）。**两者可信度不同，必须分开表达。**
2. **`scope` 只有"范围"，没有"方向"** —— 契约层面就不存在 `impact` / `sentiment` / `direction` 字段。
3. **`evidence` 里只有来源大类**（"东方财富"这种**公开展示的第三方数据商**可以写；
   但你自有的私有情报源**一律不写** —— 与 `INTEL_PERMISSION_DESIGN.md` §5 同一口径）。

## 10. 验收标准

1. **前瞻**：未来 7/30 天视图非空，且**不含历史事件**
2. **确定性分级**：`confirmed` 正确区分（解禁=true / 预约披露=false）
3. **变更可见**：改期的公司在界面上有独立标记，不是静默覆盖
4. **无方向**：抓包任何日历接口响应，**不存在** `impact`/`sentiment`/`direction`/`target_price` 字段
5. **行业用申万**：映射结果只出现申万分类，不出现"概念板块"
6. **节假日正确**：国庆期间定时任务记 `skipped`（不是失败，也不执行）
7. **不新增数据源**：全部走 akshare 已有接口 + 静态 YAML，无新付费源

**「确定性」字段是日历独有的**，也是它和舆情最大的区别：

```

公司预约·可改期 → 财报披露日由公司预约，会改期
                  → 所以界面把「已改期 N 次」单独标出
                  → 改期本身就是一条提示，比"哪天披露"更值得注意
```

**自查结果**：双重扫描命中 0（词表已加强，新增 `利好/利空/上涨概率/胜率`）。
