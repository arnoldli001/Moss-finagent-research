3LangGraph 依赖图（真实边）

与 build_research_graph() 里 supervisor.py:4885-4916 的 33 条 add_edge 逐条对应（21 个节点）。三处形状值得注意：

  • 数据层之后是 3 路 fan-out：store 同时接出 verify_info(A05) / extract_events(A06) / liquidity_ctx(本地量化) —— A06 不等 A05， 本地量化也不等信息层（2026-09-28 第九轮并行化，见源码注释）。
  • 分析层是 10 条独立扇出边 + 10 条独立扇入边，不是循环也不是条件边 —— "跳不跳过"由节点内部 return {} 决定，图的拓扑始终固定。
  • 零 LLM 节点也在图里：liquidity_ctx 是纯本地计算， 但它与 sentiment 在同一个超步收尾， 于是最宽超步 = 10 个 analyze_* + sentiment = 11 路。
  • 路径长度只有两种数法，别混用：12 条 root→leaf 路径全部等长 —— 只数真实节点是 9 个节点 / 8 跳（PRD §43.2 用这个口径）； 把 START/END 两个哨兵也算进去则是 11 个节点 / 10 条边（本页与 atlas-facts 用这个口径）。 两个数都对，混着比才会得出"数量不一致"。

层 1 的旁路通道：为什么需要 live_state

LangGraph 的 state 在节点间是值传递 + reducer 聚合的，节点内对 state 的原地修改 不会被持久化。但前端要展示"正在追问 A10…"这种实时过程，等节点返回就太晚了。 解法是把 state 的引用挂在 CancellationToken.live_state 上， 节点内直接往里追加：

store.set_live_state(task_id, state)
cancel_token.live_state = state          # 节点内可通过 token 直接改 state

# src/core/cancel.py — 节点内的实时写入
def push_progress(self, msg):   self.live_state.setdefault("progress", []).append(msg)
def push_messages(self, msgs):  self.live_state.setdefault("agent_messages", []).extend(msgs)

# src/orchestration/supervisor.py — A17 追问后立刻可见
if token is not None:

这套设计的统一原则，可以一句话概括：
能用确定性代码做的，绝不交给 LLM；必须交给 LLM 的，必须给它硬上界和降级路径。
协作上 —— 图拓扑固定，Agent 用"是否在 plan 中"决定自己参不参与， 而不是让图去动态变形；
冲突上 —— 数值在本地算，LLM 只解读，从源头消除大部分冲突， 剩下的观点分歧由 A17 显式仲裁并留痕到 conflicts_resolved；
记忆上 —— 共享一份 ResearchState 黑板， 但每个 Agent 按自己的上下文预算取不同窗口，而不是全量广播；
熔断上 —— 每层循环都有硬上界，到界后不是抛错中断， 而是走一条已经准备好的体面退出路径，保证任务永远有产出。
