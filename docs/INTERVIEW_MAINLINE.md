## 0. 先讲哪一套

### 0.1 三十秒电梯陈述（主线挖掘版）

> 我做了一个**概念板块主线挖掘**系统：对 138 个概念板块每天算一个六维景气度分数，
> 分数进**横截面分位**，据此给出强/中/弱三级告警，目标是**在板块启动前 1~2 周发出信号**。
> 真正的难点不在打分，而在**两件事**：
> 一是**怎么证明它有效** —— 我用「20/35 日涨幅 >15% 的首日」当启动真值，
> 把每次告警归到 TP/FP 四象限，并且明确区分「误报」和「亏钱」；
> 二是**怎么保证它读的不是旧数据** —— 我做了「分区 / 仓库 / 应有日期」三层水位比对，
> 因为这个系统最贵的错误是**静默用旧数据**：分数、排名、告警全都正常，只有日期是旧的。

### 0.2 三分钟版（问题 → 判断 → 动作 → 结果 ×3）

| # | 问题 | 判断 | 动作 | 结果（实测） |
|---|---|---|---|---|
| 1 | 用户要删掉 184 个不再关注的概念 | 删除是**池级**语义，不是删成分股 | 9 批台账 + 脚本解析代码（**不手写代码**）+ 侧表备份 | 池 324 → 139 → 138；每批可复核、可回滚 |
| 2 | 误报太多，能不能抬门限？ | **误报 ≠ 亏钱**，先量化再决定 | 四象限 + 逐板块 FP×20日盈亏 | 实测「误报但赚」827 笔是最大格 → **否掉了抬门限** |
| 3 | 量化选股报「数据滞后」 | 数据早下好了，只差灌库 | 三层水位比对 + 启动自检 + 自动补 | 8 个数据集全部 0922；启动自检留痕 |

## 1. 本会话做了什么（按「能讲什么」组织）

### 1.1 主线挖掘打分链路

| 组件 | 设计 | 面试可讲点 |
|---|---|---|
| 六维打分 | 各维 `score × w` 加权平均，**只对可用维归一**；反向维取 `100 − score` | 「缺数据不是当 0，而是从分母里去掉」——降级而不是惩罚 |
| 候选集 | 按六维分数取池内 **前 20%**（下限 8、上限 80） | 横截面分位 ⇒ **池子一变，全部历史分数都变**（本会话最重要的认知） |
| 总分 | 候选 `[六维×80 + 蓄势×20]/100`，非候选直接 `=六维`；再加 ETF/门限加分后 clamp | 分层加权 + 加分的可解释性 |
| 告警分级 | 🔴强 / 🟡中 / 🟢弱（弱仅观察）；冷却键 `(板块, 级别)` 5 天；确认期 2 期 | 「冷却按级别而不是按板块」避免强势板块被自己压住 |
| 告警范围 | 四种模式：`excluded` / `seasonal` / `strong_only` / `medium_up`，另有按板块的 `min_score` / `max_score` | **单一决策点 `permits()`**；未知级别、缺分数一律 **fail-closed** |

### 1.2 板块池治理（本会话最大的一块）

- **9 批共 184 个概念**从池中删除，交付为 `configs/concept_removal_batches.yaml` 台账（每批带 `label`/`note`/`raw`）。
- 关键语义辨析（面试常被追问）：用户说「删除概念」**不是**删除其成分股 ——
  一个成分股可能被别的概念复用，所以只从池里摘掉板块，不动成员表。
- 删除动作三件套：追加黑名单 + `visible=0` + 侧表备份 `ml_board_bak_pre{N}`。
- **拥挤度是另一套独立名单**（58 个概念 → 82 个代码），与主线池删除**合并但不混用**。
- 一个真实的判断错误：拥挤度过滤最初用了**整份 604 条黑名单**，
  会把 337 个板块（含 192 个 GICS/行业板块）一起隐藏 —— 收敛到 `load_removed_concepts()` 的 184 条。

### 1.3 成分股提纯（Task 1）

三路规则（**这是设计里最值得讲的一处**）：

| 情况 | 处理 | 为什么 |
|---|---|---|
| LLM 主营分 `≥70` | 放行 | 有业务依据 |
| LLM 主营分 `<70` | **否决**（即使股价相关性很高） | 业务判定优先于统计相关 |
| **没有判定结果** | **不惩罚**（fail-open） | 没有证据就不动，避免误杀未判定的票 |

实测效果：`corr` 且主营分 <70 的 **2879 行 → 0**；池内真正纳入的 `relevant=1` **12223 → 9358（−2865，23.4%）**。

> ⚠️ 这里有个**我差点误读的坑**，很适合当面试故事：
> 表总行数从 **42504 → 22551**，看着像「删多了」；拆开才发现旧表里有
> **185 个池外板块的 20198 行**（之前几批删掉的板块，旧表还留着它们的成分股）。
> **看错了量纲，结论就会反过来。**

### 1.4 业务相关性（资金龙头 ≠ 业务龙头）

`identify_leaders()` 原本只做**三维交集**（5 日净流入 / 10 日涨幅 / 5 日成交额，各取前 3，命中 ≥2）——
这选出的是**资金龙头**，与「这家公司真的做这个业务」无关。
新增 `business_score` 展示列，并把 LLM 主营分接进 `LeaderInfo`。
另一个隐蔽缺陷：`ml_member_pure.business_score` 对 `source='corr'` **恒为 NULL**，
不回头查 `ml_stock_theme` 就会把「业务相关 95 分」的票标成「仅股价相关」。

### 1.5 拥挤度水位（一个被问倒过的问题）

用户问：「为什么商业航天、人形机器人的水位是空的？」

答案在算法里：`water_level = 该板块自己的 ma5_crowding ÷ 它自己回看窗口内的最大值`，
门槛是**该板块自身 ≥750 根有效数据**。所以：

- 它是**板块自参照分位，不是横截面分位** —— 别的板块删不删都和它无关；
- 年轻板块（商业航天 563 根、人形机器人 624 根）**必然为空**，不是 bug。

实测复核：水位为空的 **801 条全部 `bars<750`**，`bars≥750` 却为空的 **0 条**；
接口返回值与库值**逐条一致（0 处不同）**。决定**不降低门槛**，改为前端显示「数据不足 N/750」。

### 1.6 评估体系（最能体现「量化」素养的一块）

| 工具 | 做法 | 关键设计 |
|---|---|---|
| 启动真值 | 滚动 20/35 日涨幅 >15% 的首日 = 启动日；命中后 `t += 4` 跳过 | 避免同一波行情被重复计数 |
| 命中判定 | 告警落在启动日 **±[−10, +5]** 个交易日内算命中 | 允许「提前 1~2 周」，与用户口径一致 |
| 四象限 | 命中×赚 / 命中×亏 / 误报×赚 / 误报×亏 | **误报 ≠ 亏钱**：实测「误报但赚」827 笔是最大格 |
| 逐板块 FP | 每板块 FP 率 + 20 日盈亏 | 找出「稳定误报」的板块，而不是只看全池均值 |
| 阶梯回测 | −7% 止损；+10% 起每 +10% 减 30%，缺口用 `min(open, stop)` / `max(open, target)` | 1963 笔：均值 +2.91%、**中位 −7.00%**、胜率 38.0% |
| 留出窗口 | 训练 / 留出分开看 | 防止只在样本内好看 |

### 1.7 数据链路治理（AI 应用架构师最该讲的部分）

**两阶段流水线**：`download`（落 CSV 分区）→ `ingest`（灌 SQLite 仓库）。
幂等 upsert，可反复跑。

**三层水位**（本会话新增）：

| 层 | 含义 |
|---|---|
| 分区（CSV） | 数据**下没下来** |
| 仓库（SQLite） | 数据**进没进库** |
| 应有日期 `latest_complete_trade_date()` | 按交易日历 + 发布线（16:30）算**应该是哪天** |

四态判定：`已同步` / **`已下载未灌库`** / `两者都落后` / `判定不了`（不猜）。
`synced` 的语义是「**已确认**全部同步」，不是「没发现落后」——
缺统计时报「未确认」，否则启动自检会以为一切正常、连补偿都不做。

**启动自检 + 自动补偿**：服务启动 30 秒后（延迟 + 后台线程）比对三层水位，
缺了就自动触发一次同步作业，并落盘 `data/quant/sync_check.json` 留痕。

**同步节奏**：从「工作日 16:40 一天一次」改成「**16:00~23:30 每 30 分钟**」——
因为一天一次若撞上 Tushare 还没发布（`moneyflow` 实测晚约 2 个交易日），
就只能等下一个工作日，中间页面一直显示「数据滞后」而不自愈。

### 1.8 工程方法论（我认为面试里最加分的部分）

| 做法 | 为什么 |
|---|---|
| **重型离线任务跑副本**（`MOSS_SQLITE_PATH`） | 全量重打分 90 分钟；压生产库会占写锁把用户的手动刷新挤掉（**实际发生过两次**），且 `--force` 先清空再重算，期间界面是空的 |
| **备份 / 还原 / 换入**（`--tag` / `--restore` / `--promote`） | 用户明确要求「不要影响我原有的效果」——**只有能一键还原，这句话才有意义** |
| **先定判据，再看结果** | 工具里预写「留出 FP/TP 变差就回退」；实测提纯让 3 个聚合指标变好、却让留出精确性变差 → **按预设判据回退**。只看好看的那三项，结论会正好相反 |
| **跨池变更的副本不能换入** | 副本基于 139 池算的，而运行期间用户应用了第十批删除（池→138）；换入会把删掉的板块**加回来** |
| 回归测试 + 断言清单同源 | `JOB_REGISTRY` 的数据集清单与 `DAILY_DATASETS` 同源，测试断言两者相等 —— 防止「面板要读的」与「作业会同步的」慢慢漂开 |

## 2. 踩坑集（每条都是一个独立故事）

> 用法：面试时挑 2~3 条讲。每条按 **现象 → 根因 → 修法 → 可迁移教训** 组织。
> 带 ⭐ 的是最能体现深度的。

### 2.1 ⭐ 静默用旧数据（整个会话最贵的一类错误）

**现象**：界面报「本次用的是 20260917 的行情，最近一个已收盘交易日是 20260922」，
但分数、排名、告警**全都正常**，没有任何报错。

**根因**：`stk_limit` 的**分区已经到 20260922，仓库却停在 20260917** ——
数据早就下载好了，只是没灌进库。选股的涨停/情绪特征要读它，整条链被它一个卡住。
而作业每天如实记「已是最新」：它的补灌逻辑用 `daily` 的水位算出待灌清单，
再把这个清单**喂给每一个数据集**，默认了「所有数据集水位一致」。
`daily` 已最新 ⇒ 清单为空 ⇒ `stk_limit` 自己的那几天**永远补不上**。

**修法**：补灌改成**每档用自己的水位去截自己的分区**（`_ingest_gaps`），
加上「分区 / 仓库 / 应有」三层显式比对与启动自检。

**可迁移教训**：
> 分布式/流水线系统里最贵的错误不是「报错」，而是**每一层各自看都正常、缺口只在层与层之间**。
> 所以水位这种东西**必须跨层比对**，而不是各报各的一列数字。
> 我做这个判定时特意选了「纯函数、零 I/O」的实现 —— 输入就是两份已有的落盘统计，
> 所以放进请求路径不新增任何开销。

### 2.2 ⭐ `NameError` 遮蔽真实异常

**现象**：选股报 `NameError: name 'brief' is not defined`，看不出真正的原因。

**根因**：11 个文件（`moss_selector/` 6 个模块 + 5 个脚本）都是
`from src.core.errors import BRIEF_DEFAULT` —— **只导入了常量，没导入函数**，
而正文里到处在 `except` 分支里调 `brief(exc, ...)`。
于是**任何真实异常都会在格式化异常消息时再抛一个 NameError**，把原始错误彻底盖掉。

**修法**：补上导入；用 AST 静态扫描（收集本文件的绑定名，找「用了 `brief(` 但没绑定 `brief`」的文件）一次找全。

**可迁移教训**：
> **异常处理路径本身就是代码，也需要被测。** 一个只在出错时执行的辅助函数，
> 出错的代价是「你永远看不到真正的错误」。
> 这也是我为什么先修数据、让链路真的跑一次 —— 否则这个 bug 会继续表现为「某个说不清的 NameError」。

### 2.3 ⭐ 跑测试写坏了正在运行的服务

**现象**：新功能上线自测时，8 个数据集**全部变成 `unknown`**，而仓库明明是好的。

**根因**：顺着缓存文件摸到内容是一段**测试夹具的假地址**
（`mysql+pymysql://nobody:***@127.0.0.1:1/none`），写入时间与那次 `pytest` 结束时间完全吻合。
某个测试会 ① 把 `MOSS_DB_URL` 设成假 MySQL ② `invalidate_cache(include_disk=True)` **删掉生产缓存**
③ `build_data_health(force=True)` **把「仓库不可用」写进同一个生产路径**。
后果：跑一次测试，运行中的服务在接下来 10 分钟里把本地 14GB 的 SQLite 仓库报成「MySQL 不可用」。

**修法**：缓存路径改为**可重定向**（`MOSS_HEALTH_CACHE_DIR`）+ `conftest.py` 一条
**autouse** fixture 指向临时目录。验证：跑完 32 个用例后生产缓存**哈希逐字节未变**。

**可迁移教训**：
> 测试隔离不是「测试之间的事」——**它会打到生产进程上**。
> 而且要 autouse：将来任何新增测试只要碰同一个入口就会再犯，「记得自己清理」是防不住的。
> 落盘缓存、全局单例、共享临时文件，这三类是同一个坑。

### 2.4 ⭐ 空集也能「通过」（我自己的审计脚本骗了我）

**现象**：换源一致性审计报告印着「✅ 全部逐位一致（可直接换源）」。

**根因**：两个叠加错误 ——
① 腾讯接口只认 `2026-01-01` 这种带短横的日期，我写成了 `20260101`，
接口返回 `msg: param error` + `data: []`（**HTTP 仍是 200**）；
② 脚本照直读 `data[code]` → `TypeError` → **整个日线章节被跳过**，
而小结那行代码在空集上照样输出「✅ 全部一致」。

**修法**：按**字段类**分开判定（价格四字段要求逐位一致；成交量单列，因为 Tushare 带两位小数、
腾讯取整，天然差 <1 手 —— **把取整差和口径差算成同一件事，就会得出错误的换源结论**）；
并且返回体的 `msg`/`data` 形状异常一律报错，不再当成「没有重叠日」。

**可迁移教训**：
> **「全部通过」和「一条都没比」必须能区分。** 任何 `all(...)` / `every()` 形式的校验，
> 都要先断言样本数 > 0；否则你的校验在空集上永远绿。
> 我后来给这个脚本加了这条自检，才发现真实结论是：腾讯**价格可换**、成交量有取整差、
> 而它**根本不提供成交额** —— 与原结论完全不同。

### 2.5 横截面分位 ⇒ 池一变，全部历史都变

删掉 184 个板块之后，**所有历史分数都变了**，因为分数是**当日池内的横截面分位**。
所以「改池子」必然触发一次 90 分钟的全量重打分（903 个交易日 / 89.2 分钟）。

**可迁移教训**：任何用**横截面统计量**（分位、排名、z-score）做的特征，
都要在设计时就想清楚「成分变化时怎么重算」，否则会出现新旧分数不可比、
回测报告里出现一个看不见的台阶。

### 2.6 全量重打分压生产库（我造成的，两次）

90 分钟的重打分占着写锁，把用户的一次手动刷新挤掉了（同步成功但打分没产出）。
`--force` 还会**先清空区间再重算**，中断就丢数据。

**修法**：新增 `MOSS_SQLITE_PATH` 让重打分跑在**副本库**上，验证通过才换入生产库。
隔离实测（重打分进行中同时查两个库）：生产库 94940 行**全程未动**、副本库在逐日写入。

### 2.7 跨池变更的副本不能换入（运行期撞车）

89 分钟的重打分跑到一半时，用户应用了**第十批删除**（参股银行 885835，池 139 → 138）。
副本是基于 139 池算的 —— **换入会把用户刚删掉的板块加回来**。
这条与指标好坏无关，是纯粹的时序一致性。

**修法**：删除失效副本，并在文档里写死「换入前必须确认副本建立之后池子没动过」。
另外 `ml_member_pure` 在 `mainline_cache.db` 里是**生产与副本共用**的，
所以「不换入」时必须同时还原它，否则会停在「新输入 + 旧分数」的混合态。

### 2.8 先定判据，再看结果

提纯这件事：`P(>+10%)` 18.5%→19.0%、`P(<−10%)` 7.4%→6.9%、20 日均值 +2.56%→+2.72%
—— 三项全变好；但**你（用户）最在意的精确性代理指标**（启动集留出 FP/TP）**1.27 → 1.38 变差**。

工具里早有预设判据：「留出 FP/TP 变差就该回退」。所以我**回退**了。

**可迁移教训**：
> 如果先看结果再选指标，这次会得出**完全相反**的结论。
> 「预注册判据」在量化里叫 anti-p-hacking，在工程上就是「先写验收标准再动手」。

### 2.9 看错量纲，结论会反过来

提纯后表总行数 42504 → 22551，像删过头；实际池内 `relevant=1` 只从 12223 → 9358（−2865，正是预期值），
差额 20198 行是**已删板块的池外残留**。**报告要报「纳入数」，不是「表行数」。**

### 2.10 误报 ≠ 亏钱（否掉了一个看似合理的优化）

用户的直觉是「误报影响大，抬门限」。四象限实测：

| | 赚钱 | 亏钱 |
|---|---:|---:|
| **命中启动** | 785 | 464 |
| **误报** | **827** | 730 |

「**误报但赚**」是最大的一格。所以抬高门限会**同时砍掉有效信号** —— 这个优化被数据否掉了。

### 2.11 换源的真正门槛是**口径**，不是可达性

| 候选源 | 实测 | 结论 |
|---|---|---|
| 腾讯日线（价格四字段） | 6 只票 × 1021 个交易日 × 4 字段 = **4084 个值逐位一致** | 价格可换 |
| 腾讯成交量 | 每日差 <1 手（取整） | 分位/阈值场景可忽略 |
| 腾讯成交额 | **不提供** | 补不全 |
| 新浪个股资金流 | 符号一致率 **88.2%**、中位相对偏差 **37.5%** | ❌ 不可换 |
| 东财「主力」定义 | 与 Tushare `net_mf_amount` 不同 | ❌ 会把序列切出台阶 |

`board_flow` 进的是**截面分位** ⇒ 口径一变排序就变、告警就变，**而界面上看不出来**。

⚠️ 我在这里说过一句过头话（「东财全部不可用」），后来修正：
项目本就有 SNI 阻断规避（`MOSS_EM_DIRECT`），实测**同一进程内**
一个接口成功（120 行）另一个失败（`RemoteDisconnected`）—— 项目自己的结论是
「阻断会漂移、不存在稳定绕过」，所以东财只能排链尾。

### 2.12 字段序陷阱（数值全都合理、不会报错的错）

腾讯日线返回顺序是 `[日期, 开, **收**, 高, 低, 量]` —— **收在高之前**。
按 OHLC 的直觉解会把最高价写成收盘价，而且**数值都合理、不会报错**。

### 2.13 差点相信的假验证

我用 `git show HEAD:<file> | ruff --stdin` 判断「这些 lint 错误是不是我引入的」，
得到「HEAD 版本全部通过」。**这是假阴性**：文件在 HEAD 里不存在时 `git show` 报错，
而我把 stderr 丢进了 `2>$null`，ruff 于是检查了**空输入** → 报「All checks passed」。
正确做法是「把我的改动反向还原，再跑一遍」——那才证明 `I001`/`E402` 是既有的、
而 `F821 Undefined name brief` 是原先就有的真 bug。

**可迁移教训**：**验证手段本身也要被验证**；一个「通过」如果可能来自空输入，它就不算证据。

### 2.14 小工具类坑（可当「你踩过什么工程细节」的补充）

- PowerShell `Select-Object -First N` **会提前终止管道并杀掉** python 进程 →
  报告文件根本没写成，而我当时以为跑完了。
- 中文字符串里用了 ASCII 双引号 → Python 语法错误；统一改「」。
- 手工敲 6 个板块代码，**错了 4 个**（会误删三胎概念/食品安全/元宇宙）→

- 黑名单范围搞错：拥挤度过滤最初用整份 604 条，会隐藏 337 个板块。

**必答的两道硬题**：
1. 「你的回测怎么保证没有前视偏差？」→ 讲 PIT 成分、上市日期闸门、**发布线 16:30**、以及

### 3.2 AI 应用开发

| 知识 | 你必须能讲清 | 本项目对应 |
|---|---|---|
| **Agent / Multi-Agent 架构** | Supervisor 调度、分层 Agent、消息契约 | LangGraph StateGraph；18 个 Agent 分 5 层；标准 JSON 消息 |
| **工具调用 / MCP** | 工具 schema、幂等、错误语义 | Agent 经 MCP 调工具 |
| **Prompt 工程与缓存** | 结构化输出、版本化、可复现 | LLM 主营分带 `prompt_sig` 版本标记；结果**缓存复用**（`--no-llm` 只用缓存分） |
| **LLM 不确定性与兜底** | 无判定时怎么办 | 三路规则里的 **fail-open**：没有判定就不惩罚 |
| **成本与延迟** | 批处理、并发、限流、只跑增量 | `--no-llm` 零成本重跑；`--redo-over` 只重判候选过多的票；分批落盘（每 100 次 flush） |
| **可观测性** | trace、run log、留痕 | `runs.jsonl`；`sync_check.json`；`gap` 列表 |
| **护栏与安全** | fail-closed、敏感信息、免责声明 | `permits()` 未知级别/缺分数 fail-closed；token 走环境变量不入库 |
| **评测** | 离线评测集、LLM-as-judge 的偏差 | 启动真值台账 + 四象限；**明确区分「误报」与「亏钱」** |

**最容易被追问**：「LLM 判定怎么保证一致性/可复现？」
答：① 判定结果**落库缓存**，键是 `(代码, 归一化后的主题)`；
② 有 `prompt_sig` 版本标记，改 prompt 可识别；
③ 重跑时可 `--no-llm` 只用缓存，**不引入新的判定噪声**；
④ 主题名有别名/空格差异 → 做了**归一化**，否则同一个主题会被算成两个（实测漏掉 460 个成员）。

### 3.3 AI 应用架构师（这块决定职级）

| 知识 | 你必须能讲清 | 本项目对应 |
|---|---|---|
| **分层与边界** | 什么该共享、什么该隔离 | 两个库：主结果库 vs 行情缓存库；主线的分数库与 14GB 仓库分离 |
| **降级链设计** | 每一环都要有兜底，且**不能把失败源留在链首** | AkShare → 腾讯 → Tushare → baostock → CSV → QMT（**QMT 默认关闭且排最后**，否则每次白等 4~5s 超时） |
| **关键路径隔离** | 慢任务不许占公共线程池 | `/health` 走**专用线程池**：走默认池时实测被自选池首屏占满、要排队 144.5 秒 |
| **幂等 / 可重放** | 两阶段提交、去重键、UPSERT | `download` → `ingest` 两阶段，分区键幂等；`ingest` 是「有则更新」 |
| **缓存策略** | 分层缓存、TTL、写时竞态 | 健康度：内存 300s + 落盘 600s/1800s + **后台刷新 + 原子写**（`os.replace`） |
| **重型任务的隔离** | 离线任务不许压生产 | `MOSS_SQLITE_PATH` 跑副本 → 验证 → promote |
| **可回滚** | 备份/还原/版本化 | `--tag` / `--restore` / `--promote`；侧表快照 |
| **可观测性** | 指标而非日志 | 四态水位判定、`sync_gap`、run log、`checked_at` 留痕 |
| **演进路径** | 现在为什么这样、将来怎么改 | SQLite 零依赖起步，预留 Postgres（`DATA_BACKEND`）；单进程分层 → 可拆微服务 |

**架构师级追问**（准备好）：
- 「这个系统的瓶颈在哪？」→ 数据 I/O（14GB SQLite 冷查 6~28 秒）与全量重打分（90 分钟）；
  所以做了**落盘缓存 + 后台刷新**与**副本重算**。
- 「什么时候该从 SQLite 换 Postgres？」→ 多写入方并发、需要行级隔离/RLS 时；
  现在读多写少 + 单进程，SQLite 的零运维优势更大。
- 「如果重做，你会改什么？」→ ① 水位判定做成**一等公民**（一开始就该有）；
  ② 全量重打分**默认就跑副本**，而不是等出了两次事故；
  ③ 横截面分位改成**可冻结的基准池**，减少「改池子就得全量重算」的耦合。
