# LLM Token 优化实战手册

> 以 Moss-FinAgent-Research（18 Agent 多智能体投研系统，DeepSeek-V4 + 本地 Ollama）为例，
> 讲解多 Agent 系统中 Token 消耗的根因分析与分层治理方法。
> 所有数字均来自本仓库的真实改动（2026-09-15）。

---

## 一、先建立计费认知：Token 到底花在哪

### 1.1 计费公式

```
单次调用成本 = 输入token数 × 输入单价 + 输出token数 × 输出单价
一个任务的总成本 = 所有 Agent 的所有 LLM 调用之和（含重试、ReAct多步、修复调用）
```

DeepSeek 定价（元/百万 token）：

| 模型 | 输入（缓存未命中） | 输出 | 倍数 |
|------|------|------|------|
| V4-Flash | 1.0 | 4.0 | 输出是输入的 **4 倍** |
| V4-Pro | 4.5 | 13.5 | 输出是输入的 **3 倍** |

**推论 1：压缩输出比压缩输入更省钱。**
**推论 2：一次重试/修复调用的成本 ≈ 一次完整调用，所以"一次成功"本身就是最大的优化。**

### 1.2 多 Agent 系统的三个"隐形放大器"

单 Agent 调一次的开销可控，但多 Agent 架构会把开销放大：

1. **System Prompt 被重复计费 N 次**：每个 Agent 独立调用，同一段固定指令（如"你是投研委员会主席…"）每次调用都按输入 token 收费。10 个 Agent = 10 次。
2. **ReAct 循环的上下文滚雪球**：`第1步 prompt → 观测1 → 第2步 prompt（含观测1）→ 观测2 → …`，每一步都把历史观测重新发送一遍。5 步循环里，观测1 被发送了 5 次。
3. **失败重试翻倍**：JSON 解析失败后的修复调用、超时重试、降级调用，都是在原 prompt 基础上再加一段文本重新请求。

> 粗略 token 估算（中文场景）：1 个汉字 ≈ 0.75 token，1 个英文字符 ≈ 0.25 token。
> 用于预算门，不追求精确。

## 二、方法论：先观测归因，再分层治理

**不要一上来就"换轻量 prompt / 加超时"这种治标操作。** 正确顺序：

### 第 1 步：定量归因（回答三个问题）

- **哪一段 prompt 在膨胀？**（system / 规则 / 数据 / 事件 / 技能 / 历史观测）
- **膨胀了多少？**（字符数 / token 数，实测而非拍脑袋）
- **是谁拼接的？**（定位到具体代码行，才能精准裁剪）

本系统可观测基础：网关审计日志 `data/audit/llm_audit.jsonl` 记录每次调用的
`tokens_in / tokens_out / latency_ms / cache_kind / provider_chain`，
`LLMResponse` 也把 token 数带回 Agent 输出。

### 第 2 步：按性价比排序治理（5 个杠杆）

| 杠杆 | 手段 | 收益 | 风险 |
|------|------|------|------|
| ① 减少调用次数 | 缓存、本地模型分流、空数据跳过、熔断 | ★★★★★ | 缓存串台 |
| ② 限制输出长度 | max_tokens 分层 | ★★★★ | 过小→截断→重试反而更贵 |
| ③ 压缩每次输入 | 条件注入、截断、规则精简 | ★★★ | 丢失语义 |
| ④ 延迟加载 | PTD 三级披露 | ★★★ | 调度复杂度 |
| ⑤ 用更便宜的模型 | 任务分层路由 | ★★★★ | 小模型能力不足 |

## 三、本次实战的具体措施

### 3.1 输出侧：max_tokens 分层（收益最大、改动最小）

`configs/models.yaml` + `src/core/config.py`：

| 参数 | 旧值 | 新值 | 说明 |
|------|------|------|------|
| flash max_tokens | 8192 | **4096** | 思维链+结构化 JSON 足够 |
| pro max_tokens | 8192 | **4096** | decision 层 |
| hard_cap 硬截断 | 8192 | **4096** | 配置错误时的最后防线 |
| 单任务累计预算 | 50000 | **30000** | 超限拒绝，防失控 |

**关键点：推理模型的 max_tokens 包含"思维链 + 正文"两部分。**
给太大，模型会把预算花在冗长的内部推理上，既慢又贵，正文还可能因预算耗尽被截断成残缺 JSON。
但也不能盲目调小——实测真实 JSON 输出通常 500–1500 token，4096（约 3072 推理 + 1024 输出）留足余量。

> 网关在调用 provider 前做硬截断（`gateway.py`），即使 yaml 配错也不会超支。

### 3.2 输入侧：条件注入（不为用不到的指令付费）

**反模式**：把所有规则无条件塞进每个 prompt。例如"大盘流动性研判顺序"这条 ~400 字符的规则，
在问"这家公司的财务风险"时毫无用处，但每次都被计费。

**做法**（`src/domain/agents/analysis/base.py`）：

```python
has_liq = "market_liquidity" in (payload.hint or {})
liq_rule = (
    "5. 大盘/买卖/仓位类问题：按「总量阶段→三市分项占比→…」顺序…"
    if has_liq else ""   # 没有流动性数据时注入空串，省 ~400 字符
)
```

这是最重要的输入优化思想：**指令的存在性应由数据驱动，而不是写死。**

### 3.3 输入侧：数据截断（控制最大的输入块）

Agent 真正的输入大头不是规则，而是喂给它的数据：

| 数据块 | 旧值 | 新值 | 位置 |
|--------|------|------|------|
| 信息层事件 | 30 条 | **15 条** | `events[:15]` |
| 已核验原文 | 10 条 | **5 条** | `verified_texts[:5]` |
| ReAct 单步观测 | 1500 字符 | **800 字符** | `react.py` `_OBS_TRUNCATE` |
| 单指标期数 | 宏观12 / 其他60 | 保持 | `context_max_periods`（设计本就合理） |

ReAct 观测截断尤其关键：`800字符 × 5步 = 4000字符` 的硬上限，防止多步循环滚雪球。

### 3.4 输入侧：规则文本压缩（保留语义，删除口水话）

同一条规则，表达可以相差 5 倍长度。原则：**祈使句 + 关键词，删除解释性从句。**

```diff
- 1. conclusion首句必须直接、正面回答用户提问「{query}」（问概率给概率或
-   数据缺口声明、问洼地给具体环节/标的与估值判断、问持有期给明确观点），
-   禁止绕开问题只给模板化周期/宏观点评；
+ 1. conclusion首句必须直接回答「{query}」，禁止绕开问题给模板点评；
```

规则 2–4 从 ~300 字符压到 ~80 字符；A17 的 system_prompt 从 ~500 字符压到 212 字符。

**踩坑**：压缩时不能删掉有测试断言的关键语义词。A17 的输出规格被压缩后，
单测 `test_recommend_conflict_arbitration_prompted` 断言 prompt 中必须出现"冲突"和"仲裁"二词，
而英文键名 `conflicts_resolved` 不含中文，导致测试失败——补回中文标注 `conflicts_resolved(冲突仲裁说明)` 即可。
**教训：精简后跑全量测试，语义契约由测试守护。**

### 3.5 网关层：输入硬上限兜底

`gateway.py` 在请求发出前统一拦截：

```python
cap = self._settings.llm_input_char_hard_cap  # 6000 字符 ≈ 1000+ token
if len(prompt) > cap:
    prompt = prompt[:cap] + "\n…（已截断）"
```

**截断位置选择尾部**：prompt 头部是用户问题与核心数据，尾部是附加要求，
尾部截断优先保住"回答什么"而非"怎么回答"。

### 3.6 架构侧：这些措施比抠 prompt 字数更值钱

#### ① 语义缓存（减少调用次数，杠杆①）

`src/infrastructure/llm/cache.py`：两级缓存——精确命中（规范化后 SHA256）
+ 语义命中（字符 3-gram 余弦相似度 ≥ 0.85），TTL 24h，命中零 API 费用。

两个关键设计：
- **按 agent_id 隔离**：A05 核验和 A06 提取的输入大量重叠，跨 Agent 复用会导致"结论串台"。
- **阈值不能太低**：0.85 是"高相似才复用"的保守值，宁可不命中也不能错命中。

#### ② 任务分层路由（杠杆⑤，省钱主力）

`configs/models.yaml` 把任务分四档，简单任务走免费的本地模型：

- `light`（清洗/格式化）→ qwen2.5:1.5b 本地
- `medium`（A05/A06 信息处理）→ qwen3:8b 本地，DeepSeek 仅兜底
- `reasoning`（核心分析）→ DeepSeek-Flash
- `decision`（A17 决策）→ DeepSeek-Pro，失败降级 Flash

#### ③ 技能 PTD 三级披露（杠杆④）

上一轮 Skill 建设的核心就是 token 优化：
- **L0 索引**：只注入 name + description（< 100 token），列在 system prompt 里供 LLM 点名
- **L1 正文**：技能被触发短语命中才载入完整步骤（< 5000 token）
- **L2 参考**：references/*.md 按需加载

分析层用**确定性触发短语匹配**（零额外 LLM 调用），A17 才用 LLM 自主 `load_skill` 工具。

#### ④ 空数据直接跳过 LLM

`base.py`：当 `data_points / events / verified_texts` 全空时，
直接返回"无法形成有依据的分析结论"，不发起调用。**最便宜的调用是不调用。**

### 3.7 可靠性措施如何"不增加 token 反而省 token"

容易误以为防护机制会增加 LLM 开销，本项目刻意设计成纯本地、零额外调用：

| 机制 | 是否调用 LLM | 省钱逻辑 |
|------|------|------|
| HallucinationGuard（幻觉防护） | **否，纯正则规则** | 在本地校验数字/股票代码是否出自输入，不花一个 token |
| CircuitBreaker（熔断器） | **否** | DeepSeek 60s 内失败 3 次即熔断 30s，熔断中**直接跳过 API**，不浪费超时等待和失败计费 |
| 本地预计算（A05/A07） | LLM 只解读结果 | 可信度评分、情绪分由本地公式算好，LLM 不生成数字 → prompt 更短且不幻觉 |

熔断器状态机：`CLOSED`（正常）→ 60s 内 3 次失败 → `OPEN`（拒绝，直接降级本地模型）
→ 冷却 30s → `HALF_OPEN`（探测）→ 连续 2 次成功 → `CLOSED`。

## 四、优化效果汇总

### 单次调用维度

| 项目 | 旧 | 新 | 降幅 |
|------|-----|-----|------|
| 输出上限 | 8192 | 4096 | 50% |
| A17 system_prompt | ~500 字符 | 212 | ~58% |
| 流动性规则（非流动性任务） | ~400 字符/次 | 0 | 100% |
| 规则 2–4 | ~300 字符 | ~80 | ~73% |
| 注入事件数 | 30 | 15 | 50% |
| ReAct 单步观测 | 1500 | 800 | 47% |
| 单任务累计预算 | 50000 | 30000 | 40% |

### 系统级保障

- 491 项 pytest 全通过、ruff 零错误（语义由测试守护，精简不破坏功能）
- 缓存命中 / 熔断跳过 / 本地分流不直接体现在单次数字上，但在真实多任务运行中
  显著降低总调用次数（这才是成本大头）。

## 五、可复用 Checklist（下次接到任何 LLM 项目）

**先诊断**
- [ ] 有没有按调用记录 input/output token、延迟、缓存命中、重试次数？（没有观测就别谈优化）
- [ ] 算清楚：钱主要花在调用次数、单次输入、还是单次输出？

**减次数（优先）**
- [ ] 精确缓存 + 语义缓存（按租户/Agent 隔离，阈值保守）
- [ ] 简单任务路由小模型/本地模型
- [ ] 空输入、熔断中、已取消的请求直接跳过
- [ ] 大块知识用 PTD 延迟加载，不要一次性全塞

**压输出**
- [ ] max_tokens 按任务分层，基于"实测真实输出长度"设定，留余量而非翻倍
- [ ] 推理模型要给思维链留预算，避免正文截断触发更贵的重试

**压输入**
- [ ] 规则按数据条件注入，无数据场景注入空串
- [ ] 数据条数/期数/观测长度全部设上限
- [ ] 规则用祈使句，删解释性从句
- [ ] 网关层设输入字符硬上限，截断保头部
- [ ] system prompt 当成"被调用 N 次"的成本来审视，尽量短

**防回退**
- [ ] 改完跑全量测试：prompt 中的关键语义词可能有断言依赖
- [ ] 防护机制（校验/熔断）尽量本地实现，别为了防幻觉再调一次 LLM

## 六、一句话总结

> **Token 优化不是"把 prompt 改短"，而是"让每一次调用都必要、每次调用都只带必要的信息、每次调用都一次成功"。**
> 顺序永远是：观测归因 → 减调用次数 → 限输出 → 压输入 → 便宜模型，且每一步都由测试守护语义不被阉割。
