## 0. 先解决一个问题：怎么诚实地讲"AI 辅助开发"

这个项目大量使用 AI 辅助编码，**这本身不是问题，面试里也很常见**。真正会挂掉的是两种情况：

1. **讲了说不出来的东西** —— 面试官往下追一层（"为什么是 0.55 不是 0.6"），答不上来；
2. **把"跑出来的数字"当成"我懂了的东西"** —— 被问"这个 28% 可信吗"，答"应该可信吧"。

所以本文的写法是：**每个功能都配上"我为什么这么做 / 怎么验证的 / 它的边界在哪"**。
你可以直接说："这个功能是我用 AI 辅助实现的，但判断标准是我想的——比如我坚持回测必须调用实盘同一个分类器，而不是另写一套。"

**一句话话术**：
> "代码主要靠 AI 辅助产出，我的角色是把需求翻译成可验证的判断标准，并且在结果不对时定位到根因。这个项目里最有价值的产出不是功能数量，而是一批**'看起来正常但其实是错的'**的坑被找出来了。"

## 2. 六块功能逐个拆（每块都能独立讲 3 分钟）

### 2.1 超短战法回测 —— 面试里最能打的一块

**做了什么**：把六个超短战法（追击式/破冰式/龙回式/无极式/出水式/趋龙式）拿去跑 2026-06-26 ~ 2026-09-16 的历史，回答"这套打法到底有没有超额"。

**四个我能讲清楚的设计决定：**

**① 回测调用实盘的同一个分类器，不另写规则。**
`modes.classify_mode` 是线上竞价选股用的那个函数。如果为回测另写一套，回测出来的就是**另一个策略**，结论不能指导实盘。
为了做到这一点，我把生态判定从有 IO 的 `build_snapshot()` 抽成纯函数 `snapshot_from_series()`，**实盘与回测共用**。

**② 每个模块的"缺口"分四种处理，不是一刀切。**

| 情况 | 处理 |
|---|---|
| 缺一个维度 | 从权重分母**剔除**，并加覆盖率惩罚 |
| 缺关键输入（涨停价/昨收/均量） | **放弃这个判断**并记 gap，不用估算值顶上 |
| 结构性缺失（历史无题材榜） | 整个模式标为**"不可评估"** |
| 一条可降级判据 | 降级为"只扣分不否决"，并把降级**逐条列出来** |

> **为什么要分四种**：把"数据不足"和"没机会"混在一起，就会拿 0 笔冒充胜率 0。

**③ A 股制度约束进了收益率。**
- **T+1**：买入当日不可卖——哪怕当天就跌破止损。当日触发只记 `breached_entry_day`，**次日开盘**卖；
- **一字涨停买不进**：T+1 开盘价 = 涨停价 → 记 `buy_blocked`，不建仓；
- **跌停卖不出**：开盘/收盘价 = 跌停价 → 挂到下一交易日开盘（一字跌停可能连挂几天）。

**④ 均值必须配中位数和"去掉最好一笔"。**
超短收益分布右偏极重，一笔翻倍就能把均值拉正。所以报告里同时给三个数。

**实测结果**（信号日 59 个交易日，61 笔）：

| 模式 | 笔数 | 胜率 | 平均单笔 | 去掉最好一笔 |
|---|---:|---:|---:|---:|
| 出水式 | 26 | 15.4% | −4.26% | −4.75% |
| 追击式 | 7 | 28.6% | −6.66% | −8.51% |
| **无极式** | 24 | 50.0% | **+3.92%** | +2.21% |
| 龙回式 | 4 | 50.0% | −4.56% | −7.33% |
| **全部命中** | 66 | 30.3% | −1.70% | −2.39% |
| **无条件对照**（当日全部涨停股、同样卖出规则） | 3090 | 30.7% | −1.67% | −1.71% |

**三条结论（这就是"讲得出来"的部分）**：
1. **战法选择几乎没带来超额**：−1.70% vs 无条件对照 −1.67%。亏钱的主因是**买卖规则本身**，不是选股。
2. **只有无极式是正的，但它 26 笔在严格模式下全部不会出现** —— 历史没有逐笔委托数据，它的"盘口强势有气质"判据被降级才让它成立的。**这个前提没被验证过**，所以那个正收益要打问号。
3. **破冰式 0 信号是行情事实**（59 天里没有一天是冰点）；趋龙式因为**没有历史题材榜**直接标"不可评估"，**没有拿 0 笔冒充胜率 0**。

**这套方法论的名字**：**把"策略"和"执行规则"分离归因**。不分离这两个因素，就会一直去换选股逻辑，而问题其实在止损/止盈上。这条在面试里非常加分。

### 2.2 模型回测变体对比 —— "不重跑选股也能做实验"

**问题**：跑一轮完整回测要做 242 天的选股（几十分钟），但**选股结果与交易规则是正交的**。换止盈线、换止损滑点、去掉某个市值档，用的是同一批信号、同一批入场价。

**做法**：写 `scripts/model_backtest_variants.py`，从已保存的成交明细 + 从仓库补取的日线路径，用**同一个 `simulate_trade` 引擎**重跑变体（不是另写一套近似）。

**关键验证**：基准行复现了原报告的 **+19.51% / 含费 +13.28%** —— 数字对上了才敢用后面的结论。

**顺手修了一个报告 bug（这条最能体现"读数字要读口径"）**：
原报告写"含费 +13.28% → 再叠加止损滑点 → **−4.35%**"。我核对后发现 −4.35% 是**只叠滑点、不含费**：
`stop_slippage_sensitivity` 算的是 `总盈亏 − 滑点损失`，把佣金漏掉了。真实口径是：

```
+19.51%（零成本）
  − 6.23%（0.1% 来回费：累计买入 6.234 亿 × 0.1%）
  − 23.86%（止损滑点：4984 笔止损单成交价再低 1% → 额外损失 238.6 万）
= −10.58%
```

**滑点一项比佣金大近 4 倍**。而且 —— 见下面的变体表 —— **滑点损失 ∝ 止损触发次数**：止损收紧到 −3% 时含费+滑点变成 **−26.37%**。这是"优化方向选错会把事情做更糟"的活例子。

### 2.3 改标签重训 + 真样本外回归 —— 本会话技术含量最高的一块

**需求**：把正样本标签从"3 日最高 >8%"改成 **>10%**，砍掉 500 亿以上个股，用 **2020-09-15 ~ 2025-09-15** 训练、**2025-09-15 ~ 2026-09-15** 回归测试。

**我坚持的一件事：要改就改标签重训，不能拿旧模型跑新规则。**
模型学的是标签定义的"什么算好票"。拿 1.08 训出来的模型去跑 10% 的止盈，赚的是**模型没被训练去预测的那部分右尾** —— 样本内可能好看，样本外没有根据。

**为此我改了三处（都向后兼容，默认值 = 原行为）**：
1. `model_trainer.prepare_labels`：把 band 的四个阈值（1.08/0.96/1.05/0.95）**从硬编码改成参数**；
2. `main_train_pipeline`：支持**显式训练区间**（原来只能"从今天往回推 N 年"，训练区间会跟着当天漂移，和测试区间永远相邻）；
3. `filter_pool`：加 `max_circ_mv` 上限。

> **第 3 点有个非直觉的地方**：光在 `cap_buckets` 里少写一档是**不够**的。`cap_bucket()` 对落在任何档外的票返回 `""`，而打分侧会回落到 `next(iter(models.values()))` —— **大盘股照样会被评分并入选**。所以上限必须在**样本池**这一层就剔掉。这就是"配置看起来对、行为不对"的典型。

**训练产物**：面板 876,348 行 × 777 只票；标签 正 27,900 / 负 99,856；两档各一个模型。

| 档位 | 训练行数 | AUC | RankIC |
|---|---:|---:|---:|
| 20–150 亿 | 67,982 | 0.6471 | 0.1524 |
| 150–500 亿 | 31,939 | 0.6499 | 0.1003 |

**样本外回归结果**（2025-09-18 ~ 2026-09-17，242 交易日，9640 笔）：

| 指标 | 原基准（1.08 / 3 档 / 止盈 7%） | **新（1.10 / 2 档 / 止盈 10%）** |
|---|---:|---:|
| 平均单笔 | +0.313% | **+0.587%** |
| **年化（零成本）** | +19.51% | **+28.30%** |
| 含 0.1% 来回费 | +13.28% | **+23.48%** |
| **含费 + 止损滑点 1%** | **−10.58%** | **+2.86%** |
| **夏普** | 2.113 | **3.503** |
| **最大回撤** | −9.78% | **−6.34%** |

**收益归因（别把功劳都给止盈线）**：
- 19.51% → **22.60%**：改标签重训 + 去掉 500 亿+ 的贡献（**+3.1pp**）
- 22.60% → **28.30%**：止盈 7% → 10% 的贡献（**+5.7pp**）

**为什么这次是"真样本外"**：回归窗口起点（2025-09-18）**严格晚于训练数据结束日**（2025-09-15）。原基准那次不是——它要的"近一年"正好是模型的测试区间，属于"刚训完就在自己测试集上评估"。

**这一块能讲的三个"知道自己在做什么"**：
1. **知道什么必须一起改**：标签、模型、回测规则三者口径必须一致；
2. **知道怎么归因**：把总提升拆成"模型贡献"和"规则贡献"；
3. **知道什么不可比**：见 §4 的保留意见。

### 2.4 量化选股：一键全部加自选 + 导出名称 txt

**做了什么**：前端加两个按钮（全部加自选 / 导出名称 txt），后端加**批量接口**。

**为什么不做成前端循环调单只接口 —— 两个都是实际原因**：

1. **落盘/重建次数**：单只 `add_watch` 每次都写一遍 `configs/intraday.yaml`、重建 5 个做T子组件、作废自选概览缓存。20 只就是 20 次，紧随其后的**自选概览整表重算**（冷启动实测约 114 秒）就是卡顿主因。现在**一次写完、一次重建** —— 有单测卡这个契约（"批量加 20 只只能落盘一次"）。
2. **不能覆盖用户手配的字段**：`upsert_watch` 是整条替换（含 `boards/peers/industry/overseas`），重复加入会把用户手工配的板块映射清空。所以**已在池中的票原样不动**，只有名字为空的历史条目才顺手补名。

**回执设计**：不谎报成功，分开返回 `added / repaired / existing / failed / missing_name / total`。

**端到端验证（在运行中的服务上真跑）**：

| 检查 | 结果 |
|---|---|
| 空 `items` | 422（路由存在 + 校验生效） |
| 提交截图里那 20 只（都已在池中） | `saved=false, existing=20, added=0` —— **零改动** |
| 真实新增 000001 | `added=['000001']`，配置文件 43→44 条 |
| 重复提交同一只 | `existing=['000001']` —— 幂等，不覆盖 |
| 删除探针票善后 | 配置回到 43 条 |

**顺带修的一个坑**：SQLite 绑定参数上限 —— 一次标记 1200 个代码要**分块**（每 400 个一批），单条 `IN (...)` 会直接报错。

### 2.5 数据新鲜度治理 —— 本会话最有价值的一条

**事故现象**：用户问"今天 9:10 手动触发的量化选股，为什么选取日期是 20260915，而不是最新日期？"

**排查**：我没有猜，而是直接查了仓库和接口：
- 选股取日期只有一行 `latest = str(processed["date"].max())` —— "数据里最新的一天"；
- 而**本地行情仓库当时最新就是 0915**（0916/0917 没有任何作业去同步）；
- 选股链路**没有错**，它忠实地用了"手上最新的一天"。

**为什么这条危险**：分数、阈值、排名、模型档位**全都算得出来**，界面上看不出任何异常，但它描述的是**两天前的市场**。

**修法两层**：
1. **让它可见**：新增 `src/quant/freshness.py`
   - `latest_complete_trade_date()`：最近一个**已收盘**交易日。**盘中不算今天**（09:25 时最新可用是昨天），过了 **16:30**（EOD 发布线）才把今天算进来；
   - `freshness(data_date)` 返回 `{expected_trade_date, data_stale, note, checked}`。注意 **`checked=False` 表示"没判"**，调用方不能读成"确认新鲜"；
   - 接口**读时计算**（不落库）→ 老记录也能被正确重判；前端出「数据滞后」横幅。
2. **从根上补**：新增 `quant_data_sync` 定时作业，工作日 **16:40** 先问仓库当前最新日期、**只补缺的那几天**、下完**必须 ingest**（"下了但没入库"是这一步最容易漏的）。

**可迁移的教训**：**"算得出来"不等于"算得对"**。凡是结果依赖"最新数据"的地方，都要能把"最新是哪一天"显式报出来。

### 2.6 盘前预热磁盘缓存 —— 把一个 139s 的调用变成 0.02s

**背景**：盘前预热 4 个远端接口，`theme_strength_rank` 一项实测 **139s**。

**一个关键判断**：用户提议"改成只取前 40 名（当前已 count=40）"。我核对了代码 —— **`count=40` 已经在传了**，而这个参数只裁剪**返回条数**，服务端照样要把全市场题材榜算完才截断（实测传 40 与不传耗时一致）。
→ **优化前先确认成本发生在哪一侧**（客户端 / 网络 / 服务端），否则会做一堆无效的参数调整。

**真正的漏损在哪**：`scheduler._PREHEAT` 是**进程内**缓存，只按交易日做键，于是这 139s 在这些时刻反复付：每次服务重启、`run_selection` 直接调 `fetch_preheat()`（绕开调度缓存）、手动 force。

**做法**（`preheat_cache.py`，落在 `data/cache/auction_select/`）：
- **键是交易日**（预热内容是"那一天"的函数，跨日一律不命中）；
- **按分项记 ok/失败**：09:15 那次 `limit_ladder`/`theme_strength_rank` 会被数据源以 `ShortlineIndicatorsNotReadyError` 拒绝（"09:25 竞价完成前短线指标未就绪"），那两项**不写进缓存**，下次**只补这两项**；
- **全命中就不碰网络** —— 连 `session.ensure()` 都不调用，数据源挂了也能出池；
- **空结果不入缓存**（写进去就永远不会再补，维度永久空着）；过期/坏文件/版本不符一律丢弃。

**实测**：

| | 耗时 |
|---|---|
| 冷启动（真的拉一次） | **120.1s** |
| 暖缓存 | **0.02s** |
| 服务重启后第一次调预热接口 | `seconds: 0.13`（改前是 `159.45`） |

**顺手发现的真 bug（ST 过滤静默失效）**：
验缓存内容时发现数据源的 `limit_ladder()` 58 行里 **`name` 全是空串**，而 `daily_price_limits` 的 5574 行**全有名字**。`build_candidates` 的 ST 判定读的是前者的 `name` → **`exclude_st: true` 一条都没滤掉**，而且完全静默（notes 里还写着"剔 ST 0"，看起来像"今天正好没有 ST 涨停"）。

> **可迁移的教训**：**过滤条件是"静默失效"的最佳藏身处** —— 它不会报错，只会让结果悄悄变多。

## 3. 踩坑集（本会话真实发生，20 条）

> 讲法统一：**现象 → 根因 → 修法 → 可迁移的教训**。带数字的都是当时测出来的。

### 数据与正确性类

**坑 1｜静默用两天前的行情选股**
根因：取日期 = "数据里最新的一天"，而仓库最新就是 0915，且**没有作业在同步**。
修法：算"应该是哪一天"并显式暴露 `data_stale`；新增 16:40 同步作业。
**教训：算得出来 ≠ 算得对。**

**坑 2｜ST 过滤一直空转**
根因：ST 判定读 `limit_ladder` 的 `name`（实测 58 行全空），有名字的是另一张表（5574 行全有）。
**教训：同一个字段名在两个接口里不一定都有值。**

**坑 3｜覆盖率归一化奖励了缺数据**
现象：只有 `open_gap_pct` 一个维度可用时它满分 → 总分算出 **100 分**，比数据齐全的好票还高。
修法：加覆盖率惩罚（可用权重 <55% 按比例封顶）。
**教训：缺失值的默认处理往往是隐含的激励。**

**坑 4｜`count=40` 不省服务端算力**
**教训：优化前先确认成本发生在哪一侧。**

**坑 5｜写按偏好、读按实际（换 Python 环境就"看不见数据"）**
根因：写入会自适应（有 pyarrow 写 `.parquet`，否则 `.csv.gz`），读取却只认一种后缀。
**教训：格式自适应是双向契约。**

**坑 6｜交易日历默认倒序 + 缓存不记区间 → 只下了 11 天却报"成功"**
修法：返回前强制排序；把 `start/end` 写进 manifest。
**教训：缓存要记录"它覆盖的范围"。**

**坑 7｜`root` 路径反推少一层，SQLite 凭空建了个空库**
现象：明明配了数据库，却"成功地"去读 CSV，白付 5 秒，**一句日志都没有**。
**教训：SQLite 会"帮你"建出你写错的路径；连接成功 ≠ 连对了库，必须校验表是否存在。**

### 工程与性能类

**坑 8｜一个"位置参数 vs 关键字参数"的错误让整条数据链静默变空**
`to_thread(client.call, api, {})` —— 而签名是 `call(self, api, **params)` → `TypeError`，**被 except 捕获后归类成"数据源不可用"**。
**教训：宽泛的 `except Exception` 会把"程序写错了"和"外部服务挂了"混成同一件事。**

**坑 9｜`COUNT(*)` 把整个服务卡了几分钟**
14.28GB / 8550 万行：九张表合计 40s+，还冲掉 OS 页缓存（42s→46s）→ `/health` 300 秒超时。
修法：改 `MAX(rowid)`（写入是"原地 UPSERT 不换 rowid"且从不 DELETE，数值与 `COUNT(*)` 完全相等），0.00s。
**教训："统计一下有多少行"这种看起来无害的操作，在大表上是重操作。**

**坑 10｜引入第二层缓存后，"强制刷新"变成空操作**
`get_preheat(force=True)` 只清了进程内缓存，`fetch_preheat` 仍读到同一份磁盘缓存。
**教训：引入新缓存时，要回头检查所有"绕过缓存"的入口是否还成立。**

**坑 11｜测试读到了真实缓存，断言全部反过来**
三个"接口全挂也要返回对象"的用例从本机真实缓存里拿到了数据。
修法：加 autouse fixture 把缓存目录隔离到 tmp。
**教训：任何写文件的缓存，测试里都必须显式指到 tmp。**

**坑 12｜并发只解决了"一轮内别串行"**
4 个慢接口串行 230s+，并发后 = 最慢那项 ≈139s，但仍然每次都要付。
**教训：优化要分清"单轮成本"和"重复次数"——并发降单轮，缓存降次数。**

**坑 13｜SQLite 绑定参数上限**
一次 `IN (...)` 塞 1200 个代码直接报错；改按 400 分块。
**教训：批量接口的上限要按底层实现的硬限制来定。**

**坑 14｜`report.steps` 的元素是 dict 不是对象**
我写 `step.ok` / `step.name` → `AttributeError`（同一个坑在 `model_retrain_service` 里也踩过）。
**教训：拿不准的数据结构先 `print(type(...))`，别按直觉写。**

**坑 15｜`_print_report` 里引用了不在作用域的 `args`**
改脚本时把 `args` 当全局用了 → 报告跑到一半崩，但**指标已经算完**。
**教训：脚本里的"最后一公里"（打印/落盘）也要放在 try 里，否则白跑一轮。**

### 模型与回测类

**坑 16｜把"止损滑点"和"佣金"当成可叠加的两个数**
原报告写 `+13.28% → 再叠滑点 → −4.35%`，实际 −4.35% 是**只叠滑点、不含费**；真实口径是 **−10.58%**。
**教训：看到"再叠加"三个字要去读那个函数的实现，别信表格的措辞。**

**坑 17｜"少写一档"不等于"过滤掉这一档"**
`cap_bucket()` 对档外的票返回 `""`，打分侧会回落到 `next(iter(models.values()))` → 大盘股照样入选。
修法：在**样本池**层加 `max_circ_mv`。
**教训：配置看起来对、行为不对 —— 要顺着数据流走一遍才知道。**

**坑 18｜改止盈线却不改标签**
1.08 训出来的模型跑 10% 的规则，赚的是"模型没被训练去预测的那部分右尾"。
修法：标签 / 模型 / 回测规则三者口径一起改。
**教训：监督学习的"目标"变了，模型就必须重训。**

**坑 19｜训练区间跟着当天漂移**
原 `trade_date_range(years=5)` 永远"从今天往回 5 年"，导致训练区间和测试区间**永远相邻**。
修法：支持显式训练区间。
**教训：想做样本外，训练窗口必须能钉死。**

**坑 20｜并发会话改了配置，让两个数字不可比**
同一天里另一个会话把 `selection.threshold_mode` 从 `percentile` 改成 `none`，导致 `pool_positives` 的分母从"当日分位选中的那批"变成"整个打分池" —— **召回率 68.82% 与 13.49% 不是同一个指标**。
处理：在结论里明确标注"这两个数不可比"，而不是硬比。
**教训：报告要记录"结论依赖哪些配置"，否则换个环境就复现不出来。**

**另有两个环境类的小坑**：`manage.py` 在 GBK 控制台最后一句 `print("✅ …")` 崩溃（**命令已执行完却返回非 0，看起来像启动失败**）；以及发现**另一个会话在并发改同一个仓库**（`auction_select/config.yaml` 的市值上限一天内从 200 亿→150 亿→110 亿），因此我在报告里加了**代码版本短哈希**，让"这份数字对应哪版代码"可查。

## 5. 面试题库

### 5.1 量化开发岗

**Q1：你的 Alpha 来自哪？**
> 三条，按我信的程度：① 短周期**情绪结构**（涨停家数/炸板率/最高连板/连板家数）；② **竞价微观信息**（9:15–9:25 价格轨迹与未匹配量方向）；③ **题材内部的资金轮动**（龙头与梯队的位置关系）。
> 但我要说清：**我自己回测的结果是四个战法里三个负期望**，所以我不会说我的 Alpha 很强。

**Q2：怎么避免过拟合？**
> ① 样本外：显式钉死训练区间（2020-09-15~2025-09-15），回归窗口严格晚于训练结束日；② 参数保守（`num_leaves=31 / lr=0.05 / min_child_samples=50`）；③ 上线有闸门；④ 回测调用实盘同一个分类器。

**Q3：为什么用日频而不是高频？**
> 数据可得性 + 容量。我用的是"涨停次日接力"这类 1–3 日持仓的形态，日线足够；高频需要 tick 级存储与撮合假设，是另一套工程。

**Q4：回测里的成交假设是怎么定的？**
> 逐条摊开：入场 = 次日**开盘价**；一字涨停买不进；跌停卖不出要挂次日；T+1 当日不可卖；止损成交价先假设**精确在 −5%**，再单独给"比 −5% 再低 1%"的敏感性。
> **最后这条是故意的** —— 它把"结论对止损滑点极度敏感"这件事直接摆在报告里，而不是藏在假设里。

**Q5：胜率多少算好？**
> 看**盈亏比**。超短天然低胜率高赔率：无极式 50% 胜率 + 2.37 盈亏比是健康的；出水式 15% 胜率 + 0.67 盈亏比就是稳定亏钱。
> 另外我会同时给**中位数**和**去掉最好一笔的均值**——超短收益右偏极重。

**Q6：策略亏钱你怎么归因？**
> 把"选股"和"买卖规则"分开算：全部命中 −1.70%/笔 vs **无条件对照**（当日全部涨停股、同样卖出规则）−1.67%/笔 → **亏钱主因是买卖规则而不是选股**。不分离这两个因素，就会一直去换选股逻辑。

**Q7：怎么判断一个改进是真提升还是噪声？**
> 三个做法：① **基准复现校验**（变体脚本先复现原报告的 19.51%/13.28% 才继续）；② **归因拆解**（把总提升拆成模型贡献和规则贡献）；③ **看风险调整后指标**，不只看收益（去掉 500 亿+ 只降 2pp 收益，但夏普 +0.36、回撤改善 3pp）。

**Q8：A 股有哪些制度约束必须进回测？**
> T+1（当日不可卖）、涨跌停（买不进/卖不出）、停牌、ST 的 5% 限幅、北交所不在数据源覆盖内。漏掉任何一条，回测出来的就是另一个市场的收益率。

**Q9：止损线怎么设？**
> 我的实测给了个反直觉的结论：**止损收紧是负向的**。−3% 止损 → 含费+滑点 −26.37%；−8% → +6.32%。原因是**滑点损失 ∝ 止损触发次数**。
> 另一个口径：止损距离 = `max(百分比, 0.5×ATR)` —— 固定百分比对高波动股形同噪声（用日线 ATR 算过：ATR 占股价 5.8% 时，1% 的止损只有 9 元）。

**Q10：止盈该设多少？**
> 数据支持"不要过早下车"：止盈 7%→10% 让单笔从 0.313% 升到 0.587%；再改 15% 在**新模型上**仍有 +4pp（+2.86%→+6.88%）。
> 侧证：止盈只卖 **40%**（留 60% 跑）零成本 24.57% > 卖 70% 19.51% > 全卖 100% 14.45%。**三个变体指向同一件事：信号有延续性。**
> 但**前提是标签要一起改**——否则赚的是模型没被训练去预测的右尾。

### 5.2 AI 应用开发岗

**Q11：模型是什么？为什么不用深度学习？**
> LightGBM 二分类（`objective=binary`, `metric=auc`）。三个理由：① 日频截面、样本量与信噪比在这个规模上树模型更稳；② **可解释性**（前端能展开看每只票的因子值，这是产品需求）；③ 周度重训要能在一台机器上跑完。

**Q12：标签怎么定义？为什么这么定义？**
> **正样本 = 3 日内最高价/买入价 > 1.10 且最低价/买入价 > 0.96；负样本 = < 1.05 且 < 0.95；其余剔除。**
> 为什么正样本要加"且最低 > 0.96"：只要求涨幅会选出"先砸 8% 再拉 9%"的票——那种拿不住。加上回撤约束后，正样本是"**买入后不难受**"的票。
> 为什么负样本也要两个条件：只要求"跌"会把"横盘没动"也算成负样本，而横盘不是"该躲"，只是"没机会"。

**Q13：特征有多少？怎么防泄漏？**
> 26 个，5 大类（板块资金流 4 / 个股资金流 4 / 技术面 7 / 情绪 4 / **交叉项 7**）。
> 防泄漏三条：① 面板构建只用截至当日的数据；② 预处理是**当日横截面 percentile**（自带"当日排名"语义，不跨日泄漏）；③ 训练与推理复用同一份 `preprocess_kwargs`。
> **交叉项是刻意的**：真正要抓的是"板块有资金 **且** 个股是承接方"，这种非线性交互靠规则很难写。

**Q14：缺失值怎么处理？**
> **一律留 NaN，绝不填 0** —— 填 0 会让树模型把"没有资金流数据"当成"资金流为零"，那是两个完全不同的判断。LightGBM 原生吃 NaN。

**Q15：阈值怎么定？**
> **不能用 0.5**。标签是稀有事件（旧口径正样本率 ~9%），模型概率集中在 0.01~0.2。曾经把阈值写死 0.6 → **永远选不出票**。
> 现在用当日横截面分位或"取分数最高的 N 只"，并留一个绝对下限作保险丝。

**Q16：为什么按流通市值分档训练？**
> 不分档，模型很容易学到"**市值本身**"而不是"这只票好不好"。分档后每档独立训练、独立评估；**推理时按票自己的流通市值分发模型**，而不是先定一个模型再打全市场。
> 数据也支持：去掉 500 亿+ 后 AUC 从 0.6250 升到 0.6499，说明大盘档确实在拖后腿（大票定价更有效，模型没有 edge）。

**Q17：模型怎么上线？**
> 周度重训 → 逐档回归对比（AUC/RankIC）→ **过闸门才原子替换** → 失败回滚成完整旧套。
> 为什么"半套状态"必须挡住：服务读模型是按公开文件名 glob 取最新，出现"新模型已就位、特征列表还是旧的"时**模型照样能加载但分数全错**。

**Q18：LLM 用在哪？会有幻觉吗？**
> 消息面情绪打分、新闻事件抽取。风险控制：时效红线（拒用超期数据）、缓存、以及**关键链路不依赖 LLM**（选股/打分/回测全是确定性代码）。

**Q19：你怎么做特征/结果的可解释性？**
> 三层：① 每个维度的打分配一句人话 note 并**指回语料出处**；② 前端可展开看每只票的因子值（已做当日截面名次映射到 [-1,1]）；③ 报告里主动列出"哪些信号只因为数据降级才出现"。

### 5.3 AI 应用架构师岗

**Q20：系统的分层是怎么切的？**
> 三条边界：① **取数层唯一入口**（`load_dataset` 返回 `(DataFrame, 来源字符串)`，禁止各模块直连库）；② **打分器是纯函数**（输入 dict、输出 `(分数, 人话说明)`，不碰 IO）→ 单测覆盖率极高且能被回测复用；③ **服务层与 Agent 配置分离**（跨会话共享的放宿主，一次会话的能力放 preset）。

**Q21：为什么取数必须回传"来源"？**
> 否则"这次到底查的库还是文件"会变成**查不出来的问题**。回测复现性直接依赖它。

**Q22：`covers()` 为什么要看最大日期而不是"有没有行"？**
> 入库是按分区键**顺序**进行的，库里任何时候都只是缓存的一个**前缀**。用"区间内有没有行"判定，一个灌到一半的数据集会被判为"走库" → 回测**静默丢掉后半段数据** —— 净值曲线照样画得出来，只是少了一半样本。**这比直接报错危险得多。**

**Q23：多源容灾怎么判断该不该切？**
> 判据是"**够不够新**"而不是"成功/失败"：带日期的查询把库里最新日期当**新鲜度下限**，链上某源返回成功但比它旧 → 继续试下一源；**过旧不记失败冷却**（"这个源本身是好的，只是这份数据旧了"，记冷却会把它连"最新可得的源"都当不成）；全部比下限旧就返回其中最新的那份。
> **空结果也算"没拿到"**（实测某源被阻断时返回 `[]` 而不是异常），否则会把后面的源挡掉。

**Q24：缓存一致性怎么保证？**
> 三条规则：① **键必须包含"数据的时间维度"**（预热按交易日，跨日一律不命中）；② **"跑了但没拿到"不能写进缓存**（否则永远不会再补）；③ **版本号 + 交易日双重校验**，不符就当没有缓存。
> 另外：引入第二层缓存时，必须回头检查所有"绕过缓存"的入口（我们踩过 `force` 失效）。

**Q25：状态接口为什么要小心？**
> 我们踩过：`/health` 里跑了一次全表行数统计 → 整个服务卡几分钟、300 秒超时。
> **状态接口应该只读缓存好的标量，不做重计算。**

**Q26：怎么做数据新鲜度治理（架构级）？**
> 把它做成**能被检查的东西**而不是口头约定：算"应该是哪一天"（区分盘中/收盘后）、在接口**读时**标注、前端显式提示、并有一个**定时作业**去补齐。
> 关键是 `checked=false` 表示"没判"，不能读成"确认新鲜" —— **架构上要允许"不知道"这个状态存在。**

**Q27：怎么写"AI 辅助产出"的代码才可控？**
> 我的做法是把**判断标准**写进代码注释和文档，并指回出处。比如权重表里写明"权重不是语料里的原始数值，语料只给方向与优先级，这里是我们自己的标定"。这样后面任何一次调参都能查到"当初为什么是 19 不是 15"。

**超短回测（2026-06-26 ~ 2026-09-16，59 个交易日）**

**预热缓存**
- `theme_strength_rank` **139s**；冷 **120.1s** → 暖 **0.02s**；重启后 159.45s → 0.13s

**模型回测（基准，1.08 / 3 档 / 止盈 7%）**
- 12477 笔 / 45.83% / 年化 **+19.51%** / 夏普 **2.113** / 回撤 −9.78%

- 滑点 23.86% vs 佣金 6.23% → **滑点大 4 倍**

**重训样本外（1.10 / 2 档 / 止盈 10%，2025-09-18 ~ 2026-09-17）**
- 9640 笔 / 42.73% / 年化 **+28.30%** / 含费 **+23.48%** / **含费+滑点 +2.86%**
- 夏普 **3.503** / 回撤 **−6.34%** / 平均单笔 **+0.587%**
- AUC 0.6471 / 0.6499；RankIC 0.1524 / 0.1003
- 归因：+3.1pp 来自重训+砍大盘，**+5.7pp 来自止盈线**

**变体扫描（新模型上）**
- 止盈 15% → 含费+滑点 **+6.88%**（夏普 3.723）
- 止损 −8% → **+10.71%**（回撤 −7.86%）；止损 −3% → **−14.71%**
- 止盈只卖 40% → +3.69%；全卖 100% → −8.04%
- 只做 20–150 亿 → 回撤仅 **−3.02%**

**工程**
- 仓库 14.28GB / 8550 万行；`COUNT(*)` 40s+ vs `MAX(rowid)` 0.00s
- 列裁剪 2.2×；股票池下推 SQL **225×**；面板装配 103.9s → 27.3s
- 自选池 43 只；批量加自选 **一次落盘**（vs 20 次）
