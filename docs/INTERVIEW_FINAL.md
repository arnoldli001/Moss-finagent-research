### 0.2 一句话结构

```
同一套代码库，两条业务线
├── 竞价选股（短线，9:25 出池）      ← 量化岗主讲这条
│     └── 规则引擎 + 自研回测 + QMT 双进程实盘
└── AI 投研平台（中长线，多 Agent）  ← AI 应用/架构岗主讲这条
      └── 19 Agent 分层编排 + LLM 网关 + 数据连接器路由 + 多租户合规
```

**这不是一个项目，是"一个平台 + 一个策略"。** 面试时**先问清楚对方要哪条**，
不要一股脑讲完——量化岗听多 Agent 编排会觉得跑题，AI 岗听 12 维打分权重也会跑题。

## 第 1 章 · 电梯陈述

### 1.1 三十秒版（开场白，两岗通用）

> "我做了一个 **A 股量化投研系统**，同一套代码里有两条线：
> 一条是**集合竞价短线选股**——9:25 集合竞价定格后，对昨日涨停股做 12 维打分选 3 只，
> 我自己写了回测引擎做四年全周期验证，最后拆成「本地选股端 + QMT 执行端」双进程实盘；
> 另一条是**多 Agent AI 投研平台**——19 个 Agent 分 5 层做产业链研究，
> 我自己搭了 LLM 网关、数据源故障转移路由和多租户合规层。
> 整个项目 25 万行左右、4,000 多个单测。"

### 1.2 两分钟版（量化岗，按这个顺序讲）

**① 策略是什么（20 秒）**
在**昨日涨停股**里选。9:25 集合竞价定格后，用竞价量能、开盘位置、承接强度、题材热度等
**12 个维度加权打分**（权重和 100），加抢筹 +4 / 大量抢筹 +5，取分数最高的 3 只、
每只约 3 成仓位；次日开始按**严格优先级的卖出规则**择机离场。

**② 我怎么验证它（40 秒）**
自研回测引擎，**100% 复用生产选股代码**
（`build_candidates → build_feature → score_candidate`），回测只负责组合与撮合。
四年全周期 **969 个交易日**：

| | 总收益 | 年化 | 夏普 | 最大回撤 | Calmar | 每元交易额收益 |
|---|---:|---:|---:|---:|---:|---:|
| V3 基准 | +67.14% | +13.81% | 0.528 | −51.11% | 0.270 | 0.252% |
| **加装净值熔断 40日/10%** | **+157.01%** | **+26.83%** | 0.950 | **−29.13%** | **0.921** | **0.634%** |

**③ 我最大的技术贡献（40 秒）—— 回撤控制的方法论**
原始策略最大回撤 −51%、**96.8% 的交易日净值在水下**。我没直接调参，先做归因，发现两件事：

- 这段回撤是 **20 个月的弥散失血**（466 笔交易、笔均只亏 1,557 元）——**不是事件性崩盘**；
- 根因是**选股 alpha 在特定区间整体消失**（段内每元交易额收益 **−0.872%**、胜率 35.4%；
  段外 **+0.958%**、41.7%）。

> 注：数字来自 `docs/竞价选股_量化回测报告.md` §4.1，与 `result_v3_2021_2025.json` 的 stats 一致。

然后我**否定了自己两个直觉**：均匀降仓位（回撤只改善 12pt，收益崩 63pt）、
接入市场情绪闸门（回撤反而扩大到 −67.78%）。最后找到有效的**组合层净值熔断**，
并且有一个决定性对照：

| 方案 | 平均仓位 | 总收益 |
|---|---:|---:|
| 基准仓位 × 0.5 | 24.4% | +4.40% |
| 净值熔断 40日/10% | **25.5%** | **+157.01%** |

**平均仓位几乎相同，收益差 35 倍。** 结论：这个策略的 alpha 全部来自
「**什么时候在场**」，而不是「下多大注」——**这个结论直接决定了风控该往哪个方向做**。

**④ 工程上做了什么（20 秒）**
把实盘拆成**信号端 + 执行端**：本地跑完整 12 维选股（QMT 拿不到题材数据，
最多只能还原 76.5/100 权重），QMT 只负责下单。中间用一份**显式契约**
（`SIGNAL_CONTRACT.md`）解耦，含 schema 精确匹配、幂等 `plan_id`、过期时间、金额守卫、
原子写、心跳六项强制校验；并设计了**不对称降级**：本地挂了，QMT 仍能独立执行价格类止损。

### 1.3 五分钟版（AI 应用/架构岗，按这个顺序讲）

**① 系统是什么（30 秒）**
面向二级市场的多 Agent AI 投研系统。18+1 个 Agent 分 5 层：数据层(4)、信息层(3)、
分析层(5)、行业层(4)、决策层(1)、审计层(1)。用 LangGraph StateGraph 做 Supervisor 编排，
分析层并行 fan-out 后汇总到 ReAct 决策，最后审计层做**哈希链**封存。

**② 我自己搭的三块基础设施（90 秒）** ← **这是架构岗的核心得分点**

| 基础设施 | 解决什么问题 | 关键设计 |
|---|---|---|
| **LLM 网关**（~800 行） | Agent 直连模型 API 会失控 | 取消令牌 → 输入截断（保头保尾）→ 两级缓存 → token 预算 → 熔断降级链，全程落审计 |
| **数据连接器路由** | 单一数据源不可靠 | 分档 TTL 缓存 → per-key lock 防击穿 → 多级降级 → **真实源全失败时宁可报缺口，绝不回退 simulated** |
| **自学习数据补充** | 缺指标要等开发者补 | LLM 生成 connector → AST 静态校验（禁 os/subprocess/eval）→ 子进程沙箱冒烟(15s) → 双通过才落库复用 |

**③ 一次真实重构（60 秒）**
集合竞价选股的判定原本散在 **4 个文件、3,853 行、329 处 `if/elif`**，
且有隐性顺序约束（"规则 6 必须先于规则 5"，改一次顺序就静默出错）。
我把它收敛成**四张声明式规则表 + 位掩码引擎**：

| 指标 | 重构前 | 重构后 |
|---|---:|---:|
| 规则可读性 | 跨 4 文件 3,853 行 | `--dump` 一张纸打印 |
| 隐性顺序耦合 | 有 | **0**（Pass1 打标签 / Pass2 否决，两遍纯函数各自同时求值） |
| 决策链路耗时 | 1231 ms | **36 ms（34×）** |
| 行为一致性 | — | 黄金回归 **564 处逐位一致** |

> ⚠️ **必须主动划清归属**："34× 这个数字**不能记在规则重构头上**。
> 拆开看：规则判定只占 **8.1 ms（0.66%）**，**1223 ms（99.3%）**是生态序列
> 每轮读三张全市场表。所以真正的优化是**把一天一变的结果挪出热路径**
> （加了 `ecology_cache`），不是优化规则本身。"
> **主动把功劳划给正确的部分，比宣称"我优化了 34 倍"可信得多。**

**④ 多租户与合规（60 秒，投金融科技/券商时重点讲）**
三层隔离：网络分区 + PostgreSQL 原生 RLS（`FORCE ROW LEVEL SECURITY`）+ 应用层查询期下推，
并且"**未登记租户列的表直接报错**"——让漏配表现为失败而不是静默无隔离。
权限四维正交：RBAC（角色）× ABAC（数据四级分档）× 信息隔离墙（研究/投资/控制三组，
跨墙需显式审批凭据留痕）× 证券名单。高权操作走 break-glass 临时提权（限时 + 双人批准 + 自动到期），
禁止自批**落在 DB 约束上**；访问审计走哈希链 + 每日锚定。

> ⚠️ 讲合规时**三个词不能写错**：
> ① 是《**证券基金**经营机构信息技术管理办法》，不是"证券期货"；
> ② "日志 6 个月"出自《**网络安全法**》第二十一条，**不是等保条款**；
> ③ 规章里**没有"双人复核"这个措辞**，强制依据是第三十二条的"**岗位相互制衡**"。
> 这三处错一个，合规背景的面试官会立刻判定"在背材料"。

## 第 2 章 · 三个岗位的差异化打法

> **同一个项目，三个岗位关心的是三件不同的事。**
> 开场先问："您更想听**策略与风控**这条线，还是**系统与工程**这条线？"
> —— 这一句就能让对方知道你做过取舍。

### 2.1 量化开发 / 量化交易员

**他们只关心两件事：这个信号能不能赚钱、风险在哪。**

| 优先讲 | 为什么 |
|---|---|
| **回撤归因方法论**（弥散失血 vs 事件性崩盘） | 显示你不是调参选手，是先归因再动手 |
| **同买点对照 + 每元交易额收益** | 基数无关指标，剔除净值路径污染。**这是量化面试里最能体现"你会不会做归因"的一招** |
| **前视偏差的处置**（熔断用当日收盘价 → 9:25 开盘价） | 90% 的人只会说"我避免了未来函数"，你能讲**修正后参数排序被改掉** |
| **可执行性审计**（一字板买不进 0 笔 / 一字跌停真卖不掉 1.2%） | 主动暴露反而加分，说明你知道回测成交假设需要单独验证 |
| **过拟合检查**（参数邻域是平台不是尖峰） | 8 个参数组合全部优于基准，但要主动说"仍不足以替代 walk-forward" |

**少讲**：多 Agent 编排、前端、多租户。这些交易员不关心。

**陷阱问题预判**：
- 「最大回撤多少？」→ **必须脱口而出 −51.11%（基准）/ −29.13%（熔断）**，别答"没算"
- 「年化才 13.81%，这也叫策略？」→ 见 [§6 Q2](#q2年化只有-1381这算好策略吗)
- 「你实盘跑了吗？」→ **诚实说没有真实资金**。纸面交易模式做了，实盘验证没做

### 2.2 AI 应用开发工程师

**他们关心：你能不能把模型/数据接进生产、出错怎么办。**

| 优先讲 | 为什么 |
|---|---|
| **LLM 网关的五道闸**（取消/截断/缓存/预算/降级） | 生产级 LLM 工程的通用语言 |
| **"真实源全失败宁可报缺口，绝不回退 simulated"** | 一句话说清 AI 系统里"数据可信度 > 可用性"的取舍 |
| **自学习数据补充的安全边界** | LLM 生成代码 → AST 校验 + 子进程沙箱。**主动说"这是子进程级隔离，不是安全容器"** |
| **降级要不对称**（按"失去这个能力有多痛"分级） | 从 QMT 双进程架构迁移过来的通用原则 |
| **幂等 + 过期**（`plan_id` 内容哈希 + `expire_at`） | 分布式动作必须防重复、防陈旧，LLM 调用同样适用 |

**少讲**：统计显著性、回撤归因（提一句就够）。

**这个岗位的独特机会**：你能讲**"数据管道 vs 模型调用"的边界**。
很多 AI 应用开发者只会调 API，你能说清"哪些环节上模型会破坏可审计性"——
比如**审计 Agent A18 是零 LLM 的**，因为审计结论必须可复算。

### 2.3 AI 应用架构师

**他们关心：技术判断力、边界划分、演进路径。**

| 优先讲 | 为什么 |
|---|---|
| **分层判断：问题该修在哪一层** | 例：补数据缺口选在**写入端**而不是展示端兜底——因为"插一行有行情无份额的记录"**正是出事的机制**，展示端兜底会掩盖它 |
| **接口命名的架构含义** | 一个字段命名歧义导致"自检永远不补数且不报错"。→ **接口契约的语义必须无歧义** |
| **能力边界要承认，然后换架构** | QMT 拿不到题材数据（缺 23.5/100 权重）→ 不硬凑权重归一化，而是**把选股挪到有数据的机器上** |
| **演进路径** | 主动说出当前方案的层次局限 + 下一步怎么走 |
| **规则的生命周期** | 13 个样本的规则不能当已验证规则；需要样本量下限 + 定期复核机制 |

**架构师会追问的、你要提前想的**：
- 「规模放大 100 倍怎么办？」→ 现在是单进程 + SQLite；仓储层已抽象，
  换 PostgreSQL 只改配置。但**真正的瓶颈不是数据库**——实测单条写入中位 10.1ms
  里 7.6ms 是 INSERT 的 fsync，读路径 1.4ms/100 只，**取数才是瓶颈**
- 「多数据源怎么保证一致性？」→ 这个项目里板块名称口径（同花顺 vs 东财代码体系）
  **零重叠**，只能按名称匹配——这是个真实的踩坑
- 「为什么本地跑 1.5B 模型而不是全用云端？」→ 规划是分类任务，本地 3-5s vs 云端 18s，
  且简单任务零 token 成本。**这是成本与延迟的取舍，不是技术炫耀**

| ③ | **收盘跌停**（收盘价 ≤ 跌停价） | 清仓 |
| ④ | 当日**收盘跌幅** ≥ 7% | 清仓 |
| ⑤ | 收盘跌破 **5 日线** | 清仓 |
| ⑥ | 持有满 **10 个交易日** | 清仓 |
| ⑦ | 收益 >10% 且当日收盘跌幅 >2% | 卖 30% |
| ⑧ | 买入次日收盘**未涨停** | 卖 50% |

**T+1 约束**：买入当日不可卖（回测里 `held <= 0` 直接 return；实盘用 `can_use_volume`）。
⑦⑧ 可在同一天叠加，作用于剩余仓位。

### 4.3 三个「反直觉」结论（**面试最有杀伤力的部分**）

**① 删掉看起来像止盈的规则⑧ → 收益从 +67% 掉到 −29.87%**

我一开始判断它是换手来源、建议删掉，**结果数据打了我的脸**。
归因后发现它的实质不是止盈，是「**T+1 未封板 = 弱势 → 减半仓**」的过滤器。
同买点对照（637 个决策点）证明：**它只对最终会亏钱的仓位起作用**（−7.58% → −4.50%），
对赚钱的仓位几乎零影响。

> **深层价值**：说明我理解「**风控规则和止盈规则在数据上长得完全不同**」——
> 止损规则永远是亏损源，止盈规则才是利润源。
> 看起来像风控的「当日收盘跌幅 ≥7% 清仓」，实测是**最强的单条规则**：
> 145 笔、**+419 万**、每元 +11.85%、胜率 69.0%——它是**移动止盈**（先大涨、某天暴跌 7% 就落袋）。

**② 接入市场情绪闸门 → 回撤反而扩大到 −67.78%**

直觉是"弱市别开仓"，实测更差。原因是**结构性的**：
**停买不阻止已有持仓继续下跌，却砍掉了"分歧转一致"这类最佳进场点。**
虽然 >5% 回撤段数从 9 段降到 4 段，但**最深的那段更深了**。

**③ 均匀降仓位 → 回撤只改善 12pt，收益崩 63pt**

| 方案 | 平均仓位 | 总收益 | 最大回撤 | Calmar |
|---|---:|---:|---:|---:|
| V3 基准 | 42.6% | +67.14% | −51.11% | 0.270 |
| 基准仓位 × 0.5 | 24.4% | **+4.40%** | −38.96% | **0.028** |
| 熔断 40日/10% | **25.5%** | **+157.01%** | −29.13% | 0.921 |

**降低仓位不是回撤控制，只是把盈亏同比缩小**——而且 Calmar 从 0.270 恶化到 0.028。

### 4.4 三张「硬牌」（现场可以展示的）

**硬牌 1：同买点对照 + 每元交易额收益**
不同配置的净值路径不同，**绝对金额归因会被基数效应污染**。所以我把归因换成两个
基数无关的口径：**每元交易额收益**，以及**同买点对照**——取两版都买过的
`(code, buy_day)` 决策点，直接比同一决策点的最终结果。637 个交集买点
让规则改动的真实效应被隔离出来。

**硬牌 2：盈亏桥精确闭合**
把 V3 → V3删T1 的 −893,281 拆成四个分量，做到**分量求和 = 实际差**逐位闭合。
这证明归因不是估算，是可验证的分解。

**硬牌 3：逐位复现验证**
在源码被并行修改的多个时间点复跑关键配置，期末净值**逐位一致**：

| 配置 | 复跑净值 |

| V3 基准（1 年） | 3,740,272.25 |
| 熔断 40/10 | 2,570,139.66 |
| 熔断 120/10 | 1,624,305.86 |

实验性项目里代码在变是常态，关键是**能不能证明哪批结果属于哪个版本**。

## 第 5 章 · 踩坑复盘（STAR 版，面试主战场）

> **「你踩过什么坑」是区分真做过和背概念的题。**
> 下面 8 个坑每个都按 **现象 → 定位 → 根因 → 修复 → 可迁移教训** 整理。
> **不要全讲**——挑 2~3 个讲透，其余留作追问弹药。
>
> 🔴 标记的是**最该讲**的（有代码位置、有数字、有反直觉结论）。

### 5.1 🔴 静默失效类（最危险：不报错，只是结果错了）

**坑 1：硬编码日期导致 4 年数据被静默跳过**

- **现象**：抓取脚本跑完只生成了 2025 年 1~3 月的文件，**没有报任何错**
- **定位**：`bt_fetch.py` 里 `prev_of` 用了 `trading_days("20250101", end)` 取上一交易日
- **根因**：所有 2025 年以前的日期都**算不出**「上一交易日」→ 被跳过，且**静默**
- **修复**：改成 `trading_days("20000101", args.end)`，并**显式打 warning**
- **可迁移教训**：**静默跳过比崩溃可怕得多**。数据管道必须统计
  「应处理 N 条 / 实际处理 M 条」，**不等就告警**。
- **代码位置**：`scripts/bt_fetch.py:158`（注释里还留着这段历史）

**坑 2：参数顺序反了导致情绪序列全空**

- **现象**：回测跑出来全市场情绪为空，**所有交易日被误标「降仓」**
- **根因**：SQL 里 `trade_date<=?` 的位置传了 `start` 而不是 `end`
- **可迁移教训**：**SQL 位置参数是类型不敏感的**——两个都是字符串，传反了不会报错。
  这类 bug 只能靠「结果合理性检查」发现，不能靠类型系统。

**坑 3：测试桩的键不匹配导致风控静默失效**

- **现象**：单只上限测试失败，但代码看起来没问题
- **根因**：真实 `Broker.positions()` 返回的键是**裸代码**（`bare(stock_code)`），
  测试桩用了带 `.SH` 后缀的键 → `pos.get(code)` 返回 `None` →
  **加仓与上限逻辑全部走 else 分支算出错误仓位，且不报错**
- **可迁移教训**：**mock 必须与真实实现同构**。这类 bug 在生产里极难发现，
  因为它是「算错了」而不是「崩了」。

### 5.2 🔴 前视偏差类（回测报告最常见的高估来源）

**坑 4：熔断用当日收盘价判断当日 9:25 能否买入** ⭐ **最该讲的一个**

- **现象**：熔断配置年化 **+91.55%**，好得可疑
- **根因**：`cur = cash + Σ(_px(day, code, "close") * shares)` ——
  买入决策发生在 **9:25**，却用**当天收盘价**算净值
- **修复**：改用**当日 9:25 开盘价**标记持仓（与 `buy()` 的成交价同源）
- **结果**：**修正后三个可比配置全部上升**（20日/10%：+58.41% → **+150.38%**；
  60日/10%：+91.55% → **+110.64%**；60日/15%：+50.22% → **+70.29%**）
- **更关键的损害**：**参数排序被改掉了**——修正前 60日/10% 看着最好，
  修正后最优变成 40日/10% 与 60日/8%，**而这两个修正前根本没跑过**
- **🎤 面试怎么讲这一条**：**不要只说"修正后变差了"（那是错的）**。要说：

  > 前视偏差的危害**不是「让结果变好」，而是「让结果不可信」**——
  > 它连参数排序都能改掉，你会据此选错参数。
  > **修正偏差不一定让数字变差，但未修正的数字一律不能用。**

**坑 5：收益基数用错（口径 bug）**

- **现象**：汇总脚本算出近 1 年总收益 **+269.64%**，引擎自己算的是 **+274.03%**
- **根因**：用 `days[0].equity` 当基数，但**第 1 天开盘就建仓了**，
  该值已是当日**收盘**净值（1,011,763），不是初始的 1,000,000
- **可迁移教训**：**统计口径必须与引擎同源**。汇总脚本不该自己重算，
  应该读引擎的 `stats`。
- **附带价值**：这个 bug 是**"口径审计"**发现的，不是"跑测试"发现的——
  说明我建立了「同一个数字只能有一个来源」的纪律。

### 5.3 性能类

**坑 6：O(n) 查询把 4 年回测拖到 110 分钟**

- **现象**：1 年回测 94 秒，4 年回测 **110 分钟**（超线性）
- **根因**：`ma()` / `prev()` / `idx()` 每次都**全表扫描 + `list.index()`**
- **修复**：预先建 `_close` 字典与 `_cal_pos` 位置索引，把这三个操作降到 **O(1)**
- **结果**：**110 分钟 → 94 秒**，并且**逐位验证**了 297 个采样点结果不变
- **🎤 面试加分点**：**优化后必须验证结果不变，否则那不是优化是改逻辑**。
  我用的是「297 个采样点逐位比对期末净值」。

### 5.4 🔴 架构设计类（最能体现架构思维）

**坑 7：心跳缺失导致执行端永远拒绝开仓** ⭐ **架构岗最该讲**

- **现象**：信号正常生成、日志全绿，但 **QMT 从不下单**
- **根因**：`--phase buy` 默认**不写心跳**（`--heartbeat-seconds` 默认 `0.0`，
  falsy）；执行端读不到新鲜心跳（>180s）就判定本地离线 → **拒绝开仓**
- **后果**：**照我自己的部署文档跑，策略永远不会交易，而且不报错**
- **修复**：产出信号后顺手写心跳 + 文档把心跳守护列为必需任务 + **加测试锁住**
- **🎤 面试怎么讲**：这是一个「**文档与实现不一致**」的缺陷，**比代码 bug 更难发现**，
  因为每一段代码单独看都是对的。
  ⚠️ **归属要说准**：它由**一次追问触发**（「只用方案 B 是什么？」），
  我为了回答去按部署文档逐步核实才暴露——**不要说成"我肉眼发现的"**。
  → 可迁移：**文档也是被测对象**；一次"按文档走一遍"的验证，
  比十个单元测试更能抓住这类缺陷。

**坑 8：卖出规则①需要的标签在下午已经拿不到了**

- **现象**：规则①（最高连板 ≥7 且盈利且竞价抢跑 → 清仓）依赖 **9:24:40~9:25**
  的竞价撮合价序列，但**卖出判定发生在 14:56**
- **修复**：早上算出持仓股的「抢跑」标签**存进 state**，下午取用；
  并把持仓一并纳入竞价采集列表
- **可迁移教训**：**分布式/分时系统里，「什么时候能拿到什么数据」是架构约束，
  不是实现细节**。

### 5.5 被测试抓出的实盘致命 bug

**坑 9：`st.get(a.code, {})` 多传参数 → 实盘 14:56 崩溃**

- **现象**：契约测试跑**卖出路径**时抛 `TypeError: State.get() takes 2 positional arguments`
- **后果**：如果没测出来，**第一天收盘卖出时就会抛异常、持仓完全没人管**
- **可迁移教训**：**卖出路径必须单独测试**。买入路径容易覆盖到，
  卖出路径往往在收盘那一刻才第一次执行。

### 5.6 可复现性工程

**坑 10：源码被并行修改导致结果跨版本**

- **现象**：发现 `result_v3_2021_2025.json`（20:08）跑在 `sources.py` 改动**之前**，

## 第 6 章 · 量化岗 FAQ

### Q1：这个策略的 alpha 来自哪里？

**答**：来自「**昨日涨停股在 9:25 竞价的结构分化**」。昨日涨停代表资金已确认的强势，
但次日竞价会出现分化——有的高开抢筹、有的低开出货。12 维打分就是在捕捉这个分化。

**关键证据**：同期候选池等权买入（9:25 买次日 9:25 卖）四年 **−99.4%**（年化 −72.68%），
策略超额年化 **+86.48%**。说明收益来自**选股与择时**，
**不是承担了池子的 beta**——**池子本身是持续失血的**。

### Q2：年化只有 13.81%，这算好策略吗？

**答**：**单看收益率不够，要看风险调整后**。夏普 0.528、Calmar 0.270 确实一般。
但这个策略的**真正问题不是收益低，是回撤大**（−51.11%，**96.8% 时间在水下**）。

所以我花最多精力的不是提高收益，是**把回撤从 −51% 压到 −29%**，
同时收益反而从 +67% 提到 +157%（Calmar 0.270 → **0.921**）。

> **这个回答的价值在于**：展示你知道「**先控风险再谈收益**」的优先级。
> 而且我**没有调参**——是先归因（发现是弥散失血 + alpha 段内消失），
> 再推导出"该用什么工具"，最后才验证。

### Q3：怎么防止过拟合？

**答**：分三层：

1. **参数平台 vs 尖峰**：熔断的 **8 个参数组合全部优于基准**
   （N = 20/40/60/90/120 在 F = 10% 下的 Calmar 分别 0.742 / **0.921** / 0.553 / 0.470 / 0.490，
   全部高于基准 0.270）→ 是**平台**不是尖峰
2. **样本外**：近 1 年窗口（完全不同的市场环境）40/10 熔断**从未触发**、
   结果与基准**逐位一致**——说明它在牛市不乱动，**这是风控该有的样子**
3. **诚实声明局限**：8 个参数是在**同一样本**上选的，
   **仍不足以替代 walk-forward**，我在报告里主动写了这一点

> **追问「那你怎么知道不是数据挖掘？」** → 讲辛普森悖论那个案例：
> 门控来自**机制解释**（国家队托底行为），不是参数搜索；而且我**保留了被门控的对照组**
> （223 条 +0.52% / 52.9%），不是只报好的一格。

### Q4：滑点和容量怎么考虑？

**答**：**这是这个项目最大的未验证风险，我如实标注了**。

回测里 **87% 的卖出是「收盘价判定 + 收盘价成交」**，这个假设**从未做过压力测试**。
所以我补了**纸面交易模式**：用真实信号 + 真实行情，把「模型以为的成交价」和
「真实可成交价」逐笔记下来，量化三件事：**未成交率、不利滑点(bp)、滑点成本占比**。

这直接回应了「限价买单在 9:30 跳空时根本买不到」这个**回测看不见的风险**。

**容量**：持仓中位 3 个交易日、单只中位占权益 20.5%、同时最多持 3 只。
标的是 40~110 亿市值段的主板股，**单笔 30% 仓位的资金规模上限受流动性约束**——
按日成交额估算，百万级资金无压力，千万级以上需要拆单。**这个我没有实测，只能说估算。**

### Q5：为什么「当日收盘跌幅 ≥7% 清仓」不能删？

**答**：这条**看起来像风控，实测是最强的单条规则**：

| 指标 | 值 |
|---|---:|
| 笔数 | 145 |
| 净盈亏 | **+419 万** |
| 每元交易额收益 | +11.85% |
| 胜率 | 69.0% |
| 相对成本涨幅中位 | +4.71% |

它是**移动止盈**——股票先大涨、某天暴跌 7% 就落袋。删掉它总收益掉 **15.4pt**。

> **深层价值**：说明我理解「**风控规则和止盈规则在数据上长得完全不同**」——
> 止损规则永远是亏损源（299 笔 −620 万），止盈规则才是利润源。
> 只看规则的名字会判断错它的作用。

### Q6：最大回撤 −51% 是怎么发生的？

**答**：它**不是一次崩盘，是一段 20 个月的弥散失血**：

- 2022-08-02 峰值 → 2024-04-02 谷底，**404 个交易日**才见底、600 天才收复
- 段内 **466 笔**交易，**笔均只亏 1,557 元**——没有任何单笔能解释它
- 根因是**选股 alpha 整体消失**：段内每元收益 **−0.872%**、胜率 35.4%；
  段外 **+0.958%**、41.7%

> **这个诊断直接决定了风控方向**：既然是弥散失血，
> 针对「市场状态」的闸门就无效（**实测确实更差，−67.78%**），
> 必须用**组合层熔断**。

### Q7：T+1 怎么处理的？

**答**：三层：

1. **回测引擎**里 `held <= 0` 直接 return（当日买入当日不可卖）
2. **实盘**用 `can_use_volume`（券商返回的可用数量）保证
3. 「持有满 10 日」按**交易日**计数，用**交易日历**算而不是自然日

### Q8：为什么选 9:25 集合竞价而不是开盘价？

**答**：三个理由：

1. **9:25 定格**：集合竞价的撮合价与量在 9:25:00 一次性确定，之后不再变——
   这是**唯一一个"可复现的盘中时点"**。用开盘价（9:30）意味着还要等 5 分钟，
   短线策略这 5 分钟就是滑点
2. **撮合价 = 日线开盘价**：我验证过 89/89 例一致，所以回测可以用日线数据近似，
   不需要分钟级数据
3. **量价信息最丰富**：9:15-9:25 的委托变化（尤其 9:24:40-9:25 的最后 20 秒）
   包含抢筹/抢跑信号，开盘后这些信息就消失了

### Q9：你的策略为什么不做空 / 不做 T+0？

**答**：A 股制度约束——**个人投资者无法做空个股**，且股票是 **T+1**。
所以策略设计必须在「只能做多 + 当日买入不可卖」的约束下工作。
这也是为什么规则⑧（买入次日未涨停卖 50%）有意义——**它是 T+1 约束下的产物**：
你无法当天纠错，只能第二天用减仓来限制风险敞口。

### Q10：如果给你 1 个亿，这个策略还能跑吗？

**答**：**不能原样跑，我没实测过容量上限**。定性判断：

- 标的市值段是 40~110 亿主板股，**竞价成交额本身有限**
- 单笔 30% 仓位意味着 3,000 万单票，需要拆单到竞价+连续竞价
- **最致命的是 9:25 撮合价成交假设**——大额买单会推动撮合价，抢掉自己的 alpha
- 熔断方案平均仓位 25.5%，持仓中位 3 天，换手高 → 冲击成本会显著侵蚀薄边

**要做的第一件事不是加钱，是加成交价压力测试**（`--fill-mode {close, next_open, close_auction}`），
这是我在报告里列为**优先级最高**的下一步。

## 第 7 章 · AI 应用开发岗 FAQ

### Q1：为什么所有 LLM 调用必须过网关，禁止 Agent 直连？

**答**：**架构红线**。直连会失去五道闸：

```
complete(tier, system, prompt)
  ├─ 取消令牌检查      调用前拦截，用户点停止后不再产生费用
  ├─ 输入截断          保头保尾（尾部是指令与 JSON schema）——不能砍掉 schema
  ├─ 两级缓存          精确 + 语义，按「模型层级 + json_mode + agent」分区
  ├─ token 预算        单任务累计超限直接拒绝，不是警告
  └─ 降级链            熔断器准入 → 主模型 → 备模型，全程落审计
```

**取消令牌放在最前面**是刻意的：**它必须在花钱之前生效**。
如果把取消检查放在调用之后，用户点了停止但请求已经发出去了——**钱已经花了**。

### Q2：怎么控制 LLM 成本？

**答**：四层：

1. **Planner 用本地 1.5B 模型**（Ollama）——规划是分类任务，
   本地 3-5s vs 云端 18s，且**简单任务零 token 成本**
2. **语义缓存**——按「模型层级 + json_mode + agent」分区，
   同层级不同 agent 的 prompt 不互相污染
3. **单任务 token 预算**——超限直接拒绝
4. **输入硬截断 + max_tokens 硬上限**——保头保尾，**尾部是指令与 JSON schema，绝不能砍**

> ⚠️ **诚实补充**：`models.yaml` 里写了定价块但**网关不读**，
> 现在只统计 token 不折钱。**成本核算链路未闭环**——这是我在 README 里主动列的已知不足。

### Q3：怎么防 LLM 幻觉？

**答**：**不声称完全解决，只做"可发现、可追溯"**：

- **时效红线**：拒绝引用过期数据（数据点带 `publish_time` / `fetch_time`）
- **审计链留痕**：每次调用记录 `prompt_hash` / `response_hash` / token / 延迟 / 降级链
- **A18 审计 Agent 零 LLM**：审计结论必须可复算，**引入模型就破坏了可审计性**
- **溯源标签**：每个数据点带 `source_url / publish_time / fetch_time / raw_content_hash`

> **这一段对 AI 岗特别加分**：它体现你理解**"哪些环节上模型会破坏可审计性"**。
> 很多 AI 应用开发者只会调 API，说不出这条边界。

### Q4：为什么用 LangGraph 而不是 AutoGen / CrewAI？

**答**：我需要**可控的 fan-out / fan-in**——分析层 5 个 Agent 并行、
再汇总到决策 Agent，我要能控制并发度与**失败边界**（某个 Agent 挂了是跳过还是整体失败）。
AutoGen 的 group chat 是黑盒，我控不了这些。

而且 LangGraph 的 StateGraph 是**显式状态机**——节点和边都在代码里，
面试官问「数据怎么流动」我可以直接指给你看。

### Q5：18 个 Agent 是不是过度设计？

**答**：**是分层职责，不是 18 个独立微服务**。三件事说明：

1. **Demo 阶段是单进程内注册**，接口无状态，保留拆成 FastAPI 微服务的路径
2. **真实跑一次不会全唤醒**——Planner 按「指标目录 + Agent 目录」挑子集
3. **分层是业务需要**：数据层(纯规则) → 信息层(去伪/抽取) → 分析层(并行推理) →
   行业层(领域知识) → 决策层(ReAct 综合) → 审计层(零 LLM)。
   这不是按"能拆就拆"拆的，是**按职责边界和是否需要 LLM** 拆的

### Q6：数据源都失败了怎么办？

**答**：**分级降级，最终宁可报缺口**：

```
请求 → 分档 TTL 缓存（月频宏观 24h / 估值 12h / 行情 4h / 实时流动性 5min）
         │ 未命中
         ↓
      per-key lock（防缓存击穿：同一 key 并发只放一个请求到远端）
         ↓
      多级数据源自动降级（任一级 DataFetchError → 下一级）
         ↓ 全失败
      宁可报"数据缺口"，绝不回退 simulated
```

> **这条"不回退模拟数据"是刻意的取舍**：假数据进了最终投研建议，
> 比"这次没数据"危险得多。代价是偶尔需要人工补数据源。

### Q7：自学习数据补充（LLM 生成采集代码）的安全边界在哪？

**答**：两道校验，**并且我明确知道它的边界**：

1. **AST 静态校验**：禁 `import os` / `subprocess` / `eval` / `exec`
2. **子进程沙箱冒烟**：15s 超时，跑通才落库注册

> ⚠️ **必须主动说**：这是**子进程级隔离，不是安全容器**。
> 只适合"半信任"的生成代码在小规模数据源上使用。
> 这一点写在 `docs/CODE_AUDIT_CHECKLIST.md` 里。
> **要真做生产，得换成容器 + 网络白名单 + 资源配额。**

### Q8：多租户隔离怎么做的？

**答**：**三层，而且让漏配表现为失败而不是静默无隔离**：

1. **网络分区**（实例级）
2. **PostgreSQL 原生 RLS**（`FORCE ROW LEVEL SECURITY`）
3. **应用层查询期下推**

关键设计：**「未登记租户列的表直接报错」**——注册表里没有这张表就拒绝查询，
而不是"查了但没加 WHERE"。**静默无隔离比报错危险得多。**

权限模型四维正交：RBAC（角色）× ABAC（数据四级分档）×
信息隔离墙（研究/投资/控制三组，跨墙需显式审批凭据留痕）× 证券名单（观察/限制）。

### Q9：怎么保证「选股逻辑只有一份实现」？

**答**：三道防线：

1. **回测复用生产代码**：`bt_run.py` 调的是生产链路的**三个同一个函数**——
   `sources.build_candidates` → `service.build_feature` → `scoring.score_candidate`，
   **一个都不重写**。回测只负责组合与撮合。
   （⚠️ 不要说成"调 `service.run_selection`"——那是另一条入口，说错会被追问穿。）
2. **执行端复用卖出规则**：`qmt_executor.py` **import** `auction_v3_qmt.py` 的 `plan_sells`，
   而不是复制一份
3. **一致性测试**：`qmt/test_parity.py` 把 QMT 移植实现与仓库规则表**逐点比对**

> **这条测试真的抓到过 bug**：我原以为「盘口适配」维度读的是预算好的比值，
> 实际仓库读**两个原始字段**自己算——测试当场报不一致，我才改对。
>
> **可现场跑**（这是你最强的一张牌）：
> ```
> python qmt/test_parity.py
> # → 打分维度 171 点全一致 / 市场周期 15,360 组全一致 /
> #    承接强度 300 组序列全一致 / 卖出规则 9 用例 + 抢筹抢跑 6 用例 + 涨停价 6 用例全通过
> ```

### Q10：纸面交易模式怎么设计的？

**答**：**只替换 broker，不改变决策链路**。

`qmt_executor.execute_buy / execute_sell` **一行不改**地被复用，
只是拿到一个 `PaperBroker`（接口与真实 `Broker` 完全一致，
唯一区别是 `_order()` 不报单、只登记待成交意向）。

**为什么这样设计**：纸面交易的价值在于验证**真实的决策路径**，
如果另写一套简化逻辑，**验证的就不是同一个东西了**。

**结算用真实行情**：买入用 **9:30 真实开盘价**判成交（开盘 > 限价 → 记 `unfilled`），
卖出用 **15:00 真实收盘价**。这样能测出「**追不上**」这个回测完全看不见的风险。

**安全性**：不连交易柜台，只用 `xtdata` 取行情，**不可能误下真单**。

## 第 8 章 · AI 应用架构师 FAQ

### Q1：为什么要拆成「信号端 + 执行端」？（架构师最爱的题）

**答**：因为一个**数据可得性的硬约束**，不是一个技术偏好。

QMT 的 `xtdata` **没有「涨停原因/题材」数据**，导致打分模型里：

| 缺失维度 | 权重 |
|---|---:|
| 题材热度 | 12 |
| 题材龙头 | 3 |
| 封流比 | 6 |
| 昨日质量的一半 | 2.5 |
| **合计** | **23.5 / 100** |

硬塞进 QMT 只能靠**权重归一化降级**（最多还原 **76.5/100**），
分数分布会变、**门槛要重标**。

**我的选择是「不勉强」**：让有完整数据的本地机器负责选股，QMT 只做它擅长的事。
这样 12 维**一个都不缺**，回测用的 **55 分门槛**（回测 v3 预设值）**可以直接沿用、
无需重标**——因为权重一个都没缺席，分数分布与回测同源。

> ⚠️ **三个门槛值别混**：生产规则表 `min_total_score` 是 **51.9**；
> **回测 v3 预设**与**实盘脚本常量**（`auction_v3_qmt.py:SCORE_THRESHOLD`）是 **55.0**。
> 说「生产门槛是 55」是错的；说「回测门槛是 51.9」也是错的。

> **架构原则**：**不要强迫一个组件做它数据上做不到的事**——
> 该换的是架构，不是参数。

### Q2：两个进程怎么解耦？

**答**：一份**显式契约**（`qmt/SIGNAL_CONTRACT.md`），不是靠口头约定：

| 设计 | 解决什么问题 |
|---|---|
| `schema` 精确匹配（`auction_v3.signal/1`） | 版本错配时**宁可拒收**也不要半懂不懂地执行 |
| `plan_id` 内容哈希 | **幂等**——QMT 重启不重复下单 |
| `expire_at` | 买入计划只活 **6 分钟**，防**隔夜陈旧信号** |
| `guards`（金额/笔数守卫） | 信号端出 bug 也不会打爆仓位 |
| 原子写（`.tmp` → `rename`） | 对端不会读到半截 JSON |
| 心跳（每 5s） | 判断本地是否在线，决定是否敢开仓 |

**核心的职责切分**：

- **买入决策 100% 在本地**（QMT 没有选股能力，收不到信号绝不开仓）
- **价格类卖出决策 100% 在 QMT**（14:56 那一刻它离行情最近，且不依赖传输）

> **这是"按能力边界切分职责"，不是"按技术层次切分"。**

### Q3：本地挂了怎么办？（★ 架构师最爱的追问）

**答**：**降级自保，而且是不对称的**：

| 能力 | 本地在线 | 本地离线（心跳 >180s） |
|---|---|---|
| 开新仓 | ✅ | ❌ **停止**（没有选股依据宁可不做） |
| 价格类止损 ②~⑦ | ✅ | ✅ **照常执行** |
| 规则①（需题材数据） | ✅ | ❌ 跳过 |

**设计理由**：本地电脑关机、断网、崩溃，**持仓依然有止损保护**。
**宁可少赚，不可失控**——这是**风险不对称**下的正确取舍。

> **可迁移到通用架构**：降级要**按"失去这个能力有多痛"分级**，而不是一刀切全停。
> 问自己两个问题：① 这个能力失效会不会造成不可逆损失？
> ② 我有没有足够的依据继续做这个动作？

### Q4：这个项目里，你做过最难的架构判断是什么？

**答**：**判断一个问题该修在哪一层**。

具体案例：ETF 份额监控发现"自检永远不补数，而且不报错"。表面看是展示层问题，
但我判断**必须修在数据层**——因为出事的机制是「**插入了一行有行情、无份额的记录**」，
在展示层兜底会**掩盖这个机制**，问题会继续产生。

另一个案例：一个字段命名歧义——
`etf_share_coverage["ratio"]` 里的 `ratio` 既可能是"已覆盖率"也可能是"缺口比例"，
**理解反了导致自检逻辑永远判定"已覆盖"**。
→ **接口契约的语义必须无歧义**，尤其在跨模块的字典/JSON 里。

### Q5：多数据源怎么保证一致性？

**答**：两条纪律，一个真实踩坑：

**纪律 1：按交易日精确取，绝不取"最新一天"**

所有备源查询都是 `WHERE trade_date = <目标日>`。源过期时它**自然返回空** → 回退链继续往下走。
而"取最新一天"会把**陈旧数据冒充成昨日数据且毫无痕迹**——
这正是 `src/scheduler/jobs.py:415` 记的那次事故（选出来的日期是两天前的市场，
**界面上却看不出任何异常**）。

**纪律 2：有数据就不再取（短路）**

这是机制的定义，不是优化：`SourceChain.resolve()` 一旦某个源给出非 None 就返回，
后面的源**根本不会被调用**。

**真实踩坑**：板块名称口径**零重叠**——同花顺和东财是**两套完全不同的代码体系**，
只能按名称匹配，而名称又有别名/简称/带空格。所以板块映射需要人工复核表
（`configs/mainline_etf_mapping_manual.yaml`）。

### Q6：为什么启动自检而不是定时任务？

**答**：因为**启动是必经路径**。

份额数据一般在**次日 8:30** 发布，而服务通常在份额发布之后才启动。
放在启动路径上，**"启动"这个动作本身就成了检查时机**，不需要额外等待定时器。
而且启动自检失败是**可见的**（服务起不来或明确报缺），
定时任务失败可能被忽略。

> **可迁移原则**：**把校验放在必经路径上，而不是放在"希望它会被执行"的地方。**

### Q7：规模放大 100 倍怎么办？

**答**：**先说清楚现在的瓶颈在哪，再说怎么扩**：

**当前实测**：单条写入中位 **10.1 ms**，其中 **7.6 ms 是 INSERT 的 fsync**（连接只占 0.1 ms）；
读路径 **1.4 ms / 100 只**。
→ **本地库不是瓶颈，取数才是**。

**放大路径（分层说）**：

| 层 | 现状 | 放大后 |
|---|---|---|
| 存储 | 单进程 SQLite（**刻意的零依赖选择**） | 仓储层已抽象，换 PostgreSQL 只改配置；实测证明瓶颈不在 DB |
| 取数 | 分档 TTL 缓存 + per-key lock | 独立的数据质量服务 + 事件驱动的补数 |
| 计算 | 单实例实测饱和 5~6 req/s，**根因是重复计算不是核数**（实测整机 CPU 仅 6~13%） | 共享因子层 + 口径指纹缓存，**目标计算次数降 13×** |

> ⚠️ **必须主动说清**：上面标"目标"的是**设计目标，不是已实现**。
> 简历里不能写"已支撑 100 人并发"、"完成分布式改造"。
> **可以把"判断"当加分项写，但不能把"设计"说成"已实现"。**

### Q8：为什么审计 Agent 零 LLM？

**答**：因为**审计的可信度来自可复算性**。

A18 做的是哈希链完整性校验——输入相同必然输出相同，任何有随机性的组件
（哪怕 temperature=0）都引入了不可复算的可能。**审计结论必须能被第三方独立重算**，
这是"可审计"的定义。

> **这是本项目里"该不该上模型"的最清晰一条边界**：
> **凡是结论需要被独立复算的环节，都不该上模型。**

### Q9：这个项目有什么你明知道是错的、但没改的？

**答**：有三处，我主动列出来：

1. **`qmt/` 脚本的规则数落后于生产**：实盘脚本是「前置筛选 9+2 条、否决 10 条」，
   而 `src/auction_select/rulebook.py` 已经演进到「12 条 / 14 位」。
   因为 QMT 侧改动需要重新做一致性验证 + 重新标定门槛，**不能只改代码**。
2. **`bit12` / `bit13` / `bit14` 已成死规则**：因为它们依赖「昨日首板」，
   而首板在**前置筛选**就被剔掉了。保留它们只为**不重排已落库的 bit 编号**
   （位掩码已写进历史数据，重排会让旧数据解析错位）。
3. **止损在收盘判定，实际兑现 −7.8% ~ −22.3%**：跳空尾部没封住。
   建议加「开盘跳空保护」，但**没做**——因为要重新验证它会不会砍掉正常波动。

> **面试怎么讲**：主动讲技术债是加分项。**"我知道但没改，因为改的代价大于收益"**
> 比"我不知道"强，也比"我全改了"可信。

## 第 9 章 · 「项目是 AI 帮你开发的」怎么答

> ⚠️ **这一章是最关键的。** 这个问题**一定会被问到**，
> 而且问法会很刁钻：「这块是你自己写的吗？」「这个 SQL 优化你怎么想到的？」
> 「前视偏差你是怎么发现的？」

### 9.1 三条红线（千万别做）

1. ❌ **别说「都是我写的」**——一追问细节就崩，而且**诚信问题比技术问题严重得多**
2. ❌ **别贬低自己**「都是 AI 写的，我只是跑了一下」——那你来面试什么？
3. ❌ **别含糊其辞**「AI 辅助但主要是我做的」——面试官听得出来这是话术

### 9.2 推荐框架：「我是主导者，AI 是我的执行团队」

> "这个项目我是**用 AI 结对开发**的，我把它当成一个**执行力很强但需要严格验收的团队**。
> 我的价值在四个地方：
>
> **第一，我定目标和验收标准。**
> 比如我要求所有结果必须可复现，所以强制记录了**规则指纹 `rules_hash` 和源码 SHA-256**
> ——**这个要求后来真的救了场**：因为源码被并行修改过，
> 没有指纹我根本说不清哪批结果属于哪个版本。
>
> **第二，我做技术判断和取舍。**
> 举个具体例子：AI 建议删掉「次日未涨停卖 50%」这条规则，理由是它换手太高。
> **我要求先跑归因再决定**——结果删掉后收益从 +67% 掉到 **−29.87%**。
> 后来又发现它的实质不是止盈，是**弱势减仓过滤器**。
> **AI 给的是建议，采纳与否是我的判断。**
>
> **第三，我做质量把关。**
> 这里要说准：我们修掉了一处**前视偏差**——熔断用当日收盘价判断当日 9:25 能否买入。
> **它是 AI 回头审代码时提出来的，不是我用肉眼发现的。我的分量在两件事上**：
> 一是**判断它必须修**（当时那个配置年化 +91.55%，看着很漂亮，很容易放过）；
> 二是**要求做双向验证**——因为修正后有的配置变好有的变差，
> 而"有的变好"恰恰证明**未修正的数字全都不可信**。
>
> **第四，我补 AI 想不到的工程约束。**
> 比如实盘的两个进程写同一个状态文件会重复下单、
> **心跳缺失会导致执行端永远拒绝开仓**——
> 后者是**按部署文档逐步核实**才暴露的（由「只用方案 B 是什么」这个问题触发），
> 属于"每一段代码单独看都对、合起来不对"的那类缺陷。
>
> 所以我更愿意说：**我负责定义问题、判断对错、承担结果；AI 负责快速产出。
> 这个协作模式本身，可能比项目本身更能说明我的工程能力。**"

### 9.3 追问应对预案

| 追问 | 怎么答 |
|---|---|
| 「那你怎么保证 AI 写的代码是对的？」 | 三层验证：与生产规则表**逐点比对**（**171 个打分点 + 15,360 市场周期组 + 300 承接强度序列，可现场跑 `python qmt/test_parity.py`**）、契约测试（10 项）、黄金回归（564 处逐位一致）。**而且测试真的抓到过 bug** |
| 「你能独立写吗？」 | 诚实：**复杂算法的第一版我依赖 AI 更快，但 review、定位、取舍我能独立做**。举一个我自己定位的例子——SQL 位置参数传反导致情绪序列全空，**类型系统抓不到，因为两个都是字符串** |
| 「AI 写的代码你看得懂吗？」 | **现场指一段你最熟的**——比如 `bt_run.py` 的 8 条卖出规则优先级，或熔断的时点纪律，**逐行讲设计意图** |
| 「如果 AI 给你错的东西你没发现呢？」 | 承认这是真实风险，所以我**建立机制**而不是靠眼力：一致性测试、逐位复现验证、**口径审计**（那个收益基数用错的 bug 就是审计发现的，不是测试发现的） |
| 「你花了多长时间？」 | 诚实说一个区间，并说明**大部分时间花在验证和归因上，不是写代码上**——这本身就是答案 |

### 9.4 一个能加分的小技巧

**主动讲一个「AI 错了、我纠正了」的具体案例**，比讲十个「我做对了」更有说服力。
最好的三个素材（都在 [第 5 章](#第-5-章踩坑复盘star-版面试主战场)）：

1. **删规则⑧的建议被打脸**（AI 判断错，**数据纠正**）
2. **前视偏差**（AI 回头审代码提出，**我判断该修、并要求做双向验证**）
3. **心跳缺失**（AI 文档与实现不一致，**由我的追问触发核实**）

> ⚠️ **归属必须说准**：这三件事**都不是我肉眼发现的**。
> 说「都是我发现的」——一追问「你当时看的是哪一行代码」就崩。
> 正确的分量在：**我判断了该不该修、要求了怎么验证、并承担结论**。
> 完整口径见 [§9.2](#92-推荐框架我是主导者ai-是我的执行团队)。

### 10.1 🔴 三处确认的前视偏差（**必须主动说**）

> 这是 2026-09-24 一次专门的前视偏差审计的结果。
> **"你项目里有没有未来函数"是量化岗必问题**，而这一节的答法比"我做了三层防线"有力得多——
> 因为面试官只要追问"第二层具体截了什么"，就会知道你有没有真查过。

**结论分三档**：

| 层 | 判定 |
|---|---|
| **实时决策链**（竞价选股、做T实时、主回测行情侧） | ✅ **干净**——12 维日期来源逐维追到取数端，没有一处用当日收盘/最高最低/全天量 |
| **数据层 PIT**（35 因子、财务 `ann_date`、DSL 时序拒绝截面函数） | ✅ **真的做了**，有代码证据 |
| **回测工具 / 离线链路** | 🔴 **三处确认的前视偏差** |

#### ① `src/intraday/backtest.py:312-317` —— 用当日全天极值做盘中决策

```python
replay["day"] = replay["ts"].str.slice(0, 10)
for day, group in replay.groupby("day", sort=True):
    day_low[day]  = float(group["close"].astype("float64").min())
    day_high[day] = float(group["close"].astype("float64").max())   # 先算好全天极值
```

然后**逐 bar 循环**里用它（`:341` / `:353`）：

```python
if total >= action and price <= low * (1 + touch_band_pct/100):      # 回踩买
elif total <= -action and price >= high * (1 - touch_band_pct/100):  # 冲高卖
```

**为什么是未来函数**：`low`/`high` 是**当日全天** `close` 的最小/最大值。
逐 bar 回放时，09:35 那根 bar 不可能知道当日全天极值。

**后果比"偏乐观"更严重**：
- **入场只发生在当日极值附近** —— 择时近乎完美
- **止损形同虚设**：`stop_price = low*(1-stop_pct)` 恒低于当日最低收盘 →
  `price <= stop` 几乎永不成立
- **出场只发生在当日最高点附近**

**可访问性**：`POST /api/v1/intraday/backtest` 直接暴露，同文件 docstring 写着"（无未来函数）"。

> **修复方向**：`day_low/day_high` 改为随 bar 递推的 running min/max。

#### ② `moss_selector/model_trainer.py:144-147` —— 标签窗口起点早了 1 天

```python
output["_buy"] = pd.to_numeric(output["close"], errors="coerce")   # :143 尾盘买入
future_high = grouped["high"].transform(
    lambda series: series[::-1].rolling(horizon_days, min_periods=1).max()[::-1])
```

反向 rolling 的语义是 `future_high[i] = max(high[i .. i+H-1])`——**包含 i 日自身的高点**，
而买入发生在 i 日**尾盘**。docstring 自己写的定义是"**未来** H 日内 high 的最大值"，
实现比定义多含了一天。

**后果**：当天冲高 10% 后回落收平的票会被打成正样本，而这个高点在尾盘买入时已经过去了。
负样本（`:156-158` 的 `future_low`）同样问题。

> **修复方向**：窗口起点改为 `i+1`。⚠️ 改完要**重训模型**才生效。

#### ③ `src/mainline/datastore.py:1446` —— 用今天的成分股名单聚合历史每一天

```python
members = self.member_map()          # :1446 → SELECT board_code, code FROM ml_member（无日期条件，:782）

```

——**成分归属没有日期上界**。

**这条直通回测**：`ml_board_flow` → `board_flows()`（`service.py:662`）→ 六维打分资金流维度
→ `score_date_sync()` → `backtest._score_grid()`（`backtest.py:234`）。

项目**知道**这件事：`datastore.py:928-937` 注释明写"一只 2026 年才上市的票，
会被算进 2023 年的板块资金流里"。但它只修了**一个方向**（上市日期闸门，挡"当时还没上市"），

| 岗位 | 先练哪条链 |
|---|---|
| 量化 | **链 C（门控 / 统计显著性）** → 链 B（伪重复）→ 链 A |
| AI 应用开发 | **链 B（伪重复，考"你会不会改错东西"）** → 链 A → 链 C |
| AI 架构师 | **链 A（边界与失效条件）** → 链 C → 链 B |

## 附录 E · AI/Agent 层 7 条 nominal 核实项（**主动承认素材**）

> **这是"主动承认"最有价值的一块。** 面试官问"你这套 AI 架构真的落地了吗"，
> **拿出这张表比辩解十句都有用**——它证明你**核对过自己的文档**。

| # | 文档里的说法 | 实际核实结果 | 怎么答 |
|---:|---|---|---|
| 1 | "基于 MCP 协议调用工具" | **`src/` 里 `MCP` 零命中**。实际是进程内模块注册 + 统一 `BaseAgent` 接口 | "MCP 是**设计方向**，实现在进程内。我把它写在架构演进路径里，不是已完成状态" |
| 2 | "所有 Agent 必须实现统一的 `BaseAgent` 接口" | **A05/A06/A07（信息层）不继承 `BaseAgent`**，是独立实现 | "信息层三个 Agent 是先写的，没走统一基类。**我知道这是不一致**，收口它们在做 T 模块时做过一部分" |
| 3 | "18 个 Agent" vs "19 个 Agent" | `AGENTS.md` 写 18（A01-A18）；`README.md` 写 19（含 A19 代码工程师）。**另有影子 Agent**（注册表里有但无独立实现） | "**18 个专业 Agent + 1 个自学习代码工程师**。两个文档不一致，我核对时发现的" |
| 4 | "所有输出附带免责声明" | **`AgentOutput` 结构里没有 disclaimer 字段**。免责声明在 API 层/前端统一加 | "免责声明做在**出口层**而不是每个 Agent 里——集中一处比分散 19 处更不容易漏" |
| 5 | 语义缓存 | **字符 3-gram 余弦**，不是向量库 | "**轻量实现，不是向量检索**。长 prompt 下区分度会下降，要上生产得换 embedding" |

## 附录 F · 一页速查卡（考前 10 分钟只看这一页）

### 六个必须脱口而出的数字

| # | 数字 | 含义 |
|---:|---|---|
| 1 | **+13.81% / −51.11%** | 全周期年化 / 最大回撤（基准） |
| 2 | **+26.83% / −29.13% / 0.921** | 熔断方案年化 / 回撤 / Calmar |
| 3 | **969 个交易日** | 全周期（2021-09-17 ~ 2025-09-17） |
| 4 | **1231 ms → 36 ms** | 提速（并主动说 1223 ms 是生态序列，规则只占 8.1 ms） |
| 5 | **−99.4%** | 候选池等权基准（证明收益不是 beta）※ 别和基准最大回撤 −99.56% 混 |
| 6 | **−97pt** | 删掉规则⑧的代价（+67.14% → −29.87%） |

### 三个反直觉结论

1. 删掉看起来像止盈的规则⑧ → 收益腰斩（它其实是**弱势减仓过滤器**）
2. 接入市场情绪闸门 → 回撤**反而扩大到 −67.78%**（弥散失血不吃这套）
3. 均匀降仓位 → 回撤只改善 12pt，收益崩 63pt

### 一个决定性对照

| 方案 | 平均仓位 | 总收益 |
|---|---:|---:|
| 基准仓位 × 0.5 | 24.4% | +4.40% |
| 净值熔断 40日/10% | **25.5%** | **+157.01%** |

→ **alpha 来自「什么时候在场」，不是「下多大注」。**

### 三个要主动说清的边界

1. **没有真实资金实盘**（纸面交易跑了）
2. **可执行性审计的数字没有落盘佐证**（审计脚本未入库）
3. **成交价假设从未做压力测试**（87% 是收盘判定 + 收盘成交）

### 三句话定场

> ① "我负责定义问题、判断对错、承担结果；AI 负责快速产出。"
> ② "前视偏差的危害不是让结果变好，而是让结果**不可信**——它连参数排序都能改掉。"
> ③ "34× 这个数字不能记在规则重构头上，规则只占 0.66%。"
