# 长任务事故复盘：两次 LLM 成果丢失的经过与工程经验

> 场景：用 LLM 为 335 个概念板块做成分股提纯（主营业务相关度判定）。
> 全池 4225 只股票、约 4 万对 (股票, 概念)，需要 3400+ 次 LLM 调用、
> 单次约 4000 输出 token（推理层思维链）。累计浪费约 3250 次调用。
>
> 这份文档记录**两次丢失的经过、直接原因、根本原因与改进**，
> 重点是"为什么同一个错误会重复发生"以及怎么用机制而不是注意力来防住它。

---

## 一、背景：任务的成本结构

| 项 | 数值 |
|---|---:|
| 待判定股票 | 3481 ~ 3972 只（每只一次调用） |
| 单次输入 token | 平均 **738** |
| 单次输出 token | 平均 **3950**（其中最终答案是 ~100，其余是思维链） |
| 单次耗时 | 2 ~ 34 秒（随候选概念数增长） |
| 全量耗时 | **约 2 小时** |
| 全量成本 | 约 **$12** |

**关键特征：单次任务耗时以小时计、花费以十美元计、且调用结果不可重建**
（同一输入重复调用会得到不同分数，所以丢了的调用必须重花）。这类任务的第一设计约束就是**可恢复性**，而不是吞吐。

---

## 二、两次事故

### 事故一：pwsh-54（试点，30 个概念）

**经过**

- 为了让试点结果能被后续全量复用，跑之前加了 `merge_scores`（把 LLM 分数写回
  `ml_stock_theme` 缓存）——但**它只在 `run()` 的最后调用一次**。
- 任务跑到 **450/2247** 时我发现写回逻辑尚不完整，决定停掉重启以启用完整版本。
- 停掉 → 那次 `merge_scores` 从未执行 → **450 次调用的结果全部丢失**。

**直接原因**：持久化挂在"成功路径的末尾"，进程被中断就永远不会执行。

**当时的错误判断**：以为"结果在内存里、随后会写"，所以中途停止是廉价的。
实际上**内存态只存在于进程生命周期内**，而停止 = 进程结束。
不仅要补全写回内容，还要改变写回时机，修了症状还要修结构。

---

### 事故二：pwsh-59（全量重跑，3481 只）

**经过**

- **已经加了分批落盘**：每 100 只股票调用一次 `merge_scores` 写回缓存。
- LLM 阶段**完整跑完**（7053 秒，拿到 15067 个分数对）。
- 但在收尾时：

```
分批落盘失败（继续打分）：OperationalError     ← 多次
LLM 完成：拿到 15067 个分数对，耗时 7053s
Traceback ...
  merge_scores → sqlite3.OperationalError: database is locked
```

- 最终 `merge_scores` 抛异常 → **`write_pure`（真正的交付物）从未执行**。

**损失清点**

| 项 | 状态 |
|---|---|
| LLM 调用 | ✅ 成功，15067 个分数对（约 2 小时、约 $12） |
| 分批落盘已持久化 | 13082 行 / **1071 只股票** |
| 其余约 2400 只 | ❌ 丢失（只在内存） |
| `ml_member_pure`（交付物） | ❌ **完全没更新**，仍是几小时前的 29 个板块 |

**直接原因（两个，都是设计错误）**

1. **并发写同一个 SQLite 库。** 在这个任务运行期间并发启动了
   `fina_mainbz` 同步（12.5 分钟、77 万行）。SQLite 只允许**一个写者**，于是分批落盘和最终写库连续撞锁。
   ——**我在更早的一轮里已经写下"应该串行"，却在那之前就把同步并发起了。**
2. **控制流顺序反了。** `merge_scores`（**可选的缓存优化**）排在`write_pure`（**真正的交付物**）之前，且异常直接向上抛：

```python
if fresh:
    merge_scores(conn, fresh, model=tier)   # ← 这里抛异常
    ...
written = write_pure(conn, rows)            # ← 永远执行不到
```

一个可选优化摧毁了交付物。

## 三、根本原因

### 1. 把"可恢复性"当成收尾工作，而不是启动前提

两次共同点：**在启动一个以小时/美元计的任务之前，没有先把断点做好。**
- 事故一：完全没有断点。
- 事故二：有断点，但**收尾写库不在断点保护范围内**。

正确的顺序是反的：**先让"中断也能续跑"成立，再启动任务。**

### 2. 修复了症状，也要修复结构

事故一"写回的内容"，问题更是"写回的时机"。**判断一个修复是否有效，要看它是否消除了"同类中断再次发生时仍会损失"这个结构条件。**

### 3. 关键路径与非关键路径的顺序排错

`write_pure` 是交付物，`merge_scores` 是省下次钱的优化。**优化失败不该让交付物失败。** 排错顺序的代价是一次性丢掉全部成果。

### 4. 对已知约束没有强制执行

"SQLite 单写者"是我早就写进注释的知识，但**没有变成机制**
（没有进程锁、没有写队列、没有 busy_timeout）。
**写在文档里的约束不等于被执行的约束。**

### 5. 失败被记录但没有被"看见"

事故二运行中日志里其实一直有：

```
分批落盘失败（继续打分）：OperationalError
```

但我的实现是"捕获 + 继续打分"（这一点是对的），**却没有在运行中检查日志**，
也没有在落盘连续失败到一定次数时**主动告警或停止**。
于是"落盘一直在失败"这件事直到收尾抛异常才暴露。

## 四、已落地的改进（对应上面每条）

| 问题 | 改进 |
|---|---|
| 中断即全丢 | **分批落盘**：每 100 只写一次缓存（`flush_every`） |
| 缓存写失败拖垮交付物 | **调换顺序**：`write_pure` 先落库；`merge_scores` 后执行且异常只告警 |
| 撞锁即失败 | **`PRAGMA busy_timeout=30000`** + `sqlite3.connect(timeout=30)` |
| 锁竞争仍可能超时 | **写操作重试**（线性退避 5 次，只重试含 "lock" 的 `OperationalError`，其它异常原样抛出以免掩盖真问题） |
| 失败不可见 | `score_pending` 增加 `stats`：区分 `ok / empty（解析为空）/ partial（解析不全）/ error`，跑完打印并保留失败样例 |
| 断点续跑 | `build_tasks` 会跳过已缓存的对 —— **天然续跑**，重跑只花没跑过的钱 |
| 已知约束要强制执行 | （待做）长任务用**锁文件**串行化，而不是靠"我记得不要并发" |

### 断点续跑的实际效果

事故二之后重跑，日志直接显示：

```
候选池 335 个概念；已载入主营描述 6294 只、缓存主营分 24854 对
需 LLM 判定：25261 对 / 3481 只股票
```

——**1071 只已存档的被自动跳过**，不需要重花那部分钱。
这就是"断点续跑"的价值：让**下一次**中断的代价从"全部"降到"增量"。

## 五、可迁移的工程经验（面试可讲的部分）

1. **长任务的第一行代码应该是断点，不是主逻辑。**
   判据：任务耗时是否以小时计、失败是否会导致不可重建的损失。
   两个都成立时，"能不能中断续跑"是启动前置条件。

2. **持久化要挂在"持续路径"上，不能挂在"成功路径的末尾"。**
   末尾写回的失败率等于整个任务的失败率；分批写回的失败率等于单批的失败率。

3. **按关键性排序而不是按逻辑顺序排序。**
   交付物先写，优化后写，且优化失败不致命。
   自检问法："这一步失败了，用户还能拿到东西吗？"

4. **对已知的资源约束，要么机制化，要么不写。**
   知道"单写者"却靠自觉不并发，等于没有约束。机制可以是：
   `busy_timeout`、重试、进程锁、写队列。**文档不是机制。**

5. **"捕获异常并继续"必须配一个"连续失败要升级"。**
   否则容错设计会变成问题掩盖器：任务看起来在正常推进，
   实际上每一步都没落盘。计数 + 阈值告警是必要的另一半。

6. **修复的验证标准是"同类中断不再造成损失"，不是"这次跑通了"。**
   事故一补了内容也不能漏了时机。问自己："如果现在再中断一次，损失和上次一样吗？"

7. **区分"用户要求停止"与"任务失败"两条路径，但它们的持久化要求相同。**
   事故一是外部停止，事故二是内部异常 —— **损失机制完全一样**。
   所以"可恢复性"不能只针对崩溃设计，也要覆盖主动停止。

8. **金钱成本要能事前可测。** 抽样 10 次调用读出真实 `tokens_in/tokens_out`
   再外推，比拍脑袋估算可信得多。实测发现输出 token 是估算值的 4 倍思维链占 84%），**估算错了 4 倍**。

---

## 六、一句话总结

> 两次丢失的根因是同一个：**把"能恢复"当成了收尾工作，而不是启动前提。**
>
> 第一次我没有断点，没有正确的保存时机。
> 第二次断点覆盖了中途却没覆盖收尾，且被我的并发操作摧毁。
>
> 教训是：**长任务的可靠性必须由机制保证，而不是由注意力保证** ——
> 因为注意力会在"任务正在顺利推进"的错觉里失效。
