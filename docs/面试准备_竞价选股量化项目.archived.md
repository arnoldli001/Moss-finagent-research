## 第一部分：三分钟项目陈述（背熟）

### 一句话版本
> 我构建了一套 **A 股集合竞价短线选股系统**：从 9:25 集合竞价的量价特征做 12 维打分选股，
> 配套自研回测引擎做四年全周期验证，最后拆成「本地选股信号端 + QMT 执行端」双进程实盘架构。

### 三分钟版本（按这个顺序讲）

**1. 策略是什么**
在**昨日涨停股**里选。9:25 集合竞价定格后，用竞价量能、开盘位置、承接强度、题材热度等
**12 个维度加权打分**（权重和 100），加上抢筹 +4 / 大量抢筹 +5 的加分，取分数最高的 3 只，
每只约 3 成仓位。次日开始按**严格优先级的规则**择机离场（**回测引擎 8 条 / 实盘 7 条**）。

**2. 我怎么验证它（60 秒）**
自己写了回测引擎（`bt_run.py`，v1~v4 四套出场模式），**100% 复用生产选股代码**
（`build_candidates → build_feature → score_candidate`），不重写选股逻辑——
回测只负责组合与撮合。四年全周期 969 个交易日：

| | 总收益 | 年化 | 夏普 | 最大回撤 | Calmar |
|---|---:|---:|---:|---:|---:|
| V3 基准 | +67.14% | +13.81% | 0.528 | −51.11% | 0.270 |
| 加装净值熔断 | **+157.01%** | **+26.83%** | 0.950 | **−29.13%** | **0.921** |

**3. 最大的技术贡献是什么（60 秒）**
**回撤控制的方法论**。原始策略最大回撤 −51%、96.8% 的交易日在水下。
我没有直接调参，而是先做归因，发现两件事：

- 这段回撤是**20 个月的弥散失血**（466 笔交易、笔均只亏 1,557 元），不是事件性崩盘；
- 根因是**选股 alpha 在特定区间整体消失**（段内每元交易额收益 −0.872%，段外 +0.958%）。

然后**否定自己两个直觉**：均匀降仓位（回撤只改善 12pt，收益崩 63pt）、
接入市场情绪闸门（回撤反而扩大到 −67.78%）。最后找到真正有效的**组合层净值熔断**，
并且有决定性对照：

| 方案 | 平均仓位 | 总收益 |
|---|---:|---:|
| 基准仓位 × 0.5 | 24.4% | +4.40% |
| 净值熔断 40日/10% | **25.5%** | **+157.01%** |

**平均仓位几乎相同，收益差 35 倍** → 证明这个策略的 alpha 全部来自「**什么时候在场**」，
而不是「下多大注」。这个结论直接决定了风控该往哪个方向做。

**4. 工程上做了什么（30 秒）**
把 QMT 实盘拆成**信号端 + 执行端**双进程：本地跑完整 12 维选股（因为 QMT 拿不到题材数据），
QMT 只负责下单。中间用一份**显式契约**（`SIGNAL_CONTRACT.md`）解耦，含 8 条强制校验
（幂等 `plan_id`、过期时间、金额守卫等），并设计了**降级自保**：本地挂了 QMT 仍能独立执行
价格类止损。另外补了**纸面交易模式**，用真实行情验证回测里从未验证的成交价假设。

## 第三部分：踩了哪些坑（★ 面试最有价值的部分）

> 这一节请重点准备。**"你踩过什么坑"是区分真做过和背概念的题**。
> 每个坑都按「现象 → 定位 → 根因 → 修复 → 教训」准备一遍。

### 3.1 静默失效类（最危险：不报错，只是结果错了）

**坑 1：硬编码日期导致 4 年数据被静默跳过**
- 现象：抓取脚本跑完只生成了 2025 年 1~3 月的文件
- 定位：`prev_of` 用了 `trading_days("20250101", end)` 取上一交易日
- 根因：所有 2025 年以前的日期都算不出「上一交易日」→ 被跳过，且**不报错**
- 修复：改成 `trading_days("20000101", args.end)`，并**显式打 warning**
- 教训：**静默跳过比崩溃可怕得多**。数据管道必须统计「应处理 N 条 / 实际处理 M 条」，不等就告警

**坑 2：参数顺序反了导致情绪序列全空**
- 现象：回测跑出来全市场情绪为空，所有交易日被误标「降仓」
- 根因：SQL 里 `trade_date<=?` 的位置传了 `start` 而不是 `end`
- 教训：SQL 位置参数是**类型不敏感**的——两个都是字符串，传反了不会报错

**坑 3：测试桩的键不匹配导致风控静默失效**
- 现象：单只上限测试失败，但代码看起来没问题
- 根因：真实 `Broker.positions()` 返回的键是**裸代码**（`bare(stock_code)`），
  我的测试桩用了带 `.SH` 后缀的键 → `pos.get(code)` 返回 `None` →
  **加仓与上限逻辑全部走 else 分支算出错误仓位，且不报错**
- 教训：**mock 必须与真实实现同构**。这类 bug 在生产里极难发现，因为它是「算错了」而不是「崩了」

### 3.2 前视偏差类（回测报告最常见的高估来源）

**坑 4：熔断用当日收盘价判断当日 9:25 能否买入**
- 现象：熔断配置年化 +91.55%，好得可疑
- 根因：`cur = cash + Σ(_px(day, code, "close") * shares)` —— 买入决策发生在 9:25，
  却用**当天收盘价**算净值
- 修复：改用**当日 9:25 开盘价**标记持仓（与 `buy()` 的成交价同源）
- 结果：**修正后三个可比配置全部上升**（20日/10%：+58.41% → +150.38%；
  60日/10%：+91.55% → +110.64%；60日/15%：+50.22% → +70.29%）
- 更关键的损害是**参数排序被改掉**：修正前 60日/10% 看着最好，
  修正后最优变成 40日/10% 与 60日/8% —— 而这两个**修正前根本没跑过**
- **面试怎么讲这一条**：不要只说"修正后变差了"（那是错的）。要说：
  > 前视偏差的危害不是「让结果变好」，而是「让结果**不可信**」——
  > 它连参数排序都能改掉，你会据此选错参数。
  > 修正偏差不一定让数字变差，但未修正的数字一律不能用。

**坑 5：收益基数用错（口径 bug）**
- 现象：汇总脚本算出近 1 年总收益 +269.64%，引擎自己算的是 +274.03%
- 根因：用 `days[0].equity` 当基数，但**第 1 天开盘就建仓了**，
  该值已是当日**收盘**净值（1,011,763），不是初始的 1,000,000
- 教训：**统计口径必须与引擎同源**。汇总脚本不该自己重算，应该读引擎的 `stats`

### 3.3 性能类

**坑 6：O(n) 查询把 4 年回测拖到 110 分钟**
- 现象：1 年回测 94 秒，4 年回测 110 分钟（超线性）
- 根因：`ma()` / `prev()` / `idx()` 每次都全表扫描 + `list.index()`
- 修复：预先建 `_close` 字典与 `_cal_pos` 位置索引，把这三个操作降到 O(1)
- 结果：**110 分钟 → 94 秒**，并且**逐位验证**了 297 个采样点结果不变
- 面试加分点：优化后**必须验证结果不变**，否则那不是优化是改逻辑

### 3.4 工程健壮性类

**坑 7：argparse `--help` 直接崩溃**
- 现象：`python bt_run.py --help` 抛 `ValueError: unsupported format character`
- 根因：help 字符串里有未转义的 `%`，后跟中文全角引号 `」`，被 argparse 当成格式化占位符
- 教训：**`--help` 是最少被测试的代码路径**，而它恰恰是别人第一次接触你的入口

**坑 8：Excel 文件被占用导致整个导出失败**
- 现象：`PermissionError [Errno 13]`（用户开着 Excel）
- 修复：捕获后改写带时间戳的副本，**不让整个导出失败**
- 教训：交付物的写入要**降级而非失败**

**坑 9：`global` 声明位置错误（`ast.parse` 放过，`import` 抓到）**
- 现象：`ast.parse` 说语法 OK，但 `import` 抛 `SyntaxError: name used prior to global declaration`
- 教训：**`ast.parse` 只检查语法，不检查符号表语义**。轻量自检要用 `import` 而不是 `ast.parse`

**坑 10：多进程/多任务共用状态文件 → 重复下单**
- 现象：核实发现 `auction_v3_qmt.py` 与 `qmt_executor.py` 写**同一个** `auction_v3_state.json`
- 后果：两者同时 live 会导致**同一只票被买两次、仓位翻倍**
- 教训：双进程架构必须**显式定义状态归属**，并在文档里写死「不要同时运行」

### 3.5 架构设计类（这两条最能体现架构思维）

**坑 11：心跳缺失导致执行端永远拒绝开仓**
- 现象：信号正常生成、日志全绿，但 QMT 从不下单
- 根因：`--phase buy` 默认**不写心跳**；执行端读不到新鲜心跳（>180s）就判定本地离线 → 拒绝开仓
- 后果：**照我自己的部署文档跑，策略永远不会交易，而且不报错**
- 修复：产出信号后顺手写心跳 + 文档把心跳守护列为必需任务 + 加测试锁住
- **面试怎么讲**：这是一个「**文档与实现不一致**」的缺陷，比代码 bug 更难发现，
  因为每一段代码单独看都是对的。这是**按部署文档逐步核实**才暴露的（由「只用方案 B 是什么」这个问题触发）

**坑 12：卖出规则①需要的标签在下午已经拿不到了**
- 现象：规则①（最高连板≥7 且盈利且竞价抢跑 → 清仓）依赖 9:24:40~9:25 的竞价撮合价序列，
  但卖出判定发生在 14:56
- 修复：早上算出持仓股的「抢跑」标签**存进 state**，下午取用；并把持仓一并纳入竞价采集列表
- 教训：**分布式/分时系统里，「什么时候能拿到什么数据」是架构约束，不是实现细节**

### 3.6 工具链类

**坑 13：PowerShell 解析不了 15.9MB 的 JSON**
- 现象：收尾汇总循环抛 `ArgumentException`
- 定位：不是嵌套深度（只有 4 层），是**文件体积**
- 教训：脚本化处理大 JSON 用 Python，别用 PowerShell 的 `ConvertFrom-Json`

**坑 14：滑点的符号语义（买/卖相反）**
- 现象：报告把买/卖滑点混在一起统计
- 根因：买单滑点为正 = 买贵了（不利）；卖单滑点为正 = 卖高了（有利）——**语义相反**
- 后果：不区分会得出「卖出滑点很大所以很好」的荒谬结论
- 修复：方向化为「**不利滑点**」，两边可直接比较

**坑 15：源码被并行修改导致结果跨版本**
- 现象：发现 `result_v3_2021_2025.json`（20:08）跑在 `sources.py` 改动**之前**，
  而熔断结果（21:38）跑在 `service.py` 改动**之后**、`scoring.py`（21:47）**之前**
- 应对：记录规则指纹 + 源码 SHA-256，并在多个时间点**复跑关键配置做逐位对比**

| 配置 | 复跑净值 | 结论 |
|---|---:|---|
| V3 基准（4年） | 1,671,368.66 | 逐位一致 |
| V3 基准（1年） | 3,740,272.25 | 逐位一致 |
| 熔断 40/10 | 2,570,139.66 | 逐位一致 |
| 熔断 120/10 | 1,624,305.86 | 逐位一致 |

- **面试怎么讲**：这是「**可复现性工程**」。实验性项目里代码在变是常态，
  关键是你能不能**证明**哪批结果属于哪个版本

### 3.7 被测试抓出的实盘致命 bug

**坑 16：`st.get(a.code, {})` 多传参数 → 实盘 14:56 崩溃**
- 现象：契约测试跑卖出路径时抛 `TypeError: State.get() takes 2 positional arguments`
- 后果：如果没测出来，**第一天收盘卖出时就会抛异常、持仓完全没人管**
- 教训：**卖出路径必须单独测试**。买入路径容易覆盖到，卖出路径往往在收盘那一刻才第一次执行

## 第四部分：量化开发岗必答题

### Q1：这个策略的 alpha 来自哪里？
**答**：来自「**昨日涨停股在 9:25 竞价的结构分化**」。
昨日涨停代表资金已确认的强势，但次日竞价会出现分化——有的高开抢筹、有的低开出货。
12 维打分就是在捕捉这个分化。**关键证据**：同期候选池等权买入（9:25 买次日 9:25 卖）
四年 **−99.4%**（年化 −72.68%），策略超额年化 **+86.48%**。
说明收益来自选股与择时，**不是承担了池子的 beta**——池子本身是持续失血的。

### Q2：为什么年化只有 13.81%？这算好策略吗？
**答**：**单看收益率不够，要看风险调整后**。夏普 0.528、Calmar 0.270 确实一般。
但这个策略的**真正问题不是收益低，是回撤大**（−51.11%，96.8% 时间在水下）。
所以我花最多精力的不是提高收益，是**把回撤从 −51% 压到 −29%**，
同时收益反而从 +67% 提到 +157%（Calmar 0.270 → 0.921）。
**这个回答的价值在于：展示你知道「先控风险再谈收益」的优先级。**

### Q3：怎么防止过拟合？
**答**：分三层：
1. **参数平台 vs 尖峰**：熔断的 8 个参数组合**全部**优于基准
   （N=20/40/60/90/120 在 F=10% 下 Calmar 分别 0.742/0.921/0.553/0.470/0.490，
   全部高于基准 0.270）→ 是平台不是尖峰
2. **样本外**：1 年窗口（完全不同的市场环境）40/10 熔断**从未触发**、结果与基准逐位一致
   ——说明它在牛市不乱动，这是风控该有的样子
3. **诚实声明局限**：8 个参数是在同一样本上选的，**仍不足以替代 walk-forward**，
   我在报告里主动写了这一点

### Q4：滑点和容量怎么考虑？
**答**：**这是这个项目最大的未验证风险，我如实标注了**。
回测里 87% 的卖出是「收盘价判定 + 收盘价成交」，这个假设**从未做过压力测试**。
所以我补了**纸面交易模式**：用真实信号 + 真实行情，把「模型以为的成交价」和
「真实可成交价」逐笔记下来，量化三件事：**未成交率、不利滑点(bp)、滑点成本占比**。
这直接回应了「限价买单在 9:30 跳空时根本买不到」这个回测看不见的风险。

### Q5：为什么规则⑦（次日未涨停卖50%）不能删？
**答**：我一开始判断它是换手来源、建议删掉，**结果数据打了我的脸**：
删掉后总收益从 +67.14% 掉到 **−29.87%**（−97pt）。

归因后发现它的**实质不是止盈，是「T+1 未封板 = 弱势 → 减半仓」的过滤器**。
同买点对照（637 个两版都买过的决策点，每元交易额收益）：

| 子集 | 买点数 | 有规则⑦ | 无规则⑦ |
|---|---:|---:|---:|
| 触发且最终止损 | 118 | **−4.50%** | **−7.58%** |
| 触发未止损 | 248 | +1.69% | +1.81% |
| 未触发 | 271 | +1.07% | +1.01% |

**它只对最终会亏钱的仓位起作用，对赚钱的仓位几乎零影响。**
那 118 个买点最终都跌到 −5% 止损，但在止损前 T+1 已经砍掉一半仓位。

### Q6：为什么「当日收盘跌幅≥7%清仓」也不能删？
**答**：这条看起来像风控，实测是**最强的单条规则**：145 笔、**+419 万**、
每元 +11.85%、胜率 69.0%、**相对成本涨幅中位 +4.71%**。
它是**移动止盈**——股票先大涨、某天暴跌 7% 就落袋。删掉它掉 15.4pt。

**这个回答的深层价值**：说明我理解「**风控规则和止盈规则在数据上长得完全不同**」——
止损规则永远是亏损源（299 笔 −620 万），止盈规则才是利润源。

### Q7：最大回撤 −51% 是怎么发生的？
**答**：它**不是一次崩盘，是一段 20 个月的弥散失血**：
2022-08-02 峰值 → 2024-04-02 谷底，404 天才见底、600 天才收复。
段内 466 笔交易，**笔均只亏 1,557 元**——没有任何单笔能解释它。
根因是**选股 alpha 整体消失**：段内每元收益 −0.872%、胜率 35.4%；
段外 +0.958%、41.7%。逐年每元收益：2021 **+2.99%** → 2022 **−0.54%** →
2023 **+0.06%** → 2024 **+1.23%** → 2025 **−0.06%**。

**这个诊断直接决定了风控方向**：既然是弥散失血，
针对「市场状态」的闸门就无效（实测确实更差），必须用**组合层熔断**。

### Q8：T+1 怎么处理的？
**答**：回测引擎里 `held <= 0` 直接 return（当日买入当日不可卖）；
实盘用 `can_use_volume` 保证。同时「持有满 10 日」是按**交易日**计数，
用交易日历算而不是自然日。

## 第五部分：AI 应用开发 / 架构师必答题

### Q1：为什么把 QMT 拆成信号端 + 执行端？
**答**：因为一个**数据可得性的硬约束**：QMT 的 `xtdata` **没有「涨停原因/题材」数据**，
导致打分模型里 **题材热度 12 + 题材龙头 3 + 封流比 6 + 昨日质量一半 2.5 = 23.5/100 权重**算不出来。
硬塞进 QMT 只能靠权重归一化降级，分数分布会变、门槛要重标。

**我的选择是「不勉强」**：让有完整数据的本地机器负责选股，QMT 只做它擅长的事。
这样 12 维**一个都不缺**，回测的 **55 分门槛**（回测 v3 预设值）**直接沿用、无需重标**。

> ⚠️ **三个门槛值别混**：生产规则表 `min_total_score` 是 **51.9**；
> 回测 v3 预设与实盘脚本常量是 **55.0**。说「生产门槛 55」是错的。

### Q2：两个进程怎么解耦？
**答**：一份**显式契约**（`SIGNAL_CONTRACT.md`），不是靠口头约定。核心设计：

| 设计 | 解决什么问题 |
|---|---|
| `schema` 精确匹配（`auction_v3.signal/1`） | 版本错配时**宁可拒收**也不要半懂不懂地执行 |
| `plan_id` 内容哈希 | **幂等**——QMT 重启不重复下单 |
| `expire_at` | 买入计划只活 6 分钟，防**隔夜陈旧信号** |
| `guards`（金额/笔数守卫） | 信号端出 bug 也不会打爆仓位 |
| 原子写（`.tmp` → `rename`） | 对端不会读到半截 JSON |
| 心跳 | 判断本地是否在线，决定是否敢开仓 |

**架构原则**：**买入决策 100% 在本地**（QMT 没选股能力，收不到信号绝不开仓）；
**价格类卖出决策 100% 在 QMT**（14:56 那一刻它离行情最近，且不依赖传输）。

### Q3：本地挂了怎么办？（★ 架构师最爱的题）
**答**：**降级自保**，而且是不对称的：

| 能力 | 本地在线 | 本地离线（心跳 >180s） |
|---|---|---|
| 开新仓 | ✅ | ❌ **停止**（没有选股依据宁可不做） |
| 价格类止损 ②-⑦ | ✅ | ✅ **照常执行** |
| 规则①（需题材数据） | ✅ | ❌ 跳过 |

**设计理由**：本地电脑关机、断网、崩溃，**持仓依然有止损保护**。
宁可少赚，不可失控。这是**风险不对称**下的正确取舍。

### Q4：怎么保证选股逻辑「只有一份实现」？
**答**：三道防线：
1. **回测复用生产代码**：`bt_run.py` 调 `service.run_selection` 的同一套函数，不重写
2. **执行端复用卖出规则**：`qmt_executor.py` **import** `auction_v3_qmt.py` 的 `plan_sells`，
   而不是复制一份
3. **一致性测试**：`test_parity.py` 把我的移植实现与仓库规则表**逐点比对**
   （171 个打分点 + 15,360 组市场周期 + 300 组承接强度序列）

**这条测试真的抓到过 bug**：我原以为「盘口适配」维度读的是预算好的比值，
实际仓库读**两个原始字段**自己算——测试当场报不一致，我才改对。

### Q5：纸面交易模式怎么设计的？
**答**：**只替换 broker，不改变决策链路**。
`qmt_executor.execute_buy / execute_sell` **一行不改**地被复用，
只是拿到一个 `PaperBroker`（接口与真实 `Broker` 完全一致，
唯一区别是 `_order()` 不报单、只登记待成交意向）。

**为什么这样设计**：纸面交易的价值在于验证**真实的决策路径**，
如果另写一套简化逻辑，验证的就不是同一个东西了。

**结算用真实行情**：买入用 **9:30 真实开盘价**判成交（开盘 > 限价 → 记 `unfilled`），
卖出用 **15:00 真实收盘价**。这样能测出「**追不上**」这个回测完全看不见的风险。

**安全性**：不连交易柜台，只用 `xtdata` 取行情，**不可能误下真单**。

### Q6：这对 AI 应用架构有什么可迁移的经验？
**答**：四条：
1. **契约优先**：多组件系统的耦合面要显式化、版本化、可校验，而不是靠约定
2. **幂等 + 过期**：分布式动作必须防重复、防陈旧（LLM 调用同样适用）
3. **降级要不对称**：按「失去这个能力有多痛」分级，而不是一刀切全停
4. **能力边界要承认**：QMT 拿不到题材数据 → 不是硬凑，而是**换架构**。
   这对应到 AI 系统里就是：**不要强迫一个组件做它数据上做不到的事**

## 第六部分：「项目是 AI 帮你开发的」怎么答（★ 最关键）

### 先接受现实
这个问题**一定会被问到**，而且问到的方式会很刁钻：「这块是你自己写的吗？」
「这个 SQL 优化你怎么想到的？」「前视偏差你是怎么发现的？」

### 三条红线（千万别做）
1. **别说「都是我写的」** —— 一追问细节就崩，而且诚信问题比技术问题严重得多
2. **别贬低自己**「都是 AI 写的，我只是跑了一下」—— 那你来面试什么？
3. **别含糊其辞**「AI 辅助但主要是我做的」—— 面试官听得出来这是话术

### 推荐框架：**「我是主导者，AI 是我的执行团队」**

> "这个项目我是**用 AI 结对开发**的，我把它当成一个执行力很强但**需要严格验收**的团队。
> 我的价值在四个地方：
>
> **第一，我定目标和验收标准。** 比如我要求所有结果必须可复现，
> 所以强制记录了规则指纹和源码哈希——**这个要求后来真的救了场**，
> 因为源码被并行修改过，没有指纹我根本说不清哪批结果属于哪个版本。
>
> **第二，我做技术判断和取舍。** 举个具体例子：AI 建议删掉「次日未涨停卖50%」这条规则，
> 理由是它换手太高。**我要求先跑归因再决定**——结果删掉后收益从 +67% 掉到 −30%。
> 后来又发现它的实质不是止盈，是弱势减仓过滤器。
> **AI 给的是建议，采纳与否是我的判断。**
>
> **第三，我做质量把关。** 我推动修掉了一处**前视偏差**——它由 AI 回头审代码时
> 提出，**由我判断它必须修、并要求做双向验证**——
> 熔断用当日收盘价判断当日 9:25 能否买入。这个 bug 让结果虚高。
> 修完我还要求做**双向验证**，因为修正后有的配置变好有的变差，
> 这恰恰说明未修正的数字全都不可信。
>
> **第四，我补 AI 想不到的工程约束。** 比如实盘的两个进程写同一个状态文件会重复下单、
> 心跳缺失会导致执行端永远拒绝开仓——**这些是我逐条核实部署文档才发现的**。
>
> 所以我更愿意说：**我负责定义问题、判断对错、承担结果；AI 负责快速产出。
> 这个协作模式本身，可能比项目本身更能说明我的工程能力。**"

### 追问应对预案

| 追问 | 怎么答 |
|---|---|
| 「那你怎么保证 AI 写的代码是对的？」 | 三层验证：与生产规则表**逐点比对**（171 个点）、契约测试（10 项）、端到端联通测试。**而且测试真的抓到过 bug** |
| 「你能独立写吗？」 | 诚实：**复杂算法的第一版我依赖 AI 更快，但 review、定位、取舍我能独立做**。举一个我自己定位的例子（比如 SQL 参数顺序反了导致情绪全空） |
| 「AI 写的代码你看得懂吗？」 | 现场指一段你最熟的（比如 `plan_sells` 的 8 条优先级、或熔断的时点纪律），**逐行讲设计意图** |
| 「如果 AI 给你错的东西你没发现呢？」 | 承认这是真实风险，所以我**建立机制**而不是靠眼力：一致性测试、逐位复现验证、口径审计（那个 `days[0].equity` 的 bug 就是审计出来的） |

### 一个能加分的小技巧
**主动讲一个「AI 错了、我纠正了」的具体案例**，比讲十个「我做对了」更有说服力。
最好的素材就是：
- 删规则⑦的建议被打脸（AI 判断错，数据纠正）
- 前视偏差（AI 写错，我发现并修）
- 心跳缺失（AI 文档与实现不一致，我核实发现）

## 第九部分：现场可以展示的三张「硬牌」

如果面试让讲细节，**挑这三个讲，最不容易被问倒**：

**硬牌 1：同买点对照 + 每元交易额收益**
> 不同配置的净值路径不同，绝对金额归因会被**基数效应**污染。
> 所以我把归因换成两个基数无关的口径：**每元交易额收益**，
> 以及**同买点对照**——取两版都买过的 `(code, buy_day)` 决策点，
> 直接比同一决策点的最终结果。637 个交集买点让规则改动的真实效应被隔离出来。

**硬牌 2：盈亏桥精确闭合**

## 二、前视偏差

**背景**：回撤控制的探索。我先否定了两条路（均匀降仓位、情绪闸门都失败），然后实现了「**组合层净值回撤熔断**」——净值跌破过去 N 日最高净值的 (1−F) 就停止开仓。

**写错的代码**：算当前净值时我用了 **`_px(day, code, "close")`（当日收盘价）**，但**买入决策发生在 9:25**。等于用当天收盘价判断当天早上能不能买。

**怎么暴露的**：我先跑了 5 个配置的扫描，其中 60日/10% 得到 **+91.55%**、看起来是最优。就在扫描还在后台跑的时候，我回头审自己的代码，发现时点不对——**主动杀掉了正在运行的作业**，改代码，重跑。

**结果**（我刚核对过，这也是我报告里写错、刚修好的地方）：

| 配置 | 修正前 | 修正后 |
|---|---:|---:|
| 20日/10% | +58.41% | **+150.38%** |
| 60日/10% | +91.55% | **+110.64%** |
| 60日/15% | +50.22% | **+70.29%** |

**三个可比配置全部上升**。所以关键不是「虚高」——**真正的损害是参数排序被改掉了**：修正前 60日/10% 看着最好，修正后最优变成 40日/10%（+157.01%）和 60日/8%（+135.48%），而这两个**修正前根本没跑过**。

**一句话总结**：前视偏差的危害不是「让结果变好」，而是「让结果**不可信**」——它连参数排序都能改掉，你会据此选错参数。

## 三个实验的结论

### 实验 A：阈值凭什么 0.55

以 324 个板块的**原始成分股**为候选空间（52,384 对）全区间扫描：

| 阈值 | 保留对 | 内部一致性 | 覆盖代价 | 效率（Δ一致性/丢1%覆盖） |
|---|---:|---:|---:|---:|
| 全保留 | 52,242 | 0.309 | — | — |
| 0.50 | 35,843 | 0.377 | 12% | 0.0014 |
| **0.55** | **30,080** | **0.397** | **16%** | **0.0013** |
| 0.60 | 22,764 | 0.419 | 24% | 0.0009 ← 开始衰减 |
| 0.65 | 16,022 | 0.438 | 30% | 0.0006 |
| 0.70 | 11,005 | 0.446（峰值） | 31% | 0.0003 ← 几乎白丢 |
| 0.75 | 7,963 | **0.431 ↓** | 28% | **负** |

**回答**：0.55 合理但偏保守；**0.65 是性价比上限**；0.70 之上收益归零；**0.75 反而有害**（成员中位只剩 14 只，统计不稳）。这是"过犹不及"的直接证据。

### 实验 B：提纯是否达成目标

```
内部一致性   0.308 → 0.397   （+29%）
一致性变好的板块   316 / 322  （98%）
变差的仅 5 个，最大 −0.023
```

**强证据**：提纯在它声称的目标上确实有效，且效果普遍。

### 实验 C：对板块信号有用吗（**最有价值**）

| 信号 | IC 均值 | ICIR | ΔICIR |
|---|---|---:|---:|
| A 价格动量 | +0.0376 → +0.0401 | +0.092 → +0.099 | +0.008 |
| **B 资金流强度** | **+0.0060 → +0.0259** | **+0.022 → +0.080** | **+0.058** |

**资金流的提升是价格动量的 7 倍以上，IC 均值提升 4.3 倍。**

原因能解释清楚：板块指数本身就是成分股聚合，噪声股票的影响已被"分摊"过一次；而**资金流是直接按成员求和的**——一只不相关的股票被计入板块资金流，就是把它的资金动作**直接混进**了信号。这正好解释了为什么主线模块第一层看资金流，而提纯对它改善最明显——两者是配套设计。

## 二、功能清单（附能拿来讲的数字）

### 1. ETF 份额监控：定位「整块空白」的根因（诊断，未改代码）

**问题**：面板上 9 只核心宽基 ETF 的份额栏**全部**显示 "—"。

**根因链条**（这是很好的一条"数据时序 vs 业务口径"故事）：
1. `fund_share`（份额）**次日 8:30** 才发布，`fund_daily`（行情）当晚就有 → 每晚 17:30 的全市场同步**必然**给最新交易日写入一批 `shares = NULL` 的行。
2. 面板锚点是 `SELECT MAX(trade_date)`，且每只 ETF **只读最后一行**。
3. 于是"最新那天份额没发布" → 该行 `shares=None` → `change_1d/5d/10d/20d` 全走 `_pct_change(None, …)` → `None` → **五列一起变 "—"**。
4. **关键点**：锚点是**一个全局日期**，不是逐只各取各自最后一天 → 所以是"**都没数据**"而不是"部分没数据"。
5. 已有的"NULL 不覆盖旧值"保护**无效**——那些行是当晚**新插入**的，没有旧值可保护。

**实测数字**：2026-09-21 17:55 那次同步落了 2138 行、只有 765 行有份额，9 只监控宽基里 **7 只**中招。全表 377/2138 缺份额是**正常**的（LOF/场外基金长期不发布份额，不在监控清单里）。

**我另外查出的两件事**（面试可当"我发现现有修复还不完整"）：
- `ml_sync` 台账里**没有任何 `etf_share` 记录** → 说明那条"启动自检补拉"的路径**在生产上从未成功执行过一次**，只有单测覆盖。
- 残留缺口：① 傍晚到次日 8:30 之间面板必然空白，且**不会回退到上一个份额齐全的交易日**（锚点写死）；② 「立即刷新」是只读路径、**不触发自检**；③ 只有"最新一天"会被回补，更早的 NULL 永不回补。

### 2. ETF 回测四张表的口径（分析 + 子代理复核）

## 三、踩过的坑（分类，这是你最该背的部分）

### A. 数据时序类
1. **T+1 发布 vs 当晚同步** → 全局锚点把整块打空（上面已述）。
2. **修复方向的选择**：`UPDATE … WHERE shares IS NULL` —— **幂等、只补不造**，绝不插入"有行情没份额"的新行（那正是当初出事的机制）。

### B. 统计学类（面试重点）
4. **样本独立性**：同一个事件连续报多日（判据是"份额 5 日累计"，而份额是**存量**）+ 同系列 4 只 ETF 同日触发 + T+34 前瞻窗口重叠 → "66 个样本"实际只有 **5 个独立事件**。

6. **达标必须看方向**：看空信号预测下跌，用"中位数 ≥ +4.5%"判 → 结构性地永久失败。
7. **冗余指标**：假阳性率 ≡ `1 − 胜率`（因为赢的定义是 `>0`），给它再设一条门槛等于把同一个条件写两遍。
8. **我自己算错过**：第一版"3 个独立时段"是错的——我用"信号日集合"当伪日历算交易日间隔，把距离放大了；改用真实主指数日历后是 **5**。**这个"自己发现并修正"的故事很加分**。

# 一、这个会话真正做了什么（可以讲的部分）

## 1. 数据新鲜度与幂等自愈（最有料的一段）

**现象**：面板"核心宽基 ETF 份额"全部空白。

**根因链**（面试时讲这条链就很值钱）：
```
份额是 T+1 发布（次日 8:30），日线当晚就有
  → 当晚的全市场同步给最新交易日写入 shares = NULL
  → 该行的 ON CONFLICT "NULL 不覆盖旧值" 保护**对新插入行无效**
  → 面板以 MAX(trade_date) 为锚点，只读最后一行
  → 份额、1/5/10/20 日变化率、对应指数分位**一起变空**
```

**关键设计判断**：
- 修法选在**数据层**而不是展示层：新增 `sync_etf_shares()` 只做 `UPDATE ... WHERE shares IS NULL`，**永不插行**——因为"插一行行情有、份额无的记录"正是出事的机制本身；
- 幂等性可证明：已有份额一个都不动，重复调用只补剩下的 NULL；
- 启动自检 + 每日作业双挂载：因为**这是每晚都会重演的时序问题**，不是一次性事故；
- **状态机区分**：`fresh` / `filled` / `unpublished` / `stale` / `offline`。把"份额还没发布"（正常时序）和"数据源挂了"（要人排查）分开报——混成一种，运维会为一个正常现象每天收到一条像故障的记录。

**可以主动说的量化细节**：自检在正常情况下 **0.03 秒、零网络请求**（缺口比例低于阈值就直接返回）。

## 2. 份额拆分/合并的识别（本会话最硬的一段）

**现象**：半导体设备 ETF 在 2026-03-30 后的三条"行业反转警示"。

**根因**：那是 **1 拆 2**——
```
价格 1.660 → 0.852   (-48.67%)
份额 1,200,859 → 2,357,118  (+96.29%)
份额×价格: 1,993,426 → 2,008,265   只差 0.74%   ← 总市值不变
```
系统把机械换股读成了"史上最大的一次申购"。

**判据设计**（三个条件同时成立，缺一会把真实申赎误判）：
1. 份额跳变 ≥15%
2. 价格**反向**跳变 ≥10%（拆分必然一涨一跌）
3. `份额比 × 价格比 ≈ 1`（市值不变）—— 这条排除"真申购 + 恰好当天大跌"

**扫全历史发现 3 次全中，且影响可量化**：

| 代码 | 日期 | 真实事件 | 系统读成 |
|---|---|---|---|
| 512100.SH | 2022-09-05 | 份额合并 -64%/+176% | 巨额赎回 |
| 159516.SZ | 2026-03-30 | 1拆2 | 巨额申购 |
| 512170.SH | 2021-02-25 | 1拆2 | 巨额申购 |

**修复效果**：1242 条信号里消失 **11 条，精确落在这 3 只上，其余 6 只一条没动**。

**"伪重复"这个坑你应该重点准备**（量化岗杀手问题）：

判据用的是**存量**指标"份额 **5 日累计** > +10%"。一次流入发生后，之后 5 天的累计值**天天超标**——同一事件连报 **5~21 天**。

```
512100.SH 风险信号    43 条 → 只有 9 个独立事件（最长连报 12 天）
159516.SZ 行业反转    41 条 → 只有 4 个独立事件（最长连报 21 天）
300 行明细 → 只有 63 个独立事件   放大约 4.8 倍
```

面试可以这样讲：**"这是伪重复（pseudo-replication）：一次事件被当成 N 个独立样本计入统计，样本量虚增。我把连续同事件合并、只保留首日并标注连报天数。"**

## 3. 门控与样本分层（这是量化岗最该讲的一段）

原始规则跑出来：582 个机会信号 **T+34 中位数 -0.04%、胜率 49.48%** —— 等于抛硬币。

按市场环境拆开，**符号完全相反**：

| 环境 | 样本 | T+34 中位数 | 胜率 |
|---|---:|---:|---:|
| 熊市 | 77 | **+8.78%** | **76.6%** |
| 牛市 | 60 | -1.53% | 36.7% |
| 震荡市 | 445 | -0.70% | 46.5% |

**这是辛普森悖论的教科书案例**——混在一起正负相抵，看起来像噪声。

加门控后（机会信号只在熊市放行）剩 66 条：**T+34 +9.18%、胜率 83.3%**，而且 **T+1 口径几乎不变（+8.90%）**——这一条是关键：说明收益**不来自信号日当天已经涨完的部分**，次日 8:30 看到数据时**还买得到**。

面试时这三个词要能顺着说出来：**分层统计 → 辛普森悖论 → 信号可交易性检验（T vs T+1 口径差）**。

## 4. 回测的"未来函数"边界（这条体现你懂回测）

```
total = len(calendar) - max_horizon     # max_horizon = 34
while cursor < total:
```

**回测明细结构上就到不了最新交易日**——因为每条记录要记 T+34 的**实际**收益，最近 34 个交易日"未来还没发生"。实测明细只到 2026-08-04，最后可评估日是 08-06。

这个设计是对的（不能算未来），但**界面上完全没提示**，用户会以为工具坏了。我在前端补了说明。

# 二、我自己踩的坑（这一段**最值得讲**，但讲法要对）

我在实现份额拆分还原时，**同一个函数写错了两次**：

**第一次：改错了对象。** 我把"拆分日及之后"的行乘以份额比，结果把真实存量又放大一倍（2,357,118 → 4,626,692）。正确做法是改**拆分日之前**的历史行。

**第二次：乘除方向反了。** 我改成"之前的行除以份额比"（得 611,790），仍然错——旧口径换算到新口径是**乘**（1,200,859 × 1.9629 = 2,357,197 ≈ 拆分日的 2,357,118）。

**为什么会连错两次**：我在**边改边测**，检测循环读的是已被修改的序列，导致同一位置被重复识别成拆分。最后把不变式写清楚才收敛：

> **份额比 s 意味着"拆分后 1 股 = 拆分前 1/s 股"。当前值必须是原始值（匹配券商），所以历史行要折算到新基准：`新基准下的历史份额 = 原始份额 × ∏(之后各拆分日的 s)`**

**面试的正确讲法**（不要说"我不小心"，要说工程方法）：
> "时序数据的变换不能靠试。我一开始调了两轮方向都不对，后来停下来先把不变式写清楚——当前行不能动（要匹配券商口径），所以历史行折算到新基准；检测必须用原始序列，不能边改边测。把不变式写进注释后一次就对了。**教训是：金额/份额这类可加量的变换，先确定基准和方向，再写代码。**"

**另一个我犯的错**：跑测试时用 PowerShell 的 `Get-Content -Raw` + `Set-Content` 做文本替换，把测试文件的 UTF-8 编码弄坏了（中文全乱码）。我用 `git checkout` 恢复后改用编辑工具重做。**这个坑很真实**：Windows 上 PowerShell 的默认编码会静默损坏 UTF-8 文件，而且 Python 会报 `invalid continuation byte` 才暴露。

**还有一个测试夹具的坑**：我造的"份额合并"夹具只让变化持续一天就恢复了（真实合并不可能第二天复原），结果测试失败在夹具上而不是代码上。**教训：夹具必须符合真实数据的形态，否则你测的是夹具自己的毛病。**

# 三、展示层的坑（AI 应用/前端岗可以讲）

| 坑 | 根因 | 修法 |
|---|---|---|
| 明细"全是 2018 年的数据" | `records[:300]` 取头部，而 records 是**从旧到新**追加的 | 取尾部 `[-300:]` **并且倒序**（前端只渲染前 200 行，顺序反了会再截错一次） |
| 同一事件连报十几行 | 判据用存量指标 | 合并连续事件，标注 `×N日` |
| 同一板块名显示两遍 | 板块的 `code` 就是 `name`（榜单层拿不到东财真代码），前端两个字段都渲染 | `code !== name` 时才补代码 |
| 自选票挤占排行榜 | 自选被塞进同一个 `stock_rank` | 分离成 `stock_watch` 单列一节，两段互斥 |
| 默认视图一屏噪声 | 1253 条里真正会告警的只有 66 条（5%） | 默认只显示"要行动的"，观察项/门控项改为主动切换 |

**共性教训**（面试可以总结成一句）：**"排序 + 截断"类 bug 的共同形态是"方向搞反"——取头部 vs 取尾部、升序 vs 降序、默认显示 vs 默认隐藏。这类 bug 不报错，只让用户看到错误的东西。**

# 二、踩过的坑（面试最值钱的部分，按"可迁移教训"归类）

## A. 静默使用旧数据（这类是投研系统的头号事故）

1. **图停在前一天：交易日历缓存把自己锁死**
   - 现象：9/23 收盘后情绪周期图最后一个点仍是 9/22；作业每 30 分钟报 `success / rows=0`。
   - 根因：`latest_complete_trade_date()` 只读**本地 `trade_cal` 缓存**，缓存末日=09-22 → 目标日恒等于 09-22 → 与水位相等 → 走「已是最新」分支。更狠的是**循环依赖**：`calendar(start,end)` 只在 `end > 缓存末日` 时才联网重拉，而这个 `end` 正是从缓存算出来的 —— **它自己解不开**。
   - 修法：用**墙上时钟**顶一次日历（`_refresh_calendar_horizon()`），把环打断；联网失败只记一句说明、按旧日历走（不猜）。
   - 教训：**"应该有的日期"不能用自己缓存里的日期去推**；判定链必须有至少一个外部时钟锚点。

2. **`index_daily` 走错入口，异常把整轮同步打断在灌库之前**
   - 现象：`失败：下载 20260922~20260923 失败 KeyError: 'index_daily'`；5 个数据集分区已下好、**仓库一行没进**。
   - 根因：作业清单按"面板会读的 8 档"列，但 `index_daily` 不在下载器的日频表里（指数是 5 个代码单独拉的，入口是 `sync_index`）；异常抛在 `_ingest_gaps()` 之前。
   - 修法：`_download_one()` 分流 + **逐档隔离**（单档失败记名继续，全失败才判 failed）。

3. **"接口没报错"不等于"数据齐了"：当天指数逐板块发布**
   - 现象：`sync_board_bars` 报 `ok / missing=[]`，但 09-23 只有 **66/138** 个板块有数据；10 分钟后重跑就 138/138。
   - 根因：每个板块都返回**非空历史**，"返回非空=成功"全部通过；上游是**逐代码先后发布当天那根 K 线**。
   - 后果：缺当天的 72 个板块**拿前一日 K 线**参与当天打分 —— 分数照出、排名照排、界面无异常。
   - 修法：按 `end` **显式校验 + 有上限重试（3 轮×20s）**，仍缺的降为 `partial` 并写明「N 个板块 {日期} 当日指数上游未发布」；打分侧再加一条 gap 明说"分数沿用上一交易日"。
   - 教训：**凡是要按某一天打分的地方，都必须显式校验那一天**；逐代码接口最容易出这种形态。

4. **面板日期 = 数据水位，不是日历**（用户第一反应永远是"刷新没生效"）
   - 定位三步法：`MAX(ml_board_bar.trade_date)` → `ml_sync` 台账 → 最后才怀疑打分/画图。

5. **"水位 / 分区 / 应该有"三者要互相比较**
   - 项目里沉淀成 `sync_gap` 四态判定（ok / need_ingest / need_download / unknown），而 `unknown` **不算已同步** ——"没发现落后"和"确认同步"必须区分。

## B. 调度与进程生命周期（分布式/在线系统通用）

6. **进程内后台任务活不过一次重启**
   - 现象：用户点刷新后报 `Failed to fetch`，且数据只同步了一半。
   - 根因：刷新跑在 API 进程的**后台线程**里，18:56/18:57 两次重启把线程带走了；前端轮询撞上连接被拒 → 浏览器抛 `TypeError: Failed to fetch`。
   - 修法：① 任务**逐数据集提交 + 逐条落账**（已完成的不白干，能续跑）；② 前端**轮询容错 8 次（≈12 秒）**；③ 任务"查不到"（`state=idle`）时判断为"后端重启过"并自动重读快照，而不是显示"还没有任务"。

7. **新增定时作业当天不会补跑**
   - `mainline_daily`（17:30）是当天 **18:06** 才注册进 `JOB_REGISTRY` 的，进程 import 时读表 → 17:30 那一刻它不存在 → 当天不跑，第一班次日。

8. **一个"永远失败的可选数据集"会暂停整个每日作业**
   - `board_crowding` 在 dev 隔离库里必然 `no such table`（表只建在生产库）→ 作业连续 3 次 failed → **自动暂停** → 连 `board_bar/board_flow` 一起停 → 表现就是"面板日期再也不动"。
   - 修法：`_MAINLINE_OPTIONAL_DATASETS` 记名但不判失败，并加测试钉住"决定打分口径的档不许进这个名单"。

9. **运行记录读错目录**：`data/scheduler/` 是 prod 的，`--env dev` 会改道到 `data/dev/scheduler/` —— 差点得出"作业根本没跑"的错误结论。

## C. 数据源与连接器语义

10. **腾讯 `fqkline` 给了区间就**不返回**当天那根未收盘 bar** → 用 curl 矩阵证明后，改成"首页 open_range + 路由 `min_date` 地板（市场时钟）"。
11. **日K 慢的真凶是链路成本不是渲染**：AkShare 陈旧一跳 0.4~0.6s + 前端强制 `refresh=true` → 加 **stale-memo 跳过（90s）** + 前端 SWR（先画缓存再补强刷），且**刷新时不清屏**。
12. **QMT 放在链首只是白等 4~5s**（终端失去权限）→ 降为链尾且默认关闭；**"配置顺序 = 默认顺序"**（健康排名样本不足时照抄配置）—— 只改开关不改顺序，它照样顶到链首。

## D. 前端与 CSS（小坑但面试官爱问细节）

## 3. 20 个坑里最该讲的 5 个

1. **`.env` 粘行**：`DEEPSEEK_API_KEY=...` 被粘在注释行尾 → dotenv 整行当注释 → reasoning 档**静默降级**到本地 8B → 打分被压扁 → 告警恒 0。教训：**"配置存在、格式合法、被解析器吃掉"最贵**，降级必须可观测。

## 核心：单票完整快照的落盘热加载

之前只有"自选概览"有落盘热加载，而用户重启后真正盯的是**当前这一只票的四面板快照** —— 它要跑完整取数链，冷进程实测 **11.1 秒**（QMT 关闭后更慢）。现在照搬同一套 stale-while-revalidate：

- `src/intraday/hot_cache.py`：新增按代码的 payload 缓存（`save/load/drop_snapshot_payload`、`PAYLOAD_VERSION`、`PayloadLoad`），原子落盘、逐代码一个文件。
- `src/intraday/service.py`：
  - 每次算完完整快照就落盘（`_remember_snapshot`）；
  - **只在"本进程还没算过这只票"时**吃它（`_snapshot_fresh_at`）—— 稳态下重复快照只要 ~3 秒，不必用旧数据糊弄已经热起来的进程；
  - 命中时**同时排一次后台真算**（`_schedule_snapshot_refresh`，单飞 + `force_refresh=True` 绕过数据源 TTL），WS/轮询随后覆盖；
  - **不伪造新鲜度**：`generated_at` / `trade_date` / `health.stale` 原样保留，另外在 `health.gaps` 写明"本面板是上次运行缓存的快照（N 分钟前），正在后台刷新"；
  - **口径指纹**（`_snapshot_fingerprint`）：权重/阈值/档位/因子参数 + 该票的板块/海外/同业绑定任一变化就作废旧快照 —— 防的正是"改了权重但分数没变"；
  - `force_refresh` / `light` / 权重预览一律**不吃也不落盘**；
  - **降级快照不落盘**（`_snapshot_is_worth_caching`）：落盘的是下次启动的首帧，空图不许占首屏。
