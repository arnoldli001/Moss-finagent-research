## 2. 做过什么功能（按可讲深度排序）

### 2.1 量化选股（可讲：模型分档 + 工程隔离）

| 项 | 内容 |
|---|---|
| 模型 | LightGBM 分档模型，按**流通市值分 3 档**：`20-150亿` / `150-500亿` / `500亿+` |
| 特征 | 26 个因子（动量、反转、量价、估值分位等） |
| 输出 | 全市场打分后**按分数取 Top 10**（不是设固定阈值，阈值模式 `none` + `min_score` 兜底） |
| 实测 | 790 只打分、选出 10 只、**28.77 秒** |
| 前端 | 结果表：居中 + 全表格线；去掉「用到模型档」「归类板块」两列；新增「当日涨跌幅」与「个股消息」（东财搜索 API，5 分钟 TTL 缓存 + 线程池批量） |

**可讲的架构点**：
- 选股跑在**短生命周期子进程**里（不是服务进程内）——理由见 §3.1，这是本会话最有价值的工程决策；
- 结果落 SQLite（`SelectionItem`），列可增量扩展（`_ADDABLE` 映射做迁移）；
- 模型缺失时**自动补训**（子进程跑训练流水线）+ 手动重试按钮。

### 2.2 涨停事件量价回测（可讲：严谨的口径定义）

用本地 15GB 仓库做了 4 组统计（都产出 xlsx + markdown）：

- **6 年样本**（2020-09-18 ~ 2026-09-17），**77,105 个有效涨停事件**，事件日流通市值 ≥ 25 亿；
- 涨停判定：`close == stk_limit.up_limit`（不是"涨幅 ≥ 9.9%"这种近似）；
- 竞价涨幅：`next_open / 涨停日 close − 1`（9:25 集合竞价结束价 = 当日 open）；
- 停牌样本剔除并**如实报告剔除数量**（不做静默丢弃）。

**核心结论（面试可以直接报数）**：

| 指标 | 概率 |
|---|---|
| 涨停次日竞价涨幅 > 1% | **56.16%** |
| 涨停次日收盘涨幅 > 1% | 52.89% |
| 连续两日涨停 | 22.92% |

按连板数拆分（恰好 n 板 → 次日竞价 > 1% / 次日收盘 > 1%）：
`1→46.44%/40.52%`，`2→49.95%/33.63%`，`3→51.60%/30.27%`，
`4→51.01%/27.69%`，`5→48.10%/24.38%`，`6→55.88%/26.47%`，`7→49.24%/16.67%`。

**竞价涨幅分 10 档的分布**：`> 5%` 的概率从 1 连板的 9.9% 升到 7 连板的 29.0%；
`≤ −5%`（大幅低开）从 2.1% 升到 18.9%。

> **这段话的杀伤力**：你在说「连板数越高，竞价溢价越强、但收盘胜率越低」——
> 这是**接力资金行为**的直接证据，能自然引到"为什么高板不适合做 T"。

### 2.3 做 T 辅助（可讲：AI + 量化的产品化）

### 2.4 全市场量能预测（可讲：算法选型 + 数据源攻坚）

**需求**：「盘中给出沪深京三市全天预测量能，低于 2 万亿或比昨日缩量 1000 亿以上 → 不追高」

**算法选型（这是重点）**：

- ❌ 项目里原有的做法：`全天预测量 = 当前累计 ÷ 已交易时间占比`
  → 我否掉了，因为 A 股日内量能是 **U 型**，早盘一小时常占全天 25~30%，
  却只占交易时长 12.5%，**早盘会系统性高估两三倍**。
- ✅ 改成**同一时刻同比**（与开盘啦 `MarketCapacity` 同源）：
  ```
  预测量能 = 昨日全天成交额 × (今日当前累计额 ÷ 昨日同一时刻累计额)
  ```
  分子分母取同一天的同一时刻，**U 型分布被完全约掉**。

**实测稳定性（这条最能打）**：

| 时点 | 沪市预测全天 | 相对昨日 |
|---|---|---|
| 10:30 | 8,060 亿 | 缩量 2,020 亿 |
| 11:30 | 8,137 亿 | 缩量 1,942 亿 |
| 14:00 | 8,159 亿 | 缩量 1,921 亿 |
| 14:50 | 8,274 亿 | 缩量 1,806 亿 |

**10:30 到 14:50 只漂移约 2%** —— 这就是"开盘 5 分钟就能推"的量化依据。

**数据源攻坚**：腾讯 `day/query` 一次请求返回**最近 5 天、每天 242 个点**的累计成交额曲线
（`"0930 3951.37 3982082 6255472603.00"` = 时刻/价/累计量/累计额），
今日与昨日曲线在同一份响应里 → 不用为"昨日同时刻"再打一次网络，且两个口径同源。

## 3. 踩过的坑（面试主战场，建议每个都准备 STAR）

### 3.1 【最强故事】LightGBM 在长驻进程里段错误 → 用子进程隔离

**现象**：点选股**没有任何输出**，无异常、无报错、耗时正常。

**排查**：789 只票**全部**失败，异常是
`OSError: exception: access violation reading 0x0000000000000000`，
发生在 `LGBM_BoosterPredictForMat`。同一份代码/数据在独立脚本里跑完全正常。

**定位**：服务进程内是 `asyncio.to_thread` 的工作线程 + 满负荷后台任务同时跑，
LightGBM 自带的 OpenMP 与进程内其它原生库/线程池在**多线程预测**下崩溃。
是原生运行时问题，不是特征或模型问题。

**修法（两层）**：
1. **执行隔离**：选股跑在短生命周期子进程（`quant_select_worker` / `runner`），
   进程退出即释放原生状态；
2. **降线程**：LightGBM `num_threads=1` 让它走串行分支，绕开 OpenMP 交互
   （789 行串行预测亚秒级，代价可忽略）。

**面试可延伸**：进程隔离 vs 线程隔离、GIL 与原生扩展、`fork` vs `spawn`、
为什么"脚本能跑、服务里不能跑"是经典的**状态泄漏**信号。

### 3.2 【强故事】静默失败：日志级别选错让 bug 隐身

**现象**：同 3.1，但一开始**连异常都看不到**。

**根因**：`score_stocks_multi` 的逐行失败记在 `debug` 级别，
而 `moss_selector` 这个 logger 在 `main.py` 里 `propagate=False` 且只在那里装了 handler
→ 服务进程里**根本没有 handler → 日志被丢弃**。

**修法**：改成 `warning` + `exc_info` + **失败分布汇总**（不只是第一条），
并挂一个诊断文件 handler（`data/run/quant_select_diag.log`）。

**面试可延伸**：为什么"没有日志"和"没有异常"是两件事；
可观测性要在**跨进程/跨 logger 边界**上验证，而不是假设它会冒出来。

### 3.3 【强故事】"模型又丢了" —— 缺依赖伪装成文件丢失（本会话最后一个坑）

**现象**：界面报「`moss_selector/models` 下没有可用的模型文件；已自动开始训练」，
但目录里 6 个 `.joblib` 都在。

**排查路径（这段讲出来很有说服力）**：
1. 先看错误文案的**精确措辞**：是「没有**可用**的模型文件」而不是「没有模型文件」
   → 读源码发现前者在 **glob 找到了文件、但每个都加载失败被跳过** 时才抛
   → **立刻排除了"文件不存在"**，指向"加载失败"；
2. 复现：6 个模型全部抛 `ModuleNotFoundError: No module named 'lightgbm'`
   —— `joblib.load` 在 `pickle.find_class` 阶段要 `import lightgbm`；
3. 查环境：服务跑在**系统 Python 3.13**（`C:\veighna_studio`，无 lightgbm），
   而项目 `.venv`（Python 3.12）里 lightgbm 4.7.0 + sklearn 1.9.1 都在；
4. 交叉验证：翻训练日志，成功那次的路径是 `.venv\Lib\site-packages\lightgbm\sklearn.py`
   → 证实历史训练用的是 venv。

**修法**：用 venv 解释器启动 → 模型立即恢复（790 只打分、选出 10 只）。
另在 `manage.py` 启动自检里加**依赖探测**：缺 lightgbm 就**拒绝启动**并打印修法，
而不是让它伪装成"模型丢失 → 自动重训"。

**面试可延伸**：这是"**让漏配表现为失败**"原则的实例 ——
能静默降级的错误，最终都会以**误导性症状**的形式还回来，排查成本远高于启动即失败。

### 3.4 【强故事】假成功：命令"成功"了，其实什么都没发生

**现象**：我连续重启了三次后端，但界面行为一直像旧代码。日志里 grep 新加的字段
一个都没有。

**根因**：重启命令写成 `python manage.py start ... | Select-Object -First 1`，
PowerShell 的管道被 `-First` 提前关闭 → **进程被提前掐断**，
`--replace` 的"停止旧实例"那一步没执行完 → **旧进程一直占着 8100 端口**。

**修法**：去掉管道截断，或 `| Out-String | Write-Output`。
并且**用事实校验**：比对 `Get-Process` 的 `StartTime` 是否真的变了、
`Get-CimInstance` 看监听进程的 `ExecutablePath`。

**面试可延伸**：**永远不要用命令的退出码代替事实校验**。
"部署成功"和"代码生效"是两件事，要有独立的验证手段（版本号/时间戳/行为探针）。

### 3.5 数据源不可靠（量化岗最爱问，你有一手材料）

| 坑 | 现象 | 处理 |
|---|---|---|
| 东财 TLS SNI 阻断 | `push2*.eastmoney.com` 握手后立即断连，**会漂移**（时通时断） | 项目自带 `MOSS_EM_DIRECT=1` 直连 IP + Host 头绕行；但阻断漂移导致绕行也救不回来 → **东财只能当链尾备用，不能当主源** |
| 腾讯指数接口不支持 `899xxx` | 北证50 直接抛"暂支持 000xxx/399xxx/880xxx" | 北交所单独走一跳 |
| 北交所拿不到日内成交额 | `day/query` 只返回当日一天、且它的点连成交额字段都没有；`fqkline` 只有一行；快照只有今日 —— **三条路都缺一环** | **如实排除并写清原因**，不用三层折算凑一个"看起来完整"的三市数（京市占全市场约 1%，对 2 万亿地板/1000 亿阈值无影响） |
| 东财单指数口径歧义 | `quant_index_daily` 里深证成指 amount 是真实深市的**正好一半**（5,686 亿 vs 逐股求和 11,275 亿）→ 不可用 | 改用实时接口；并对表验证沪指口径（10,079.96 亿 vs 逐股求和 10,078.48 亿，吻合 0.015%） |

**这一段的价值**：证明你有「**先验证口径，再写代码**」的习惯，
而不是拿到一个字段就往公式里代。面试官问"你怎么保证数据可靠"，
这几个例子比我泛泛而谈强得多。

### 3.6 量化口径的坑（量化岗必问）

- **`shift(1)` 用在单日截面上**：当日涨跌幅一开始全是 NaN ——
  因为 `shift(1)` 需要多日面板，单日截面没有"上一行"。
  → 改成在**多日 panel** 上 `groupby(code)` 再 `shift(1)`。
- **连板段长度算错**：
  `groupby(code)["is_up"].transform("sum")` 把**一只票整个历史上的涨停日**当成段长
  （求和 2.61 亿、只有 309 段，显然荒谬）。
  → 正确做法：先 `run_key = (~is_up).cumsum()` 造段号，再
  `groupby(run_key)["is_up"].transform("sum")` → **80,069 段**；
  并用 `pos_in_run >= run_len` 排除窗口边缘不完整的段。
- **涨停判定用手册口径**：`close == stk_limit.up_limit`，
  而不是"涨幅 ≥ 9.9%"——后者会把 20% 涨跌幅的创业板/科创板股票和 ST 股搞错。
- **前复权 vs 不复权**：涨停判定必须用**不复权**价（复权会破坏 `close == up_limit`）；
  我的回测用不复权价，这一点要在面试里主动说清。

### 3.7 工程小坑（体现细节把控）

- **前端改了但浏览器没变**：`web/dist` 是**改动前**构建的产物；
  服务是从 `dist` 静态托管的 → 必须重新 build。**"代码改了"≠"产物更新了"**。
- **同一行里两枚徽标被写进同一个 CSS grid-area** → 直接叠在一起盖住了。
  改成各占一个网格单元。
- **表头 6 列、数据 7 列**：多出的"备注"列没有表头 → 用户说"很丑"。
  修法是把备注挂到徽标 `title` 上，而不是再加一个表头。
- **热缓存与字段序列化**：想把估值结论做成 `dict` 塞进热缓存，
  但热缓存的 `_to_plain` **只保留叶子类型**（str/int/float/bool/None/list），
  dict 会被**静默丢弃** → 改成两个标量字符串字段，并写测试锁住这个约束。

## 4. 面试高频问题 + 你的答案素材

### 4.1 量化岗

**Q：你的回测怎么避免未来函数？**
> 涨停判定只用当日及之前的数据；次日收益用 `next_open / close − 1`，
> 时间上严格在后。特征侧全部用因果指标（rolling / shift）。
> 做 T 的逐 bar 打分类链路还专门做了"全因果重放"。

**Q：样本量够吗？统计显著性怎么看？**
> 6 年 77,105 个事件，量级足够；但我更关注**分层样本量**——
> 比如 7 连板只有很低的比例，所以那一行的置信区间明显更宽。
> 我在报告里是按连板数分层给的概率，而不是只给一个总数。

**Q：为什么按连板数分层的概率是"先升后降"？**
> 竞价溢价随连板数上升，说明接力资金愿意给更高溢价；
> 但**次日收盘**胜率单调下降（1 板 40.5% → 7 板 16.7%），
> 说明高开之后承接不住、日内被兑现。这正好支持"高板不做 T"的风控结论。

**Q：换手率/流动性/停牌怎么处理？**
> 事件日流通市值 ≥ 25 亿做初筛；停牌样本剔除并报告数量；
> 本地仓库有 `quant_suspend_d` 表专门标记停牌。

**Q：你会怎么继续改进这个策略？**
> ① 加交易成本与冲击成本（现在只算价格收益）；
> ② 做**样本外**分段检验（不是全样本调参）；
> ③ 事件研究法看 T-5 ~ T+5 的累计异常收益，而不是只看 T+1；
> ④ 把"竞价高开幅度"做成连续因子做截面回归，而不是只做概率统计。

### 4.2 AI 应用开发岗

**Q：你的 Agent 架构怎么设计的？**
> LangGraph `StateGraph` + Supervisor 调度，18 个 Agent 分 5 层
> （数据/信息/分析/行业/决策+审计）。Agent 间标准 JSON 消息通信、
> 基于 MCP 协议调工具；Demo 阶段单进程分层（`src` layout），
> 进程内模块注册到 Supervisor，接口无状态 ——
> **保留演进为独立微服务的路径**。

**Q：LLM 调用成本怎么控制？**
> 三层：① 网关**磁盘缓存**（跨进程复用，默认 6 小时）；
> ② 内容未变则复用上次打分（跳过 LLM 调用，有 `reused_calls` 统计可验证省了多少）；
> ③ 分层模型路由 —— 轻量任务走本地 Ollama（qwen2.5:1.5b / qwen3:8b），
> 核心推理才走 DeepSeek API。

**Q：怎么保证 LLM 输出的可靠性？**
> ① LLM 只负责**信息抽取与情绪打分**这类模糊环节，数值计算全部本地确定性代码；
> ② 推理记录 `prompt_hash` + token 数，可审计；
> ③ 结构化输出 + 数值兜底（取不到就"未判定"，**绝不编造**）。

**Q：多租户隔离？**
> 数据层 PostgreSQL RLS 策略自动隔离；审计日志独立存储、不可篡改、不低于 3 年。
> 开发环境用 `--env dev` 做数据目录隔离（独立 SQLite + 调度目录 + 审计目录，
> 且禁用定时任务），避免调试实例同时写生产库。

### 4.3 架构岗

**Q：这个系统的瓶颈在哪？**
> 数据取数链路。实测：冷启动整表重算（45 只自选）约 200 秒，
> 其中单只票 3~5 秒的 pandas 计算**全压在事件循环上**，
> 事件循环被连续占用最长 36.5 秒 → 任何请求（哪怕返回静态字典）都要等几分钟。
> 修法是**限并发 + 批间让路**：每批 1~4 只、批间 `await asyncio.sleep(0)`，
> 总耗时不变但事件循环最长占用从 36.5s 降到 0.4s。

**Q：你怎么做缓存设计？**（这里你有很多可讲）
> 按数据**变化频率**分层，而不是一刀切：
> - 秒级：报价快车道（5 秒 TTL，批量 tick）
> - 分钟级：自选打分（60 秒）、分钟 K 线（45 秒）
> - 小时级：估值结论（3600 秒）、消息面情绪（600 秒）
> - 日级：全市场成交额曲线（腾讯 `day/query` 一次给 5 天）
>
> 再叠加 **stale-while-revalidate**：过期时**先给旧值、后台补新的**，
> 绝不让请求等重算。比如估值那一步冷取 42.4 秒、命中 0 秒，
> 若在 TTL 到期时同步重取，42 秒会叠加到本身 200 秒的整表重算上，
> 把报价刷新从 60 秒拖成 5 分钟。

**Q：可用性怎么保证？数据源挂了怎么办？**
> ① 多源有序路由 + **失败冷却（熔断）+ 半开重试**：
> 失败进入冷却期内不再调用（避免每次都白等超时），冷却期每隔 30 秒放行一次探测，
> 成功即立刻恢复（否则用户重开终端后最长等满 300 秒才被重新使用）；
> ② 短期记忆：某个源刚被判定"数据太旧"，90 秒内直接跳过它，不再白付延迟；
> ③ **绝不使用模拟数据** —— 取不到就如实记 `health.gaps` 并在界面列缺口。

**Q：诚实性怎么在架构上落地？**（这题答好很加分）
> 这条在项目里是**硬约束**，落地成几个具体规则：
> - 取不到数据 → 置 `None` + 记 gap，**绝不填 0 或编一个像样的值**；
> - 宁可不显示也不猜：北交所拿不到昨日同时刻额，就把它从合计里排除并写清原因，
>   而不是用"量比 × 价"凑一个看起来完整的三市数；
> - 旧值必须带时间戳（`quote_ts`），前端据此标明新鲜度，**不伪造新鲜度**。

## 5. 需要补的知识（你目前没覆盖或没深入的）

按优先级排：

1. **交易成本建模**：佣金/印花税/过户费、滑点、冲击成本（Almgren-Chriss 入门即可）、
   竞价成交概率。面试官常问"你的收益扣成本后还剩多少"。
2. **样本外与过拟合**：Walk-forward、Purged K-Fold（de Prado）、
   Deflated Sharpe Ratio、多重检验问题（你扫了很多组合就会踩）。
3. **因子评价体系**：IC / RankIC / ICIR / 分层单调性 / 因子正交化 / 市值行业中性化。
   （你已经在用 RankIC 和 AUC 了，但要注意：**AUC 0.62 在选股里是正常水平，
   不要说得像很差** —— 金融信噪比天然低。）
4. **组合优化**：均值方差、风险平价、约束优化、换手率约束。
5. **RAG 与 Agent 进阶**：检索召回评估、rerank、多 Agent 通信的失败模式、
   长上下文 vs 摘要的取舍。你的项目里 Agent 偏"流程编排"，RAG 深度可能不够。
6. **流式与异步**：WebSocket 背压、`asyncio` 与多进程结合、
   为什么 CPU 密集任务不能放事件循环（你已经踩过了，要能讲原理）。
7. **可观测性**：结构化日志、指标（延迟分位 P50/P95/P99）、链路追踪、告警阈值设计。
