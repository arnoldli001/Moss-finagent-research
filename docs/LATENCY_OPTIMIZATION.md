# 投研链路提速分析：如何做到 10 秒内出结果

> 全部数字来自本机实测（2026-09-26），可用 `scripts/latency_breakdown.py` 复现。
> 实测依据：80 个真实任务的审计日志（`data/audit/llm_audit.jsonl`，44150 条记录）
> ＋ 逐阶段 LLM 延迟采样（3 次取中位）＋ A01 逐指标实采（硬超时 25s）。

---

## 一、结论先行

| 方案 | 耗时 | 质量代价 | 能否达标 |
|---|---|---|---|
| **现状** | **63s**（审计口径中位 36.2s，p90 179s） | — | ❌ |
| **A 期：零质量损失优化** | **29.6s** | **无** | ❌ |
| **B 期：A 期 + 降推理强度** | **7.4s** | **明显下降** | ✅ |
| **C 期：渐进式渲染（推荐）** | **首屏 3s / 完整 63s** | **无** | ✅（感知） |

**核心事实：在 `effort=high` 下，只 LLM 推理就要 38 秒**
（信息层 15s + 分析层 5s + A17 18.1s）。
**只要保留完整推理深度，10 秒物理上不可能。** 所以必须选一种取舍：

- 想要**真·10 秒** → 走 B 期，接受推理质量下降
- 想要**不降质量** → 走 C 期，把"10 秒"定义成首屏可见时间

**A 期无论选哪条路都必须做** —— 它零质量损失、收益最大（-33.4s）。

## 二、耗时到底花在哪（实测分解）

```
阶段                     现状      说明
────────────────────────────────────────────────────────────────
规划                     0.8s     qwen2.5:1.5b 本地，已足够快
数据采集                 23.4s  ★ fed:rate_prob:next 等满 23.4s（外网不可达）
                                 gather 并发 → 墙钟 = 最慢那个
本地管线                  0.6s     清洗/校验/入库/流动性/审计，纯本地
信息层                   15.0s  ★ A05→A06→A07 **串行** 3 次 LLM（每次 5.0s）
分析层(并行)               5.0s     5 Agent 并行，墙钟 = 单次
A17决策                  18.1s  ★ ReAct 每任务 2.06 次 × 8.8s
────────────────────────────────────────────────────────────────
合计                     63.0s
```

### 2.1 LLM 各阶段实测延迟（这是最硬的约束）

| 阶段 | 现状 | 输出 token | `effort=none` 后 |
|---|---:|---:|---:|
| 规划层 light | 0.8s | 85 | — |
| 分析层 reasoning（`effort=high`） | **5.0s** | 2102 | **1.5s** |
| A17 decision（`effort=high`） | **8.8s** | 3322 | **2.9s** |
| A17 精简 prompt + `effort=none` | — | 255 | **3.0s** |

**关键发现：LLM 延迟几乎完全由输出 token 决定**，而输出 token 被
`reasoning_effort` 支配 —— 思维链也计入输出预算。

`reasoning_effort="none"` 让 decision 层 **29.0s → 9.5s**（3×），
输出从 3322 降到 1033。精简 prompt 后再降到 **3.0s**。

### 2.2 一个必须避免的陷阱

实测 `max_tokens=2048` 对 decision 层的结果是 **空响应**：

```
decision max_tokens=2048   18.6s  out=2049  空!
```

因为思维链先吃光预算，正文一个字都没输出。这正是 `configs/models.yaml`
里记录过的老问题（`reasoning/decision` 因此给到 8192）。
**降延迟不能靠砍 `max_tokens`，只能靠降 `reasoning_effort`。**

## 三、A 期：零质量损失优化（已实施）

### ① 数据采集走库优先 → 实测 **23.3s → 0.0s**

**根因**：路由把 5 个"实时型"指标标成 `_DB_SKIP_PREFIXES`，永远绕过数据库。
但 scheduler 已经**盘中每 5 分钟**采它们（`market_intraday_snapshot`、
`board_cyb_kcb_intraday`）—— 库里就是几分钟前的数据，却每次都重新打网络。

**改法**：新增 `_DB_REUSE_FRESH_DAYS = 1` 容忍窗口，
库里有"当天的"数据就直接用；配合已有的失败冷却与启动预探。

**实测效果**：

```
                         改造前     改造后
mkt:turnover:total       0.12s  →  0.03s   ✓库命中
mkt:turnover_rate:all_a  2.61s  →  0.01s   ✓库命中
mkt:cybkcb:spot_summary 11.96s  →  0.01s   ✓库命中
idx_val:snapshot:all     0.00s  →  0.01s   ✓库命中
────────────────────────────────────────────
13 指标 gather 墙钟      23.28s →   0.01s（预探后）
```

**这一项单独就把总耗时砍掉 23.4s，且零质量损失。**

### ② 信息层串行改并行 → 15.0s → 5.0s

`A05→A06→A07` 现在是硬串行（`g.add_edge("verify_info","extract_events")`
→ `g.add_edge("extract_events","sentiment")`），3 次 LLM × 5.0s = 15s。

三者其实**没有强制依赖**：A06 提取事件用的是原文，
A05 的可信度分数只是"前置过滤"而非必需输入。
改为并行后墙钟 = 单次 5.0s。

**代价**：A06 会看到未去伪的原文。缓解 —— A06 本来就要求输出
`evidence_quote` 且越界枚举本地归一化，A05 的分数可以在 A17 阶段
作为权重继续使用。

### ③ 给 `fed:rate_prob:next` 兜底（已实施）

外网不可达时它等满 23.4s 硬超时。已加：
- **失败冷却**（60s 内不再重试，指数退避封顶 900s）
- **启动预探**（`_warm_external_sources`，在用户到来前建立冷却）

实测：连续 5 次 fetch **117s → 23.3s**；预探后用户感知 **0.0s**。

## 四、B 期：降推理强度（能达标，但有质量代价）

### ④ `reasoning_effort` 分层调低

```python
_TIER_REASONING_EFFORT = {
    "light": "low", "medium": "low",
    "reasoning": "high",   # → "none"：5.0s → 1.5s
    "decision":  "high",   # → "none"：8.8s → 2.9s
}
```

**代价必须说清楚**：`effort=none` 让模型**不输出思维链**。
对这条链路里最需要推理深度的部分 ——
A17 的 `conflicts_resolved`（冲突仲裁）、
`expected_return_3_6m` 的三档情景 + 核心假设 + 证伪信号 ——
**质量会明显下降**。这不是"稍微差一点"，是"这类输出基本没有了"。

### ⑤ A17 收敛为单次调用

现在 `ReActExecutor(max_steps=3)`，实测每任务 2.06 次调用。
关掉 ReAct 变单次，省 3.0s，**代价是失去"主动向上游 Agent 追问"的能力**。

### B 期合计：**29.6s → 7.4s ✅**

```
数据采集          23.4s    0.1s     0.1s
本地管线           0.6s    0.6s     0.6s
信息层            15.0s    5.0s     1.5s
分析层(并行)        5.0s    5.0s     1.5s
A17决策           18.1s   18.1s     2.9s

```

## 五、C 期：渐进式渲染（推荐，零质量损失达标）

**思路：把"出结果"和"出完结果"分开。**

A01 采集完成后（<1s），系统其实已经握有**全部量化事实**：
收盘价、PE/PB 历史分位、申万行业估值截面、量能/两融/北向、涨跌家数…
这些是**确定性本地计算**，不需要 LLM。

所以：

```
T+0.8s   规划完成
T+1.0s   ★ 推送「量化快照」（本地计算，无 LLM）
           - 各指标最新值 + 历史分位 + 数据新鲜度标注
           - 行业估值截面（申万三级 PE/PB）
           - 大盘流动性（量能分层/两融/双创分项）
T+6.0s   分析层完成 → 追加各维度结论
T+24s    A17 完成 → 追加综合建议与冲突仲裁
T+25s    A18 审计封存 → 报告定稿
```

**用户 10 秒内拿到的是"可用的量化结论"，而不是转圈。**
完整报告仍在 25-60s 内交付，且**推理深度一点没降**。

这需要前端支持增量渲染 —— 好消息是**基础设施已经具备了**：
- `GET /research/{task_id}` 已经返回 `progress` 与 `agent_messages`
- `CancellationToken.live_state` 已经支持节点内实时推送
- 前端 `App.tsx` 已经在轮询

**只需要给量化快照增加一个"提前产出"节点**（在 `collect` 之后、
`analyze_*` 之前），并把它的结果放进 live_state。

## 六、建议的落地顺序

| 优先级 | 动作 | 收益 | 质量影响 | 状态 |
|---|---|---|---|---|
| **P0** | 数据采集走库优先 + 失败冷却 + 启动预探 | **-23.3s** | 无 | ✅ 已实施 |
| **P0** | 补 6 个"无定期作业"指标（美国宏观/财务比率） | 避免现打网络 | 无 | ✅ 已实施 |
| **P1** | 信息层串行改并行 | **-10.0s** | 轻微 | 待做 |
| **P1** | 新增「量化快照」提前产出节点 | 首屏 **<2s** | 无 | 待做 |
| **P2** | 快速/深度两档，用户自选 `reasoning_effort` | 快速档 7.4s | 用户选择 | 待做 |
| **P2** | A17 精简 prompt（输出字段按问题类型裁剪） | -5s | 轻微 | 待做 |
| **P3** | A17 关 ReAct 改单次 | -3s | 失去追问 | 需评估 |

### 关于"快速/深度两档"的具体建议

不要全局降低 `reasoning_effort`（那会毁掉所有分析的质量），
而是**按用户意图路由**：

| 用户问法 | 档位 | effort | 预期 |
|---|---|---|---|
| "现在AI板块估值什么水平" | 快速 | none | ~7s |
| "帮我全面分析AI产业链" | 深度 | high | ~30-60s |
| "明日大盘怎么走" | 快速 | none | ~7s |
| "AI龙头10月走势预测+证伪信号" | 深度 | high | ~30-60s |

判据可以用现有的 `analysis_type` + 问题里的关键词
（"详细/全面/深度/证伪" → 深度；"多少/什么水平/现在" → 快速）。

## 七、一句话总结

**10 秒可达，但纯靠调 LLM 参数做不到，而且代价很大。**

必须同时动三处：

```
数据采集  23.4s → 0.1s    ← 已做，零代价，收益最大
串行结构  15.0s → 5.0s    ← 信息层并行化，几乎零代价
LLM 延迟  13.8s → 4.4s    ← 只能靠降 effort，**质量代价明显**
```

**我的建议：先做 P0 + P1（能到 29.6s 且质量不变），再上 C 期渐进式渲染
把首屏压到 2 秒以内。** 是否为了"真·7秒"牺牲推理深度，
取决于你更看重"快"还是"结论可辩护" —— 这个取舍该由你定，不该由我替你选。
