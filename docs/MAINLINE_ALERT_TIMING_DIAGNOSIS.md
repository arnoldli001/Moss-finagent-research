# 告警时点诊断（用户报障：告警滞后真值日，在板块顶部才报）

## 一、先把用户看到的那张表说清楚

用户说的是 **V2.2 版本的回测结果**。那一版的 `mainline_alert` 是
**多次运行的并集**（当时 `--force` 不清告警表，见 §16.34 五），
所以同一个板块同一天会有**双等级行**：

```
农业种植 885812（V2.2 备份表）
  20260626  medium 59.39   ← 与下一行同日、不同等级
  20260626  strong 73.52
  20260818  strong 91.42   ← 同日还有 weak 52.31
  20260908  strong 91.63   ← 用户看到的"顶部告警"
  20260908  medium 66.01
```

对比同月总量：**202606 该备份表 463 条 / 182 个板块**，
而清空后重算的 V2.4 表只有 **155 条 / 88 个板块** —— 约 3 倍虚高。

**结论**：用户读到的"实际告警日"来自一张**混了多轮配置**的表，
且其中 `strong`/`medium`/`weak` 并存。所以"滞后很久"这个印象里
**有一部分是表本身的问题**，不是触发逻辑的问题。

## 二、统一口径后重测（`scripts/alert_timing_report.py`）

口径：每个真值事件，取该板块在 `[真值 −20, 真值 +40]` 个交易日内的
**首次告警**；只计 `medium`/`strong`（`weak` 是"单一维度极端异常"，
噪声大，算进去会让"首次告警"大幅提前）；差值为**交易日**数。

分档（用户给的验收标准）：提前 ≤10 日或滞后 ≤5 日 = ✅ 合格。

### 结果：**主要问题不是"滞后"，而是"太早"与"漏报"**

| 版本 | 合格率 | 差值中位 | 范围 |
|---|---:|---:|---|
| V2.2 备份（并集，虚高） | 5% | −15 | −20 ~ +38 |
| **V2.4（干净表）** | **0%** | −16 | −20 ~ +26 |

V2.4 的失败模式分布：

- **⚠️太早（提前 15~20 个交易日）**：Sora概念 −13、人形机器人 −16、
  铜缆高速连接 −16、人形机器人（延续）−15、创新药/CRO −20
- **⚠️滞后**：大基建/人形机器人 **+26**（唯一一个明显滞后）
- **❌漏报（窗口内没有 medium/strong）**：短剧游戏、低空经济、
  有色金属/石油石化、家用电器/基础化工、CRO/创新药(2024-04)、
  券商/综合金融、机器人/低空经济、新消费、算力硬件、农业种植、
  种植链 —— **11 个**
- **❓无法评估**：2023 年事件（不在打分区间 20231009 起）、
  真值日不是交易日、`codes` 待补（含"创新药首次异动"）

### 两个例子逐日核对

**创新药 886015**：V2.4 在 **20260623 `strong` 83.43** ——
正是用户说的启动日，**没有滞后**。V2.2 里首条 `strong` 是 20260713。

**农业种植 885812**：V2.4 有 `strong` 20260629（提前约 5 周）、
之后只有 `weak`；用户看到的 20260908 是 V2.2 的 `strong` 91.63。
逐日看它的成分：20260618 起才进候选池（rank 21→**8**），
`total` 靠 `gate_bonus` 才够到 73.5；也就是**它靠加分才越线**。

## 三、真正的机制：绝对阈值 + 加分才越线

把上面的逐日数据摊开，问题很清楚：

| 日期 | rank | six_dim | accumulation | base_total | total | 等级 |
|---|---:|---:|---:|---:|---:|---|
| 20260617 | 69 | 58.6 | — | 58.6 | 58.6 | none |
| 20260618 | 21 | 62.6 | 48.4 | 55.5 | 55.5 | none |
| **20260623** | **8** | 66.6 | 58.0 | 62.3 | 62.3 | **none** |
| 20260626 | 45 | 60.8 | 56.3 | 58.5 | **73.5** | strong |

**20260623 那天六维排名是全市场第 8**（板块确实启动了），
但 `total` 只有 62.3，**低于中信号线**，所以不报。
真正报出来靠的是 20260626 的 **门控加分 +15**（total 73.5）。

也就是说：**能不能报，主要由"有没有拿到加分"决定，而不是由
"这个板块自身是不是刚突破它自己的震荡区间"决定。** 这与用户的判断
一致：

> 触发应该是过了某一长期震荡的分数上限，而不是达到足够极端高的分数再报。

绝对阈值（`medium_score`/`strong_score`）是**全市场统一**的，
所以：

1. 全市场普涨时，真正的领涨板块可能只排到 60 分档 → **漏报**；
2. 而它自己要等"足够极端"才越线 → **滞后到顶部**；
3. 反过来，全市场普跌后反弹时，很多板块会同时越线 → **太早/噪声**。

## 四、要改的东西（用户给的方向是对的）

新增一条**突破触发**，与绝对阈值**并行**：

```
对每个板块取它自己的 total 历史（过去 N 个交易日）：
    ceiling = 该历史的分位数（如 90%）
    breakout = total > ceiling  且  total ≥ floor（全局下限，防"矮子里拔将军"）
命中 breakout → 直接给中信号（理由写明"突破自身 N 日震荡上限"）
```

要点：

- **自己的历史**是重点：突破的是**它自己**的长期震荡上沿，
  而不是"达到某个全市场统一的极端分"；
- `floor` 必须有：否则一个长期在 30 分徘徊的板块冲上 35 分也会报；
- `N` 要够长（约 120 个交易日 ≈ 半年）才叫"长期震荡"；
- 需要用**当时之前的**数据（不能含未来），所以是严格 PIT 的。

这样做同时治两个病：**漏报**（不必等到极端高分）与
**滞后**（突破当天就报，而不是等加分把它推过绝对线）。

验收：`scripts/alert_timing_report.py` 的合格率（提前 ≤10 / 滞后 ≤5 个
交易日）应当显著抬升，且**告警量不能爆**（用
`scripts/compare_rescore_runs.py` 核对在 0.7~1.4x）。

## 五、同时确认的一件事：V2.2 的"腰斩"bug 是真的

顺手用 3618 个候选行核对了两代公式：

```
与 naive(0.5·six + 0.5·acc) 相符: 3618
与 aware(只在有数据的层之间平均) 相符: 0
```

所以 §16.39 的机制成立：V2.2 确实**没看层的 `available`**。
（注意 `accumulation_coverage=1.00` 不能当"有数据"的证据 ——
它是 `LayerScore.coverage` 的默认值，层不可用时也会是 1.0。
核对必须用层的 `available` 字段。）
