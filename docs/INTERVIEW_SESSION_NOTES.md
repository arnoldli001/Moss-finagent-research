## 0. 一句话地图：这个模块长什么样

竞价选股（`src/auction_select/`）的核心是**一张声明式规则表**（`rulebook.py`），
分三层按时间顺序跑，而不是散落的 `if`：

| 层 | 时机 | 数据边界 | 作用 | 本会话实例 |
|---|---|---|---|---|
| **前置筛选** `_prefilter_gates` | **9:15 盘前** | 只有昨日及更早 + 本地仓库 | 定义"候选池" | 剔非涨停/ST/科创板、市值区间、昨收上限、站上 MA20、**剔高位连板(6~7)**、**剔首板** |
| **打标签** `_assign_gates` | 9:25 | + 竞价快照 | 只打标不否决 | 主板 >6% + 抢筹 + 量比>7% → 「大量抢筹」 |
| **否决** `_veto_gates` | 9:25 | + 竞价快照 | 位掩码 + 原因文案 | bit4 量比超限、**bit11 已删**、bit12/13（已成死规则）、bit14 规则 C |

**分层不是为了好看，是因为数据可用时间不同** —— 这条是面试考点，见 2.A.1。

## 1. 本会话做了什么

### 1.1 竞价选股策略（改动最密集）

1. **新增**「昨日首板 且 近 10 日涨停 < 4」→ 先做**前置筛选**，后**搬到否决表 bit14**
   并追加「竞价涨幅 > 3%」。
2. **bit4 加附加条件**：竞价量比 > 15% 的否决，从"只看量比"改成
   "**量比 > 15% 且 昨日换手率 > 阈值**"（1.8% → 后来改成 2.2%）。
   动机：昨日一字缩量时分母极小 → 量比虚高 → 误杀强势股。
3. **新增前置筛选**：**剔高位连板（6~7 板）**（闭区间，`ge 6 且 le 7`）。
4. **删除 bit11**（首板 + 竞价 < 1.7% + 近 18 日 < 4）、
   **新增前置筛选「剔首板」**、**硬否决线 0.97 → 0.95**。
5. 查明"10% 阈值到底定义在哪"：用户口中的 `volume_ratio_pct` 其实是**函数形参名**，
   真正的配置键是 `rush_out_volume_pct` / `RUSH_OUT_VOLUME_PCT`，
   共 **4 处**定义（yaml / config.py / features.py / qmt 脚本）。

### 1.2 量化数据分析：首板次日表现 → Excel

- 直连 15.4 GB 的 `warehouse.db`（SQLite，1500 万行级），
  统计"首板涨停 → **次日竞价高开幅度 vs 当天竞价买入赚钱概率**"，分档出表。
- **两个口径都给**（刻意）：口径A「1 连板段（段长=1）」632 样本 → 竞价均值 **+0.18%**、
  收盘 **−1.63%**；口径B「首板（段首）」770 样本 → 竞价 **+1.21%**、收盘 **+0.48%**。
- 结论：**Pearson r ≈ −0.11**，赚钱率全程 **38%~49%（低于 50%）**，
  **不存在"高开越多越赚"的单调关系**。

### 1.3 前端

- 删除日内分时的「市场情绪周期」条，**连 `useState`/`useEffect`/死 CSS 一起删**
  （只删 JSX 会留一个"每切模式白跑一次"的请求）。
- **个股「关联板块 / 海外映射」绑定持久化**：存 DB、**启动时热加载**进内存、
  切股**预填输入框** + 历史配置 **datalist 联想**。
- **批量股票输入**：抽出共用的 `resolveStockTokens()`，顶部「加自选」与抽屉
  「加成分股」**同一实现**（分隔符 `,，、;；\s`、6 位数字直通、名字/拼音模糊匹配、
  **认不出就报错绝不入库**）。
- 自定义板块成分行**复用自选行设计**：名称 + 代码 + 涨跌幅（+ 若也在自选里则带分数/信号），
  行情走**按 code 共享**的缓存（一票多板块只抓一次）。

### 1.4 后端

- 新增 `GET /intraday/stock-bindings[/{code}]`、`GET /intraday/quotes?codes=`。
- `dim_intraday_profile` 表加 `boards_json` / `overseas_json` 两列，

## 2. 踩的坑（面试主菜：现象 → 根因 → 修法 → 教训）

### A. 领域口径类（量化岗必答）

#### A1. 前置筛选拿不到 9:25 数据 → 规则"永不命中且无痕迹"
**现象**：要把「竞价涨幅 > 3%」加到一条**前置筛选**规则上。
**根因**：`open_gap_pct` 是 **9:25 集合竞价**的产物，而前置筛选跑在 9:15，
它的 row 里**根本没有这一列**；规则引擎对缺失列返回 `False`
→ **整条规则永远不命中**，不报错、notes 也看不出来。
**修法**：整条搬到**否决表**（bit14），9:25 之后再判。
**教训**：规则引擎里必须区分「**字段缺失**」与「条件不满足」。
本项目做成了**三态**：未知（窗口没算出来）/ 确定 0 / 确定 N，缺数据一律"不猜"。

#### A2. 规则互相遮蔽：10 日窗口是 18 日窗口的**后缀**
**现象**：既有 bit11（首板 + 竞价<1.7% + **近18日**<4）在实际运行里**从不命中**。
**根因**：一条前置筛选（首板 + **近10日**<4）把它整个遮蔽 ——
因为 `近18日 < 4` ⟹ `近10日 < 4`（后者是前者的**后缀计数**），
凡 bit11 想拦的票都被前置筛选先剔掉，根本走不到否决阶段。
**修法**：把该条前置筛选撤掉/搬走，遮蔽关系消失（bit11 随后又被用户整条删除）。
**教训**：多条规则做交集/并集前，先做一次**蕴含关系分析**，否则会留下"永不复现的死规则"。

#### A3. 边界效应：阈值之间的"留白区间"没人管
**现象**：中新赛克(002912) 竞价 **−0.49%**、中持股份(603903) 竞价 **+2.88%** 都没被拦。
**根因**：规则 C 是**严格 > 3%**，而 bit11 是 **< 1.7%** → **1.7%~3% 这段是留白**。
603903 的 2.88% 正好卡在缝里（**只差 0.12 个百分点**）。
另外 002912 是**低开**，本就不属"高开 > 3%"那一类；它本该由 bit11 管，
但 bit11 还要求"近 18 日 < 4"，它却有 **5 次** → 两条都不管。
**教训**：给区间阈值时必须问"**两端之间的缝谁管**"；`>` 与 `>=` 的差异要显式记录。

#### A4. 涨停价四舍五入污染了收益率分档
**现象**："竞价高开 8%~10%"这一档的赚钱率异常低（34.1%）。
**根因**：该档 **59.1% 其实是"开盘即涨停"** —— 涨停价四舍五入到 0.01，
使一字板的跳空算出来是 **9.98%**（例：昨收 8.42 → 涨停价 9.26），
刚好落进 8~10% 档而没进 ≥10% 档。这些票**竞价根本买不到**、实体涨幅恒为 0，
混进来把该档压成假象（剔除后该档从 34.1% **反转**为 83.3%）。
**教训**：分档边界会被**最小变动单位（tick size）**污染；
解读前先做**结构检查**（这批样本真的是我以为的那批吗）。

#### A5. 量比的分母陷阱
`竞价量比 = 今竞价量 ÷ **昨日全天量**`。昨日一字缩量 → 分母极小 → 量比虚高。
实测 **603230 量比 52.79%（全池最高）但昨日换手率只有 1.68%** ——
这就是"加换手率附加条件"的实证依据。
**教训**：任何**比值型因子**都要问"分子分母各自的量纲与稳定性"，并检查分母极小值。

#### A6. 小样本 + 置信区间
某档只有 **18 个样本**、83.3% 胜率 → **95% 置信区间约 ±17pp**，不能当结论。
分档后每档 18~317 个，只能说方向。
**教训**：报概率必须带**样本量与置信区间**；小样本档位要显式标注。

#### A7. **池级因子的间接效应**（最隐蔽，最加分）
**现象**：把候选池从 36 只砍到 11 只后，**留下来的票分数也变了**。
**根因**：`auction_sentiment`（9:25 全体候选的高开均值/中位数/占比，**占 5 分权重**）
是**按池子算的**，分母换了分数就动。实测 600354 从 **53.01 → 51.81**，
以 **0.09 分之差**掉出 51.9 的门槛。
**教训**：**改动"入池条件"会通过池级因子影响所有票的分数**，不只是被剔掉的那些。
复盘时要区分"直接剔除"与"间接漂移"。

### B. 工程 / 架构类

#### B1. 一个 3 元组当对象用 → 503（最精彩的排障）
**现象**：点「重新拟合」报 `503 档位拟合结果不可用`。
**根因**：路由把 `IntradayDataProvider.fetch_quote()` 的返回值**直接当 `Quote`** 用，
但那个方法返回的是 **3 元组 `(Quote, 源名, 尝试记录)`**（多源容灾链）
→ `quote.price` 抛 `AttributeError` → 被 `level_fit` 的 `except` **吞成 `None`** → 503。
**指纹完全对上用户现象**：只有 `refresh=true`（强制重算）必现；
`refresh=false` 因为先命中**当日缓存**（那份缓存是快照路径用**正确解包过**的 Quote
写进去的）而看起来正常。
**修法**：正确解包（与同一段代码上一行的 `fetch_bars` 一致 —— 那行**解了包**，
漏的只有 `fetch_quote`）。并确认这是**唯一**同类漏解包处。
**教训**：① 同一个类里两个同名方法返回类型不同（3 元组 vs Quote）是 API 毒药，
调用方必然漏解包；② `except: return None` 会把根因变成一句无用的用户提示；
③ "**只在某个按钮上复现**"这种指纹，往往指向"另一条路径有缓存兜住"。

#### B2. `bit = -1` 的否决规则是**静默空操作**
**现象**：新增一条"首板 → 否决"，实测**毫无效果**。
**根因**：它被放进了**否决表**且没给 `bit=`。否决规则靠**位置掩码**生效，
没有位号 → `veto_bits` 返回 `bits=0` → 命中但**不置位 = 等于没生效**，且不报错。
**修法**：挪到**前置筛选**（命中即 `_drop`）。
**教训**：位掩码式规则引擎里，"没有位号"= 规则**静默失效**；
新增规则必须验证"它真的能置位"，不能只看"它在表里"。

#### B3. 位掩码持久化 → **bit 号不能重排**
删掉 bit11 后，**没有**把后面的规则往前挪。因为 `veto_bits` **落库**，
重排会让历史行的 0/1 指向另一套规则 → **复盘直接读错**。
于是序列里从此留一个**空洞（11 缺失）**，并写了退役说明 + 专门的契约测试
（`test_bit11_is_retired_and_not_renumbered`：11 必须不在、12/13/14 必须在原位）。
**教训**：任何**存进数据库的枚举/位号**都是对外契约，**只能追加、不能重排/删除**。

#### B4. 缓存版本号的纪律（不要轻易 +1）+ "部分写入"陷阱
给缓存分项加字段时**没有**升 `CACHE_VERSION`。项目里的原话：
纯加字段就升版本会让**当天已落盘的整份缓存失效**，迫使重跑全部远端接口（实测 180s+）。
做法改成：让旧缓存分项"校验不过 → **只重算这一项**（读本地仓库，几秒）"。
**但有个致命细节**：必须在**任何写入之前**判定并**整项**拒绝 ——
否则 `limit_up_days_as_of` 一旦写上，重算那一步就会被跳过，新字段**永远补不上且无声**。
**教训**：缓存失效粒度要尽量小；**"部分写入 + 部分拒绝"是最危险的状态**。

#### B5. SQLite 打不开：`disk I/O error` → `immutable=1`
15.4 GB 的 `warehouse.db` 被运行中的进程占用，`mode=ro` 直接报 `disk I/O error`
（而 DB 文件本身完好）。退到 `mode=ro&immutable=1` 才读得到。
**关键**：`immutable=1` 会**忽略 WAL**，用之前必须确认 `-wal` 为空
（否则读到缺最新事务的快照）。**先验证再降级**这个动作本身就是面试加分项。

#### B6. 前端到底"谁在服务"
先搞清 `8100`（Python 静态托管 `web/dist`）才是本项目前端，`43129` 是 harness 自己的 GUI；
**没有 vite dev server 在跑** → 改完必须 `npm run build`（脚本 `tsc -b && vite build`）并刷新。
**教训**：改前端前先确认"**构建产物谁在服务、有没有 HMR**"，否则改了看不到效果。

#### B7. TS 严格模式的反向约束
`noUnusedLocals` / `noUnusedParameters` 开着 → 删一个按钮必须**连它的 prop、
调用处、手写契约类型一起删**（`onBack`）。"只删 UI"会**直接构建失败**。
反向也逼出了**死代码清理**：删展示条要连 `useState` / `useEffect` / 死 CSS 一起删。

#### B8. 表结构演进：`PRAGMA` 补列而非迁移脚本
给已有表加列靠 `_ADDABLE_COLUMNS` + `ALTER TABLE`，**无需 alembic**；
并且新列**刻意不放进 `_COLUMNS`**，使权重档案的 `ON CONFLICT DO UPDATE`
碰不到它 —— 用一条测试把这个不变量钉住（"改权重不能清掉板块绑定"）。

### C. **AI（我）自己犯的方法论错误** —— 讲"AI 辅助开发"的核心素材

#### C1. 我的验证曾经是"空转"的（最该讲）
- 用 `repo.upsert(...)` 验证"权重 upsert 不会清掉绑定"，但那个方法是 **async**、
  我**没 await** → 根本没执行 → **"验证通过"是假的**。发现后改成 `asyncio.run` 才真验。
- 用 `git diff` 找"我改了哪些行"再与 lint 告警求交集，结论"无新增告警"。
  但**这个模块被 `.gitignore` 排除了** → diff 为空 → 交集恒为空 → **检查空转**。

**教训（可直接当面试答案）**：`测试通过` ≠ `验证有效`。
必须问：**"如果我把修复回退，这条检查会不会失败？"**
我后来对 400 / 503 两个 bug 都这么做了 —— **故意把修复改回旧写法，确认回归测试真的红**，
再改回来（red-green 验证）。

#### C2. retype 字符串引入静默错误
改写测试时我把标签「剔昨收未站上 20 日均**价**」打成了「日均**线**」
→ 断言 `assert None == 1`（查找的键在字典里根本不存在）。
**教训**：不要手抄关键字符串，用锚点/枚举；断言失败先 `--showlocals` 看真实值。

#### C3. 差点把"数据没传"当成"渲染错了"
板块成分显示 `300308 / 300308`（代码显示两遍）。**根因不是渲染**，
是添加时**只发了 `{code}` 没发 `name`**，而接口**本来就收 `{code, name?}`**。
**教训**：先确认"数据有没有传上来"，再怀疑"展示对不对"。

#### C4. 回归测试要**在旧代码上验证它会失败**
我给"漏解包 3 元组"写的测试，第一次跑**在旧代码上也通过** ——
因为我用于回退的脚本断言失败、**静默没生效**，测试其实跑在**已修复**的代码上。
重做后确认：旧代码上红（`assert not isinstance(quote, tuple)` 打印出那个 3 元组）、
恢复后绿。**教训**：回归测试必须做 **red-green 验证**，否则只是装饰。

#### C5. 改测试 ≠ 改断言让它过（golden 重锚的纪律）
改规则后有 12 个测试红。修的时候每一条都要写清"**为什么期望值变了**"：
- 删除的规则 → 连同它的用例一起删，并留一条**退役契约测试**（bit 号不许重排）；
- golden 基准 → 逐条记录 **36 → 7、入选 3 → 2、以及"一进一出"的原因**；
- 受影响的编排用例 → 改**夹具**而不是放松断言（例：连板高度必须是 **2** ——
  取 1 会被「剔首板」剔掉、取 ≥3 会被"连板>2 豁免主板 >6%"豁免，都测不到目标规则）。

## 3. 面试可能被问的问题

### 3.1 量化开发

1. **什么是前视偏差？** 你怎么保证 9:15 的前置筛选**真的**没用 9:25 的数据？
   （答：规则**分层** + 缺列即"判不了"，而不是悄悄用默认值）
2. **涨停怎么判定？** 为什么用 `close == up_limit` 而不是 `pct_chg >= 9.8%`？
   （答：覆盖主板 10% / 双创 20% / 北交所 30% / ST 5%，除权日也由权威涨停价兜住）
3. **复权口径**：为什么收益率一律用**未复权**？（涨停规则作用于未复权价）
4. **一字板 / 流动性**：为什么"竞价买不到"的样本必须剔除？不剔会怎样？（见 A4）
5. **样本量与显著性**：18 个样本 83% 胜率能不能用？置信区间怎么算？
6. **过拟合 / 样本外**：walk-forward 是什么？为什么 `in_sample` 与 `walk_forward`
   两个成功率要**一起看**？
7. **交易成本**：为什么用 `body > 0.2%` 做"净赚"门槛？
8. **池级因子的间接效应**（A7）、**幸存者偏差**、**停牌/退市处理**。
9. **集合竞价机制**：9:15–9:20 **可撤单**、9:20–9:25 **不可撤单**、9:25 撮合出开盘价
